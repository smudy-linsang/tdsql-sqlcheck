# v1.6.0.1 ZK 标准化导入开发自测报告

> 作者：智能体O

## 1. 本次变更

本次将“从 ZK 自动发现”后的旧直写导入改为“配置—预检—预览—确认提交”流程：

1. ZK 扫描读取集中式自身 SET、分布式 group 的完整 SET 列表，并按 `noshard/groupshard` 固定实例类型。
2. 导入操作者输入业务账号和每个目标集群的 MonitorDB 五项配置；不再使用 ZK `setrun` 内部账号，也不写死监控库信息。
3. 服务端用实例 ID 在 MonitorDB `m_data_cur` 中解析实例名称，再使用业务账号经发现 Proxy 执行 `SHOW DATABASES`。
4. 每个业务库生成一条独立连接，名称规则为 `实例名称-Proxy端口-库名`；系统库和本次输入的 MonitorDB 库不生成连接。
5. 提交在元数据库事务中完成，写入类型、完整 SET、MonitorDB 配置和批次审计；发现既有同地址端口库或同名连接时拒绝覆盖。

旧的 `POST /api/v1/tdsql/discover/register` 已返回 410，避免绕过预检继续创建 `ALL` 库或默认错误类型的连接。

## 4. 未在本地宣称通过的事项

本机不持有内网生产/测试集群的业务及 MonitorDB 凭据，也不应在开发自测中把它们写入仓库。因此以下为部署后的必做 UAT，而非本报告中的“已通过”：

1. 选择一个真实 `group_*` 和一个真实 `set_*`，确认 MonitorDB 解析名与赤兔实例名称完全一致。
2. 用受控业务账号验证多个 Proxy 的 `SHOW DATABASES` 结果一致。
3. 提交预览后逐项核对连接名称、Proxy、业务库、MonitorDB、类型、SET 列表和批次来源。
4. 对一条分布式导入连接执行慢 SQL 扫描，确认读取保存的全量 SET。
5. 验证名称未解析、Proxy 不一致、连接重复和 ZK 不可达均明确失败且零部分写入。

## 5. 结论

开发自测和全量拆分回归均无失败。本次代码已消除 ZK 直接导入把实例 ID/`ALL`/内部账号写入连接管理的路径；进入内网发布前，仍需按第 4 节完成真实集群 UAT，方可确认“赤兔名称—ZK 拓扑—业务库—实例连接”全链路与现场数据一致。
