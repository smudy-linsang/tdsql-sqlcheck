## 0. 一句话说明要你做什么

**在两台已知类型的 TDSQL 实例上跑同一批只读语句，原样带回输出，用于判断"有没有办法通过 SQL 区分集中式实例和分布式实例"。**

结论可能是"有"，也可能是**"没有"**。**"没有"是完全可接受的答案，不要为了凑出结论而做任何推断或加工。**

---

## 1. 背景：为什么要重做这次实测

v1.5 的实例类型自动探测被证实是**一个常量函数**——对任何能连上的实例恒返回"分布式"，导致 `SIT-集中式实例A` 上 R077 等 27 条规则持续误报，v1.5 的核心目标完全未达成。

两个失效判据：

| 原判据 | 失效原因 |
|---|---|
| `/*proxy*/show status` 返回非空 | `/*proxy*/` 只是一个 SQL 注释，**任何 MySQL 兼容端点都返回非空** |
| `information_schema.TDSQL_SHARDING_RULES` 存在 | 该视图在本版本 TDSQL **根本不存在** |

你上一轮在后端节点（`jmysql.sh 4002` / `4003`）的采集**非常有价值**——它证明了**后端 TXSQL 数据节点上，集中式实例与分布式实例的分片完全同构**（两端口输出逐字一致）。

**所以本次实测只针对 Proxy 层。** 后端节点已经排除，不用再测。

---

## 2. 硬性前提（违反其中任意一条，数据作废）

> ### ⚠️ 这一节比后面所有用例都重要，请务必逐条确认

### 前提 1：必须走 **Proxy 端口**，禁止使用 `jmysql.sh` / 本地 socket

上一轮采集走的是后端 socket（`/data1/tdengine/data/4002/prod/mysql.sock`），采到 458 行；而系统实际是经 **Proxy 端口 15002** 连接的，只看到 2 行。

> **同一条语句，两个入口，输出差了 456 行。** 这个差别正是本次事故的核心。**从后端采回来的数据，无法迁移到生产判定。**

### 前提 2：必须使用**系统实例配置中的同一个账号**

不同账号权限不同，能看到的 `information_schema` 内容、能执行的 proxy 命令都可能不同。用 `root` 或管理员账号采到的东西，系统用业务账号未必看得到。

请从「实例管理」中确认每台实例配置的 `host` / `port` / `username`，**用完全相同的三元组**去连。

> **口令请从内网配置获取，不要写进本文档、工单、聊天记录或任何输出文件。**

### 前提 3：两类实例**成对采集**，缺一不可

判据的本质是**差异**。只采一台，无论输出多详细，都无法得出任何结论。

### 前提 4：**原样粘贴，不要概括、不要截断、不要"整理"**

请直接回传命令的原始输出文件。

> 上一轮 "rows: 2" 这个概括，让"这 2 行到底是什么"这个关键信息丢失了整整一轮。**行数不是证据，行的内容才是。**

如输出确实过大（如某条返回数千行），保留**前 100 行 + 后 20 行**并**明确标注已截断及原始总行数**，不要自行挑选"看起来重要的"。

## 4. 执行方式（推荐脚本法）

### 4.1 准备采集脚本

在跳板机上创建 `probe_collect.sql`：

```sql
-- ============================================================
-- v1.5.1 Proxy 层实例类型判据实测
-- 全部为只读语句。单条失败属正常现象（用 --force 继续）。
-- ============================================================

SELECT '===== T00 会话上下文（确认连的是哪里）=====' AS marker;
SELECT VERSION() AS version, DATABASE() AS cur_db, USER() AS cur_user,
       @@hostname AS hostname, @@port AS port;

SELECT '===== T01 proxy show status =====' AS marker;
/*proxy*/show status;

SELECT '===== T02 proxy show connectionpool =====' AS marker;
/*proxy*/show connectionpool;

SELECT '===== T03 proxy show shard =====' AS marker;
/*proxy*/show shard;

SELECT '===== T04 proxy show sets =====' AS marker;
/*proxy*/show sets;

SELECT '===== T05 proxy show variables =====' AS marker;
/*proxy*/show variables;

SELECT '===== T06 show databases =====' AS marker;
show databases;

SELECT '===== T07 information_schema 中的 TDSQL 专有对象 =====' AS marker;
SELECT TABLE_NAME FROM information_schema.TABLES
 WHERE TABLE_SCHEMA='information_schema'
   AND (TABLE_NAME LIKE '%TDSQL%' OR TABLE_NAME LIKE '%SHARD%'
        OR TABLE_NAME LIKE '%PROXY%' OR TABLE_NAME LIKE '%SET%')
 ORDER BY TABLE_NAME;

SELECT '===== T08 information_schema 全量对象清单 =====' AS marker;
SELECT TABLE_NAME FROM information_schema.TABLES
 WHERE TABLE_SCHEMA='information_schema' ORDER BY TABLE_NAME;

SELECT '===== T09 常规 show status 行数（对照 T01）=====' AS marker;
SELECT COUNT(*) AS plain_show_status_rows FROM information_schema.SESSION_STATUS;

SELECT '===== T10 EXPLAIN 输出形态 =====' AS marker;
-- 分布式实例的 EXPLAIN 由 Proxy 改写，输出结构可能与单机不同
EXPLAIN SELECT 1;
```

### 4.2 执行（两台各跑一次）

```bash
# ── 集中式实例 ──
mysql -h <CENT_HOST> -P <CENT_PORT> -u <CENT_USER> -p \
      --force --table --comments \
      < probe_collect.sql > out_CENT.txt 2>&1

# ── 分布式实例 ──
mysql -h <DIST_HOST> -P <DIST_PORT> -u <DIST_USER> -p \
      --force --table --comments \
      < probe_collect.sql > out_DIST.txt 2>&1
```

**参数说明（不要省略）**：

| 参数 | 作用 | 为什么必须加 |
|---|---|---|
| `--force` | 遇错继续 | 部分 proxy 命令预期会失败，不能因一条报错就中断整批 |
| `--comments` | **保留注释不剥离** | **关键**：`mysql` 客户端默认会剥掉注释，`/*proxy*/` hint 会被吃掉，那就白测了 |
| `--table` | 表格输出 | 便于人工比对 |

> **`--comments` 漏加是本次采集最容易犯的错误。** 漏了它，`/*proxy*/` 在发到服务端之前就被客户端删掉了，T01–T05 全部退化成普通 `show` 命令——采回来的数据看似正常，实则毫无意义。
>
> **自检方法**：如果 `out_DIST.txt` 里 T01 的输出和 T09 的行数一样是几百行，说明 hint 很可能被剥掉了，请检查参数后重采。

### 4.3 需要单独执行的一步：样本表 DDL（T11）

这一步需要你先挑表，无法写死在脚本里。

**在两台实例上各挑一张真实业务表**（有数据的、正式的表，不要挑临时表或系统表）：

```sql
-- 先看有哪些表
SHOW TABLES;

-- 然后取 DDL（把 <表名> 换成实际表名）
SHOW CREATE TABLE <表名>\G
```

**分别记录两台各 2–3 张表的完整 DDL。**

> **T11 是先验最强的候选判据**：TDSQL 规范要求分布式实例不允许建单表（这正是 R077 的内容），所以分布式实例上每张表的 DDL 尾部应当带 `shardkey=xxx` 或广播表标记；集中式实例上则永远不会有。
>
> **请特别留意 DDL 的最后一行**——`shardkey=` 通常跟在 `COLLATE=xxx` 之后，容易被忽略。

## 5. 用例清单与观察点

| # | 语句 | 想验证什么 | 若两侧有差异，可能成为判据吗 |
|---|---|---|---|
| **T00** | 会话上下文 | **自检**：确认两次确实连到了不同实例、且走的是 Proxy | 否（仅作校验） |
| **T01** | `/*proxy*/show status` | **本次重点**。你上轮报告经 Proxy 只有 2 行——这 2 行到底是什么？现有 `discover_sets()` 正指望从中解析 `Variable_name='set'` 的 SET 列表 | **可能，优先级最高** |
| **T02** | `/*proxy*/show connectionpool` | 是否暴露后端 SET 拓扑 | 可能 |
| **T03** | `/*proxy*/show shard` | 该版本是否支持此命令 | 可能 |
| **T04** | `/*proxy*/show sets` | 同上 | 可能 |
| **T05** | `/*proxy*/show variables` | Proxy 配置项中是否含分片相关变量 | 可能 |
| **T06** | `show databases` | 两类实例系统库是否有差异 | 较弱 |
| **T07** | TDSQL 专有 information_schema 对象 | 经 **Proxy** 查询时，是否会出现后端节点上没有的对象 | 可能 |
| **T08** | information_schema 全量清单 | T07 的兜底，防止关键字没匹配上 | 参考 |
| **T09** | 常规 status 行数 | **对照组**：与 T01 比对，判断 `/*proxy*/` hint 是否被 Proxy 真正拦截 | 否（仅作校验） |
| **T10** | `EXPLAIN SELECT 1` | 分布式 EXPLAIN 由 Proxy 改写，列结构可能不同 | 可能 |
| **T11** | 业务表 `SHOW CREATE TABLE` | 分布式表 DDL 是否带 `shardkey=` / 广播表标记 | **可能，先验最强** |

## 7. 请**不要**做的事

| ❌ 不要 | 原因 |
|---|---|
| 不要用 `jmysql.sh` / 后端 socket / 后端端口（4002、4003…） | 后端节点已被上轮实测排除，两类实例在那一层完全同构 |

## 8. 本次实测之后会发生什么

```
G 回传数据
    ↓
A 按设计文档 §8.4 三项标准逐条评审候选判据
    ↓
  ┌─────────────────────┬──────────────────────────┐
  │ 找到可用判据          │ 未找到可用判据             │
  ├─────────────────────┼──────────────────────────┤
  │ 写入设计文档 §8       │ 设计文档标注"SQL 层无判据" │
  │ Q 一次性开发          │ Q 一次性开发（S2 恒无结论）│
  └─────────────────────┴──────────────────────────┘
                      ↓
              两条路径都能交付
```

**判据采纳标准**（摘自设计文档 §8.4，供你了解数据会被怎么用）：

1. 两类实例上**实测输出确有差异**——不接受"按文档应该有差异"；
2. 差异**方向明确**：命中即为分布式的**阳性证据**；
3. 未命中时**不得**判集中式，必须返回"无结论"下沉至下一判定源。

> **特别提醒**：即使 T01 经 Proxy 两侧行数不同，也**不能**直接用"行数"做判据——那就是重蹈"非空即分布式"的覆辙。判据必须落在**具体某一行的具体值**上（例如 `set` 行里 SET 的个数）。**这是要看内容而非形态的原因。**

## 9. 常见问题

**Q：某条 proxy 命令报语法错误怎么办？**
A：正常，`--force` 会继续。报错内容本身也是数据，请保留在输出文件里，不要删除。

**Q：两台实例的输出看起来完全一样，还要交吗？**
A：**要，而且这是极有价值的结论。** 它会直接推导出"SQL 层无可用判据"，让我们停止在这个方向上投入，专注 ZK 权威源。**证明此路不通，和找到一条路同样有价值。**

**Q：我能不能顺手把结论也分析了？**
A：欢迎附上你的观察，但请**与原始数据分开写**，标明哪些是原文、哪些是你的推断。判据评审需要基于原文进行。

**Q：需要在生产实例上做吗？**
A：不需要。`SIT-集中式实例A` 与 `SIT-分布式实例A` 两台即可。全部为只读语句，但仍请避开业务高峰。
