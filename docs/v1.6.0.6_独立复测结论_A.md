## 4. 本轮新发现（2 项，均为历史遗留、均不阻断）

### 4.1 A-P2-02：MonitorDB 填错时整个预检 500，提示无任何指向

复测跨 worker 会话时顺手撞见的。三种 MonitorDB 输入对比（真实连接，不打桩）：

```
① 主机留空          → 逐行返回 1 行 failure={'MONITOR_CONNECT_FAILED'}     ✅
② 主机对、端口填错   → 整体抛出 OperationalError (2003 Can't connect)       ❌
③ 主机端口对、口令错 → 整体抛出 OperationalError (1045 Access denied)       ❌
```

②③ 逃出 `build_preview`，被接口兜底成 **HTTP 500 `{"detail":"生成 ZK 导入预览失败"}`**，服务端日志 `ZK_IMPORT_PREVIEW_ABORTED error_type=OperationalError`。

**根因**：`zk_connection_import_service._connect`（第 62-81 行）只包了 `ImportError`，没包 `pymysql` 的连接异常；而逐实例的 `except ZKImportPreparationError` 自然接不住裸的 `OperationalError`。代码里**已经有** `MONITOR_CONNECT_FAILED` 这个码，但只在"主机为空"时抛——而这一种恰恰是前端拦得住的（监控五项都是 `required`）。**真正会发生的两种（填错端点、填错口令）反而没有它。**

**影响**：运维在导入弹窗里打错一个字符，整批实例的预检全部炸掉，页面只说"生成 ZK 导入预览失败"；这也是"一条坏输入毁掉整批"的老毛病（同 v1.6 的 P1-A）。内网正在密集做 ZK 导入，这个提示的可诊断性值钱。

**是不是本版引入**：不是，`_connect` 从 `8abc29a`（v1.6.0.1）起就是这样。

**修法（很小）**：

```python
    def _connect(self, host, port, username, password, database):
        try:
            import pymysql, pymysql.cursors
        except ImportError as exc:
            raise ZKImportPreparationError("PYMYSQL_UNAVAILABLE", "数据库客户端不可用") from exc
        try:
            return pymysql.connect(...)
        except Exception as exc:
            # 连接类异常必须转成逐实例可读的失败，不能整批掀翻
            raise ZKImportPreparationError("DB_CONNECT_FAILED", f"连接 {host}:{port} 失败") from exc
```

注意 `_connect` 还被 `_list_business_databases` 用着，那边现在是 `except Exception: continue`，**能接住这个新异常，不会改坏**；名称解析分支把 `DB_CONNECT_FAILED` 映射成 `MONITOR_CONNECT_FAILED` 展示即可。

**补用例（R-12）**：MonitorDB 端口不通 / 口令错各一条 → 断言**逐行 error 且 `failure_code` 可读**，而不是整体 500。

### 4.2 A-P3-02：存过的业务账号，页面上再也删不掉

```
① 先存上业务账号（username=bizuser, password=bizpw）        → 200
② 清空用户名保存（口令框本来就是空的，页面从不回显口令）    → 400 "扫描富集的业务用户名与口令需同时填写或同时留空"
③ 同时关掉「启用富集」再试                                   → 400（同上）
④ 保留用户名、只关富集开关                                   → 200（可行的规避路径）
```

**根因**：`zk_discovery_config_service.py` 第 241-250 行，口令为空时会**继承既有密文**（这是"不重填口令也能改其他项"的合理设计），于是"用户名空 + 继承来的密文非空" 永远触发 `bool(username) != bool(pw_enc)`。清空用户名成了死路，**没有任何入口能把已存的业务凭据抹掉**。

**影响**：功能上可以用 ④ 规避（留着用户名、关掉富集，富集确实不再跑）。但**银行场景下"凭据轮换/人员离场后必须能清除已存凭据"是硬要求**，所以我按 P3 记而不是忽略。

**是不是本版引入**：不是，v1.6.0.3 起就是这样，`zk_discovery_config_service.py` 本版未改动。

**修法**：用户名与口令**同时为空**时，显式把 `business_pw_enc` 置空（视为"清除"），而不是继承旧密文：

```python
supplied_business_pw = str(data.get("business_password") or "")
if supplied_business_pw:
    business_pw_enc = encrypt_password(supplied_business_pw)
elif not business_username:
    business_pw_enc = ""          # 用户名清空 = 明确要求清除该组凭据
elif current and current.get("business_password_encrypted"):
    business_pw_enc = str(current["business_password_encrypted"])
else:
    business_pw_enc = ""
```

MonitorDB 那组同理（主机置空时一并清 `monitor_password_encrypted`），顺手一起改。
