## 1. 执行摘要

三组新旧报告的 802 条 SQL 在数量、顺序和归一化内容上全部一致，输入漂移为 0。但两类 HTML 分别来自“在线元数据规则审核”和“文件审核”，直接相减同时混入了模块入口与生效规则集差异，不能把所有差异直接归因给 v1.6.2.2。

本次采用两层核查：

1. **HTML 现象层**：开发报告比生产报告多出 R036 767 条、R037 752 条、R033 26 条；其他规则完全一致。
2. **纯版本因果层**：把相同 802 条 SQL 分别放到 v1.6.2.1 发布点 `f99de2a` 和 v1.6.2.2，统一走 `RuleChecker.audit_file(instance_type="distributed")`、统一默认规则集，比较到完整违规消息。两版均产生 1,858 条命中，802 条语句中变化 **0 条**，新增、消失、严重度变化、消息变化全部为 **0**。

因此：

- 本批样本未发现 v1.6.2.2 引入次生灾害；
- R033/R036/R037 均是用户已确认的生产关闭、开发启用的规则开关差异；
- R033 在 v1.6.2.1 同入口复跑中也恰好命中 26 条，进一步证明它不是 v1.6.2.2 新增；
- 六份附件没有覆盖 `UNIQUE INDEX ... COMMENT` 或 `PRIMARY KEY ... COMMENT`，所以只能证明大样本零回归，不能单独证明原始崩溃用例已经关闭。

总体建议：版本代码核查通过。投产前应核对升级过程不会覆盖生产现有的 R033/R036/R037 关闭状态，并按该生产规则快照再跑一次留证。

## 3. 为什么不能只看两份 HTML 的通过率

生产旧报告来自在线元数据审核，开发新报告来自文件审核。两条链路的语句切分、注释保留和规则覆盖可能不同。

另外，`passed` 的判定是“违规列表为空”，INFO 也会把语句标成未通过。生产 v1.6.2.1 明确关闭 R036/R037，而开发报告启用了两者：

| 指标 | v1.6.2.1 生产 HTML | v1.6.2.2 开发 HTML |
|---|---:|---:|
| 通过语句 | 549 | 2 |
| 未通过语句 | 253 | 800 |
| R036 | 0 | 767 |
| R037 | 0 | 752 |

开发报告 99.75%“未通过”主要是规则开关口径造成的页面效果，不等同于 99.75% SQL 质量恶化。

## 5. 纯版本差复跑

### 5.1 方法

1. 从 v1.6.2.2 文件审核报告还原三组完整 SQL；
2. 检出 v1.6.2.1 发布点 `f99de2a`，不创建分支；
3. 两版使用同一 Python/sqlglot 运行环境、同一输入、同一默认规则集；
4. 统一调用 `RuleChecker.audit_file(..., instance_type="distributed")`；
5. 按语句序号比较 `(rule_id, severity, message)` 完整三元组。

## 6. 修复目标核验

### 6.1 R054 假 UNIQUE

三组报告中 R054 新旧均为 0，同入口双版本复跑也没有 R054 差异。本批语料包含 10 条带 UNIQUE 定义的语句，其规则集合两版完全一致，说明既有 UNIQUE 语义没有被破坏，也未污染 R061/R077 等 legacy 索引消费者。

但本批 802 条 SQL 没有命中原始“普通索引被误判为 UNIQUE”的目标形态，因此只能判定“无反向证据、无回归”，不能用本批附件单独证明目标误报已被消除。

### 6.2 唯一索引注释解析崩溃

六份 HTML 均无 E999，802 条 SQL 全部形成审核结果；其中 3 条带普通索引 COMMENT 的语句两版结果一致。

附件覆盖不足：

- `UNIQUE INDEX/KEY ... COMMENT`：0 条；
- `PRIMARY KEY ... COMMENT`：0 条。

所以本批大样本证明“没有产生新的批量解析崩溃”，但精确目标语法仍应以已完成的专项/SIT/UAT用例为准，或补充一份包含目标语法的开发环境报告。

### 6.3 R077 保护

R077 在两组版本中均命中 2 次，落在相同语句上；同入口版本差为 0。未出现分片表/广播表识别回退，也没有既有 R077 被意外消除。

## 7. R033 的闭环归因与遗留风险

### 7.1 不是 v1.6.2.2 次生灾害

生产在线元数据报告 R033 为 0，开发文件报告为 26。用户现已补充确认：**内网生产 R033 与 R036/R037 一样处于关闭状态**。同时，同一文件审核入口下 v1.6.2.1 与 v1.6.2.2 都命中 26 条，故因果链已闭环：

- 生产 HTML 为 0：R033 被生产规则配置关闭；
- 开发 HTML 为 26：开发规则配置启用 R033；
- 双版本同入口均为 26：不是 v1.6.2.2 新增，也不是本次修复的次生灾害。

投产风险从“待确认项”降为“配置保持项”：升级不得把生产 R033/R036/R037 的关闭状态重置为默认启用。

### 7.2 R033 本身存在既有误报

26 条中至少 21 条的名称末段为 `_his`（18）、`_status`（1）、`_trans`（1）、`_sys`（1）。当前 `_check_plural()` 对完整表名执行 `endswith("s")`，而 `PLURAL_IGNORE` 只与完整名称比较，所以组合名 `_status` 仍会被判为复数；项目缩写 `his/trans/sys` 也会被尾字母规则误判。

这是两个版本都存在的既有规则质量问题，不应归到 v1.6.2.2，也不应为本次版本制造代码变更。建议另案修复：先提取 schema 后的表名和 snake_case 最后语义段，再应用忽略词；对 `his/sys/trans` 等稳定缩写保守不报，并为 26 条真实语料建立脱敏回归 fixture。

### 8.1 版本判定

| 判定项 | 结果 |
|---|---|

| 精确目标注释语法覆盖 | 附件不覆盖 |
| 总体结论 | **核查通过（附生产规则开关保持要求）** |

### 8.2 投产前配置保持检查

1. 从生产数据库或规则管理接口读取并留存规则快照，确认 R033/R036/R037 均为关闭；
2. 核查升级脚本、初始化脚本和配置迁移不会把这三条规则恢复为默认启用；
3. 在 v1.6.2.2 上按该生产规则快照重放三组 802 条 SQL，逐语句规则集合应与批准口径一致；
4. 补充包含普通 KEY、UNIQUE KEY/INDEX、PRIMARY KEY 带 COMMENT，以及注释内含 `unique`/右括号/转义单引号的真实报告证据。

完成第 1～3 项即可确认投产配置不会改变用户现有体验；第 4 项用于补齐本次附件对修复目标的直接证据。
