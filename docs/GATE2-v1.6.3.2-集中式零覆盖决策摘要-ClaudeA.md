## 1. 一句话说清变了什么

| 对象类型 | 改前（v1.6.3.0） | 改后（v1.6.3.2） | 集中式实例的净效果 |
|---|---|---|---|
| 视图 VIEW | R030 拦（全模式） | R030 仅分布式 | **无任何规则治理** |
| 存储过程 PROCEDURE | R030 拦（全模式） | R030 仅分布式 | **无任何规则治理** |
| 触发器 TRIGGER | R030 拦（全模式） | R030 仅分布式 | **无任何规则治理** |
| 临时表 TEMPORARY TABLE | R032 拦（全模式）+ R024（仅分布式） | R032、R024 均仅分布式 | **无任何规则治理** |
| **自定义函数 FUNCTION** | R030 + R031 | R030 仅分布式，**R031 保持全模式** | **仍由 R031 拦住**（不属于零覆盖） |

分布式实例侧：**一条都没少**，R030/R032/R024/R031 全部照常生效。

## 2. 事实核验（我在当前代码上实跑，不是照抄设计）

```text
对象类型                          分布式命中              集中式命中
CREATE VIEW v AS SELECT 1        ['R030']               []          ← 零覆盖
CREATE PROCEDURE p() …           ['R030']               []          ← 零覆盖
CREATE TRIGGER tr …              ['R030']               []          ← 零覆盖
CREATE TEMPORARY TABLE tt (…)    ['R024', 'R032']       []          ← 零覆盖
CREATE FUNCTION f() RETURNS INT  ['R030', 'R031']       ['R031']    ← 仍有覆盖
```

我另外穷举了全部 121 条规则的描述与文档串，确认**没有第二条规则接管**视图/存储过程/触发器/临时表
（`R017` 的"临时表"指 ORDER BY RAND() 产生的内部临时表，`R115` 指 proxy 内嵌 myisam 临时表，
两者都与"用户建临时表"无关）。

## 3. 影响的现实场景

| 场景 | 改后会发生什么 |
|---|---|
| 开发在集中式实例上提交 `CREATE VIEW` | 审核通过，质量门禁放行（strict 也放行） |
| 开发在集中式实例上提交 `CREATE PROCEDURE` / `TRIGGER` | 同上 |
| 开发在集中式实例上提交 `CREATE TEMPORARY TABLE` | 同上 |
| 开发在集中式实例上提交 `CREATE FUNCTION` | **仍被 R031 拦住（ERROR）** |
| 上述任一在分布式实例上提交 | 与改前一致，照常拦截 |

**一个值得你留意的不对称**：改完之后，集中式实例上"自定义函数不让建、但视图/存储过程/触发器随便建"。
如果你的治理意图是"集中式实例本来就是 MySQL，这些对象允许使用"，那 R031 就显得多余；
反过来如果你要保留对这四类对象的管控，那 R030/R032 就不该改域。
**两种意图都合理，但它们指向不同的后续动作**——见 §4 选项 B/C。
