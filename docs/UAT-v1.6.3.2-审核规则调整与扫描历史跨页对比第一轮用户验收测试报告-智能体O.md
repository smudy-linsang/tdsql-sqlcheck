## 1. 管理结论

本轮从真实用户在浏览器中的操作路径出发，对本期规则调整、在线元数据审核、文件审核和四个扫描历史跨页对比页面进行了严格验收；未改模块以全量回归、三方黑盒套件和少量页面冒烟放行。

结论分为两层：

- **功能层通过**：R011、R120、R030、R032、R035、R058、R121 的规则行为符合设计；四个页面均能跨页选择两条记录并完成比较；超选、不可比、查询清空、刷新保留、模块切换、迟到响应和跨用户隔离均正确。
- **发布层不通过**：发现 **1 项 P1 发布阻断**。正式部署后验证脚本 `deploy/verify_deploy.sh` 调用了不存在的 `J` JSON 解析函数，导致真实登录成功仍被判失败，后续规则、审核和元数据库检查连锁失败；失败分支还会输出登录响应前缀，存在管理员令牌泄漏风险。脚本另有首页假失败和健康探针无条件记 PASS 的问题。该脚本是部署手册指定的正式准出入口，因此不能绕过。
- 设计已明确的三项书面门禁仍未回填：目标分布式实例 DML LIMIT 版本前提、DBA 接受集中式零覆盖、活动规则集及流水线负责人接受门禁双向变化。它们不否定本轮软件功能结果，但在回填前不得发布到生产。

## 6. 新发现缺陷与照图施工整改方案

### UAT-O-1632-REL-01（P1）：正式部署验证脚本失效，并在解析失败时泄漏登录响应

#### 6.1 可复现事实

在 v1.6.3.2、认证开启的隔离服务上执行正式部署验证脚本：

```text
deploy/verify_deploy.sh --port 18833

服务实际状态：
  /health = 200，version=1.6.3.2
  / = 200，HTML 长度 242835，包含 TDSQL
  三个静态资源 = 200
  admin 登录 = 200，真实返回令牌

脚本结果：
  J: command not found（登录、规则总数、Oracle 数、R080、概览共 5 处）
  登录被误判失败，后续携带空令牌而连续 401
  首页被误判不可访问
  PASS=6，FAIL=6，exit=1
```

代码事实：

- `deploy/verify_deploy.sh` 共调用 `J` 五次，但全文件没有定义 `J`，也没有 source 任何提供该函数的脚本。
- 首页使用 `echo "$FRONT" | grep -q "TDSQL"`；脚本启用了 `pipefail`，大 HTML 在 `grep -q` 提前退出后可能使 `echo` 收到 SIGPIPE，整条管道被判失败。
- 健康检查直接执行 `ok "探针响应 $(curl ...)"`，即使 curl 失败仍无条件增加 PASS。
- 登录解析失败时输出响应体前 120 字符。真实登录成功响应的开头就是管理员令牌，因此会把有效令牌写入终端或部署日志。本轮隔离令牌已通过重置管理员口令立即作废，报告不记录其内容。

#### 6.2 影响

1. 部署手册指定的正式冒烟命令确定性退出 1，无法证明 v1.6.3.2 可发布。
2. 健康、首页、登录三处存在真阳性/假阴性混乱，运维不能信任脚本结论。
3. 管理员令牌可能进入跳板机终端回滚、CI 日志或变更留痕，形成 8 小时会话泄漏风险。
4. 本期直接修改了该脚本的规则总数断言，因此它属于“动过的发布代码”，不能以问题早于本期为由放行。

#### 6.3 按以下步骤施工

修改文件：`deploy/verify_deploy.sh`。

1. 在首次 HTTP 请求前选择应用虚拟环境 Python，找不到时记 FAIL 并退出；不要依赖未声明的 shell 函数。
2. 新增白名单式 `json_get`，只支持脚本实际需要的六个 selector，不使用 `eval`：

```bash
PY_BIN="${SCRIPT_DIR}/../venv/bin/python"
if [[ ! -x "$PY_BIN" ]]; then
  for c in python3.11 python3.10 python3.9 python3; do
    if command -v "$c" >/dev/null 2>&1; then PY_BIN="$c"; break; fi
  done
fi
[[ -n "${PY_BIN:-}" ]] || { bad "找不到可用 Python，无法解析 JSON"; exit 1; }

json_get() {
  local selector="$1"
  "$PY_BIN" -c '
import json, sys
d = json.load(sys.stdin)
s = sys.argv[1]
if s == "version": value = d.get("version", "")
elif s == "token": value = d.get("token", "")
elif s == "total": value = d.get("total", "")
elif s == "oracle_count": value = sum(r.get("category") == "oracle_compat" for r in d.get("rules", []))
elif s == "r080_hit": value = any(v.get("rule_id") == "R080" for v in d.get("violations", []))
elif s == "today_count": value = d["audit"]["today_count"]
else: raise SystemExit(2)
print(value)
' "$selector"
}
```

3. 所有 JSON 读取改为 `printf '%s' "$BODY" | json_get <selector>`；任何解析异常都用 `|| true` 收敛为对应检查 FAIL，不能让未定义命令或 traceback 污染结论。
4. 健康检查必须检查 curl 退出码并解析版本，禁止无条件调用 `ok`：

```bash
HEALTH=""
if HEALTH=$(curl -fsS -m 3 "${BASE}/health"); then
  ok "健康探针 HTTP 成功"
else
  bad "健康探针不可达"
fi
VER=$(printf '%s' "$HEALTH" | json_get version 2>/dev/null || true)
```

5. 首页判断去掉 `pipefail + grep -q` 管道，改成 Bash 字符串匹配：

```bash
if FRONT=$(curl -fsS -m "$TIMEOUT" "${BASE}/"); then
  [[ "$FRONT" == *TDSQL* ]] && ok "首页可访问" || bad "首页内容异常"
else
  bad "首页不可访问"
fi
```

6. 登录请求使用 Python `json.dumps` 生成请求体，正确处理口令中的引号、反斜杠等字符；HTTP 失败或 token 解析失败时只输出状态和固定错误码，**绝不输出 LOGIN 响应体、Authorization 头或 token 前缀**。
7. token 为空时，规则、审核、概览检查应明确记为“登录前置失败而跳过”，不能继续伪装成业务接口故障。
8. 新增 `tests/test_verify_deploy_contract.py`，启动隔离真实服务或协议桩，至少锁定：
   - 健康服务 + 正确口令：脚本 exit 0、`FAIL=0`，121/42/R080/概览/metrics 全部 PASS；
   - 服务不可达：健康项 FAIL、exit 1，不能打印 PASS；
   - 正确登录响应：token 被成功提取但输出全文不含 token；
   - 错误口令/畸形 JSON：安全失败且不回显响应体；
   - 24 万字节以上首页：不得因 SIGPIPE 假失败；
   - `bash -n` 和 `shellcheck` 通过。
9. 同步新增 v1.6.3.2 部署验证说明；不要修改 v1.6.3.0 历史实测样例。说明中写明口令已改后使用 `SQLCHECK_VERIFY_PASSWORD` 临时注入，执行后清除环境变量。
