## 4. ⚠️ 新发现：`DEF-A-6.2-b`——奇数个反斜杠转义单引号会使 A-6.2 失效

### 4.1 现象

```
CREATE TABLE `t1` (
  `id` int NOT NULL COMMENT '主键',
  `c0` varchar(20) DEFAULT NULL COMMENT 'it\'s note0',      ← 反斜杠转义单引号
  PRIMARY KEY (`id` DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='表注释' shardkey=id
```

暴力扫描"语句中反斜杠转义单引号的个数 n = 0…5"：

| n | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 索引 `DESC` 是否被正确剥离 | ✅ | **❌** | ✅ | **❌** | ✅ | **❌** |
| 审核结果 | 正常 | **E999 + R003/R004/R005 误报回归** | 正常 | **同左** | 正常 | **同左** |

**奇数个 `\'` 时 A-6.2 完全失效，退回修复前的原始缺陷形态。**

### 4.2 根因

`_LITERAL_OR_COMMENT_RE` 的单引号分支写作 `'[^']*'`，**不认识反斜杠转义**：

```python
_LITERAL_OR_COMMENT_RE = re.compile(
    r"('[^']*'|\"[^\"]*\"|`[^`]*`|--[^\n]*|#[^\n]*|/\*.*?\*/)", re.DOTALL)
```

遇到 `'it\'s note0'` 时，正则在 `\'` 处提前收束字符串，后续文本的"引号内/外"判定整体错位；
奇数次错位使真正的 `PRIMARY KEY (`id` DESC)` 被误判为"在字符串内"，于是不剥离。

### 4.3 建议修法（已验证）

单/双引号分支支持反斜杠转义与双写转义，反引号支持双写：

```python
_LITERAL_OR_COMMENT_RE = re.compile(
    r"('(?:\\.|''|[^'\\])*'"
    r"|\"(?:\\.|\"\"|[^\"\\])*\""
    r"|`(?:``|[^`])*`"
    r"|--[^\n]*|#[^\n]*|/\*.*?\*/)", re.DOTALL)
```

复测该正则：

| 验证项 | 结果 |
|---|---|
| n = 0…5 各种转义引号数量下，索引 `DESC` 均被正确剥离 | ✅ 6/6 |
| 字符串内 `' DESC,'` 不被误改 | ✅ |
| 转义引号字符串内 `DESC` 不被误改 | ✅ |
| 双写引号字符串内 `DESC` 不被误改 | ✅ |
| 块注释 / 行注释内 `DESC,` 不被误改 | ✅ |
| 反引号列名 `` `desc` `` 不被误改 | ✅ |

### 4.4 严重度与可达性

* **不是回归**：奇数形态下的行为与修复前**完全一致**（都是 E999），没有变坏；
  无 `DESC` 索引的语句在两版下逐条一致。故**不阻断已合入的修复**。
* **可达性**：
  * 本次 2172 张表的真实语料中 **`\'` 出现 0 次**，故本轮线上样本不受影响；
  * 本地 MariaDB 的 `SHOW CREATE TABLE` 对注释内单引号输出为 `''` 双写（当前正则可正确处理）；
  * 但**文件审核模块接受任意 SQL 文件**，`\'` 是 MySQL 系工具链常见转义形态，该路径可达；
  * 平台"在线元数据审核"在 MySQL 8/TXSQL 上是否产出 `\'`，本地无 MySQL 8 环境，**未能确证**。

**建议**：按 §4.3 补一版，并补 2 条用例（奇/偶转义引号各一）后关闭 A-6.2。

## 5. 其他边界：三处越界剥离（不改变审核结论）

| # | 形态 | 现行行为 | 审核结论是否改变 |
|---|---|---|---|
| I | `CREATE TABLE t2 SELECT … ORDER BY a DESC, b`（MySQL 合法的无 `AS` CTAS） | 被剥离 | **否** |
| J | `CREATE TABLE t2 AS (SELECT … ORDER BY a DESC, b)`（带括号子查询） | 被剥离 | **否** |
| N | 转义引号字符串内的 ` DESC,` | 被剥离 | **否** |

CTAS 门控 `\bas\s+select\b` 漏掉了"无 `AS`"与"`AS (SELECT`"两种写法。
逐例实测**均未改变审核结论**（审核不执行 SQL，且无规则依赖 `ORDER BY` 方向），
故列为**观察项**而非缺陷。若要收紧，建议把门控改为"语句体内出现 `\bselect\b` 即视为 CTAS，不剥离"。

已验证**不受影响**的边界（各 1 例，全部正确）：
反引号列名 `` `desc` ``、`DEFAULT 'DESC'`、列名以 `_desc` 结尾、
块/行注释内的 `DESC,`、纯 `SELECT`、`CREATE VIEW`、`ALTER TABLE … ORDER BY`。

### 6.4 复测环境阻断（**非 Q 本次改动**）

本地元数据库为 **MariaDB 10.11.14**，迁移结构验收失败：

```
迁移结构验收失败 [v4_040_instance_type_scope]:
列 tdsql_connections.instance_type_probe_error 默认值不符: 期望 '' 实际 "''"
```

* 根因：`migrator._normalize_default()` 未处理 **MariaDB 把字符串默认值加引号返回**
  （`information_schema.COLUMNS.COLUMN_DEFAULT` 在 MariaDB 返回 `''`，在 MySQL 8 返回空串）。
* 归属：该严格验收 + 失败关闭由 **`8fee172`（O-23）+ O-29** 引入；
  在 `2659722`（O-23 之前）该用例 8 passed，在 `8bf2963`（Q 修复前）已经失败。
  **与 Q 本次提交无关。**
* 交叉验证：同一时刻同一 DB 状态下，`8bf2963`（修复前）与 `073a994`（修复后）
  的全量失败画像基本一致（107 failed/211 errors vs 104 failed/238 errors），
  **不是 Q 引入的**。
* 影响：本项目的**元数据库实质上已成为 MySQL-only**——若内网元数据库使用 MariaDB，
  v1.6.2.2 会在启动时失败关闭。**建议确认内网元数据库品类**；若确为 MariaDB，
  需在 `_normalize_default()` 中剥一层字符串引号后再比较。
