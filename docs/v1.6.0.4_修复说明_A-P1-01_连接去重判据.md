## 1. 问题确认

v1.6.0.1 的 v9 迁移"按 name 去重并建 uq_conn_name"，会把**同名但端点/库不同**的两个真实实例
当成重复静默删除，连带 `instance_gate_rules`（ON DELETE CASCADE）静默删除、25 张表逻辑引用变孤儿。
内网 209 个实例命名撞车概率不低，属升级即丢数据的 P1。属实。

## 2. 修复（方案 A）

1. **v9 迁移改为 no-op**（`backend/schema/v9/090_connection_unique.sql`）：不再删除任何数据、
   不再建 `uq_conn_name`；仅保留版本号连续与可追溯。
2. **真重复去重 + 端点唯一约束改由 Python 层执行**（`database.py::_dedup_connection_endpoints`）：
   - 只对 `host+port+database` 完全相同的真重复去重，保留 `created_at` 最早（同则 id 较小）；
   - **同名不同端点绝不删除**（是两个不同实例）；
   - 删除冗余前先处置门禁：保留方无门禁则迁移过去，否则删冗余方门禁，**不静默 CASCADE**；
   - 逐条 `logger.warning` 记录被删连接及其 scan_tasks/slow_queries 关联数（可追溯）；
   - 用 `_add_unique_index_if_not_exists` 只建 `uq_conn_endpoint`；用 `_drop_index_if_exists`
     自动丢弃旧 v9 误建的 `uq_conn_name`（已应用旧 v9 的库下次启动即恢复）。
3. **应用层**：`_mark_existing`/`commit` 仍对同名/同端点标记冲突（不删数据）；同名冲突交由
   界面提示，不用删数据解决。

## 3. 反向鉴别用例（R-12，`tests/test_v9_migration.py`）

1. 同名不同端点两条 → 去重后**两条都在**；
2. 同端点同库两条 → 合并为一条；
3. 真重复去重后门禁规则不丢（迁移到保留方），不静默 CASCADE。
