## 二、A-6.1（认可，已修复）：解析降级时 `--` 注释残片被当表名，R001 误报

**复现**（两版一致）：文件审核保留 `-- SQL Object:` 注释头，语句解析失败走降级路径时，表名正则从注释内部提取出 `--` 残片当表名，R001 报"表/库名 '--' 不符合命名规范"；样本中 `kitp_rate_plan` 即此形态。

**修复**（两处，与 A 建议对齐）：
1. **降级路径提取前剥离注释**（`parser_legacy.py` 新增 `_strip_comments_for_fallback()`）：ParseError 与 Command/UNKNOWN 两处降级表名提取正则的输入先剥离 `--`/`#`/`/* */` 注释，从源头杜绝注释残片进入表名；
2. **R001 防御性跳过**（`naming.py`）：候选表名不含任何字母/数字/下划线（纯标点残片）时直接跳过，不报命名违规；真实不合规表名（大写开头、数字开头等）行为不变（含反向鉴别用例）。

**验证**（`tests/test_a_verify_desc_index_and_comment_fragments.py`）：注释头+解析失败 → 表名为真实表名、无 `--`、R001 无误报；纯标点候选跳过；大写/数字开头表名仍报。

## 三、A-6.2（认可，已修复）：MySQL 8.0 降序索引 `PRIMARY KEY (col DESC)` 无法解析

**复现**（两版一致）：`PRIMARY KEY (`id` DESC)` 在 sqlglot 29.0.0 / 30.14.0 / 30.17.0 **全部**解析失败（升版本无解），整表退化降级路径，结构类规则覆盖不完整且 R054/R077 因正则提取的列名带 `DESC` 后缀误报"分片键不在主键"。

**修复**（按 A 建议的纯文本预处理，爆炸半径受控）：
1. **解析层剥离索引列排序修饰**（`parser_legacy.py` 新增 `_strip_index_order_modifiers()`）：
   - 仅对 `CREATE TABLE` / `CREATE [UNIQUE] INDEX` / `ALTER TABLE` 生效（前导注释感知的 DDL 门控）；
   - **跳过 CTAS**（`CREATE TABLE ... AS SELECT` 可能携带 ORDER BY，不剥离方向语义）；
   - 只在字符串字面量与注释之外的普通文本段剥离 `\s+(ASC|DESC)(?=\s*[,)])`；
   - 非 DDL 语句（SELECT 的 ORDER BY 等）完全不动；
   - `sql_clean` 与 `sql_recover` 同步处理（恢复链 span 同源），`raw_sql` 保持原文（R077/R054 分片键提取不受影响）；
   - 修复后解析成功、结构类规则（R003/R004/R005/R028/R029 等）恢复完整覆盖——不再需要登记 KFN（解析已通，无假阴性）。
2. **R054/R077 正则回退列名规范化**（`distributed.py` 新增 `_strip_index_col_order_suffix()`）：主键/唯一索引正则回退提取的列 token 去除尾随 ASC/DESC 后缀（不改变既有正则的匹配范围，仅后处理），分片键合规判定对 DESC 主键/唯一索引不再误报；反向鉴别：分片键不在 DESC 主键内仍必须触发。

**验证**：
- `kitp_rate_plan` 现场样例：无 E999、结构完整、R003/R004/R005 不误报、shardkey=id ∈ 主键 → R054/R077 不误报；
- 多列混合 ASC/DESC 索引、CTAS 不剥离、字面量内 ` DESC,` 不剥离、SELECT ORDER BY 不剥离、注释内 DESC 文本保持；
- 反向鉴别：分片键不在 DESC 主键内 R054/R077 仍触发；R077/R054 既有 41 条用例全部保持。
