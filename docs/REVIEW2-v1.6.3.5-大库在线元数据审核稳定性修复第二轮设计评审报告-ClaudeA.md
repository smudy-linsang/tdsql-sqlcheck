## 1. 先把我上一轮的错误说清楚

**Mr.Linsang 和 O 在内存这件事上是对的，我错了。**

我把 memory 根组的 `max_usage_in_bytes = 11,465,011,200`（约 10.68 GiB）当成了推断主机容量的依据，写出"主机（约 10.7 GiB）""量级 12-16 GiB""8 GiB 约占全机 75%"。**这是错的**：那个字段是**历史使用峰值**，只是物理内存的下界，不是容量。

O 给出的是**直接证据**，我核对后确认：

| 出处 | 值 | 含义 |
|---|---|---|
| `wde.txt:107` `free -m` | total=63064 MiB | 主机约 **61.59 GiB** |
| `wde.txt:110` `/proc/meminfo` | MemTotal=64578408 kB | 同上口径 |

所以 8 GiB 是物理内存的 **13.0%**，不是 75%；4 GiB 是 6.5%，不是 40%。**我基于错误容量推出的"必先 swap""会连累 Web worker 和元数据库"那一整条次生灾害链条，前提不成立，撤回。**

更该反省的是方法：**`MemTotal` 是现成的直接读数，而我去用一个间接指标做推断**。这和我在 v1.6.3.2 犯过的 Playwright 那次是同一类错误——有一手证据不看，从旁证外推。

O 的另外 4 处纠正我也逐条查了，**全部成立**：

## 2. 本轮新增证据：把"到底是什么杀了 worker"往前推了一大步

64 GiB 这个事实纠正之后，我重新推了一遍机制，**结论反而更清楚了**。

### 2.1 内存耗尽可以被明确排除

| 事实 | 来源 |
|---|---|
| 主机 61.59 GiB，检查时可用约 57.22 GiB | `wde.txt:107/112`（O 提供） |
| memory 根组历史峰值仅 10.68 GiB | `wd2e.txt` v1 cgroup |
| 服务组历史峰值 3.62 GiB | 同上 |
| `oom_kill=0`、`failcnt=0`、三层限额均为无限制哨兵值 | 同上 |

**worker 涨到约 3.6 GiB 的时候，机器还有约 50 GiB 空着。**所以它**不是因为没内存被杀的**——这一点现在是确定的，不再是"倾向性判断"。

那么剩下的主要嫌疑就是 uvicorn 监督进程的强杀：

```python
# uvicorn/supervisors/multiprocess.py:218-222（本机 0.52.4 实读）
if process.is_alive(timeout=self.config.timeout_worker_healthcheck):   # 默认 5 秒
    continue
process.kill()   # process is hung, kill it   ← SIGKILL：无堆栈、无 OOM 记录
```

子进程靠一个 daemon 线程应答 ping。内存充足的情况下，**能让这个线程连 5 秒都抢不到 GIL 的，主要就是超大对象图上的 GC 停顿**（GC 全程持有 GIL）。

### 2.2 我实测了 GC 停顿，它精确指向 5 秒阈值

上一轮我测的是"普通线程打点间隔"，O 正确指出那不等于监督进程的真实 ping。这轮我改测**因果量本身——GC 停顿时长**（`gc.callbacks` 直接埋点）：

| 模式 | 表数 | 总耗时 | **最长单次 GC 停顿** | 每翻倍增长 |
|---|---|---|---|---|
| 现状 | 800 | 8.0 s | 0.172 s | — |
| 现状 | 1600 | 17.2 s | 0.536 s | **3.1×** |
| 现状 | 3200 | 49.4 s | **1.633 s** | **3.0×** |
| 流式修复 | 800 | 5.1 s | 0.017 s | — |
| 流式修复 | 1600 | 11.1 s | 0.020 s | 1.2× |
| 流式修复 | 3200 | 28.0 s | **0.033 s** | 1.7× |

拟合外推（现状 ~N^1.62，修复后 ~N^0.48）：

| 表数 | 现状最长 GC 停顿 | 修复后 |
|---|---|---|
| **6000** | **4.55 s** ← 逼近 5 秒阈值 | 0.04 s |
| 6400 | **5.05 s** ← **越过阈值** | 0.04 s |
| 8000 | 7.26 s | 0.05 s |

**故障发生在"6000+ 表"，而现状的 GC 停顿恰好在 6000—6400 表之间穿过 uvicorn 的 5 秒线。**而且我的合成表只有 20 列，真实业务表列更多、还有索引与视图，实际停顿只会更长、穿越点只会更早。

修复后在 6000 表的余量是 **约 119 倍**。

**这条证据的意义**：它同时解释了①为什么没有 OOM 记录、②为什么是静默 SIGKILL 无堆栈、③为什么恰好卡在 6000 表这个规模、④为什么 v1.6.3.0 正常（对象图小一个数量级）。四条现场特征一次对齐。

**但我按 O 上一轮的告诫收着说**：这是**本机合成负载 ＋ 幂次外推**，硬件、Python 版本、真实表结构都与内网不同；它是一个**可证伪的定量预测**，不是已证实的现场结论。我不写"已确定机制"，写的是"给出一条一次就能验证的路径"——见 §4 建议 A-1。

## 4. 本轮新增建议（不阻断）

### A-1（建议）把 GC 停顿列为容量验收的**必采指标**

§11.4 已要求记录"Web worker 心跳应答延迟"，§12.4 也区分了四类延迟。但按 §2.2 的数据，**真正的因果量是 GC 停顿时长**，而它：

* 是**进程内可直接测**的（`gc.callbacks` 埋点，无需插桩 uvicorn、不新增第二路 ping、不改 site-packages——完全符合 O 在答复 §6 第 3/4 条划的边界）；
* 开销极低（回调只做两次 `perf_counter`）；
* **一次运行就能证伪或坐实机制**：若 6000 表跑下来最长 GC 停顿逼近或越过 5 秒 → 机制坐实；若远低于 5 秒 → 我这条外推被证伪，需另找方向。

建议在 §11.4 的记录清单中，把"心跳应答延迟"扩写为：

> 记录 **Web worker 与元数据子进程各自的最长单次 GC 停顿、GC 累计停顿、GC 次数**（`gc.callbacks` 埋点，仅在版本受控的验收构建启用），与心跳应答延迟、事件循环 lag 一并归档。判读口径：最长 GC 停顿与 `--timeout-worker-healthcheck` 的 5 秒直接可比；**若修复后该值仍逼近阈值，说明机制另有其因，不得因"三次跑通"就认定根因已消除**。

同时建议在 §11.4 通过门槛中加一条可判读的量化项：**修复后子进程最长 GC 停顿 ≤ 1 秒**（我的外推是 0.04 秒，留 25 倍工程余量）。这比"没有 worker 重启"更早、更灵敏——没重启可能只是这次运气好。

### A-2（建议，成本近零）同一指标顺带覆盖其他"长时间待在 Web worker 里"的操作

本版正确地把范围限制在元数据审核（§1 明确不迁移慢 SQL/网关任务），我**不主张扩大范围**。但 §2.2 揭示的是一个**通用**隐患：任何在 Web worker 内长时间持有大对象图的操作，都可能撞上同一条 5 秒线。项目里至少还有**表类型统计（180 秒预算）**、日常巡检、大表治理走类似路径。

建议：既然验收阶段已经要埋 GC 观测，**在这些模块的既有冒烟测试里顺手记一次同样的指标**（不新增用例、不改它们的实现、不扩大本版交付范围），只是把数据存档。目的很明确——**下一次如果别的模块出现 worker 消失，我们手上已经有基线，不用再来一轮取证**。

若数据显示某模块也逼近阈值，那是**另立版本**处理的输入，不在 v1.6.3.5 范围内。

## 6. 向 Mr.Linsang 汇报

**先认账：内存那件事我错了，您和 O 是对的。**

我拿一个"历史用量峰值"（10.68 GiB）去反推主机有多大，推成了十几 GiB，然后据此说 8 GiB 会占掉四分之三、会把机器拖进 swap。**而 `MemTotal` 这个直接读数就在现场文件里摆着——64 GB。**我用旁证外推，没去看一手数据。8 GiB 实际只占 13%，我那条"次生灾害链"的前提根本不成立，已经撤回了。

O 另外还纠正了我四处：我说故障注入清单里没有内存越界那一条（其实 JOB-09 就是）、我给的错误响应格式会让旧页面显示成一坨对象、我把表名写错、我要求给不跑 Uvicorn 的服务写 Uvicorn 参数。**这四条我逐条查过代码，O 全对。**

不过有一点想说明：**那个参数最后还是从 8 GiB 收到了 1 GiB**，但用的是 O 的理由，不是我的——"在还没有修复后的完整内存实测数据之前，默认值先收紧是合理的防御"。这个理由比我原来那个站得住。**结论对了，但我的论据是错的，这两件事得分开说。**

**然后是这轮真正有价值的东西：我把"到底是什么杀了那个进程"往前推了一大步。**

正因为主机有 64 GB——出事那会儿还空着约 50 GB——**"内存不够被杀"这个可能性现在可以彻底排除了**。那到底是什么？我去测了一个之前没人测的东西：**垃圾回收的停顿时长**。

结果很说明问题：

| 表数 | 现在的代码，最长一次 GC 停顿 |
|---|---|
| 800 张 | 0.17 秒 |
| 1600 张 | 0.54 秒 |
| 3200 张 | **1.63 秒** |
| **6000 张（外推）** | **4.55 秒** |
| 6400 张（外推）| **5.05 秒** |

**而 uvicorn 的规矩是：worker 5 秒不吭声，就直接杀掉。**

出事的库正好是"6000 多张表"，而这条曲线**恰好就在 6000 到 6400 之间穿过那道 5 秒线**。而且我造的测试表只有 20 列，真实业务表列更多、还有索引和视图，实际只会更早撞线。

这一条同时解释了四件之前对不上的事：为什么日志里查不到任何 OOM 记录、为什么进程死得悄无声息连个报错都没有、为什么偏偏卡在 6000 表这个量级、以及为什么 v1.6.3.0 好好的。

**修好之后是多少？0.04 秒——离那道线还有 119 倍的余量。**

**但我这次学乖了，不把话说满**：这是我在本机用合成数据测出来再外推的，硬件和真实表结构都跟内网不一样。所以我没写"机制已经查实"，而是给了一条**一次就能验证的路子**：让 O 在验收时顺手记一下 GC 停顿时长——埋点只有两行、开销几乎为零、也不用去动 uvicorn。跑一次 6000 表，这个数要是逼近 5 秒，机制就坐实了；要是远低于 5 秒，就是我这条推测被证伪，得换方向查。**两种结果都有用。**

**方案本身我评下来是通过的，可以让 Q 开工了。**上一轮那五项 O 全都落实了，其中四项比我要求的还严——比如那个回滚制品，他要求**提前构建好并测试过**，而不是等回滚那天现拼。这一点做得比我提的还到位（回滚方案如果自己没被验证过，等于没有回滚）。

我只加了两条建议，都只是"验收的时候多记一个数"，不改设计、不改架构、不扩范围，**Q 不用等它们，现在就能动手**。
