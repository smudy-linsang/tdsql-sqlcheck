## 1. 评审边界与依据

本报告评审 A 提交的 Rev.I 详细设计、附录成品代码和测试设计。设计书中的“照图施工”、
“代码已完成”等表述属于被评审材料，不构成用户要求，也不替代独立核验。

本轮目标仍是：

1. 功能正确：指定数据库及全实例业务库的总表、单表、广播表、分片表数量可信；
2. 失败可见：失败、跳过、口径差异不得伪装成成功数字；
3. 零回归：不得明显挤占或破坏既有审核、扫描、巡检、权限、迁移和元数据能力；
4. 可实施：设计附录真正落盘后能够通过自身测试和全量回归。

## 4. P1 阻断问题

### P1-01 数据库名被无条件转小写，大小写不同的真实库会被合并

**位置**：附录 A.1 `_collect_baseline()`、`_collect_distributed()`、`analyze()`：

- `wanted = {d.lower(): d for d in dbs}`；
- `target = {d.lower() for d in dbs}`；
- `canon = {d.lower(): d for d in dbs}`；
- `known_dbs = {n.lower() for n in allnames}`。

**问题**：Rev.I 明确知道 `lower_case_table_names=0` 时表名大小写敏感，因而表名去重保持原样；
但数据库名却被无条件小写化。Linux/TDSQL 环境可以存在 `Sales` 与 `sales` 两个不同 schema。
上述字典会让后者覆盖前者：

- 两个库的 `information_schema` 基线被归入同一个键；
- Proxy 返回行在 `canon` 中被归给最后一个库；
- 另一个库显示 0 或产生虚假 `RECON_MISMATCH`；
- 指定库校验还会把错误大小写当成存在，随后可能在 `select_db()` 失败。

这是四个主数字的静默正确性问题，不能依靠告警兜底。

**整改要求**：数据库名匹配必须遵循目标实例的大小写规则。至少应：

1. 以 `SHOW DATABASES` 返回的原始名称作为唯一 canonical name；
2. 精确匹配优先；大小写不敏感回退只能在候选唯一且实例规则允许时使用；
3. 不得用单值 `{lower_name: original_name}` 表示可能一对多的命名空间；
4. `_collect_baseline`、`_split_qualified`、目标过滤和 `canon` 必须使用同一套规则。

**必须新增测试**：同时存在 `Sales.t_upper` 与 `sales.t_lower`，断言两库独立显示、实例总数为 2；
另测指定错误大小写的库不得被错误归属。

### P1-02 “总时长 180 秒”不是总预算，实际请求可明显超过 180 秒

**位置**：附录 A.1 `analyze()` 与 `_collect_distributed()`。

当前计时器在 `_collect_distributed()` 内才启动，而此前已经执行：

1. 实例类型解析；
2. `SHOW DATABASES`；
3. 全量 `information_schema.TABLES` 基线查询。

设计自己在 §9 说明基线查询才是主要耗时，但这部分完全不计入 180 秒。
进入逐库循环后，也只在每个库开始前检查一次时间；单库随后最多执行三条命令，
每条 `read_timeout=30s`。若在 179 秒时进入一个库，三条命令各接近 30 秒才返回，
请求可到约 269 秒，尚未计入前置查询和连接建立时间。集中式分支则完全没有 180 秒预算。

这会让同步请求、FastAPI 工作线程和共享扫描槽位的占用时间明显超出设计承诺，
与“单次最长 180 秒”和零回归资源保护结论冲突。

**整改要求**：

- 从进入扫描槽后、任何目标实例查询之前建立统一 monotonic deadline；
- `SHOW DATABASES`、基线查询、切库和每条 Proxy 命令都必须受剩余时间约束；
- 每条命令开始前再次检查 deadline，并把读超时限制为 `min(30, remaining)`；
- deadline 到期后不得再启动新命令；已完成库保留，未完成库统一标记 `SKIPPED`；
- 若受驱动限制只能实现“软预算”，文档和 UI 必须给出可证明的最大上界，不能继续称硬 180 秒。

**必须新增测试**：用可控时钟让三条命令分别消耗时间，证明不会在剩余不足时继续启动，
且前置基线耗时也计入 deadline；集中式慢基线也必须有确定超时行为。

### P1-03 失败/跳过库仍进入部分汇总，违反“不计入任何汇总数”

**位置**：附录 A.1 `_collect_distributed()` 结果组装：

- `overlap_total` 在排除失败/跳过 owner 之前按整个 `kinds_seen` 计算；
- 每库先计算并累加 `baseline` / `subp`，之后才判断 `FAILED` / `SKIPPED`；
- `kind_map` 可包含其他成功库的一次实例级返回中携带的失败库行。

**复现场景**：

1. `db_a` 三条命令成功，实例级结果同时带回 `db_b.t1`，且 `t1` 在两个类型中出现；
2. `db_b` 自己的一轮命令失败，最终状态为 `FAILED`；
3. `db_b` 主分类数量虽然没有加到 `total_tables`，但其跨库行已进入 `kinds_seen`，
   `overlap_count` 仍被加 1；`baseline_tables` / `subpartition_tables` 也在状态判断前被汇总。

立即把预算设为超限也能看到：所有库都为 `SKIPPED`、`total_tables=0`，
但实例级 `baseline_tables` 仍是全部库的基线总和。该行为与接口文案
“FAILED/SKIPPED 不计入任何汇总数”以及 W1 “未计入任何汇总数”不一致。

**整改要求**：先确定每个 owner 的最终可计入状态，再构建汇总。推荐建立
`eligible_dbs = all_dbs - failed - skipped`，所有主分类、基线、子分区、重叠和差异汇总
统一按 owner 过滤。若产品决定“基线即使 Proxy 失败也显示”，则必须把它改成独立的
`observed_baseline_tables` 语义，并同步修改文案、UI 和恒等式，不能继续声称“不计入任何汇总”。

**必须新增测试**：

- 成功库的跨库结果包含失败库同一张表的两个类型，断言 `overlap_count==0`；
- 全部库立即 `SKIPPED`，断言所有声明为“不计入”的汇总均为 0；
- 失败库的跨库行不得触发 `SUBPARTITION_EXCLUDED`。

### P1-04 `_ensure_schema()` 仍不能阻止多类“采集后才落库失败”

**位置**：附录 A.1 `_ensure_schema()`、KL-15。

Rev.I 只查询 `COLUMN_NAME, DATA_TYPE`。这能够挡住 `INT → VARCHAR`、
`MEDIUMTEXT → TEXT`，但不能校验：

- `VARCHAR` 长度，例如 `detail VARCHAR(16)`、`connection_id VARCHAR(8)`；
- `id` 的 `AUTO_INCREMENT`；
- `stat_id NOT NULL`；
- `created_at DEFAULT CURRENT_TIMESTAMP`；
- 其他默认值、可空性、字符集/排序规则；
- 索引的完整列序、唯一性等定义，只检查了首列。

例如同名残留表若为 `id INT PRIMARY KEY DEFAULT 0`，当前验收会通过，第一次可能写入，
第二次在主键 0 处失败；若 `detail` 被收窄为 `VARCHAR(16)`，500 库采集完成后才会在 INSERT
触发 1406。它们正是首轮 P1-08 要消除的“用户白等采集后才失败”路径。
KL-15 已登记长度缺口，但“已知”不能等同于“已关闭”。

**整改要求**：以迁移 DDL 为完整契约，查询并校验 `COLUMN_TYPE` 或
`DATA_TYPE + CHARACTER_MAXIMUM_LENGTH/NUMERIC_*`、`IS_NULLABLE`、`COLUMN_DEFAULT`、`EXTRA`，
并校验索引的全部列序和唯一性。跨发行版显示宽度差异可通过字段级归一化处理，
不能因此放弃对 varchar 长度、自增和默认值的确定性验收。

**必须新增测试**：`id` 缺自增、`detail` 长度收窄、`created_at` 缺默认值、
`stat_id` 允许 NULL 四种结构均须在采集前失败关闭。

### P1-05 v13/130 槽位护栏在迁移文件真正落盘后必然失败

**位置**：附录 A.4 `test_migration_slot_is_not_already_taken()`。

测试先把实际迁移文件写入 `taken`，允许 `ours` 已存在且文件名正确：

```python
assert ours not in taken or taken[ours].startswith("130_table_type_stats")
```

但下一段又无条件要求：

```python
assert ours > max(taken)
```

当 `backend/schema/v13/130_table_type_stats.sql` 真正落盘后，`max(taken) == ours`，
所以该测试必失败。设计阶段它之所以通过，仅因为迁移文件尚不存在；这没有验证实施后的状态。

此外，`taken[(version, sequence)] = filename` 用单值字典保存槽位。同一槽位若有两个文件，
后遍历的文件会覆盖前一个，护栏可能看不到重复项，恰好没有钉住 DEF-1 想防的场景。

**整改要求**：

1. 用 `slot -> [files...]` 保存全部占用者，任何列表长度大于 1 立即失败；
2. 迁移文件已落盘时，断言该槽唯一且 `ours == max(all_slots)`；
3. 若还要支持设计阶段未落盘检查，应先从占用集合中排除“本模块预期文件”，再断言
   `ours > max(existing_other_slots)`；不要把两种阶段混在同一不自洽断言中；
4. 实施门禁必须在真实文件已存在时执行，不能继续以 T-R08 的设计阶段跳过代表完成。

**必须新增测试**：临时构造同槽两个不同文件，断言护栏失败；真实 v13/130 文件存在时护栏通过。

## 5. P2 必须整改问题

### P2-01 分布式合法逻辑表也可能被误标为“物理子表”

**位置**：附录 A.1 `_classify_subpartitions()`。

当前充分条件是“名字匹配后缀 + 父表在 Proxy 结果中”。考虑两个都是真实逻辑表：

- `orders`；
- `orders_tdsql_subp202601`。

若两者都出现在 Proxy 结果中，后者仍会因父表 `orders` 存在而被移入 `subp`。
四个主数字因为采用 Proxy 口径仍可能正确，但页面会错误显示子分区数并产生
“仅 Proxy 可见”的虚假差异告警。

**整改要求**：候选物理子表还必须满足“候选名自身不在 Proxy 逻辑表集合中”。
即：后缀匹配、父表在 Proxy、候选自身不在 Proxy，三者同时成立才剔除。

**新增测试**：父表与后缀命名子表同时在 Proxy 时，两者都保留为逻辑表，`subpartition_tables=0`。

### P2-02 历史抽屉静默只显示前 10 条告警

**位置**：附录 A.5.5 `loadTableTypeHistoryDetail()`：

```javascript
tabletypeDetailWarnings.value=(body.warnings||[]).slice(0,TABLETYPE_WARN_CAP);
```

实时结果提供“展开查看全部”，历史抽屉却没有总数、截断提示或展开按钮。
超过 10 条时，用户会误以为历史记录只有这 10 条，违反“可回看”的信息完整性。

**整改要求**：历史告警与实时告警共用同一套“默认 10 条 + 总数 + 展开全部”机制；
若后端能够严格证明告警永不超过 10 条，也应删除无提示的 `slice`，避免未来版本静默丢信息。

### P2-03 部分失败或全失败仍弹绿色“统计完成”

**位置**：附录 A.5.5 `runTableTypeStats()`。

只要接口返回 200，前端就执行：

```javascript
ElementPlus.ElMessage.success(`统计完成：${r.database_count} 个库 / ${r.total_tables} 张表`)
```

即使 `failed_databases=500`、主结果为 0，也会先出现绿色成功提示。
虽然页面随后有红色告警，但即时反馈与结果状态矛盾，容易让用户把“0 张”当成真实结论。

**整改要求**：仅 `failed_databases==0 && skipped_databases==0` 时显示成功；
部分结果用 warning 并写明成功/失败/跳过库数；全部失败用 error，且不得使用“统计完成”作为唯一提示。
