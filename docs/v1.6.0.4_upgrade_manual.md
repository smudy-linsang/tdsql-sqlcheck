## 一、 版本核心变更与架构升级总览 (V1.5.2.5 ➔ V1.6.0.4)

从 V1.5.2.5 全量升级至 V1.6.0.4，系统完成了以下四大核心架构升级与能力拓展：

1. **ZooKeeper 自动发现内网深度适配与扫描期富集 (G10 特性)**：
   - **扫描期富集**：支持在扫描 ZK 拓扑时自动富集实例真实名称与可访问业务库，提供五级自适应名称解析链（用户手动覆盖 ➔ 扫描期富集 ➔ 链式解析）；
   - **IP 段替换与过滤器**：支持批量 IP 网段替换规则、列表分页与五维维度筛选；
   - **一库一连接规范**：以 `${instance_name}-${proxy_port}-${database}` 格式生成独立连接，防重名误删保护。

2. **系统元数据库 Schema 迁移升级 (v7 / v8 / v9 连续递进)**：
   - **v7 架构**：新增 5 张原始慢日志系统表（`slow_log_sources`, `slow_log_source_nodes`, `slow_log_cursors`, `slow_log_events`, `slow_log_runs`）；
   - **v8 架构**：新增 `zk_discovery_config` 表保存 ZK 服务节点、映射规则、扫描富集与探查配置；
   - **v9 架构**：针对 `tdsql_connections` 增加 `(host, port, database)` 联合唯一索引 `uk_host_port_database`（修正去重判据：仅按 `host+port+database` 去重，绝不按同名删除连接，迁移非静默逐条日志）。

3. **依赖库变更与离线部署规范**：
   - 增加纯 Python 协议连接驱动 `kazoo>=2.10.0`，全量发布包 `wheels/` 已内置对应离线 `.whl` 文件。
   - **注意**：离线升级**必须重新执行 wheels 依赖安装**，若仅覆盖代码目录会导致 ZK 发现因缺少 `kazoo` 而抛出 503 异常。

4. **安全与关断机制**：
   - 重复导入触发标准 `IMPORT_CONFLICT` / `409 Conflict` 提示；
   - 包含扫描探查超时防护与日志诊断。

## 二、 核心重点：元数据库（System Meta-Database）变更与自动迁移详解

**在升级至 V1.6.0.4 过程中，后台服务启动时会自动安全地应用增量 Schema 迁移文件（`backend/schema/v7/070_raw_slow_log_collection.sql`、`v8/080_zk_discovery_config.sql`、`v9/090_tdsql_connections_unique_index.sql`）以及 `migrator.run_migrations()`，无需运维人员手动执行 DDL 脚本。**

以下为元数据库变更清单：

### 1. 新增 5 张原始慢日志系统表 (v7 架构)
- `slow_log_sources`：原始慢日志采集源表；
- `slow_log_source_nodes`：采集源节点信息表；
- `slow_log_cursors`：节点字节偏移与文件唯一标识游标表；
- `slow_log_events`：逐条慢日志解析事件与脱敏 SQL 表；
- `slow_log_runs`：调度运行审计与错误追踪表。

### 2. 新增 ZooKeeper 自动发现配置表 (v8 架构)
- `zk_discovery_config`：存储 ZK 服务地址列表、根路径 (`/tdsqlzk`)、Proxy 映射规则、段替换规则、扫描富集与探查参数。

### 3. 实例连接表唯一约束与索引升级 (v9 架构)
- **`tdsql_connections` 表优化**：
  - 创建 `uk_host_port_database` 联合唯一索引 `UNIQUE KEY (host, port, database)`；
  - 自动清理历史存量重复端点记录（仅以 `host+port+database` 为唯一依据，保留主主副本，绝不按同名删除不同端点的实例）；
  - 导入/手工建连遇到已有端点时，标准化返回 `IMPORT_CONFLICT` / `409 Conflict`。

## 三、 打包与发布注意事项（打包人员说明）

1. **`--with-python` 与 `--py` 匹配规则**：
   - 运行 `./deploy/make_release.sh --with-python` 时，系统将内置独立 CPython 3.11 运行时；
   - `--with-python` 与 `--py` **不能同时指定非 311 的版本**（例如 `--with-python --py 39` 属于非法组合），打包脚本会直接拒绝并提示原因，这是为了防止目标机便携解释器与 wheels ABI 不匹配。

## 四、 全量部署与安装操作步骤（内网运维智能体执行）

### 1. 解压全量发布包与部署预检
```bash
# 解压全量发布包
tar -zxvf tdsql-sqlcheck-v1.6.0.4-linux-x86_64.tar.gz
cd tdsql-sqlcheck-v1.6.0.4

# 执行部署预检（要求全 PASS，验证依赖与环境健康）
bash deploy/preflight_check.sh
```

### 2. 配置文件校验 (`deploy/.env`)
核对并更新 `deploy/.env` 配置文件中的元数据库与网络参数：
```ini
SQLCHECK_DB_HOST=127.0.0.1
SQLCHECK_DB_PORT=13306
SQLCHECK_DB_USER=root
SQLCHECK_DB_PASSWORD=tdsql_test_2024
SQLCHECK_DB_NAME=tdsql_sqlcheck
AUTH_ENABLED=true
ADMIN_INITIAL_PASSWORD=Admin@1234
```

### 3. 执行全量安装与服务升级重启
```bash
# 执行安装脚本（停止已有服务、覆盖全量代码、重新安装 wheels 依赖、升级数据库 Schema）
sudo ./deploy/install.sh
```
> ⚠️ **重要提醒**：`kazoo` 是本版新增核心依赖。升级时**必须完整运行 `./deploy/install.sh`（或显式执行 `pip install --no-index --find-links wheels/ -r requirements.txt`）**，切勿仅替换后端 Python 源码目录，否则访问 ZK 自动发现时将引发 `503 Service Unavailable` 依赖缺失错误。

### 4. 上线最后自检 (必做步骤)
```bash
# 在目标部署机上运行部署校验脚本
bash deploy/verify_deploy.sh
```
`verify_deploy.sh` 会自动检测 Uvicorn 进程、端口监听、版本比对（输出 `1.6.0.4`）与 `/health` 端点，全部输出 PASS 即代表升级成功。
