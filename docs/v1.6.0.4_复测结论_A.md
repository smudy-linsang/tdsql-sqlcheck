## 2. 按 Q 传话的两个场景实测

### 场景 1：同名不同端点 + 各挂门禁与扫描历史 → 两条都在、门禁一条不少

```
连接: [('A1', '10.1.1.1:15001/tdsql_a'), ('A2', '10.2.2.2:15002/tdsql_b')]
门禁: [('A1', 0), ('A2', 5)]
  ✅ 两条同名连接都保留
  ✅ 门禁规则一条不少且归属未变
  ✅ 扫描历史无损失 — scan_tasks=2 slow_queries=2
```

**这正是上一轮会被静默删除的情形，现在两条都活下来了。**

### 场景 2：同端点同库 + 挂门禁与历史 → 合并为一条、门禁不丢

```
连接: [('B1', '库-旧名')]
门禁: [('B1', 7)]
  ✅ 合并为一条且保留最早的
  ✅ 门禁未丢，已迁移到保留方
  ✅ 删除动作有逐条日志
```

日志原文：

```
迁移: 删除真重复连接 id=B2 name=库-新名 endpoint=10.3.3.3:15003/tdsql_c
      保留id=B1 关联scan_tasks=1 slow_queries=1(将成孤儿,请人工核对)
```

**注意这里的细节**：门禁规则原本只挂在**将被删除的那条**（B2，阈值 7）上，保留方 B1 没有。修复后门禁被**迁移到了 B1 并保留原值 7**，不是简单删掉。这是 Q 自己加的处理，比我提的要求更周到。

日志也做到了我要求的"逐条记录删了什么"，而且**主动标注了将成孤儿的关联记录数并提示人工核对**。
