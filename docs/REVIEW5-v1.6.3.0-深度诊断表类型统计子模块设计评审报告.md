## 4. P2 必须整改问题（本轮新发现，Rev.L 引入）

### P2-01 `BINARY TABLE_SCHEMA IN (...)` 的实测代价与其声明目的相反，且对正确性零贡献

**位置**：附录 A.1 `_collect_baseline()`；§6.4 说明文字；ADR-27；E-36；
`T4-R01` 末行断言。

**设计的说法**（§6.4）：

> SQL 端用 `BINARY TABLE_SCHEMA IN (...)` **缩小返回集**

**实测结果**（本地 MariaDB 10.11.14，`lower_case_table_names=0`，
构造 120 个业务库 × 10 张表，全库 1623 张表；指定单库路径即 `database` 参数路径）：

| 写法 | `EXPLAIN` Extra | 中位耗时 | 返回行数 |
|---|---|---:|---:|
| `TABLE_SCHEMA IN (%s)` | `Skip_open_table; **Scanned 1 database**` | **0.32 ms** | 10 |
| `BINARY TABLE_SCHEMA IN (%s)` | `Skip_open_table; **Scanned all databases**` | **2.04 ms** | 10 |

**返回集完全相同（同为 10 行），代价却是 6.4 倍，且随实例库数线性增长。**
`BINARY` 使谓词不可下推，`information_schema` 从"只扫 1 个库的元数据"退化为
"扫全部库的元数据"。本设计 `MAX_DATABASES = 500`，且文档自己多处指出
**基线查询是本模块的耗时大头**——这一改动恰好打在最贵的那条查询上。

**三条独立理由说明该谓词应当删除：**

1. **对正确性零贡献。** 应用层防御（`known.resolve()` → canonical → 目标集精确
   成员判断）已经完备，且**严格强于** SQL 端二进制比较：SQL 端只能处理
   "大小写不同"，处理不了"返回了实例上并不存在的第三种大小写"这类情形，
   而应用层会判为歧义并丢弃。`T4-R01` 恰恰证明了这一点——即便 SQL 端把
   `sales.t_lower` 原样返回，服务层照样只计 `Sales.t_upper`。
   **删掉 `BINARY` 后 `T4-R01` 的行为断言依然成立。**
2. **触发它的前提在本平台并不成立，在目标平台未经验证。** 本机
   `information_schema.TABLES.TABLE_SCHEMA` 排序规则为 `utf8mb3_general_ci`
   （名义上大小写不敏感），但实测 `TABLE_SCHEMA IN ('G14PERF_001')`
   **不加 `BINARY` 也返回 0 行**——即该平台上的库名比较本就是大小写敏感的。
   "排序规则可能忽略大小写因而需要 `BINARY`"这个前提，**在 TDSQL 8.0.33 上
   尚无实测证据**。为一个未经证实的前提，付出确定的性能代价，方向是反的。
3. **`BINARY expr` 已被 MySQL 官方标记为弃用**（自 8.0.27 起，建议改用
   `CAST(expr AS BINARY)`），而内网元数据库与业务实例均为 `8.0.33-v24-txsql`。
   在一个全新模块里引入弃用语法，会给后续版本升级留坑。**此条请内网确认后再定。**

**整改要求（二选一，推荐第一项）：**

1. **删除 SQL 端 `BINARY`，恢复 `TABLE_SCHEMA IN (...)`**，正确性完全由应用层
   两层防御承担（现状已具备且已被 `T4-R01` 覆盖）。§6.4、ADR-27、E-36 的
   文字同步改为"SQL 端不做大小写假设；归一与过滤一律在应用层完成"。
2. 若内网实测确认 TDSQL 上 `TABLE_SCHEMA` 比较**确实**大小写不敏感、
   且确有必要在 SQL 端减载，则必须给出**不破坏下推的**写法并附实测
   `EXPLAIN` 与耗时对比；仅换成 `CAST(... AS BINARY)` 不解决下推问题。

**必须同步调整的测试**：`T4-R01` 末行

```python
assert any("BINARY TABLE_SCHEMA IN" in sql for sql in pool.seen)
```

把一个**实现细节**钉进了测试。该用例的价值在于"多返兄弟库时服务不吸收"这个
**行为**，而不是 SQL 长什么样。建议删除该行；确需约束 SQL 形态时，应改为断言
"不得对 `TABLE_SCHEMA` 施加使谓词不可下推的函数/操作符"，并配一条
`EXPLAIN` 断言或性能护栏，否则这条断言会把一个待纠正的决定固化下来。

**必须新增测试/验收**：在内网库数最多的实例上，对同一目标库分别执行两种写法，
记录 `EXPLAIN` 的 `Scanned N database(s)` 与耗时，作为该决定的实测依据
（可并入 §10.3 或 §12.4）。

## 5. 明确**不作为缺陷**提出的一项（附独立核查）

### 软预算导致"共享并发槽位可被无界占用"——经横向核查后，判定不构成缺陷

Rev.L 删除硬上界后，§9 如实写为"仍无硬上界"。这引出一个合理担忧：
`registry.scan_slot` 的配额是**与既有 SQL 审核、慢查询扫描共享**的（ADR-19），
若某次 G14 采集长时间不返回，会占住共享配额、挤占既有功能——
而"共享配额"当初正是作为**安全特性**引入的。

**我核查了平台内既有模块的同类口径，结论是：不应就此开票。**

| 模块 | 墙钟硬上界 | 连接读超时 |
|---|---|---|
| `scan_service`（慢查询扫描） | **无**；仅对 processlist 轮询夹取 `≤60s`（`scan_service.py:133`） | 池默认 10s |
| `index_audit_service` / `cluster_inspect_service` 等既有深度诊断子模块 | **无** | **未设置**，用池默认 10s |
| **G14（Rev.L）** | 无（软预算 180s） | **显式 30s** |

**平台内没有任何模块具备可证明的墙钟硬上界**，既有深度诊断服务甚至不显式设置
读超时。G14 的软预算 + 显式超时**严于**既有模块。用一个平台自身不满足的标准
去要求一个诊断子模块，与本文档 ADR-20 已确立的对称性原则冲突。

**建议（非阻断）**：在 KL-19 补一句横向对照，写明"该状况与既有扫描/巡检一致，
非本模块特有"，以免下一轮被重复开票。若将来平台整体引入采集看门狗，G14 一并接入。

## 8. 最终结论

Rev.L 的修订是扎实的。第四轮的 2 项 P1、2 项 P2、1 项 DOC **全部真实关闭**，
且我用实际执行做了独立验证：110 项 collect、109 通过 1 跳过、离线 87 通过，
与文档自述逐项吻合，**无虚报**。

其中 `T4-R02`（驱动真实连接池走完 ping→建连→切库→重建的 70 秒尾部）与
`T4-R03`（驱动真实 PyMySQL `_read_bytes` 证明 30 秒不是整条 SQL 的上界）
是本方案迄今**证据质量最高的两条测试**——它们用可执行的机制证据取代了我在
Rev.K 里"常量相加 + 源码字符串计数"的写法。第四轮说我那条测试名不副实，
这个批评成立，Rev.L 的修法比我原来的好。

本轮唯一的新问题是 Rev.L 为修 P1-01 而引入的 `BINARY` 谓词：它对正确性零贡献
（应用层防御已完备且更强），触发它的前提在本平台不成立、在 TDSQL 上未经验证，
而实测代价是把最贵的那条查询从"扫 1 个库"变成"扫全部库"（120 库下 6.4 倍，
随库数增长）——**方向与设计自己写的"缩小返回集"相反**。这是一处定向可改的
P2，不涉及架构。

**本次评审结论：有条件通过。P2-01 关闭后即可按附录 A 落盘实施，
不需要再走一轮全量评审。**

考虑到本方案已历经五轮评审、核心口径与失败隔离早已收敛，
继续以整文档为单位往返的边际收益已经很低。建议 P2-01 以**定点修订 + 本人复核
该单点**的方式关闭，随即进入开发，把剩余的验证力量放到落盘后的真实回归与内网 UAT 上。
