## 5. 靶场能做什么、不能做什么

### 5.1 本轮已经由靶场做掉的验证

- 应用经 TCP/MySQL 协议连接 15002，并用 `select_db` 发送 `COM_INIT_DB` 后执行三条专有命令。
- 单列 `without shardkey`、双列 `with shardkey`/`with noshardkey_allset`、`db.table` 值形态以及空结果集均进入真实解析和汇总代码。
- API、扫描槽、留档、历史、前端摘要/明细/范围时间走完完整链路。
- 4/2/2 三类集合与后端 8 张 BASE TABLE 完成逐名对账。

这些结果可以关闭“应用是否能处理预期协议形态”的外网疑问，价值明确。

### 5.2 不能替代真实 TDSQL 的原因

1. `deploy/tdsql-dev-cluster/tdsql_proxy.py` 是自研 Python 模拟器，不是腾讯 TDSQL Proxy 二进制；三条命令的结果由静态/自建分片元数据生成，而应用正是按这份预期契约解析，存在同源自证。
2. 后端只有一台标准 MySQL 8；两个虚构 SET 指向同一后端，无法验证真实多 SET 路由、跨版本返回差异、权限可见范围、物理二级分区及故障切换。
3. 实测若只在登录握手中指定默认库而不另发 `COM_INIT_DB`，模拟器三类结果均为空；当前应用因显式 `select_db` 不受影响，但这已经直接证明它不是会话语义等价实现。
4. T20 关注真实 TDSQL `information_schema` 优化器的谓词下推与扫描库数；在标准 MySQL 8 上比较普通 `IN` 与 `BINARY IN`，不能推导生产 TDSQL 的计划和耗时。

因此，**靶场不能把真实环境验证全部做掉**。真实 TDSQL 集合对账和 T20 仍须在批准的内网生产变更窗口执行。

### 5.3 靶场文档改进建议（不记为 Q 产品缺陷）

当前 README 使用“原厂 Proxy 协议网关”“100% 满足”等表述，与实现不符。建议 G 后续按以下方式修订：

1. 统一改名为“Python TDSQL 协议模拟靶场”，明确后端是标准 MySQL 8、三条命令为模拟响应。
2. README 增加能力矩阵：TCP/返回形态/COM_INIT_DB/汇总链路为“可验证”；真实路由、真实权限、版本差异、物理分区、优化器为“不可验证”。
3. 若继续提升仿真度，先修复握手默认库跟踪，再从真实 TDSQL 各版本采集并脱敏保存返回形态语料，做协议兼容回放；不得仅增加更多硬编码示例便宣称等价。
4. `docker-compose.yml` 不应在每次启动时在线 `pip install`；构建固定依赖版本的本地镜像并记录镜像摘要，提高内网复现性。

## 7. 新发现问题与照图施工方案

### UAT3-O-G14-01（P2）：异步请求所有权仍无行为级自动化

#### 现象与风险

`tests/test_g14_frontend_state_binding.py` 的三项 Rev.Q 用例读取源码文本后检查 `_deepPost`、`apiFetch`、`isTableTypeRequestCurrent`、`finally`、loading 及模板字符串。它们能防误删明显标记，但没有运行 Vue 页面、没有制造并控制两个 Promise 的返回顺序，也没有观察 toast 和按钮状态。

例如，未来代码保留全部被检查字符串，却把实际错误提示移动到守卫之前、把第二个请求的 loading 提前清掉，静态门禁仍可能通过。Q 整改报告第 41 行称其为“非纯字符串存在性”，与实际测试方法不一致；同时没有实现第二轮报告明确要求的 A/B 可控 Promise 用例。

#### 必须按以下步骤补齐

1. 在测试依赖中固定浏览器自动化版本，并把 Chromium 安装纳入 CI 镜像；本地缺浏览器不得静默 skip，G14 前端门禁任务应失败关闭。
2. 新增独立测试 `tests/test_g14_request_ownership_browser.py`，启动隔离元数据库和临时端口服务，使用实际 `frontend/index.html`，不得复制一份简化版 `runTableTypeStats`。
3. 用浏览器请求拦截精确控制 `/api/v1/table-type-stats/run`：第一次请求 A 暂不返回；切换实例/库后再发 B。响应体采用现有接口契约，不依赖真实数据库。
4. 落下四个行为用例：
   - A 延迟返回 422：切到 B 后不得出现 A 的 error toast、结果或告警，按钮可用。
   - A 未返回时启动 B：先结束 A，B 的按钮仍保持 loading；只有 B 完成后 loading 才关闭。
   - A 延迟返回 200：不得显示 A 的成功 toast 或 A 数据；B 完成后只显示 B 的 scope 与数据。
   - 不切 scope 的当前 400/422/500：必须展示服务端可读错误，按钮恢复。
5. 断言必须基于可见行为：`.el-message` 文本/数量、结果范围、汇总数字、按钮 disabled/loading class；不得只断言源码里存在某个字符串。
6. 把该测试加入默认 `pytest` 全量或单独的必过 CI job，并在整改报告中提供“故意删除 isCurrent 守卫后用例失败、恢复后通过”的一次 mutation 证据。

关闭标准：上述四个异步顺序在实际页面上自动化全绿；静态门禁可保留作补充，但不得继续冒充行为测试。

## 8. 内网生产环境最终验证施工单

由于没有独立真实 TDSQL 测试集群，本轮允许在批准的生产变更窗口按“只读、小库先行、失败即撤入口”方式完成最终验证。

### 8.1 上线前与灰度

1. 备份平台元数据库，核对 v13 两张新增留档表的字段、索引和字符集；先部署单节点/单入口。
2. G14 初始只授权内网验证账号和 DBA；确认 `/health`、页面 title 均为 1.6.3.0，并先抽查即时审核、扫描任务等既有入口。
3. 选择一座低风险且同时含单表、广播表、分片表的较小业务库，所有命令均只读；记录实例、库、账号、开始/结束时间和 request id。

### 8.2 真实集合与六数字对账（必须完成）

在同一会话、同一时间窗执行：

```sql
/*proxy*/show table without shardkey;
/*proxy*/show table with noshardkey_allset;
/*proxy*/show table with shardkey;

SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_TYPE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA IN ('目标库');
```

按“库名+表名”保存原始集合后核对：

- 单表、广播表、分片表分别等于三条 Proxy 结果的去重集合；三类不得重叠。
- 总表等于三类并集；逻辑基线只取 BASE TABLE，并按设计三条件剔除真实物理子表。
- 页面逐库的总表/单表/广播表/分片表/逻辑基线/二级分区子表六个数字与独立计算逐项一致；失败库、跳过库、重叠数和告警也要留存。
- 不一致时必须保存双向差集表名，不能只截图六个汇总数字。

### 8.3 T20（必须完成）

在业务库数量最多的真实实例选择同一目标库，对普通 `TABLE_SCHEMA IN ('目标库')` 与 `BINARY TABLE_SCHEMA IN ('目标库')`：

1. 各执行 `EXPLAIN`，记录 `Scanned N database(s)`。
2. 各预热 1 次，再实跑至少 5 次，记录每次耗时、中位数、返回行数。
3. 比较 `(TABLE_SCHEMA,TABLE_NAME,TABLE_TYPE)` 集合，必须一致。
4. 普通 `IN` 的扫描库数或中位耗时不得劣于 `BINARY IN`；若劣化，停止放量并分析，不得无证据直接恢复 `BINARY` 或 `CAST`。

### 8.4 停止与回滚

出现任一情况即停止：六数字或原始集合不一致；系统库混入；成功库被标 FAILED/SKIPPED；HTTP 500；元数据查询引发明显负载；T20 触发劣化判据；既有模块异常。

回滚顺序：先撤销普通用户的 `deep-diag-tabletype` 权限或停止新请求，再回滚应用到上一发布镜像/提交。v13 是新增留档表，旧应用不引用，紧急回滚时保留原表，禁止在生产 DROP。归档三条 Proxy 输出、`information_schema` 行集、EXPLAIN、五次耗时、应用日志和时间戳后再分析。
