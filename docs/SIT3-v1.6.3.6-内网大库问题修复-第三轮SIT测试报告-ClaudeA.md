## 2. 判据 7：开销不通过 —— 本轮唯一的 BLOCK

### 2.1 现象

取消前置过滤后，**良性子表也走 `except` 分支**，于是每张子表都往 schema.sql 里写一个
6 行 `[SKIPPED]` 存证块（`metadata_audit_pipeline.py` 第 215-221 行）。
前一版有前置过滤时，良性跳过在 `continue` 之前，**一个字节都不写**。

**文件体量实测：**

| 子表数 | schema.sql | 其中 [SKIPPED] 注释 | 注释占比 |
|---|---|---|---|
| 219 | 95,998 B | 76,042 B | 79% |
| 2,800 | 1,034,103 B | 970,270 B | **94%** |
| 5,800 | 2,124,483 B | 2,009,650 B | **95%** |

对照：内网 v1.6.3.4 那份真实产物 `extracted_lzbj_ecif_...sql` 是 **432,066 B**。
也就是说 ECIF 这个库，**用户下载到的 .sql 会从 42 万字节涨到约 100 万字节，其中 94% 是跳过注释**。

### 2.2 更要紧的是审核耗时，而且超线性

固定 100 张真实表（20 列 DDL），只变子表数：

| 子表数 | schema.sql | 注释占比 | 拆句数 | 审核耗时 | 较基线增量 |
|---|---|---|---|---|---|
| 0 | 108,587 B | 0% | 100 | 0.87 s | — |
| 200 | 177,927 B | 37% | 100 | 1.34 s | +0.46 s |
| 400 | 247,267 B | 53% | 100 | 3.33 s | **+2.46 s** |

子表数翻一倍，增量涨到 **5.3 倍** —— 明显超线性。
另一组独立测量（219 张真实表 + 2800 子表，真实表 DDL 取极小值以隔离注释成本）：
**含跳过块 121.68 s vs 去掉跳过块 0.18 s。**

两组测量都指向同一结论：**ECIF 量级（约 2800 子表）会多出 1–4 分钟纯浪费**。
这个外推跨了一个数量级，精确数值要到内网才能定死，但方向和量级是实的。

好消息是**没有污染审核结果**：拆句数 219 = 219、100 = 100，注释块不产生语句、不产生违规。
坏消息是这 1–4 分钟全是白烧的——注释里没有任何可审核内容。

任务预算 `_JOB_TIMEOUT = 1800 s`（`backend/api/metadata_audit.py:32`），
所以大概率不会撞死线；但内网 6097 表库原本 342 s，本版是为了让大库跑得动而发的，
在这条路上加几分钟纯浪费，方向是反的。

### 2.3 【R3-B-01｜BLOCK】改法（我定）

**良性跳过（`tdsql_internal`）不再逐个写 `[SKIPPED]` 块，改为在文件末尾写一行汇总：**

```
-- [SKIPPED-SUMMARY] TDSQL 物理分片子表 2800 张已跳过（父表 DDL 已纳管），明细见任务跳过清单
```

**异常跳过（`extract_failed`）保留逐个 `[SKIPPED]` 块不变** —— 需要溯源的是异常，不是良性；
而且异常有阈值告警兜底，数量有界。

这一改同时解决文件 94% 噪音和几分钟的解析浪费，且不丢信息：良性跳过的计数已经落在
`audit_history.skipped_benign`，样例在 `skipped_list`。

> 一点取舍写明：良性跳过的**逐张表名**此后只保留 `skipped_list` 的前 50 条。
> 我认为可以接受——良性子表名是可推导的（父表名 + 后缀），而且它们本来就读不到 DDL。
> 真正需要逐个留痕的是异常跳过，那个保留全量块。

**存活的每一条我都查到了确切原因**，不是"没写用例"这么笼统：

### 【R3-M-01｜MAJOR】P7：阈值锁第三次假绿，这回换了个机制

`test_adaptive_threshold_no_compact_at_64mb` 这轮确实改成真调 `publish()` 了，
R2-M-01 我提的那点已经照做。但载荷选错了：

```
载荷 = 单条 passed=True 记录（42,907,803 B）
变异后阈值 32MiB：触发压缩 = 是
   但压缩结果与原文完全相同 = True，omitted = 0
→ 单条通过记录落在"前 50 条通过样例"内，压缩退化成恒等变换
→ 用例的三个断言（条数=1、sql 相等、omitted=0）在变异下照样成立
```

**压缩触发了，但什么都没压掉，所以观测不到。** 要让这条锁真正生效，
载荷必须是**多条通过记录（>50 条）**，这样压缩才会真的丢东西、`omitted_results` 才会非 0。

### 【R3-M-02｜MAJOR】P9/P10：N4 用例的载荷压根没触发压缩

```
test_n4 的载荷 = 41,888,890 B = 39.9 MiB
当前自适应阈值 = 51.1 MiB  → 触发压缩 = 否
```

这个载荷是按**旧的 32MiB 阈值**设计的；阈值抬到 51.1MiB 后就压不着了。
于是 `compacted if i == 8 else v` 和 `+ (int(omitted_count),)` 在这条用例里都是**死代码**，
列索引锁（P9）和 omitted 锁（P10）都打不响。

这和我第二轮指出的 N4 问题是同一个——当时是"33MB 低于阈值"，这轮变成"39.9MiB 低于阈值"，
**载荷没跟着阈值走**。正确做法是从 `@@max_allowed_packet` 反算，取阈值的 1.2 倍以上。

### 【R3-M-03｜MAJOR】P12：sanitize 锁的检查粒度错了

```python
for ln in lines:                       # ← 检查的是 list 元素
    if "evil" in ln: assert ln.lstrip().startswith("--")
```

去掉 sanitize 后，`f"-- Object Name: {obj_name}"` 产出的是**一个**含内嵌 `\r\n` 的
list 元素，它**仍然以 `--` 开头**，断言照样通过。逃逸只在 `"\n".join(lines)` 落盘之后才显现。
实测确认：list 元素级命中 2 条、全部以 `--` 开头；正确口径应是
`"\n".join(lines).splitlines()` 逐行检查。

### 【R3-M-04｜MAJOR】P14/P15：L11/L12 两个呈现面没有锁

我在整改要求里明确列了 L11（历史报告 HTML 告警条）、L12（SQL 文件头节选说明），
两条都没补用例。**产品行为我实测是对的**（见 §4），但没有任何东西挡着它被删掉。

### 【R3-M-05｜MAJOR】P6/P17：缺省参数与 worker 接线没有锁

L6（缺参调用应抛 TypeError）没写；worker 那句 `instance_type or ""` 也没有锁——
分类函数本身有用例，但**函数和调用点之间的接线**没有。P17 把 `or "distributed"` 改回去，
16 个用例全绿，而这正是 R2-M-03 的缺陷本体。

### 【R3-N-01｜MINOR】P8：N2 锁只断言常量，没验证它被用上

```python
assert R._ESCAPE_FACTOR == 1.25
```

把预检里的 `* _ESCAPE_FACTOR` 删掉、常量原地留着，这条断言照样过。

### 【R3-N-02｜MINOR】P11：N9 锁是源码文本断言，不是行为断言

```python
src = inspect.getsource(R.MetadataJobRepository.publish)
assert "try:\n                conn.rollback()" in src
```

它匹配的是**带确切缩进的源码字符串**。我把 `except Exception: pass` 改成
`except Exception: raise`（行为完全破坏，2006 会重新裸穿），这条断言仍然成立。
而且换个缩进、改个格式，它会在没有任何缺陷时变红。这种锁两头都不对。

### 一句话

**三轮下来，同一个模式反复出现：断言写成了"不会失败"的样子。**
建议定一条纪律：**每写一条锁，先注入它要防的那个缺陷，确认用例变红，再提交。**
变红这一步不做，锁就不算写完。这条我也会在第四轮逐条复核。
