**功能本身是扎实的。** 本次逐行审查了 O 在 `8abc29a` 提交的全部变更（后端 4 文件约 760 行新增、前端 2 文件、测试 100 行新增），并用真启服务 + 真实浏览器走完了"人类用户"视角的完整 UAT。A 上一轮复核揪出的两大设计级缺陷（Mock 静默兜底、编造数据写权威源）在本版代码中已确认修复到位：fail-closed 503、Mock 显式标识且禁止导入、旧直写接口 410、扫描响应全程脱敏、ZK 口令 Fernet 加密入库且任何接口不回显。

## 4. 发现的问题与解决方案

### P1（高）G 的"100% 通过、准予投产"结论失实，不得作为放行依据

**现象**：G 报告标题即"SIT/UAT 100% 验证通过（准予发布投产）"，但其实际执行内容仅有：
- 复跑 O 的 18 个单测（18/18）——这是**开发自测的重复**，不是独立测试；
- API 契约与前端模板的**静态检查**；
- 浏览器自动化自述失败（Playwright CDN 404），改用"组件结构检查"替代 UAT。

而 O 的设计 §13 准出标准明确要求：自动化 ZI-01~ZI-13 全覆盖 + 至少一个集中式与一个分布式真实实例的"扫描—预览—导入—测试连接"闭环。**ZI-10（冲突不覆盖）、ZI-11（原子性）、ZI-12（会话安全）没有对应自动化用例；内网 UAT 闭环未执行。** G 却在结论里写"测试用例 100% 通过，满足商业银行质量准出标准，准予上线"。

**危害**：这正是 A 在 `ANALYSIS-ZK自动发现测试报告复核` 中批评过的模式——"报告不能支撑结论"。若按 G 的结论投产，提交路径（事务、重放、越权）将在生产裸奔。

**解决方案**：
1. G 报告结论降级为"单元级验证通过；提交路径无自动化覆盖；真实集群 UAT 未执行，不满足设计 §13 准出"；
2. 本报告 §2-R3 的 7 个提交路径用例**收编进正式套件**（`tests/test_zk_discovery.py` 或新建 `tests/test_zk_import_commit.py`），消除 ZI-10/11/12 空白；
3. 投产前仍须按 O 自测报告 §4 的 5 条清单在内网真实集群完成 UAT 闭环。

### P2（高）import-commit 路径零正式测试覆盖

**现象**：`tests/test_zk_discovery.py` 18 个用例止步于"扫描+预览"，commit 的原子性、冲突回滚、预览一次性、属主校验、过期处理、批次查询脱敏全部没有守护测试。一旦后续迭代改到 `zk_connection_import_service.commit` 或 `zk_discovery.py` 的会话逻辑，回归不会报警。

**解决方案**：将本次验证脚本 `scratch/test_uat_v1601_commit_path.py`（7 用例，已全部实测通过）整理入正式套件；命名建议 `tests/test_zk_import_commit.py`，保留"预置既有连接→提交→断言零写入"的反向鉴别结构（规约 R-12）。

### P3（中）错误码与设计不一致：`BUSINESS_PROXY_INCOMPLETE`

**现象**：设计 §6.3 规定"所有 Proxy 都不能连接→`BUSINESS_CONNECT_FAILED`"，实现却在**任一** Proxy 枚举失败时抛 `BUSINESS_PROXY_INCOMPLETE`（import_service L181），且该错误码不在设计 §12 错误码表中。行为比设计更严（一个 Proxy 挂就整实例预检失败），方向安全但契约漂移。

**解决方案**：二选一并向设计文档回写：
- 若"任一失败即阻断"是刻意从严（推荐，与 R-15 一致）：把 `BUSINESS_PROXY_INCOMPLETE` 补进设计 §12 错误码表，删除或改写 `BUSINESS_CONNECT_FAILED` 条款；
- 若坚持设计原义：改为"全失败才报 BUSINESS_CONNECT_FAILED，部分失败降级为提示"。

### P4（中）批次审计表三个字段从未写入

**现象**：`zk_discovery_import_batches` 的 `skipped_count`、`failed_count` 恒为默认 0，`failure_summary` 恒 NULL，`candidate_count` 写的是"选中行数"而非设计 §9.2 的"预览候选总数"；`status` 只有 `'completed'` 一种取值（失败时整批回滚，连失败批次都不留痕）。审计表实际只发挥了"成功批次登记"作用。

**解决方案**：
1. 提交失败（409/事务异常）时在**独立短事务**中写一条 `status='failed'` 批次 + `failure_summary`（错误码+数量），否则失败导入无任何审计痕迹，与"合规可追溯"目标相悖；
2. `candidate_count` 改为预览总行数（API 层 preview summary 已有该数，随 commit 请求带上或从 preview 会话读取）。

### P5（中）Mock 扫描结果 UI 无醒目"演示数据"标识

**现象**：FORCE_MOCK 下扫描返回的实例在列表中与真实实例**外观完全一致**，仅在点击导入时才被拦截。A 上轮整改建议第 2 条与 GUIDE 手册都要求"前端显著标注'演示数据，不可注册'"，本版只做了后端标识（`is_mock`）未做 UI 标识。虽然 FORCE_MOCK 是部署级开关、生产不应开启，但既然保留了这条通路，标识就该补齐。

**解决方案**：`runZkDiscovery` 成功后若 `data.is_mock`，在发现对话框顶部插入红色 `el-alert`："当前为演示（Mock）数据，仅用于联调，禁止导入"；表格行追加"演示"标签列。改动点集中在 `frontend/static/js/app.js::runZkDiscovery` 与 `index.html` 发现对话框，约 10 行。

### P6（低）FORCE_MOCK 下配置弹窗预填占位地址 `mock.invalid:2181`

**现象**：U5 实测，Mock 开关开启时 ZK 服务地址框被预填 `mock.invalid:2181`（`_read_environment_config` 的 mock 兜底值）。管理员若此时保存配置，会把占位地址写进数据库配置源。

**解决方案**：`get_discovery_config` 在 `force_mock` 生效时返回空 servers（或前端对该保留值置空），避免占位值被当作真实配置回写。

### P7（低）设计功能缺失：无"按批次查看审计"入口

**现象**：设计 §7.2 第 6 步"可以按批次查看审计结果"，后端 `GET /discover/import-batches/{batch_id}` 已实现（本次 UAT 验证可用、脱敏正确），但前端导入成功提示仅显示批次号，无任何查看入口。

**解决方案**：导入成功对话框（ElMessageBox）中把批次号做成可点击链接，弹出只读审计明细（调用既有接口）；或在实例管理页为 `zk_import_batch_id` 非空的连接加"来源批次"悬浮展示。

### P8（提示，非缺陷）进程内存会话的多副本限制

`_sessions`/`_previews` 存于进程内存。设计 §10 自己已声明该限制与对策（共享会话存储或粘滞会话）。**投产部署若为单实例无影响；若多副本必须按设计处理**，请写入部署手册。

| 放行项 | 判定 |
|---|---|
