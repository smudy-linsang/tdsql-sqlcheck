## 1. 拍板

**新增的「原始慢日志」模块做得不错，我上一轮设计评审提的 B1/B2/B3/C1/C4 都落地了。升级路径、全量回归、前端也都干净。**

**但这次的问题不在新模块，恰恰在项目负责人点名要查的地方——既有功能。** 为了让新旧模块共用一套 SQL 脱敏规则，O 把统一后的 `mask_sql_literals` 接进了**两条既有链路**，两处都改出了回归：

| 编号 | 级别 | 一句话 | 失效方式 |
|---|---|---|---|
| **P1-A** | 阻断 | 一条坏 SQL 会让**整次手动扫描中止**，其余有效记录全丢，扫描任务永久卡在 `running` | 响亮但破坏性大 |
| **P1-B** | 阻断 | 网关日志分析对长 SQL **静默丢弃**其 SQL 模式 | **完全不可见** |

两处**同一个根因**：`先截断、后脱敏`，以及脱敏异常的处置方向搞反了。

> **G 报告写「100% PASS，无任何遗留缺陷」并非测错**——全量套件确实 0 失败，我自己也复现了。问题是**没有任何用例把截断 SQL 喂进扫描链路、把长 SQL 喂进网关归一化**。这是覆盖盲区，不是用例失败。**100% 通过 ≠ 没有缺陷**，当新引入的失效路径根本没被覆盖时尤其如此。

## 2. 既有功能回归（本轮重点）

### 2.1 🔴 P1-A：一条坏 SQL 中止整次扫描，任务永久卡在 `running`

**改动**：`slow_query_service.add_slow_query` 把既有的 `FingerprintEngine.normalize_for_display` 换成了新的 `mask_sql_literals`，并新增：

```python
except SQLMaskingError as exc:
    raise ValueError("SQL 脱敏失败，拒绝保存可能含敏感字面量的文本") from exc
```

**问题**：`scan_service.py:219` 的入库主循环**没有任何逐条容错**：

```python
for raw in raw_queries:
    ...
    result = service.add_slow_query(record, ...)   # ← 裸调用，无 try
    results.append(result)

status_val = "failed" if errors else "completed"
service.complete_scan_task(task_id, ...)           # ← 异常时永远走不到
```

**实测（3 条慢SQL，中间一条截断在字符串字面量里）**：

```
★ 整个扫描抛异常中止: ValueError: SQL 脱敏失败，拒绝保存可能含敏感字面量的文本
最近扫描任务状态: [{'id': 1, 'status': 'running', 'total_fetched': 0}]
```

后果三条，一条比一条重：

1. **另外 2 条完全有效的慢SQL 一条都没入库**；
2. **扫描任务永久停在 `running`**——`complete_scan_task` 在异常路径之后，永远执行不到，这条脏记录不会自愈；
3. API 向前端返 500。

**对比：定时扫描路径是有保护的。** `scheduler.py:175` 的同一个调用包在 `try/except` 里，逐条降级。**手动扫描没有——这个不对称本身就是缺陷**，v1.6 只是往这个没设防的循环里又加了一个新的异常源。

**触发条件的诚实评估**：能让 `mask_sql_literals` 抛错的是「未闭合字符串 / 未闭合块注释 / 空文本」。实测三种截断形态全部抛错：

| 输入 | 结果 |
|---|---|
| `SELECT * FROM t_user WHERE name = 'zhang` | ★ unterminated SQL string literal |
| `SELECT * FROM t WHERE a=1 /* batch_id=` | ★ unterminated SQL comment |
| `INSERT INTO t VALUES ('a','b` | ★ unterminated SQL string literal |

来源可能是 processlist 的 `info`、monitordb 的 fingerprint、原始慢日志、或使用者从 `POST /api/v1/slow-queries` 手工贴入的 SQL 片段。**我本容器连不上真实 TDSQL，无法断言"上线第一天必现"**；但**结构性缺陷与后果严重度是确定的**：任何一条坏记录都能打掉整次扫描并留下永久卡住的任务。

**修复方向**（两处都要改，缺一不可）：

1. **主循环加逐条容错**，与 `scheduler.py` 拉齐——单条失败计入 `errors` 并继续，不得中止整批：

```python
for raw in raw_queries:
    ...
    try:
        results.append(service.add_slow_query(record, scan_task_id=task_id,
                                              connection_id=connection_id))
    except Exception as e:
        # 单条入库失败不得中止整批：其余有效记录必须照常入库，
        # 且必须让扫描任务走到 complete_scan_task，不能留下永久 running。
        errors.append({"source": "persist", "error": str(e)})
```

2. **`complete_scan_task` 必须放进 `finally`**，保证任何异常路径下扫描任务都能收尾，不再出现永久 `running`。

**验收**：批次内混入截断 SQL 时——其余记录全部入库、任务状态为 `completed`/`failed` 而非 `running`、`errors` 里能看到被跳过的条数。

### 2.2 🔴 P1-B：网关日志分析对长 SQL 静默丢弃（**不可见**，比 P1-A 更该早修）

**改动**：`analyze_gateway_log.normalize_sql` 委托给统一脱敏，但**保留了先截断的老写法**：

```python
s = sql_text[:200].replace("%3D", "=")...    # ← 先截断到 200 字符
try:
    return mask_sql_literals(s)[:120]
except SQLMaskingError:
    return ""                                 # ← 截断造成的未闭合 → 返回空串
```

**先截断到 200 字符，必然经常正好切在字符串字面量中间**，于是脱敏抛错，被吞成空串。而调用点：

```python
pattern = normalize_sql(fields["sql"])
if pattern:          # ← 空串直接跳过，这条日志从模式聚合里消失
```

**实测**：一条 265 字符的普通业务 SQL（`WHERE ... AND a.memo='<长文本>'`）：

| 实现 | 结果 |
|---|---|
| `analyze_gateway_log.normalize_sql` | `''` → ★ **该条日志的 SQL 模式被静默丢弃** |
| `interf_deep_analysis.normalize_sql` | 正常（它截断阈值是 800，本例侥幸没切中） |

**不需要任何异常输入**——普通长 SQL 就能触发。而网关日志分析的价值恰恰在于找出那些又长又复杂的问题 SQL，**丢的正是最该看的那批**。报告会少统计而使用者毫无察觉，属于 R-15 明令禁止的失效方向。

`interf_deep_analysis` 是同样的写法（800 字符），只是阈值高一些，**同类问题、同样要改**。

**修复方向**：**先脱敏、后截断**，顺序反过来即可：

```python
# 必须先脱敏再截断：反过来会把字符串字面量拦腰切断，
# 触发 unterminated 异常并被吞成空串，该条日志的 SQL 模式被静默丢弃。
try:
    masked = mask_sql_literals(sql_text.replace("%3D", "=").replace("%0A", " ").replace("%20", " "))
except SQLMaskingError:
    return ""          # 真正无法脱敏才返回空
return masked[:120]
```

**验收**：上面那条 265 字符 SQL 必须返回非空模式；补一条 >200 字符、字面量跨越 200 边界的回归用例。

### 2.3 🟡 脱敏口径变更导致指纹漂移（需在升级手册披露，非阻断）

新脱敏**确实比旧的更正确**——旧实现有两个真 bug：

| SQL 片段 | 旧 `normalize_for_display` | 新 `mask_sql_literals` |
|---|---|---|
| `VALUES (1, 99.5)` | `VALUES (?, ?.?)` ← 小数被切坏 | `VALUES (?, ?)` ✅ |
| `WHERE b = 0x4142` | `0x4142` ← **十六进制字面量原样泄漏** | `?` ✅ |
| `/*hint*/ ... -- comment` | 原样保留 | 已剥离 ✅ |

**但后果是：同一条 SQL 在升级前后可能得到不同的脱敏文本与指纹。** 内网从 1.2.0.9 升上来会带着多年历史数据，含十六进制/小数/注释的 SQL 其历史指纹与新指纹将不一致，**在指纹维度上历史与新数据不连续**（趋势、聚合会从升级点断开）。

七个样例里 4 个输出一致、3 个不同，影响面是**部分**而非全部。

**建议**：不必回填（符合 R-06），但**必须在升级手册里写明**："v1.6 起 SQL 脱敏规则统一，含十六进制字面量/小数/注释的 SQL，其指纹与升级前不同，历史趋势在升级点存在一次不连续。"

## 5. 准出条件

**必须修复后复测**：

1. **P1-A** —— 扫描主循环加逐条容错 + `complete_scan_task` 移入 `finally`
2. **P1-B** —— 两个 `normalize_sql` 改为**先脱敏后截断**

**必须补的回归用例**（否则修完也挡不住回潮，R-12）：

- 扫描批次内混入截断 SQL → 其余记录照常入库、任务不停在 `running`
- 265 字符、字面量跨越 200 边界的 SQL → 网关归一化返回非空模式
- 同样的用例对 `interf_deep_analysis`（800 边界）各来一条

**必须在升级手册补写**：§2.3 的指纹漂移说明。

**可以下版本**：C3 跨节点互斥、保留清理上限告警。
