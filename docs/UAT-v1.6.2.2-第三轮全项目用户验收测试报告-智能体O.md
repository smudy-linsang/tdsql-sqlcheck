## 5. 需要处理的问题：原因、机制、改法及验收标准

### O-09 / BLOCK / 本轮新增回归：R042被注释中的引号绕过

最小复现（只审核，不执行）：

```sql
# operator's note
LOAD XML INFILE '/tmp/synthetic.xml' INTO TABLE t;
```

即时审核选择分布式规则，粘贴后点击“开始审核”：绿色“审核通过”，无R042。相同SQL去掉第一行，立即触发R042；实际选择并上传 `uat_r3_load_xml_guard.sql` 也显示1条、100%通过。[页面反例](evidence/v1.6.2.2-uat-o-r3/17-load-xml-false-pass.jpg)、[对照](evidence/v1.6.2.2-uat-o-r3/18-load-xml-control.jpg)、[文件路径](evidence/v1.6.2.2-uat-o-r3/24-load-file-false-pass.jpg)

判据不是将LOAD当成合规TDSQL语句。腾讯云TDSQL MySQL版《使用限制》明确写明 **“不支持 LOAD DATA/XML”**，恰恰应保持项目R042的拒绝能力。[腾讯云官方依据](https://cloud.tencent.com/document/product/557/47511)

发生机制：

1. `backend/engine/parser/parser_legacy.py:43` 新 `_strip_comments_and_literals()` 的状态机只有引号、反引号、`--`、`/* */`，没有 `#` 行注释状态。
2. `# operator's note` 中的单引号被误当成SQL字符串起点，后面的真实LOAD关键字被替为空格。
3. 同文件 `:2361` 用该结果决定 `has_load_data`，得到false；`backend/engine/rules/dml.py:250` 仅依赖该标志，R042不触发。
4. LOAD XML在所测三版本落入Command且 `parse_error=None`，E999也不触发，于是真正绿色通过。LOAD DATA部分样例仍被E999挡住，但R042本身也已漏报。

这不是Q的KFN修复无效，而是为去除假LOAD匹配引入新的不完整词法扫描器，损伤真实LOAD识别。27条矩阵包括单引号、双引号、反引号、成对引号、普通注释、LF/CRLF、DATA/LOCAL/XML，三个版本结果一致。

可实施处理：复用项目已经选择的MySQL方言sqlglot词法器/经过同一词法边界处理的真实token，统一得到“首个有效语句的真实头部”；不要再独立维护一套不完整字符串状态机。token失败必须走明确的失败关闭路径，不能将清洗后的空白/Command直接视为通过。保留结构化KFN独立强制门禁；禁止退回全文裸正则，避免重新把COMMENT文字误判为LOAD。若采取局部补丁，也必须覆盖完整注释、引号、换行与多语句入口合同，不仅补一个 `if ch == '#'` 就宣称证明完成。

验收：27条矩阵三版本全部正确命中R042；即时/文件/上传均拒绝，UI不绿；注释、字符串、反引号中的假LOAD不触发R042；原252条KFN、全部禁用规则反例、原业务语料和1417测试重跑。语句头语义按TDSQL约束确认，不借修复扩大特殊语句豁免。

### O-08 / MAJOR / 原问题部分修复后新增跨库异常

复现：独立EXPLAIN页面选 `uat_o_local`，SQL为 `SELECT id FROM tdsql_uat_o_target_1622.t_uat_order WHERE customer_id=1`。库名留空/等于默认库成功；填 `information_schema`（确实存在）或不存在的 `uat_o_r3_workflow` 均500：`name 'TDSQLConnectionPool' is not defined`。

根因：`backend/services/slow_query_service.py:304` 新分支使用未导入的类。不能只修import：`:313`、`:480` 写成 `_ephemeral_pool.pool.close_all()`，实际类在 `tdsql_connector.py:329` 提供的是池对象自身的 `close_all()`，没有 `.pool`。异常被吞掉，无法实现“用完即关”。

白盒诊断仅在隔离进程补入缺失符号、保留真实池对象检查：成功EXPLAIN和SQL错误两路径显式close次数均0、返回后连接仍开；随后测试脚本自行关闭。**这是被NameError遮住的潜在缺陷，不冒充当前HTTP已越过NameError。** [诊断](evidence/v1.6.2.2-uat-o-r3/ephemeral_cleanup.json)

处理：正确导入池类；使用其公开清理接口；把连接预检、SQL预处理、执行/分析都包在临时池生命周期的外层try/finally，避免创建池后早退漏清理。非默认库请求不得改写共享registry/已保存默认库；不存在库映射可读4xx，不返回内部NameError。

验收：默认、显式默认、存在的其他库、不存在库、SQL错误、预处理失败、并发不同库全覆盖；每个临时池明确清理，共享默认配置不变；先看详情再打开独立EXPLAIN不串库。

另两种状态也有问题：完全未采集的离线样本大屏已正确“未评估”，但PDF仍使用“多维度深度扫描后”“健康度极佳”；已完成且零问题的索引运行被误标no_data。本轮后者用明确标注的合成父记录2表4索引0finding作合同诊断，未伪称真实扫描。[零问题合同](evidence/v1.6.2.2-uat-o-r3/report_zero_contract.json)

机制：

- `index_audit_service.py:113/117` 生产中文finding_type（重复索引、前缀冗余索引）；`ppt_report_service.py:645—653` 比较 `duplicate/prefix_redundant/unused/fragmentation`，实际问题全部漏计。该字段错位是既有实现问题，本次删除mock未解决。

- PDF `:313` 等结论以空数组作健康依据，不以采集完成、范围完整、指标可用为前提。部分模块有数据就给总健康100也会误导为整体验收完成。
