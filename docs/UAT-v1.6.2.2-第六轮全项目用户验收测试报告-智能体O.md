## 一、验收结论

Q 对第五轮三项问题的主路径整改已取得明显效果：O-22 的报告票据改为共享数据库存储后，双 worker 下 100 次签发、首次消费全部成功，100 次重放全部被拒绝；O-23 的缺列、ALTER 失败和部分迁移自愈路径已失败关闭；O-24 的普通未知 `RuntimeError` 已恢复为 500。全量自动化为 `1521 passed, 28 skipped`，正式三版本门禁 `RESULT PASS`，119 条规则主语料及解析边界与第五轮基线逐项一致，10 个真实浏览器步骤全部通过。

但本轮进一步做语义伪装和结构漂移故障注入后，发现 **2 个 MAJOR、1 个 MINOR**：

1. O-24 仍未真正收口。`RuntimeError` 或 `AttributeError` 只要消息中含 `can't connect`、`connection refused` 等短语，就会被转换为 422 连接失败，程序缺陷仍可被掩盖。
2. O-23 的“已登记迁移结构验收”只检查列是否存在，不检查列类型、可空性和默认值。版本键与校验和均正确时，错误结构会被静默视为已完成，应用继续启动。
3. 全量测试中的 8 个 HTTP 集成用例依赖外部 `127.0.0.1:8000` 服务，而正式门禁自身不负责启动和清理该服务。干净环境直接执行会得到 8 个连接拒绝；本轮只能通过外层测试驱动补齐 fixture 后得到全绿。

前两项直接影响异常可观测性和生产升级可靠性，当前提交不能放行。修复后应开展第七轮 UAT。

## 五、缺陷明细与可实施整改

### O-25（MAJOR）：程序异常只要消息含连接短语仍会被伪装成 422

**独立复现：**

| 注入异常 | 当前转换结果 | API 结果 | 应有结果 |
|---|---|---:|---|
| `RuntimeError("synthetic programming defect")` | `None` | 500 | 500，正确 |
| `RuntimeError("can't connect to internal cache")` | `ConnectionRefusedError_` | 422 | 500 |
| `AttributeError("connection refused while reading object")` | `ConnectionRefusedError_` | 未进入真实 API；直接转换已误映射 | 500 |

**发生原因：** `translate_db_error()` 虽然文档声明“任何 RuntimeError/AttributeError/TypeError 一律返回 None”，实现却在 errno 判断之后对所有异常执行消息子串匹配。异常类型没有参与兜底分支的白名单约束，因此业务程序、缓存层或对象访问缺陷只要文本碰巧含连接短语，就会被伪装成数据库连接问题。

**处理机制：**

1. errno 映射仅接受可信数据库驱动异常链，例如 PyMySQL `OperationalError`、`InterfaceError`，并从 `__cause__` / `__context__` 中受控提取；不能对任意 `BaseException.args` 中的整数或文本直接认定为 MySQL errno。
2. 文本兜底必须同时满足“异常类型属于允许的连接异常族”，例如驱动连接异常、`OSError`、`TimeoutError`、socket 超时；`RuntimeError`、`AttributeError`、`TypeError` 以及未知业务异常直接返回 `None`。
3. 调用端维持现有机制：仅映射成功时抛出领域 422；映射为 `None` 时重新抛原异常，由统一 500 处理器生成通用信息和 `X-Request-ID`，服务端保留完整堆栈。
4. 新增表驱动回归矩阵：程序异常分别携带 `can't connect`、`connection refused`、`timed out`、`access denied`、`unknown database` 文本，均必须为 500；真实 2003/1045/1049 和真实连接拒绝/超时继续为友好 422。
5. 测试不能只直接调用转换函数，还要经过日常巡检 API，断言状态码、响应脱敏、`X-Request-ID` 和服务端日志分类。

**验收标准：** 所有程序异常不受消息措辞影响，稳定返回 500；所有受支持的真实数据库连接异常仍准确返回 422。

### O-26（MAJOR）：已登记迁移只验“列存在”，错误列结构可静默通过启动

**独立复现：** 在隔离数据库中预建 `related_index_name INT`，写入与迁移文件匹配的版本键及正确 checksum，再执行 `run_migrations()`。结果无异常，列类型仍为 `int`，`strict_validation_happened=false`。

**发生原因：** `_needs_reapply()` 对每个 `ADD COLUMN` 只调用 `_column_info()` 判断是否为 `None`。只要同名列存在，就返回“不需要重放”；`run_migrations()` 随即跳过该文件。已有 `_verify_column()` 的类型、长度、可空性、默认值校验只在本次实际执行迁移后发生，未覆盖“版本已登记且校验和一致”的启动路径。因此实现只能修复历史缺列，无法兑现修复说明中的“已登记文件每次启动做结构验收”。

**处理机制：**

1. 将“是否需要补迁移”和“结构是否合规”拆为两个清晰结果：`missing` 可进入幂等补齐；`mismatch` 必须抛 `MigrationError` 失败关闭；`valid` 才允许跳过。
2. 对已登记且 checksum 一致的迁移，也逐条解析声明的列并调用 `_verify_column()`，严格核对数据类型、长度、NULL、DEFAULT；不得仅检查列名存在。
3. 错误结构不得自动 ALTER 覆盖。生产数据列的类型修复可能发生截断或锁表，必须输出表名、列名、期望与实际结构，要求专门修复迁移或人工审批后处理。
4. checksum 不一致也应纳入失败关闭，而不是只记录 warning 后继续。文件内容和数据库版本记录发生漂移时，应用不能宣称 schema ready。
5. 增加矩阵测试：正确列、缺列、错误类型、错误长度、错误 NULL、错误 DEFAULT、checksum 漂移；双 worker 同时启动也必须得到唯一一致的结构和版本状态。

**验收标准：** 已登记迁移中的任一声明列不符合预期时，应用启动失败且错误可定位；缺列可幂等补齐；完全正确时正常跳过。

### O-27（MINOR，测试工程）：正式门禁依赖外部 8000 服务，干净环境不可自洽复现

**独立复现：** 在 `127.0.0.1:8000` 无服务时直接运行全量 pytest，8 个集成用例均因 `ConnectionRefused` 失败，其余结果为 `1513 passed, 28 skipped`。本轮由 `run_round6.py` / `run_gate.py` 在外层准备隔离数据库、启动服务并等待健康后，才得到 `1521 passed, 28 skipped` 和正式门禁 PASS。

**发生原因：** 部分集成测试写死 `http://127.0.0.1:8000`，测试夹具和正式 `run_all.py` 没有负责服务的启动、健康等待、端口占用检查和清理。门禁结果会受执行者机器上的偶然进程影响，既可能误红，也可能误用非本次提交的旧服务而误绿。

**处理机制：**

1. 优先把可进程内执行的 API 用例迁移为 FastAPI `TestClient`/ASGI transport，消除固定端口依赖。
2. 必须走真实网络的用例由 session fixture 或门禁脚本统一申请可用端口、启动当前工作树服务、健康检查、执行测试并在 finally 中终止精确进程树。
3. 服务启动前校验端口所有者；不得复用未知既有服务。测试报告记录实际 commit、PID/端口、AUTH 配置和健康响应。
4. 正式 `run_all.py --mode implementation --matrix` 应在干净环境单命令可复现，无需人工预启动服务。

**验收标准：** 端口 8000 空闲和已占用两种场景均有确定行为；干净环境单命令稳定得到相同结果，且执行结束无残留服务。

- 注册规则仍为 119 条；1000 条主语料结果与第五轮签字基线逐项完全相同，未发现本次整改引入大范围规则漂移。
- 主语料观察到 114 条规则；补充上下文命中 R035、R059，共证明 116 条可观测命中。R025、R038、R049 的现有合成样例仍未命中目标规则，不能把“注册存在”写成“有效性已证明”。
- 1000 条语料仍有 3 个已知精确期望差异，均为 R036/R037 缺失，和第五轮完全一致，不是 Q 本轮新增回归。
- 324 条解析边界、27 条 LOAD、77 条语句头与第五轮逐项一致；三套 sqlglot 版本的独立执行均成功。
- TDSQL HASH 分片表未触发 R077；`shardkey=noshardkey_allset` 广播表未触发 R054/R077；CR 残缺 VIEW 命中 R030；R042 浏览器真实点击命中 ERROR。
