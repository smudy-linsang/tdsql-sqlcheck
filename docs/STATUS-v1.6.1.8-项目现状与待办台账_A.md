## 3. v1.6.1.8 RBAC 改造：已验证落地

设计文档经 **A（V2.0）→ Codex（V3.0）→ Codex 二轮（V3.1）** 三轮评审后实施。我提的 7 条修订全部被采纳。

### 3.1 最终分层权限模型

| 层级 | 范围 | 授权 |
|---|---|---|
| **L1 精简只读** | `GET /api/v1/tdsql/connections/options`（8 字段白名单） | **已登录全角色**，与菜单解耦 |
| **L2 全字段读** | `GET /api/v1/tdsql/connections` | 拥有 `instances` 菜单的角色 |
| **L3 常规管理** | 增删改 / 连接 / 探测 / ZK 发现与导入（约 20 个端点） | **仅 admin / dba**，端点级 `_require_instance_manager` 双保险 |
| **L4 高危治理** | ZK 发现配置、实例类型锁定 | **仅 admin**，端点级 `_require_admin` |

关键机制：`_MENU_INDEPENDENT_READ_ENDPOINTS` 用 **精确 `(method, path)` 元组**绕过菜单校验，而非前缀——避开了我提的"前缀放开会连带带出 `GET /connections/{id}/probe`"。

### 3.2 我抽验的 11 项（全部通过）

```
① P0 密文泄露：全字段读已剔除 monitor_password_encrypted，响应无任何 Fernet 密文  ✅✅
② /options：未分配 instances 的角色可读；字段严格 8 个，无口令/monitor_*/username  ✅✅
③ 反向鉴别：全字段读仍 403、有副作用的 /probe 仍被挡、未登录 /options 仍 401      ✅✅✅
④ 20 个实例写端点对自定义角色逐个被拒，放行 0 个                                  ✅
⑤ 反向鉴别：dba 新建连接仍放行、读全字段仍放行、L4 对 dba 收紧为仅 admin           ✅✅✅
```

## 4. 需要留意的三处变化（后续升级的关注点）

### 4.1 【重要】`02f1bd3` 大幅放宽了业务写权限，且未经独立复测

为修复"RBAC 收敛后 developer 无法导出慢 SQL PDF、大表采集按钮失效"，该提交把 `_DEVELOPER_WRITE_PREFIXES` 从 9 条扩到约 19 条，并更名为 `_OPERATIONAL_WRITE_PREFIXES`，新纳入：

```
/api/v1/scan-compare/  /api/v1/tdsql/slow-queries  /api/v1/bigtable/
/api/v1/cluster-inspect/  /api/v1/daily-inspect/  /api/v1/index-audit/
/api/v1/schema-diff/  /api/v1/emergency/  /api/v1/sql-stats/  /api/v1/toolkit/
```

同时**自定义角色从"一律不可写"改为"与 developer 同权"**（`check_permission` 的 `else` 分支新增了操作性写端点放行）。

- 方向可以理解（这些确属业务自助操作，且仍有二级菜单校验兜底）；
- 但这是**与收敛相反方向的放宽**，且发生在最后一轮独立测试之后；
- `auditor` 仍严格只读（一级 `method in _READ_METHODS`），未被波及——我已核对。
- 另注意这批前缀用的是**朴素 `startswith`**（无边界匹配），与 `_PATH_TO_MENU` 的"精确或以 `/` 开头"语义不一致。当前无路由踩坑，但属潜在风险模式，新增路由时需留意。

**建议**：发布前对这 10 个新增前缀做一轮"角色 × 端点"矩阵抽验，重点确认 `auditor` 不因此获得任何写能力、自定义角色的写范围符合预期。

### 4.2 `check_permission` 末尾仍是 fail-open

未登记 `_PATH_TO_MENU` 的路径默认放行（写端点会打 WARNING）。现有 `tests/test_rbac_path_coverage.py::test_all_write_endpoints_are_mapped` 把这道"闭"提前到了开发期，**新增写端点务必同步登记**，否则该用例会失败——这是好机制，别绕过它。

### 4.3 前端权限判断仍是硬编码角色名

`app.js` 的 `canManageInstances` 等计算属性按 `['admin','dba'].includes(role)` 判定。当前与后端一致。若将来要支持"某个自定义角色也能管实例"，前后端两处都要改，且**前端隐藏永远只是体验层，鉴权以后端为准**。

## 6. 团队规约要点（沿用）

`docs/GUIDE-团队施工规约.md` 中与后续升级最相关的几条：

- **R-11**：没量过的效果不能写成已实现；
- **R-12**：每项修复必须配反向鉴别用例（"不该能"的那一半）；
- **R-15**：失败非对称——宁可给可见的错误，不可给不可见的遗漏；
- **R-17**：提交前做 import 检查；
- **R-18**：全量回归零跳过。

本轮 RBAC 改造中"L4 对 dba 收紧""dba 仍可写""未登录仍 401""20 个端点逐个 403"这几组，正是 R-12 的典型形态，后续同类改动建议照此设计验收。
