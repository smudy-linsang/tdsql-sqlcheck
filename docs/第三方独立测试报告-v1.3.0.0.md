## 三、高危缺陷详述与修复方案（照图施工）

### D02 【高】治理概览统计口径自相矛盾 —— 治理汇报数字不可信

**现象**：`GET /api/v1/dashboard/summary` 返回 `today_passed(1) + today_failed(44) ≠ today_count(22)`，failed 是 count 的两倍。DBA 向管理层汇报时三个数字对不上，直接损害平台公信力。

**根因**：[dashboard.py](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/backend/api/dashboard.py) 第 83-95 行：

```python
audit_today = conn.execute("""
    SELECT COUNT(*) as cnt,
           SUM(CASE WHEN failed = 0 THEN 1 ELSE 0 END) as passed,
           SUM(failed) as failed_count,          # ← 量纲错误
           ...
""", (today,)).fetchone()
```

`audit_history.failed` 列存的是**该条审核记录的违规条数**（可 >1），而 `passed` 按**记录数**统计。`SUM(failed)` 求和的是"违规条数"，`COUNT(*)` 数的是"审核记录数"，两者量纲不同，必然矛盾。

**修复方案**（dashboard.py，2 处改动）：

```python
# 改动1：第 86 行，failed_count 改为按记录数统计（与 passed 同量纲）
#   原：SUM(failed) as failed_count,
#   改：
           SUM(CASE WHEN failed > 0 THEN 1 ELSE 0 END) as failed_count,
           SUM(failed) as violated_count,        # 新增：违规条数单列

# 改动2：返回体中补充新字段（第 152-159 行 return 的 audit 段）
            "today_count": today_count,
            "today_passed": today_passed,
            "today_failed": today_failed,
            "today_violated_count": audit_today["violated_count"] or 0,  # 新增
```

**验证**：修复后执行 `pytest tests_3p/test_3_uat.py::TestC2DbaJourney::test_uat05_dba_dashboard_numbers_consistent`，移除 xfail 标记后应通过；前端概览页"今日拦截"改绑 `today_violated_count`。

### S01+S02 【高】会话无吊销机制 —— 改密/登出后旧 token 继续有效

**现象**：admin 重置某用户密码后，该用户旧 token 调 `/api/v1/auth/me` 仍返回 200；调用 `/api/v1/auth/logout` 后旧 token 同样有效。员工离岗、token 泄密场景下无法紧急终止会话，违反等保 2.0 三级 8.1.4.1"应能及时终止会话"要求。

**根因**：
- [auth.py](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/backend/api/auth.py) 第 99 行 logout 注释自述："令牌为自包含短时效设计，登出由客户端丢弃令牌"——仅写审计日志，无服务端吊销；
- `auth_service.verify_token` 只校验 HMAC 签名与 exp，无用户态版本号。

**修复方案（token 版本号方案，改动 4 个文件）**：

**第 1 步**：users 表加版本列（[database.py](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/backend/services/database.py) 建表/迁移段）：

```sql
ALTER TABLE users ADD COLUMN token_version INT NOT NULL DEFAULT 0;
```

**第 2 步**：[auth_service.py](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/backend/services/auth_service.py) `issue_token` 把版本号写入载荷：

```python
def issue_token(username: str, role: str) -> str:
    user = get_user(username)
    payload = {
        "username": username,
        "role": role,
        "tv": user.get("token_version", 0),      # 新增
        "iat": int(time.time()),
        "exp": int(time.time()) + TOKEN_TTL,
    }
    ...  # 后续 HMAC 签名逻辑不变
```

**第 3 步**：`verify_token` 增加版本比对：

```python
def verify_token(token: str) -> dict | None:
    payload = _decode_and_verify_signature(token)   # 原有逻辑
    if not payload:
        return None
    user = get_user(payload.get("username", ""))
    if not user:
        return None
    if payload.get("tv", -1) != user.get("token_version", 0):   # 新增
        return None                                             # 版本不符=已吊销
    return payload
```

**第 4 步**：三处触发版本递增（auth_service.py 内）：

```python
def _bump_token_version(username: str):
    conn.execute("UPDATE users SET token_version = token_version + 1 WHERE username = ?",
                 (username,))

# 在 change_password()、reset_password() 成功后各调用一次 _bump_token_version
```

**第 5 步**：[auth.py](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/backend/api/auth.py) logout 改为真吊销：

```python
@router.post("/logout", summary="登出")
def logout(request: Request):
    from backend.services.database import log_operation
    op = _operator(request)
    auth_service.bump_token_version(op)          # 新增：立即吊销当前及历史全部会话
    log_operation(op, "logout", "user", op)
    return {"message": "已登出"}
```

**验证**：`pytest tests_3p/test_4_security.py -k "sec01 or sec02"` 移除 xfail 后应通过。

### S09 【中】登录无 IP 级限流，可密码喷洒

**现象**：对不存在账号连续 20 次登录尝试，全部返回 401，无 429 限流。现有账号锁定只保护已存在用户，攻击者可对大量账号各试 4 次（锁定阈值之下）进行喷洒。

**修复**（auth.py login 端点前增加 IP 滑动窗口，auth_service.py 新增）：

```python
# auth_service.py 新增
import time, threading
_ip_fail: dict[str, list[float]] = {}
_ip_lock = threading.Lock()

def ip_rate_limited(ip: str, limit: int = 10, window: int = 60) -> bool:
    """同一 IP 在 window 秒内失败 limit 次即限流"""
    now = time.time()
    with _ip_lock:
        hits = [t for t in _ip_fail.get(ip, []) if now - t < window]
        _ip_fail[ip] = hits
        return len(hits) >= limit

def record_ip_failure(ip: str):
    with _ip_lock:
        _ip_fail.setdefault(ip, []).append(time.time())
```

```python
# auth.py login() 第 77 行后插入
    if auth_service.ip_rate_limited(client_ip):
        raise HTTPException(status_code=429, detail="尝试过于频繁，请稍后再试")
    user, err = auth_service.authenticate(body.username, body.password, client_ip)
    if err:
        auth_service.record_ip_failure(client_ip)   # 新增
        ...
```

同时统一登录报错文案为"用户名或密码错误"（消除 SEC-05 用户枚举）。

**验证**：`pytest tests_3p/test_4_security.py -k "sec22 or sec05"`。

### P01 【中】分页参数无上限校验

**现象**：`/api/v1/audit/extracted-reports?limit=100000`、`/api/v1/slow-queries?limit=100000` 均被接受。数据量增长后单次请求即可拉全表，内存与带宽失控。

**根因**：FastAPI 函数签名中 `limit: int = 20` 未加 `Query(le=...)` 约束。涉及文件与行：

| 文件 | 端点 | 现状 |
|---|---|---|
| slow_query.py:99 | GET /slow-queries | `limit: int = 20` 无上限 |
| slow_query.py:128 | GET /slow-queries/scan-tasks | 同上 |
| sql_audit.py:328 | GET /audit/extracted-reports | 同上 |
| sql_audit.py:635 | GET /audit/file-reports | `limit: int = 50` 无上限 |
| scan_compare.py:108,241 | GET /snapshots、/reports | 同上 |
| admin.py:175 | GET /admin/operation-logs | 已有 `min(max(limit,1),500)` ✔ |

**修复**：统一改为 FastAPI 校验（各文件逐处替换）：

```python
from fastapi import Query
# 原：limit: int = 20, offset: int = 0,
# 改：
limit: int = Query(20, ge=1, le=200), offset: int = Query(0, ge=0),
```

超限自动返回 422，与 admin.py 既有保护对齐（建议全系统统一上限 200，导出场景走异步任务）。

**验证**：`pytest tests_3p/test_5_performance.py -k perf01`。

               keyword: str = ""):

# auth_service.py list_users 改造
def list_users(limit: int = 50, offset: int = 0, keyword: str = "") -> dict:
    where = "WHERE username LIKE ?" if keyword else ""
    args = ([f"%{keyword}%"] if keyword else [])
    total = conn.execute(f"SELECT COUNT(*) c FROM users {where}", args).fetchone()["c"]
    rows = conn.execute(
        f"SELECT username, display_name, role, status, must_change_password, "
        f"failed_attempts, locked_until, created_at, updated_at FROM users {where} "
        f"ORDER BY username LIMIT ? OFFSET ?", (*args, limit, offset)).fetchall()

## 五、低危与设计风险

### S08 【低】缺少安全响应头基线
**修复**：middleware.py 的 RequestContextMiddleware 响应阶段统一注入：

```python
response.headers["X-Content-Type-Options"] = "nosniff"
response.headers["X-Frame-Options"] = "DENY"
response.headers["Content-Security-Policy"] = \
    "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:"
response.headers["Referrer-Policy"] = "no-referrer"
```

### R01 【低】RBAC 未映射路径默认放行（fail-open）
**根因**：auth_service.py 注释明示"无映射的路径默认放行"。新端点若忘登记 `_PATH_TO_MENU`，即对所有登录角色敞开（sql_audit.py:43 的注释证明已踩过一次坑）。
**修复**：中间件 RBAC 段改为 fail-closed——未映射的写路径（非 GET/HEAD）默认仅 admin，GET 路径默认放行但打 warn 日志；提供装饰器 `@require_role("admin")` 供端点显式声明。
