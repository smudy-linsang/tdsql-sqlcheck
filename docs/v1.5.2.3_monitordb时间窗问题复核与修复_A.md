## 2. 复核结论

### 2.1 Q 的归因不成立

**"时间戳单位/类型差异"经验证不是原因。**

我搭了 SQL 生成探针（不连真库），对四种可能的列类型各跑一遍，检查最终下发的 WHERE 条件与参数类型：

| `timestramp` 列类型 | 下发条件 | 参数 | 参数类型 | 判定 |
|---|---|---|---|---|
| `timestamp`（**仓库文档记录的真实类型**） | `>= %s` / `< %s` | `'2026-07-29 10:00:00'` | `str` | ✅ 正确 |
| `datetime` | 同上 | 同上 | `str` | ✅ 正确 |
| `bigint`（秒） | 同上 | `1785319200` | `int` | ✅ 正确 |
| `bigint`（毫秒） | 同上 | `1785319200000` | `int` | ✅ 正确（已 ×1000） |

**四种类型的单位换算与参数类型全部正确。**

> `timestramp` 的真实类型有仓库内两处独立记录佐证：
> - `docs/TDSQL性能诊断平台升级_详细设计说明书.md:31`：「时间窗过滤走 `timestramp`（采集时刻，**timestamp 类型**）」
> - `docs/monitordb接入设计说明书评审与可行性分析报告.md:46`：「`timestramp` 列在 DDL 中为 **`timestamp` 类型**」
>
> 对 `timestamp` 类型，代码走的是**字符串直传**分支，数值单位换算逻辑根本不执行——所以"单位差异"在真实环境里连触发条件都不具备。

### 2.2 "DIST 实例特有"也不成立

用户转述为"在 DIST 实例上会清空结果"。核查后确认**该查询对 DIST / CENT 无任何结构性差异**：

- `set_ports`（唯一可能因 `set_list` 而区分两类实例的参数）**根本没有被传入**——`scan_service.py:114` 明确注释「一次取全集群、免 set_list」；
- 两类实例的查询仅 `database` 过滤值不同（`tdsql_check` vs `tdsql_check2`）。

**所以这不是 DIST 特有的代码路径问题。** Q 原文写的是"部分实例"，转述中被收窄成了"DIST 实例"。

### 2.3 但确实存在会清空结果的缺陷

复核过程中定位到 **3 处真实缺陷**，其中 **P2-01 的症状与 Q 的描述完全吻合**。

## 3. 缺陷清单与修复

### P2-01：时间文本解析失败时，发出一个静默匹配零行的过滤条件 ⭐

**位置**：`tdsql_connector.py::get_cluster_slow_queries`

**原实现**：

```python
try:
    dt = datetime.strptime(time_end, "%Y-%m-%d %H:%M:%S")
    ts = int(dt.timestamp())
    sql += " AND timestramp < %s"; params.append(ts)
except Exception:
    sql += " AND timestramp < %s"
    params.append(time_end)        # ← 把原始字符串塞给数值列
```

**失效链条**：

```
解析失败 → 下发 timestramp < '2026-07-29 10:00:00'
        → 列为 BIGINT，MySQL 隐式把字符串转成【前导整数 2026】
        → 条件变成 timestramp < 2026
        → 真实 epoch 约 1.78e9 ≫ 2026 → 匹配零行
        → 结果被静默清空，不报错、不告警
```

> **这正是"时间窗过滤会清空结果"的机制**，且失败方式完全不可见——空结果与"这段时间确实没有慢SQL"外观一模一样。

**触发条件**：`time_start`/`time_end` 不是严格的 `"%Y-%m-%d %H:%M:%S"`。

现有三个调用方（UI 日期控件 `value-format` / 定时计划 `strftime` / 压测脚本 `strftime`）**都恰好使用正确格式**，故 Q 未经此路径。但任何直接调 API 的调用方传 ISO 带 `T`、带毫秒等格式即会命中。**属高危潜伏缺陷。**

**修复**：解析失败**跳过该侧过滤并告警**，绝不发出破损条件；同时扩充支持 4 种常见格式。

```python
def _to_epoch(text):
    """解析失败返回 None（调用方跳过该侧过滤）。

    【不得回退成把原始字符串塞给数值列比较】——
    MySQL 会把 '2026-07-29 10:00:00' 隐式转成前导整数 2026，
    于是 `timestramp < 2026` 匹配零行，结果被静默清空且不报错。
    宁可不过滤（多取一些）也不能悄悄返回空集。
    """
    for f in ("%Y-%m-%d %H:%M:%S", "%Y-%m-%dT%H:%M:%S",
              "%Y-%m-%d %H:%M", "%Y-%m-%d"):
        try:
            ts = int(datetime.strptime(text, f).timestamp())
            return ts * 1000 if is_ms else ts
        except ValueError:
            continue
    return None
```

> **取舍依据（规约 R-15）**：不过滤 = 多取数据，**可见、可纠正**；破损过滤 = 静默返回空集，**不可见、直接误导结论**。必须偏向前者。

### P2-02：空结果无任何解释，与"确实没有慢SQL"无法区分 ⭐

**这是 Q 遇到的问题在真实环境中最可能的成因。**

`timestramp` 是**采集时刻**，不是 SQL 执行时刻（设计文档明载）。赤兔采集器**周期性**汇聚慢SQL入库，因此：

```
压测流程：制造慢SQL  →  立即用「近1小时」窗口扫 monitordb
实际发生：采集器尚未完成本轮汇聚 → 窗口内无采集记录 → 结果为空
对照：   不传时间窗 → 抓到【历史】已采集数据 → 有结果
```

**这与 Q 观察到的现象完全一致**，也解释了为何"部分实例"如此——各实例的采集进度与历史数据量不同。

**问题不在过滤本身，而在于空结果没有任何解释。** 使用者只看到 0 条，无从判断是"没有慢SQL"还是"采集还没跟上"。

**修复**：空结果 + 已应用时间窗 → 自动探测该库实际的采集时刻范围，给出可执行说明。

```
所选时间窗（2026-07-29 10:00:00 ~ 11:00:00）内无采集记录；
该库现有 1240 条记录，采集时刻范围为 2026-07-28 09:00:00 ~ 2026-07-29 09:30:00。
注意时间窗过滤的是【采集时刻】而非SQL执行时刻，赤兔采集器有汇聚周期，
刚执行的慢SQL需等下一轮采集才会入库——请放宽时间窗或改用 digest 数据源。
```

库中完全无数据时给出不同措辞，避免使用者白调时间窗：

```
monitordb 中库 tdsql_check 尚无任何慢SQL采集记录，与所选时间窗无关；
请确认赤兔采集器已开启并已完成首次采集。
```

该诊断经 `scan_service` 的 `errors` 通道透出，前端既有逻辑会弹窗展示。

**未改变过滤语义**：仍走 `timestramp`（命中索引 `index_time`，与原厂口径一致），只是把无声的空结果变成有解释的空结果。

### P3-03：单位探测样本值为 `0` 时被判假

```python
if sample and sample[0]["timestramp"]:     # 值为 0 → falsy → 跳过探测
```

**修复**：改为 `is not None`。边界情况，影响面小，顺手修正。

## 6. 给 Q 的反馈

1. **现象报告准确，值得肯定**——"时间窗过滤会清空结果"确有其事，且顺藤摸到了一处高危潜伏缺陷（P2-01）。
2. **归因不成立**：单位/类型换算四种情形均正确，`timestramp` 在真实环境是 `timestamp` 类型，数值分支根本不执行。**下次报问题时，若未定位到根因，建议写"现象+已排除项"而非"疑似X"**——"疑似"会把后续排查引向错误方向。
3. **绕过方式可以保留**：压测脚本对 monitordb 不传时间窗是合理的（避开采集延迟），但请在注释里把原因从"疑似时间戳单位差异"改为"避开采集周期延迟"。
4. **建议补一条压测校验**：扫描返回 `errors` 非空时打印出来——本次诊断信息正是经该通道透出，能让下次同类问题当场自证。

## 7. L-04：时间窗语义的 UI 事前提示（已补做）

### 7.1 为什么必须做

P2-02 的空结果诊断是**事后**解释——只有在查空时才出现。但时间窗的语义问题不止于查空：

- 使用者选「近1小时」会自然理解为"这1小时**执行**的慢SQL"，实际是"这1小时**被采集**的记录"；
- 更麻烦的是**查到了结果但条数偏少**——此时不触发诊断，使用者拿着一份不完整的数据得出结论，**全程没有任何提示**。

**事前提示优于事后解释。**

### 7.2 梳理清楚才发现：三种数据源的时间窗语义**各不相同**

补做时逐一核对了三个数据源的实际代码路径，结论是**没有一个**符合"这段时间执行的慢SQL"的直觉：

| 数据源 | 时间窗到底做了什么 | 依据 |
|---|---|---|
| **monitordb** | 按 `timestramp` 过滤，即**采集入库时刻**，非执行时刻；受赤兔采集周期影响 | `tdsql_connector.py::get_cluster_slow_queries` |
| **digest** | **必填但完全不参与查询**。仅作为扫描任务元数据留档；实际抓的是 `performance_schema` 中**累计至今**的摘要 | `scan_service.py:126-130`（连接器虽支持 `FIRST_SEEN/LAST_SEEN` 过滤，但扫描路径不传该参数） |
| **processlist** | **不使用**。只能捕获轮询那一刻正在执行的语句，覆盖范围由「轮询时长」决定 | `scan_service.py:132-135` → `poll_processlist()` |

> **digest 这一条尤其反直觉**：字段是必填的（不填直接报 422），填了却对结果毫无影响。原先界面上没有任何地方说明这一点。

### 7.3 做法

新建扫描抽屉的「时间窗口」项加两层提示：

1. **常驻小字**（随数据源联动，始终可见）——一句话点明该源的窗口到底管什么；
2. **标签旁 `?` 的 tooltip**（悬停展开）——三种源的完整说明，含各自的成因与规避办法。

改动仅 `frontend/index.html` 模板 + `frontend/static/css/app.css` 四条样式类，**未触碰任何后端逻辑**。
