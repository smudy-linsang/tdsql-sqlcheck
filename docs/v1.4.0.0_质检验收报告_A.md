## 二、核心目标验证（独立构造，非复用 Q/G 用例）

### 2.1 T08 反作弊核心用例 —— **通过**

构造两个尺度差异极大的项目（宽松规则集显式停用 60 条规则），对同一段含多处违规的 DDL 分别审核：

| 场景 | 违规数 |
|---|---|
| 带「严格」项目 | 8 |
| 带「宽松」项目 | 8 |
| 不带项目 | 8 |

**三次结果集合完全一致（rule_id + severity 逐项比对）。** 换项目已无法改变评估结果，设计目标达成。

### 2.2 尺度确实生效（反向验证）—— **通过**

仅证明"换项目无效"还不够，还需排除"规则集被整体忽略"这一可能：

| 操作 | 违规数 |
|---|---|
| 全局生效 = `default` | 8 |
| 全局切换为宽松规则集 | **1** |

尺度切换后结果随之改变，证明规则集确实参与判定，而非形同虚设。

### 2.3 T11b 门禁行为等价性 —— **通过**

未配置实例的兜底值实测为 `error<=0 / warning<=-1 / mode=enforce / is_default=True`，与 V1.3 `gate_rules` 默认值完全一致。**存量实例放行结论零变化**，无需迁移的判断成立。

## 四、发现的问题（均非阻断）

### 4.1 【建议】单次审核报告未标注评估尺度 —— 与 DETAIL §6.4 不符

**现状**：三类 HTML 报告中，仅对比报告标注了「评估尺度」。

| 报告 | 是否标注 |
|---|---|
| 对比报告（`scan_compare_report.py`） | ✅ 有 |
| 元数据审核报告（`/report/{id}/html`） | ❌ 无 |
| 文件审核报告（`/file-reports/{id}/html`） | ❌ 无 |

**为什么值得补**：DETAIL §6.4 要求三类报告统一标注，理由是「报告是拿去汇报的交付物，脱离尺度的问题数没有意义」。当前状态下，仍可能把两份不同尺度下产生的审核报告并排放着讲成效——这正是本次要消除问题的**线下版本**。

**影响有限**：`audit_history.rule_set_id` 已正确落库（已验证列存在且有值），数据齐备，缺的只是渲染。补齐成本很低。

**建议**：下个迭代在两处报告页眉补一行，与对比报告保持一致。

### 4.2 【建议】前端遗留不可达的死代码

`index.html` 中 `currentPage==='projects'`（1518 行）与 `currentPage==='gate'`（1655 行）两个页面区块仍在，`app.js` 中 `openGateCustom` / `saveGateCustom` / `currentProjectId` 等旧门禁逻辑亦保留。

**不构成缺陷**：菜单项已移除，四个角色的 `get_visible_menus` 均不含这两个键（已实测），`currentPage` 无从被设为这两个值，代码不可达。

**建议**：清理以免后续维护者误以为仍在使用。

### 4.3 【提示】规则集入口位于折叠子菜单内，非一级入口

设计（ARCHITECTURE §2.3）表述为「规则集提升为一级入口」，实际位于折叠子菜单中。展开后可达，功能完整（「当前生效」标识、「设为生效」按钮、30 秒生效提示均已实现且正确）。

**属表述与实现的轻微偏差**，不影响使用。若认为管理员切换尺度是高频治理动作，可考虑上提；否则维持现状即可。

## 七、关于 G 测试报告的说明

G 的报告结论（GO）与本人独立验收结论一致，其声称的 `tests_3p` 通过数（125 passed / 1 skipped）经复跑核实无误。

**一处表述需更正**：报告第三节称「SQLite 数据库自动执行 `030_global_ruleset_gate.sql` 增量 Schema 迁移」。本系统元数据库为 **MySQL/MariaDB**，迁移脚本亦为 MySQL 方言（含 `ENGINE=InnoDB`、`COMMENT`、外键约束等 SQLite 不支持的语法）。此处应为笔误，不影响测试结论，但正式质量文档中的技术事实建议更正，避免后续维护者据此误判。
