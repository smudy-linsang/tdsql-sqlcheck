## 2. 为什么两份报告不能直接相减

拿到的四份报告分属**两个不同模块**：

| 文件 | 模块 | 环境 | 时间 |
|---|---|---|---|
| `Extracted_Schema_Report_873/874.html` | **在线元数据规则审核**（`schema-extractor-audit`） | 内网生产 v1.6.2.1 | 09:49 / 09:54 |
| `TDSQL___extracted_*.sql_*.html` | **文件审核**（`file-audit`） | 开发环境 v1.6.2.2 | 10:26 / 14:27 |

两者的**语句切分方式、注释处理、生效规则集**都可能不同。直接比"通过率"会得到严重误导的结论——

* `lzbj_ecif`：内网 86.0% 通过 → 开发 0.0% 通过
* `cbs_coredb`：内网 19.5% 通过 → 开发 0.1% 通过

**这两个数字不能用来判断版本好坏**，因为 `AuditResult.passed = len(violations)==0`，只要多一条 INFO 就算"未通过"，而内网关掉的 R036/R037 恰恰是两条几乎每表必中的 INFO。

因此本次核查改用**三层比对**，把"版本差"与"环境差/模块差"彻底分离。

## 5. 修复成果验证 + 三处差异归因

### 5.1 ✅ 目标缺陷已修好，且修在正确的位置

`kcfb_list_info` 的 DDL 里，该索引声明为**普通索引**：

```sql
KEY `kcfb_list_info_idx13` (`list_unique_num`,`lgl_pern_code`),
...
) ENGINE=InnoDB ... shardkey=black_list_seq_num
```

直接调解析器对比两版：

| 版本 | `kcfb_list_info_idx13` 的解析结果 |
|---|---|
| v1.6.2.1 | `{'columns': ['list_unique_num','lgl_pern_code'], 'type': **'UNIQUE'**}` ← **误判** |
| v1.6.2.2 | `{'columns': ['list_unique_num','lgl_pern_code'], 'type': **'NORMAL'**}` ← 正确 |

同一张表的 `idx2` / `idx14` 两版都正确判为 `NORMAL`，说明**不是把判定整体放宽**，而是精确纠正了这一类误判。

**判定：真阳性消除**（R054 本就不该在一个非唯一索引上触发），而不是"把规则关小了"。这正是 DEF-1（索引类型误判）的预期修复效果。

> 触发条件推测：列名 `list_unique_num` 含 `unique` 子串。旧实现按字符串推断索引类型，因而误判。该推测不影响结论——行为已用解析器输出直接确证。

## 6. 顺带发现的两个既有缺陷（**非本次引入**，建议另案）

### 6.1 解析降级时 `--` 被当成表名，导致 R001 误报

* **现象**：语句解析失败且文本带 `--` 注释头时，R001 报 `表/库名 '--' 不符合命名规范`。
* **影响面**：本次样本 2172 张表中仅 1 张（`kitp_rate_plan`），因为只有它解析失败。影响随"解析失败语句数"放大。
* **版本**：v1.6.2.1 与 v1.6.2.2 **行为完全相同**，与本次修复无关。
* **建议**：降级路径提取表名时过滤掉注释残片；或 R001 对非标识符形态的候选名直接跳过。

### 6.2 MySQL 8.0 降序索引 `PRIMARY KEY (col DESC)` 无法解析（KFN）

* **现象**：`kitp_rate_plan` 因 `PRIMARY KEY (`id` DESC)` 触发 `E999_SYNTAX_ERROR`，整表退化到降级路径审核。
* **实测**：sqlglot **29.0.0 / 30.14.0 / 30.17.0 三个版本全部解析失败**——升 sqlglot 解决不了。
* **影响**：该表的结构类规则只能靠降级路径部分覆盖（R003/R004/R005/R028/R077 仍命中，但完整性无保证）。
* **建议**：登记为已知假阴性（KFN），并在 `pre_parser` 层做一次 `\s+(ASC|DESC)\s*(?=[,)])` 的索引列排序修饰剥离——这是纯文本预处理，爆炸半径可控。

## 7. 核查结论

1. **v1.6.2.2 的修复符合预期。** 目标缺陷（索引类型误判导致 R054 误报）已消除，且经解析器输出确证是"判对了"，不是"不判了"。
2. **未发生次生灾害。** 在把环境差与模块差剥离干净之后，2172 张表 / 11 089 条违规的消息级全量比对结果是：**新增 0 条，消失 1 条**。前序版本修复的 R077（1005）、R061（1014）等大面积规则一条未动。
3. **两份报告"通过率从 86% 掉到 0%"是口径错觉**，成因是内网停用了 R036/R037/R033 而开发环境未停用，而 `passed` 的定义是"零违规"。其中 R036 在 `lzbj_ecif` 上命中 214/214——**仅这一条就足以把通过率压到 0%**。不是质量下降。
4. **三条规则配置差异已全部闭合**：R036 / R037 / R033 内网均已停用（使用方确认），开发环境未停用，故两份报告在这三条上的差异是配置差而非版本差（§5.2 D-2）。
5. **建议另案处理** §6 的两个既有缺陷，本次不动。
