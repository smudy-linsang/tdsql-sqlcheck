## 3. 缺陷复测：三种"悬挂残留"形态下的界面表现

同一支探针（`probe_published_orphan_d36.py`）以三种模式造数，判定条件统一为
**"已选实例后两个按钮均可用 + 出现对应提示"**：

| 形态 | 构造 | 卡片与提示 | 「拉取」 | 「恢复查看」 | 结论 |
|---|---|---|---|---|---|
| **published**（UAT36-01 本体） | 任务 `PUBLISHED/PERSISTING`，槽不指向它 | 卡片照常显示；提示「结果已落库但未收口，可下载报告；如需重扫请直接重新发起」 | 可用 | 可用 | ✅ PASS |
| **accepted**（D-04 本体） | 任务非终态、槽不指向它 | 卡片照常显示；提示「该任务已不在执行器上运行（可能为中断残留），可重新发起或联系运维」 | 可用 | 可用 | ✅ PASS |
| **running_stale**（§2.1b） | `RUNNING` 且 `heartbeat_at` 超 `JOB_TIMEOUT`，槽仍指向它 | 卡片照常显示；提示「该任务长时间无执行器心跳，可能已中断；请联系运维核实后再重新发起」；接口确认 `slot_owned=true, stale_running=true` | 可用 | 可用 | ✅ PASS |

## 4. 回收行为矩阵（真实库，`probe-reclaim-matrix.json`）

| 编号 | 场景 | 期望 | 实测 | 结论 |
|---|---|---|---|---|
| L1 | `PUBLISHED` + 有 `report_id` + 槽指向它 + 超时 | SUCCEEDED + 写 `finished_at` + 释放槽 | SUCCEEDED / slot=None | ✅ |
| L2 | `PUBLISHING` + 无 `report_id` + 超时 | FAILED / `PERSIST_TIMEOUT` | FAILED / PERSIST_TIMEOUT | ✅ |
| L3 | `ACCEPTED` + 槽空闲 + 超时（D-04） | FAILED / `START_TIMEOUT` | FAILED / START_TIMEOUT | ✅ |
| L4 | `ACCEPTED` 超时但槽被**他人**占用 | 不动作、不抢槽 | 状态仍 ACCEPTED、槽仍 `someone-else` | ✅ |
| L5 | `PUBLISHED` 但未超时（刚发布） | 不动作 | 仍 PUBLISHED、槽仍指向它 | ✅ |
| L10 | `RUNNING` + 创建/更新/心跳均超 2 小时 | **不动作**（§2.1b 决策） | 仍 RUNNING、槽未动 | ✅ |

**6/6 通过**，其中 L3/L5/L10 直接对应工单里"防误杀、防抢槽、防违背决策"的三条安全边界。

## 5. 锁有效性：独立变异验证（`probe-mutation-fixreq01.json`）

对 Q 新增的 `tests/test_v1637_fixreq01.py` 做回退式变异：

| 变异 | 内容 | 结果 |
|---|---|---|
| M1 | 回收不再处理 `PUBLISHING/PUBLISHED`（UAT36-01 本体） | ✅ 变红 |
| M2 | `stale_running` 恒为假 | ✅ 变红 |
| M3 | 单独移除 `complete()` 返回值检查 | ⚪ 未变红（**等价变异**） |
| M4 | 单独移除「放槽前终态」护栏 | ⚪ 未变红（**等价变异**） |
| M5 | 前端判定退回「只看 state」 | ✅ 变红 |
| M6 | 回收分支纳入 `RUNNING`（SQL 内层 `state='ACCEPTED'` 守卫仍在） | ⚪ 未变红（**等价变异**） |
| **M7** | **同时移除 M3+M4 两层护栏（真实缺陷）** | ✅ **变红** |
| **M8** | **分支条件与 SQL 守卫同时放开（真实缺陷）** | ✅ **变红** |

**判读**：M3/M4/M6 之所以不红，是因为 Q 做了**双层防护**——去掉任一层，另一层仍使行为不变，
属**良性冗余**而非"假绿锁"；一旦**整层移除**（M7/M8），锁立刻变红。
因此结论是：**这 10 条锁对真实缺陷全部有效**，可以放心作为准出门禁。

> 方法学提示（供后续各角色复用）：判定"锁是否有效"不能只看单个变异是否变红，需区分
> ①真缺陷变异 ②被另一层防护掩盖的等价变异；对后者应施加**组合变异**再判。

## 7. 观察（非本次引入，不构成整改项）

**前端兜底恢复只查"最新 20 条"任务**：`_recoverActiveJob()` 在本地无 `meta_active_job` 线索时，
调用 `/api/v1/audit/metadata-jobs?limit=20` 后在其中找非终态任务。若用户的未决任务落在最近 20 条
之外（例如任务创建较早、本地线索又已被清理），兜底恢复将找不到它，页面不显示任务卡。

- **本轮复测踩到该边界**：探针最初把 `created_at` 也回拨 2 小时，任务随即掉出 20 条窗口，
  页面无卡片（同一任务在 `sessionStorage` 有线索时不受影响）。
- **既有行为**：该逻辑自 v1.6.3.5 起存在，**非本次整改引入**，且本轮改动未触碰。
- **建议（可选，随下版）**：把 `limit` 提到 50，或由前端按"未决状态"查询（后端已有 `state` 参数，
  可扩展为多状态过滤），使"无本地线索 + 任务较老"的用户也能恢复查看。

## 8. 边界

1. 本机为 MySQL 8.0 + 单 Web worker；内网 6000+ 表真机复跑、Linux/systemd 部署与回退门禁仍须内网执行。
2. 悬挂态为**受控构造**（等价于"runner 在 publish 与 complete 之间死亡"或历史残留），
   未在内网制造真实的 runner 崩溃；但回收与前端判定逻辑走的是真实代码路径。
3. 未覆盖：多 worker 并发受理、断电重入、CORE_SAFE 回退制品。
