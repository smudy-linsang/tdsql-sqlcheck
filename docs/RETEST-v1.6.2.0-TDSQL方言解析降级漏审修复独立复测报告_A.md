## 3. 测试资产缺口（2 处，不阻断上线）

用注入实验检验 Q 的 14 条用例能否拦住"违反设计的改法"：

| 注入的错误改法 | Q 的 14 条 | 判定 |
|---|---|---|
| **去掉 `isinstance(ast, exp.Command)` 门（改成无条件剥离）** | **14 passed** | **❌ 未拦住** |
| 方言正则去掉 `BROADCAST` 分支 | 1 failed（D4） | ✅ 拦住 |
| **重试结果无条件采用（去掉 `not isinstance(_retry_ast, exp.Command)` 校验）** | **14 passed** | **❌ 未拦住** |
| 把 `raw_sql` 也改成剥离后文本（违反 NG-3） | 1 failed（D6）；R077/R054 另有 14 failed | ✅ 拦住 |

### 3.1 【中高】缺口 1：没有测试锁住 `Command` 门

**这是本设计最核心的安全性质**——设计 §2.2 的全部论证（"影响面可从控制流证明为零"）都建立在这道门上。它一旦被移除，正常语句也会被剥离，正则的不精确性立刻暴露。

**注入实测**：去掉该门后，N1 用例的 SQL

```sql
CREATE TABLE t_n1 (id BIGINT NOT NULL, broadcast VARCHAR(32), PRIMARY KEY (id)) ENGINE=InnoDB
```

解析结果由 `['id', 'broadcast']` 变成 **`['id']`——`broadcast` 列被吃掉了**。但 N1 只断言 `len(parsed.columns) > 0`，仍为 True，**测试照样通过**。

**根因：Q 的实现弱于设计的明文要求。** 设计 §7.1 对 N1 写的是：

> | **N1★** | 列名恰好叫 `broadcast` 的普通建表 | **不进入重试**；**解析结果与改前逐字一致** |

Q 只实现了"不进入重试"（`not isinstance(parsed.ast, exp.Command)`），**没有实现"解析结果与改前逐字一致"**。

**建议补强**：N1/N3 追加列名集合的精确断言，例如

```python
assert [c.get("name") for c in parsed.columns] == ["id", "broadcast"], \
    "列名与改前不一致——说明正常语句被误剥离（Command 门可能已失效）"
```

### 3.2 【中】缺口 2：N7 的断言过弱，没锁住"重试结果校验"

设计要求"重试结果**只在**确实产出非 `Command` 节点时才采用"。Q 的 N7 断言是：

```python
assert parsed.parse_error is not None or isinstance(parsed.ast, exp.Command)
```

这是一个**几乎恒真的析取式**。注入实测：把 `if not isinstance(_retry_ast, exp.Command): ast = _retry_ast` 改成无条件 `ast = _retry_ast` 后，**14 条全过**。

**建议补强**：构造一条"剥离后 sqlglot 仍返回 Command"的语句，断言 `parsed.ast` 仍是原始的 Command 且解析结果不劣于改前。

### 3.3 定性

两处均为**测试覆盖缺口，不是产品缺陷**——Q 的实现本身是正确的，V1–V6 六轮独立验证已证明。缺口影响的是**将来**的回归保护：下一个人改动这段解析器逻辑时，这两条最关键的约束不会报警。

## 4. 准出意见

**产品代码：准出。** 六轮独立验证全部通过，与 Rev.B 设计逐字一致，九条禁令（含 NG-8 施工红线）无一违反，回归零差异。用户报告的核心问题——HASH/BROADCAST 语法表被静默漏审——已彻底解决。

**测试资产：建议补强 2 处后再作为长期回归基线。** 尤其缺口 1：设计的全部安全性论证都押在 `Command` 门上，而没有任何测试守着它。

**上线交付说明必须包含**（设计 §9 已列）：

1. **报告"通过率"会大幅下跌**——实测 7.1%→0.0%、模拟内网 64.3%→0.0%。成因是"一条 INFO 建议即判未通过"的**既有**口径被放大，**不是本次引入**，更不代表数据库质量变差；
2. **违规数明显上升是修复的目的**——把此前被掩盖的问题暴露出来。内网 HASH 语法分片表尤其明显（实测 8/8 张由"通过"变为 2–4 条）；
3. **`BROADCAST` 关键字声明的广播表同样恢复审核**（此前也被掩盖）；
4. **ADJ-7 仍然存在**：R116/R117/R118 依旧看不见 HASH 语法的分片键，不要误以为"HASH 表已被全套分片键规则覆盖"；
5. ADJ-2/ADJ-3/ADJ-8 仍留 Phase 2（**ADJ-3 是真实静默失效，建议优先**）；ADJ-4、ADJ-6 及 R037 的 `status` 口径均由用户决策保持现状。
