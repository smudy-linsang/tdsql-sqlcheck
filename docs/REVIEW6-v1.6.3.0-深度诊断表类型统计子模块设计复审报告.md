## 5. 第五轮 P2-01 三项整改要求的逐条对照

| 第五轮要求 | Rev.M 落实 | 判定 |
|---|---|---|
| 删除 SQL 端 `BINARY`，正确性由应用层两层防御承担 | §4.2 数据流、§6.4 正文、附录 A.1 均已改为普通 `IN`；§6.4 明确写入"SQL 端不做大小写语义假设" | ✅ |
| §6.4 / ADR-27 / E-36 文字同步 | 三处全部改写。**ADR-27 的备选项从 3 个扩到 5 个**，把 `BINARY` 与 `CAST(... AS BINARY)` 都列为已否决方案并写明否决理由 | ✅ **优于我的要求** |
| 调整 `T4-R01` 钉 SQL 文本的断言 | 已删除该行；用例只断言行为（变异测试已验证其仍然有效） | ✅ |
| 内网留存 `EXPLAIN` 与耗时实测证据 | 新增 **T20**（§10.3 回填模板 + §10.5 判据表 + §12.4 验收条目），并明确规定：普通 `IN` 的扫描库数或中位耗时**不得劣于** `BINARY IN`，异常则**阻断发布**、且**禁止无证据恢复** `BINARY`/`CAST` | ✅ **优于我的要求** |

**两处做得比我提的要求更好，值得点出：**

1. **ADR-27 把 `CAST(... AS BINARY)` 一并否决。** 我在第五轮只顺带提了一句
   "仅换成 `CAST` 不解决下推问题"，O 把它正式写进了备选方案否决理由。
   这堵住了"`BINARY` 弃用了那就换 `CAST`"这条最可能被后人走的错路。
2. **T20 的判据写成了双向的。** 它不只要求"证明普通 `IN` 更好"，
   还规定了"若实测反而更差该怎么办"（分析优化器 + 寻找不破坏下推的替代，
   而非直接回退），并把它定级为**阻断发布、不阻断开发**——
   这个定级是准确的：它是性能证据门禁，不是正确性缺陷。

## 7. 一项观察（不阻断，供实施时参考）

**`BINARY` 回潮目前只有文档约束与 T20 门禁，没有离线自动化护栏。**

变异 M2 显示：若有人在未来某版把 `BINARY` 加回去，`T4-R01` **不会失败**
（这正是"只钉行为"的正确代价）。目前拦住它的是 ADR-27 的明文否决 + T20 的
发布前实测门禁——在正确性上没有任何风险，逻辑上也说得通：
这是**性能**约束，离线单测确实没法真正验证谓词下推。

不过考虑到本方案的历史（迁移槽护栏前后写错过三次，都是"靠人记"的约定），
一条**零成本的源码级护栏**仍有价值，例如断言基线 SQL 中
`TABLE_SCHEMA` 前不出现函数/操作符。它抓不到所有反下推写法，
但能挡住最可能发生的那一种，并把 ADR-27 的结论固化成会失败的东西。

**这条是建议，不是整改要求。** 实施时采纳与否由 Q 判断，
**不需要为此再出一版设计**。
