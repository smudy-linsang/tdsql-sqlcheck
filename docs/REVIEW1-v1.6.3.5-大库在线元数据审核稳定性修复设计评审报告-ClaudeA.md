## 1. 结论摘要

| 级别 | 编号 | 问题 | 为什么是次生灾害/可行性问题 |
|---|---|---|---|
| **P1** | **P1-01** | `METADATA_CHILD_RSS_LIMIT_MIB` 默认 **8192 MiB**，而内网 memory 根组历史高水位仅 **10.68 GiB** | 这个"护栏"允许单个子进程吃掉主机一半以上内存。真触到就会把主机拖进 swap，**连累两个 Web worker 和元数据库**——把"一个功能坏了"升级成"整站不可用"。修复后子进程实测只需百 MB 量级，8 GiB 形同虚设 |
| P2 | P2-01 | §8.2 旧接口兼容 façade 引入一整套 legacy 包装机制，而它**唯一已知的消费者（前端）在同一版本被 FIX-03 替换掉了** | 高复杂度 ＋ 设计自认的低验收强度（"旧 façade 另列兼容测试"）＋ 与产物上限/幂等/恢复三处交互 = 典型次生灾害温床 |
| P2 | P2-02 | FIX-01（小、可证、可独立回滚）与 FIX-02（新建 systemd 服务＋v15 两表＋状态机＋产物体系＋前端重写＋部署回滚改造）**捆绑交付** | **杀进程机制至今未证实**。先上 FIX-01 本身就是一次决定性实验，其结果直接决定 FIX-02 是否对症 |
| P3 | P3-01 | 设计把"Uvicorn 健康检查强杀"列为主要工作假设，却没有针对它的任何显式防护或观测手段 | 下次再出现 worker 消失时，仍然无法判定是不是这条路径 |

**一句话**：方案是对的，FIX-01 我已独立验证等价、FIX-02 架构方向正确、回滚与发布门禁写得比我要求的还严。唯一真正会"引发次生灾害"的是那个 8 GiB 的护栏参数——它保护的对象和它威胁的对象是同一台机器。

## 2. 我独立验证通过的部分

### 2.1 FIX-01 的有界见证索引：算法等价性成立

这是本方案技术风险最高的一处——**用 ≤5 个见证槽位替代完整历史**，属于新算法，必须证明等价而不是"看起来对"。

**(a) 我逐条推演了 §4.3 的三分支证明，四种组合穷尽、无遗漏**：

| 查询 (T,Y) 与 anchor A(表 a,类型 x) 的关系 | 设计的取值来源 | 我的判定 |
|---|---|---|
| T≠a 且 Y≠x | anchor 本身即最早冲突 | ✅ 成立 |
| T=a（Y 任意） | `outside_anchor_table` 存"表≠a 的历史中最早的两个不同类型"；Y 最多排除其中一个 | ✅ 成立，且第二条恰是"最早的、类型≠第一条类型"者 |
| T≠a 且 Y=x | `outside_anchor_type` 存"类型≠x 的历史中最早的两个不同表"；T 最多排除其中一个 | ✅ 成立 |

**(b) 我按 R035 的真实语义（冲突 = `ref.table != 当前表` 且 `ref.type != 当前类型`，取历史顺序第一条）写了独立实现做差分测试**，并且**比较的是冲突引用的身份（语句序号/列序号/来源表/类型），不只是"有没有冲突"**——因为错误消息里要显示来源表和 `raw_type`：

```text
随机差分测试：960,000 次查询，差异 0 处；观测最大见证条数 4（契约上界 5）
穷举测试　：118,080 次查询，差异 0 处；观测最大见证条数 4
合计 1,078,080 次查询，0 差异
```

与 O 自己跑的模型（1,062,880 次查询、0 差异、最大 4）**独立复现一致**。契约写 5、实测最大 4，留了一格余量，稳妥。

### 2.2 FIX-01 确实能解决已证实的缺陷

我在上一轮排查中已实测过等价的流式改法：**1600 表 375.3 MB → 18.9 MB（降 95%），6000 表外推 1.92 GB → 63 MB，审核结果逐条完全一致**。O 的方案在此基础上把索引从 O(M) 进一步降到 O(U)，方向正确。

### 2.3 O 拒绝两个简化的理由都成立

* **"同名列只保留第一张表"会漏报**——`a.id INT → b.id BIGINT → c.id INT` 应为 `[否,是,是]`。正确。
* **"完整历史 + 每次从头扫"CPU 最坏仍是平方级**——这条尤其要认：**那正是我上一轮原型的真实弱点**。一个 `id` 列出现在 6000 张表且类型全同时，规则找不到冲突就会扫完整条链，6000×6000/2 ≈ 1800 万次比较，再乘以若干个全库共有列。我的实测（N≤1600，耗时幂次 N^1.09）没暴露出来，是因为规模不够。**O 说得对，我上一轮的简单方案不足以收口 CPU。**

### 2.4 回滚与发布门禁写得比我要求的严

* v15 两张表是**加法迁移、回滚保留不删**，`audit_history` 保持旧 JSON 格式，旧版本可读历史 ✅
* 明确写"回滚到 v1.6.3.4 会重新暴露缺陷，**必须暂停此类大库在线审核，不能把回滚当成已经修复**" ✅ 这句话很重要
* 发布门禁要求**内网原 6000+ 表目标连续 3 次完整成功**，并记录对象清单/hash、分阶段时间、**RSS 峰值、worker PID、退出日志**，且"无与该审核有关的 Web worker 重启或空响应" ✅
* 明确"故障注入不在生产环境执行""不得在设计阶段预签通过" ✅

### 2.5 失败关闭的边界正确

"发现第二 runner 或存储实例标识不一致时失败关闭；**不要静默退化到 Web 内同步执行**"——这一条把最危险的退化路径堵死了。升级顺序也正确：**先起 runner 并通过校验，再起 Web**（§12.2 第 5 步）。

## 3. 评审发现

### P1-01（必须整改）8 GiB 的子进程内存护栏，会把"一个功能坏掉"升级成"整台机器坏掉"

**问题**

§5.2 参数表：

| 参数 | 默认 | 允许范围 |
|---|---|---|
| `METADATA_CHILD_RSS_LIMIT_MIB` | **8192（8 GiB）** | 512—32768 |

而 `METADATA_MAX_CONCURRENT` 固定为 1，即**单个子进程被允许涨到 8 GiB**。

**证据：这台主机没有 8 GiB 可以给它**

O 自己在 `DIAG-...-O独立排查与证据边界报告.md` §14 里取到的 v1 cgroup 数据：

| memory cgroup | 历史高水位 |
|---|---|
| 服务组 | 3,889,078,272 B ＝ **3.62 GiB** |
| system.slice | 6,052,622,336 B ＝ **5.64 GiB** |
| **memory 根组** | 11,465,011,200 B ＝ **10.68 GiB** |

根组高水位 10.68 GiB 是**整机受计费内存的历史峰值**，也就是说这台机器迄今为止一共也就用到过约 10.7 GiB。**给单个子进程 8 GiB 的额度，等于允许它独占全机内存的 ~75%。**

**证据：修复后根本不需要 8 GiB**

我实测的流式修复（与 FIX-01 同向，且 FIX-01 的索引比它更省）：1600 表 **18.9 MB**，6000 表外推 **63 MB**。再加上提取的 DDL 文本（`METADATA_SQL_MAX_MIB` 上限 256 MiB）与结果文件缓冲，子进程的合理量级是**几百 MB**。

**8192 MiB ≈ 预期需求的 30～80 倍。这不是护栏，是形同虚设。**

**次生灾害路径（这正是本条定为 P1 的原因）**

```text
子进程内存回归（比如某天 R035 索引又被改回去，或换个更大的库）
   → 允许一路涨到 8 GiB（护栏不拦）
   → 主机（约 10.7 GiB）进入 swap
   → 两个 Web worker 与元数据库 MySQL 一起被拖慢甚至被内核选中
   → 从"元数据审核这一个功能不可用" 变成 "整站不可用 + 元数据库受损风险"
```

**本次修复的初衷是止损，结果护栏参数本身成了更大的风险源。**另外设计自己也承认"runner 每秒读 child RSS……采样保护非瞬时硬内存隔离承诺"——**1 Hz 采样 + 8 GiB 阈值**，等于在失控时既拦不住速度也拦不住幅度。

**整改（照图施工）**

请 O 将 §5.2 该行及相关说明改为：

> | `METADATA_CHILD_RSS_LIMIT_MIB` | **1024**，允许 512—4096 | runner 每秒读 child RSS，越界请求回收 |
>
> 取值依据：FIX-01 之后审核阶段的实测内存为 1600 表 18.9 MiB、6000 表外推 63 MiB；叠加 `METADATA_SQL_MAX_MIB`（256）与结果缓冲后，子进程合理峰值在数百 MiB 量级，1024 MiB 已留约 15 倍余量。**上界收紧至 4096 MiB**：内网 memory 根组历史高水位仅 10.68 GiB，任何超过该主机内存 40% 的取值都会在触发前先把 Web worker 与元数据库拖入 swap，护栏反而成为放大器。
>
> **新增部署预检（硬性）**：安装/升级时读取 `/proc/meminfo` 的 `MemTotal`，若 `METADATA_CHILD_RSS_LIMIT_MIB > MemTotal × 25%`，**拒绝启动并指明该参数与实测 MemTotal**，不得仅打印告警。该预检与 §12.2 的其他启动校验同批执行。
>
> **容量验收回填**：§11.4 已要求记录子进程 RSS 峰值；该实测值取得后，须据此复核本参数是否仍需 1024 MiB，**用实测校准而不是继续沿用估计值**。

同时请在 §11.2 故障注入用例中补一条：**构造子进程内存超过配置阈值的场景，断言 runner 按 TERM→KILL 回收、任务终态为明确的资源类失败、且两个 Web worker 未受影响**（当前故障注入清单里没有这一条）。

### P2-01（建议整改，需 Mr.Linsang 拍板）旧接口兼容 façade：为一个正在被本版替换的消费者，建一整套子系统

**问题**

§8.2 为了让 `POST /api/v1/audit/extract-and-audit` 对旧客户端"看起来还是同步的"，引入了：

* child 在 PUBLISHED 之后额外制备 `legacy-response.json`（把 schema.sql 与 results.json 流式重组成原 SUCCESS JSON，且"SQL 字符串须用正确 JSON 编码器分块转义"）
* 独立的 `legacy-manifest.json` 与兼容产物状态
* `transport_mode=LEGACY_WAIT` 受理上下文
* 旧同步等待上限 `METADATA_JOB_TIMEOUT_SECONDS + 60`（默认 **1860 秒 ＝ 31 分钟**）
* 504/`JOB_STATUS_UNCERTAIN`、503/`LEGACY_RESPONSE_UNAVAILABLE` 两条专属失败分支
* 与幂等键、产物上限、PUBLISHED 恢复规则三处交互

**而这个 façade 唯一已知的消费者，是本项目自己的前端——它在同一个版本里被 FIX-03 改成新的短请求轮询流程了。**

设计自己也写明："**新 UI+新 API 是内网容量验收主路径，旧 façade 另列兼容测试。**"

**风险**

高复杂度 ＋ 设计自认的较低验收强度 ＋ 三处状态交互 ＝ 典型的次生灾害温床。更具体地说：`legacy-response.json` 的制备发生在**核心结果已 PUBLISHED 之后、child 退出之前**——这是一个"主流程已成功、附加流程可能失败"的窗口，历史上这类窗口最容易产生"用户看到失败、后台其实成功"的错配。设计已经为此写了 503 分支，但**这条路径的测试强度按设计自己的安排是弱于主路径的**。

**整改建议**

请 O 在 §8.2 开头补一条前置判定，并把结论写入设计：

> **先确认调用方**：除本项目前端外，是否存在其他真实调用 `POST /api/v1/audit/extract-and-audit` 的消费者（运维脚本、其他系统、定时任务、第三方集成）？
>
> * **若不存在**（前端在本版已改造）：façade 简化为直接返回 **202 + job_id + 查询链接**，并在响应中给出迁移说明；**删除 `legacy-response.json` 制备、legacy-manifest、LEGACY_WAIT 传输模式与 503/`LEGACY_RESPONSE_UNAVAILABLE` 分支**。这样可移除一整条低覆盖高复杂度路径，本版爆炸半径显著收窄。
> * **若存在**：保留现方案，但**必须与新路径同等验收强度**——§11.4 的"连续 3 次真实内网通过"须**同时覆盖 façade 路径**，不能只写"另列兼容测试"。

这一条我不替 Mr.Linsang 决定，但**要求把"有没有其他调用方"这个事实先查清楚再定**，不能默认"保留兼容总是更安全"——在本例中保留兼容带来的机器量，本身就是风险。

### P2-02（建议整改）FIX-01 与 FIX-02 建议拆成两个可独立回滚的交付单元

**问题**

两块改动的性质、体量与确定性完全不同：

| | FIX-01 | FIX-02 |
|---|---|---|
| 改动面 | `checker.py` ＋ 新增 `r035_context.py` | 新增 systemd 服务、v15 两张表、任务状态机、产物目录体系、下载/预览接口、前端重写、部署与回滚流程改造 |
| 等价性 | **已被 O 与我双方独立验证**（合计 200 万+ 次查询 0 差异） | 无法"证明"，只能靠测试覆盖 |
| 能否独立回滚 | 可以（纯算法替换） | 涉及服务、迁移、产物，回滚有顺序要求 |

**关键论据：杀进程的机制到现在还没有被证实。**

我读了实际部署的 uvicorn 源码（本机 0.52.4，内网 0.52.1 同系列），确认了强杀路径客观存在：

```python
# uvicorn/supervisors/multiprocess.py:218-222
for idx, process in enumerate(self.processes):
    if process.is_alive(timeout=self.config.timeout_worker_healthcheck):   # 默认 5 秒
        continue
    process.kill()   # process is hung, kill it     ← SIGKILL，无 traceback、无 OOM 记录
```

子进程用一个 **daemon 线程** 应答 ping（`threading.Thread(target=self.always_pong, daemon=True)`）。这与现场"worker 静默消失、无堆栈、`oom_kill=0`"完全吻合，所以设计把它列为主要工作假设是合理的。

**但我实测复现不出来**：在审核过程中挂一个同样 0.5 秒打点的守护线程，测最大停顿——

| 模式 | 表数 | 耗时 | **最大心跳停顿** | 是否越过 5 秒阈值 |
|---|---|---|---|---|
| 现状 | 800 | 7.4s | 0.51s | 否 |
| 现状 | 1600 | 17.4s | **0.70s** | 否 |
| 流式修复 | 800 | 5.5s | 0.51s | 否 |
| 流式修复 | 1600 | 12.5s | 0.52s | 否 |

现状确实比修复版差（0.70 vs 0.52，且随 N 增长），但**在我能测到的规模内离 5 秒还很远**。也就是说：健康检查强杀在 6000 表规模下**可能**发生（堆到数 GB 时 GC 停顿会大幅恶化），但**至今无人证实**。

**因此，先上 FIX-01 本身就是一次决定性实验：**

* 若 6000 表随即通过 → 机制就是内存，FIX-02 是加固而非救命，可以从容做、从容测；
* 若仍然死 → 机制另有其因，**而这个知识会直接决定 FIX-02 的设计是否对症**（比如若是网络层或代理设备关连接，换进程也救不了）。

**整改建议**

不要求改架构，要求**把交付单元拆开**：

> FIX-01 与 FIX-02 应作为**两个可独立验收、独立回滚**的交付单元。允许在同一个 v1.6.3.5 版本内发布，但须满足：
> 1. FIX-01 单独具备完整验收证据（算法等价 ＋ 内存/CPU 实测 ＋ 全量回归），**不依赖 FIX-02 是否就绪**；
> 2. 提供"仅回滚 FIX-02、保留 FIX-01"的回滚路径（关闭 runner 受理、façade 直接失败并提示，而**不是**退回 Web 内同步执行——后者已被 §5.1 正确禁止）；
> 3. §11.4 的内网 3 次容量验收，**若条件允许，先在仅含 FIX-01 的构建上跑一次**，把"机制是不是内存"这个至今悬空的问题一次性钉死。第 3 条是建议，不是硬性门槛。

### P3-01（建议）健康检查窗口应显式固化并纳入观测

设计把"Uvicorn 健康检查触发终止"列为主要工作假设（§2.2），但全文**没有针对它的任何显式防护或观测手段**。

**建议补两条：**

1. **显式固化窗口**：在新旧两个 systemd unit 中显式写入 `UVICORN_TIMEOUT_WORKER_HEALTHCHECK`（即便仍取 5 秒），避免依赖不同 uvicorn 版本的默认值漂移。现场取证已确认该变量当前 `<not set in parent process>`，即完全依赖默认值。
2. **纳入观测**：§12.4 的一键诊断增加输出该变量的生效值；§11.4 容量验收增加一项——**任务执行期间记录 Web worker 的心跳应答延迟分布（至少最大值）**。这样下次若再出现 worker 消失，可以直接判定是不是这条路径，而不必再来一轮取证。

成本极低，但能把一个"至今只能靠推测"的机制变成"下次可直接读数判定"。

## 4. 次生灾害专项核查（Mr.Linsang 指定重点）

我按"这次改动会不会伤到别的功能"逐项过了一遍，结论如下：

| 风险面 | 设计的处理 | 我的判定 |
|---|---|---|
| **单进程内存失控拖垮全机** | `METADATA_CHILD_RSS_LIMIT_MIB=8192` | ❌ **不合格，见 P1-01**。这是本次唯一真正会制造次生灾害的点 |
| 退化回 Web 内同步执行 | §5.1 明确失败关闭，禁止静默退化 | ✅ 堵死了最危险的路径 |

## 6. 向 Mr.Linsang 汇报

**方案我评下来是可行的，方向也对。**O 这次做得很扎实：他没有走"把超时调大"或"关掉规则"这类糊弄路子，而是真的去改了那个平方级的算法，还额外发明了一个"每个列名只留 5 个见证"的省内存索引，并附了等价性证明。

**我把那个新算法独立验证了一遍**——按规则的真实语义自己写了一份实现，跟"保留完整历史"的标准答案做差分比对，跑了 **107 万次查询，零差异**，而且比对的是"报出来的是哪一张表、哪一条记录"，不只是"有没有报错"。O 自己也跑了一遍类似的模型，两边结果对得上。**这一块可以放心。**

另外有一处我要认下来：O 在方案里否掉了我上一轮给的简单改法，理由是"完整历史每次从头扫，CPU 最坏还是平方级"。**他是对的**——我那个改法在 6000 表、且全库共有列类型一致时，会退化成上千万次比较。我上一轮测到 1600 表没暴露出来，是规模不够。

**但有一个参数必须改，否则会闯出比现在更大的祸。**

方案给元数据子进程设了个内存护栏，默认 **8 GiB**。可是内网那台机器的证据显示——这是 O 自己取到的数据——**整机迄今为止一共也就用到过 10.7 GiB**。等于允许一个子进程独占全机内存的四分之三。

而修好之后，这个子进程实际只需要**几百 MB**（我实测 1600 表 18.9 MB，6000 表外推 63 MB）。**8 GiB 不是护栏，是形同虚设。**真要触到那一天，主机会被拖进 swap，**两个 Web worker 和元数据库会一起遭殃**——本来只是"元数据审核这一个功能坏了"，会变成"整站不可用"。这次修复的初衷是止损，护栏本身反倒成了更大的风险源。我要求改成 1024 MiB，并且部署时读一下机器实际内存，超过 25% 就拒绝启动。

**另外两条建议，一条要您拿个主意。**

方案为了让老接口"看起来还跟以前一样"，专门建了一套兼容机制——子进程额外生成一份兼容格式的结果文件、Web 再流式包装发出去，还带两条专属的失败分支。**问题是：这个老接口唯一已知的使用者就是本项目的前端，而前端在同一个版本里已经被改成新流程了。**方案自己也写了"新接口是主验收路径，老接口另列兼容测试"——复杂度最高、测试最弱，这种组合最容易出事。

**所以想请您确认一件事：除了咱们自己的前端，还有没有别人在调这个接口？**（运维脚本、别的系统、定时任务都算。）如果没有，建议直接砍掉这一整套兼容包装，老接口返回一个任务号就行，本次改动的爆炸半径能明显收窄；如果有，那就保留，但必须跟新接口一样严格验收，不能降级测试。

最后一条：**杀进程的真正机制，到现在还没人证实。**我读了 uvicorn 的源码，确认它确实有"5 秒不应答就 SIGKILL"这条路径，跟现场"进程静默消失、没有堆栈、没有 OOM 记录"完全对得上。但我实测到 1600 表，心跳最大只停顿 0.7 秒，离 5 秒还远——也就是说这个机制在 6000 表下**可能**发生，但没被证实过。

所以我建议把两块改动拆开交付：**先上那个算法修复**（小、可证、能独立回滚），拿到内网去跑一次 6000 表。**这一跑本身就是决定性实验**——过了，说明就是内存问题，剩下那套任务执行架构是加固，可以从容做；还是死，说明另有原因，而这个结论会直接决定那套架构是不是对症。不然一次上两大块，万一还是不行，我们连是哪一块没解决都分不出来。
