## 3. 尚未关闭 / 未覆盖项

### 3.1 D-04（P3，开放）幽灵 ACCEPTED 任务不在槽时，前端两个按钮同时禁用

**现状核实（本轮）**：造一个 120 秒前受理、从未被认领且**未被槽引用**的 ACCEPTED 残留 →
`reclaim_stale_accepted(30)` 返回 `None`，状态仍为 ACCEPTED → **未被回收，D-04 仍存在**。
证据：`probe-d04.json`；前端表现见上一轮 `s17_phantom_accepted.json` / `d-s17-phantom-accepted.png`
（任务卡常驻"执行中"、两个按钮同时禁用，用户无法自救）。

**为何我判断不构成发布阻断**：
1. 触发需要"任务状态非终态但唯一槽已不指向它"的**不一致残留**；
2. 我逐分支核对 `_run_job`：`rss_exceeded / cancelled / timed_out / PUBLISHED / FAILED / 非零退出`
   六条路径都会先落终态；`cleanup_ok=False` 走 `RECOVERY_REQUIRED` 且**不释放槽**；
   未发现正常流转可产生该组合的路径；
3. 该状态在既往版本留下的历史残留中才可能出现，且**只影响在线元数据审核一个页面**，
   不影响审核规则、慢 SQL、大表、巡检等其它模块。

**发布前建议（二选一或都做，成本极低）**：
- **发布说明**"已知问题"列出 D-04，并附运维只读自检（见下）；
- 若希望发布前彻底消除，可让 Q 按 `docs/RETEST-…-D.md` §6.1 的方案补第二条回收分支
  （仅在**未被槽引用**且超期的 ACCEPTED 上动作；`claim_next_accepted` 只从槽取任务，
  故不会误杀在跑任务），并补 `test_unreferenced_stale_accepted_reclaimed`。

**运维只读自检 SQL（发布后巡检用，不改数据）**：

```sql
-- ① 是否存在非终态残留
SELECT id, state, phase, created_at FROM metadata_audit_jobs
 WHERE state NOT IN ('SUCCEEDED','FAILED','CANCELLED') ORDER BY created_at;
-- ② 唯一受理槽当前归属
SELECT active_job_id, accepting, runner_heartbeat_at FROM metadata_audit_slot WHERE id = 1;
```

判读：若 ① 有行而 ② 的 `active_job_id` 为空 → 命中 D-04；处置方式为人工将该行置
`FAILED`（保留 `finished_at`）或升级到修复版本，**不要**直接清 `active_job_id`（会掩盖占用）。
