## 2. A-P1-01：业务库枚举只放宽了一半，另一条路径原样保留旧行为

### 2.1 系统里有两处业务库枚举，这版只改了一处

| 位置 | 用途 | v1.6.0.5 是否放宽 |
|---|---|---|
| `backend/services/zk_scan_enrich_service._list_business_databases` | **扫描期富集** | ✅ 已改为 ≥1 成功 |
| `backend/services/zk_connection_import_service._list_business_databases` | **导入预检兜底** | ❌ **原封未动**，仍是任一 Proxy 失败即 `BUSINESS_PROXY_INCOMPLETE` |

`git show --stat 3d85ced` 里 **没有 `zk_connection_import_service.py`**，这一点直接可查。

导入预检的取库顺序是：

```
手工填写 manual_dbs  >  扫描富集结果 business_dbs  >  自带枚举（未放宽的那条）
```

所以只要**富集没产出结果**，就会落到未放宽的那条上。落到那条的现实情形至少有三种：

1. 管理员在「扫描期富集（可选）」里**关掉了「启用富集」**（`enrich_enabled=0`，配置页上就有这个开关）；
2. 富集整体异常被兜底吞掉（日志 `ZK_ENRICH_ABORTED`）；
3. 某实例富集时全部 Proxy 都没通，`business_dbs` 为空。

### 2.2 端到端实测（不是读代码得出的结论）

我用**真实 shell 驱动 + 真实 MariaDB** 搭了一个可发现的 ZK 拓扑，Proxy 刻意做成内网那种"主活备死"：

```
set_uat_c1   Proxy = 127.0.0.1:13306(真实可连) + 127.0.0.1:19999(无人监听)   ← 内网症状
set_uat_c2   Proxy = 127.0.0.1:13306(真实可连)                                ← 对照组
```

同一套拓扑，只切「启用富集」开关：

```
【A】富集开启 —— 走已放宽的那条
    set_uat_c1: 29 行 status={'ready'}  source={'proxy_show'}
    set_uat_c2: 29 行 status={'ready'}  source={'proxy_show'}
  ✅ 主活备死实例(c1) 可正常生成候选
  ✅ 对照实例(c2) 同样正常

【B】富集关闭 —— 落到导入预检自带的枚举兜底
    发现项 business_dbs: {'set_uat_c1': 0, 'set_uat_c2': 0}
    set_uat_c1: 1 行 status={'error'}  failure={'BUSINESS_PROXY_INCOMPLETE'}
    set_uat_c2: 29 行 status={'ready'} failure=无
  ✅ ★主活备死实例(c1) 在此路径仍整实例失败
  ✅ 对照实例(c2，单 Proxy 全活) 正常生成候选
```

**对照组 c2 正常、只有多 Proxy 的 c1 挂掉**，排除了环境因素。这就是内网原来那个症状，一模一样。

单元层面的 A/B 也一致（同一组端点分别驱动两个实现）：

```
【2】主活备死
  ✅ A(富集) 已放宽：≥1 成功即返回业务库 — source=proxy_show 库数=28
  ❌ B(导入预检) 是否同样放宽 — code=BUSINESS_PROXY_INCOMPLETE 库数=0
```

### 2.3 放宽方向本身是对的

先说清楚：**Q 把"全部成功"改成"≥1 成功 + 不一致取并集"这个方向我认为是对的**，符合规约 R-15 失败非对称——

- 取**并集**：多算了库 → 用户在预览里看得见、可以不勾 → **可见的错误**；
- 取**交集/整实例失败**：漏掉库 → 用户根本不知道少了什么 → **不可见的错误**。

宁可多给、不可少给。所以我不建议把富集那条改回去，而是**把导入预检那条也改成同样口径**。

### 2.4 修复建议

把 `zk_connection_import_service._list_business_databases` 的口径对齐富集侧：

```python
# 逐端点捕获异常，不再 raise
catalogues, failed = [], 0
for host, port in endpoints:
    try:
        ...  # SHOW DATABASES
        catalogues.append(...)
    except Exception as exc:
        failed += 1
        logger.warning("ZK_IMPORT_BUSINESS_PROXY_FAILED instance=%s endpoint=%s:%s error_type=%s", ...)
if not catalogues:
    raise ZKImportPreparationError("NO_AVAILABLE_PROXY", "全部 Proxy 均无法枚举业务库")
union = set().union(*catalogues)
if not union:
    raise ZKImportPreparationError("NO_BUSINESS_DATABASE", "未发现可导入的业务库")
return sorted(union, ...), ("proxy_show_partial" if failed or 目录不一致 else "proxy_show")
```

**必补的反向鉴别用例（R-12）**：`enrich_enabled=0` + 双 Proxy 其一不可达 → 预检必须仍产出候选行，且 `databases_source` 带降级标记。Q 现有的 `tests/test_zk_v1605.py` 三条用例**全部只覆盖富集侧**，一条也没打到导入预检那条路径上——这正是这个半修没被自测发现的原因。

## 3. A-P1-02：全新部署存不上 ZK 发现配置（历史缺陷，v1.6.0.3 引入）

### 3.1 现象

浏览器里按页面必填项（ZK 服务地址 + 认证用户名 + 认证口令）如实填好，点「保存配置」，弹出红色失败提示：

> **保存 ZK 发现配置失败**

页面上**没有任何一处指出是哪个字段的问题**。截图见 `docs/` 同批附图说明；后端访问日志：

```
[3b930b5f2d5f4c53] admin PUT /api/v1/tdsql/discover/config 422 5ms
```

### 3.2 根因：可选字段留空传了 `null`，模型只收 `int`

- 前端 `frontend/static/js/app.js:188`：`monitor_port:null`（`el-input-number` 空值就是 `null`）
- 后端 `backend/api/zk_discovery.py`：`monitor_port: int = Field(0, ge=0, le=65535)`

Pydantic 的默认值只在**字段缺失**时生效，**显式传 `null` 一律拒绝**。直接打接口复现：

```
=== monitor_port=null（前端默认值）===
{"detail":[{"type":"int_type","loc":["body","monitor_port"],
            "msg":"Input should be a valid integer","input":null}]}
HTTP 422

=== monitor_port=0 ===
HTTP 200，保存成功
```

而 MonitorDB 那一整段在页面上写的是「**扫描期富集（可选）**」——**页面说可选，后端却必填，而且不填就整份配置存不上。**

### 3.3 为什么提示这么没用

`frontend/static/js/app.js:7` 的 `responseMessage()` 只认 `detail` 是**字符串**的情况；FastAPI 校验错误的 `detail` 是**数组**，于是直接落到兜底文案。运维看到的永远是那句没有指向的"保存 ZK 发现配置失败"。

### 3.4 影响面

- **全新部署**（内网新站点、或重建库）**只要不填 MonitorDB 端口就一次都存不上**，ZK 自动发现整条链路无法启用；
- 已存过配置的老站点，端口已有数值，改其他项时会连着原值一起提交，**暂时看不出问题**——所以内网 1.6.0.3/0.4 一路没暴露；
- 管理员**主动清空端口以关闭富集**时，同样卡死。

### 3.5 修复建议（两处都建议改）

1. **后端**（根治）：`monitor_port: int = Field(0, ge=0, le=65535)` → 允许 `None` 并归一为 0：

   ```python
   monitor_port: Optional[int] = Field(0, ge=0, le=65535)
   @field_validator("monitor_port", mode="before")
   def _null_port_as_zero(cls, v):
       return 0 if v in (None, "") else v
   ```

2. **前端**：`monitor_port:null` → `monitor_port:0`，并让 `responseMessage()` 能渲染 FastAPI 的数组型 `detail`（取第一条的 `loc` + `msg`），否则以后任何 422 都是这句无指向的话。

**补用例**：只填三项必填、可选段全空 → `PUT /config` 必须 200。

## 4. A-P1-03：shell 驱动静默丢弃**全部分布式实例**（v1.6.0.1 引入的回归）

### 4.1 实测

拿真实 shell 驱动跑我搭的拓扑（1 个 group + 2 个 noshard）：

```
[2026-08-05 03:45:51] 共发现 3 个实例 (noshard 2 + groupshard 1)
[INFO] 解析 setrun JSON: 2 条
[INFO] 输出 2 个实例
set_uat_c1,...,noshard,set_uat_c1,...
set_uat_c2,...,noshard,set_uat_c2,...
```

**脚本自己刚打印"groupshard 1"，输出里一个分布式实例都没有，而且没有任何 WARN。** 产品侧同样：

```
is_mock: False  条数: 2
  set_uat_c1  kind=noshard  ...
  set_uat_c2  kind=noshard  ...
分布式(groupshard)条数: 0
```

### 4.2 根因：一个 `%` 与 `%%` 之差

`deploy/tdsql_inventory.sh:475`

```bash
gid="${entry%|*}"      # ← 只剥掉最后一段
```

`_group_repr_set` 的每行在 **v1.6.0.1（`8abc29a`）** 由两字段扩成三字段：

```
group_id|repr_set_id            →  group_id|repr_set_id|all_set_ids
```

两字段时 `${entry%|*}` 恰好等价于 `${entry%%|*}`，是对的；扩到三字段后就错了：

```
entry       = group_uat_1|set_uat_d1|set_uat_d1;set_uat_d2
${entry%|*}   -> group_uat_1|set_uat_d1     ← 实际取到的（错）
${entry%%|*}  -> group_uat_1                ← 应该取到的
```

`gid` 里混进一个 `|`，拼出来的记录变成 **7 个字段**（约定是 5 个），于是：

- bash 侧 `IFS='|' read -r kind iid parent set_id _set_list` 错位，生成的 ZK 命令是
  `get set_uat_d1/setrun@/tdsqlzk/group_uat_1`（`bash -x` 实测原文），必然取不到节点；
- Python 侧 `if len(parts) != 5: continue` 直接跳过，**连 WARN 都不打**。

同一提交里改了 `repr_sid`/`all_set_ids` 的取法，**唯独漏了 `gid` 这一行**。

### 4.3 影响面

- 只影响 `driver=shell`（配置页上写的是"shell（兼容旧 zkCli）"），**默认的 kazoo 驱动不走这个脚本，不受影响**；
- 一旦用了 shell，**分布式实例 100% 全丢**，而"共发现 N 个实例 (noshard X + groupshard Y)"那行日志照常报 groupshard 的数量——**日志和结果对不上，且失败完全不可见**；
- 我从第一轮 ZK 分析起就一直请内网记录的正是这行日志。**如果内网当时用的是 shell 驱动，那行日志会显示有 groupshard，实际清单里却一个也没有**——请内网按 §7 核对一次。

### 4.4 修复

```bash
-    gid="${entry%|*}"
+    gid="${entry%%|*}"
```

**必补用例**：给 `tdsql_inventory.sh` 造一个含 group 的替身 zkCli，断言输出的 CSV 里 `instance_kind=groupshard` 的行数与日志里的 groupshard 计数一致（**计数与输出对账**，光断言"有输出"抓不到这个 bug）。

## 5. A-P2-01 / A-P3-01：降级不可见、"主 Proxy 优先"未实现

### 5.1 A-P2-01：备 Proxy 挂了，用户无从知道

```
【3】标记粒度：主活备死 vs 双活，source 能否区分？
  ❌ 降级(备死) 与 全成功 的 source 可区分 — 双活=proxy_show / 主活备死=proxy_show
```

端到端也一致（c1 有一个 Proxy 是死的，c2 全活）：

```
  set_uat_c1  proxies=2  dbs=29  databases_source='proxy_show'
  set_uat_c2  proxies=1  dbs=29  databases_source='proxy_show'
```

现在只有"多个 Proxy 都成功但目录不一致"才给 `proxy_show_partial`；**而"备 Proxy 直接连不上"——也就是 Q 这版要修的那个场景本身——反倒没有任何降级标记**。唯一痕迹是后端一条 `ZK_ENRICH_PROXY_FAILED` WARNING 日志。

更彻底一点：`grep -rn "databases_source" frontend/` **一条都搜不到**——这个字段**前端从头到尾就没展示过**，发现列表和导入预览都只展示 `name_source`。所以就算给了 `proxy_show_partial`，运维在页面上也看不见。

**这不是漏改，是 Q 有意为之**：`tests/test_zk_v1605.py::test_list_business_databases_one_proxy_down_still_succeeds` 明确断言了 `source == "proxy_show"`。但我认为这个取舍不合适——**"我用一个 Proxy 的目录代表了整个实例"这件事，用户有权知道**，否则备 Proxy 上多出来的库会被静默漏掉，而漏掉的东西是看不见的（R-15）。

**建议（改动很小）**：

1. `failed > 0` 时一律返回 `proxy_show_partial`（一行判断）；
2. 发现列表与导入预览的「业务库」列，`databases_source` 为 `*_partial` 时挂一个 `el-tag`（如"部分 Proxy"），tooltip 写明"N 个 Proxy 中 M 个未响应，列表可能不全"。

### 5.2 A-P3-01：发布说明写的"主 Proxy 优先"，代码里没有

发布说明与 `_list_business_databases` 的新文档串都写着"端点顺序由 `_proxy_endpoints` 保证主 Proxy 在最前（已知可达优先）"，但 `_proxy_endpoints` **这版根本没改**（diff 可查），且实现是：

```python
if primary not in raw and item.get("host"):
    raw.insert(0, primary)      # 只在 proxy_list 里【没有】主 Proxy 时才插到最前
```

而 ZK 返回的 `proxy_list` 里**本来就含主 Proxy**（`tdsql_inventory.sh` 是 `sorted(set(全部网关))`），所以走的是"已存在→不动"分支，顺序就是排序后的顺序。实测：

```
【5】端点顺序：主 Proxy 必须排在最前
  ❌ 主 Proxy 在首位 — [('10.0.0.7', 15005), ('10.0.0.9', 15005), ('10.0.0.8', 15005)]
     （item.host=10.0.0.9，排在第 2 位）
```

放宽成"≥1 成功"之后顺序不再影响**正确性**，只影响**耗时**（死 Proxy 排前面就要先等一轮 3s 超时）。所以我按 P3 记，但**发布说明里的这句话要么改代码要么删掉**——规约 R-11，没量过的效果不能写成已实现。

修法一行：

```python
raw = [p for p in raw if p != primary]
if item.get("host"):
    raw.insert(0, primary)
```

## 6. 复测通过的部分

### 6.1 Fix②　会话/预览改存元数据库（多 worker 410）——🟢 12/12

服务按**生产形态** `uvicorn --workers 2` 起（`ss -ltnp` 确认端口上确实有 2 个 worker 进程共享监听）。

我没有采用"多打几次没出 410"这种证据——那可能只是恰好都落在同一个 worker 上。**决定性判据是：从进程外直接往元数据库里塞一条会话，任何 worker 内存里都没有它；接口若能读到，就只可能来自库。**

```
【1】决定性证据 — 从进程外直接写库注入会话，接口必须能读到
  ✅ 进程外注入的会话未被判为 410（说明会话来自库而非内存） — HTTP 500
  ✅ 请求进入了真实预检逻辑（非 404/422 参数问题）

【2】内网症状回归 — 同一会话连打 40 次，410 必须为 0
    状态码分布: {409: 40}
  ✅ 40 次请求 0 次 410
  ✅ 全部命中 Mock 禁止预检的 409（会话每次都被找到）

【3】反向鉴别 R-12 — 过期会话必须仍报 410
  ✅ 已过期会话仍返回 410     ✅ 过期会话行被顺带清理

【4】反向鉴别 R-12 — 他人会话必须 403          ✅
【5】反向鉴别 R-16 — Mock 会话必须 409          ✅

【6】预览存储 — 跨 worker 可读 + 口令密文落库
  ✅ business/monitor 口令未以明文落库 — 密文样本=gAAAAABqcq20HwoDjzqRh7qrXRbb…
  ✅ 密文可正确解密回原值
  ✅ 进程外注入的预览未被判为 410（预览同样来自库）

【7】反向鉴别 — 预览过期必须 410               ✅
```

第 3~5、7 组反向鉴别是必要的：**"永远不再 410"也可能是把校验删掉了**，必须证明该 410 的时候仍然 410。结果是该拒的都拒了。

顺带一提，这次改动把口令从**进程内存明文**变成了**库里 Fernet 密文**，安全性是往好的方向走的。

### 6.2 Fix③　关导入弹窗清勾选与预览——🟢 真实浏览器 8/8（另 1 项是我的断言写错）

为了真正点到这条路径，我搭了**非 Mock 的真实发现会话**（Mock 结果在前端就被"Mock 发现结果禁止导入"挡掉了，走不到导入弹窗）：

```
  ✅ 发现列表有数据可勾选 — 2 行
  ✅ 未勾选时导入按钮为灰（禁用）
  ✅ 勾选 2 条生效
  ✅ 勾选后导入按钮变为可用
  ✅ 导入弹窗已打开
  ✅ ★关闭导入弹窗后表格勾选被清空 — 残留勾选 0 条
  ✅ ★关闭后导入按钮重新变灰（旧选择未被复用）
  ✅ 清空后可正常重新勾选（未把功能清死）
```
