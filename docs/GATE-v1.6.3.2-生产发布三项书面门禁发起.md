## 0. 为什么开工就发起

设计 §12 明确：v1.6.3.2 生产发布仍有**三项书面门禁**，任何一项未确认都**不影响开发和测试**，但**不得发布相关规则行为到生产**。

A 在开工叮嘱中指出：v1.6.3.0 的教训是"这类书面确认最容易卡在最后一公里"。因此本单在编码开工当日即发起，把责任方、验证方法、确认栏一次性摆到台面，避免开发/测试全部完成后再临时找人签字导致的发布延误。

**回填说明**：每项门禁的"书面确认栏"由对应责任方填写结论（接受/不接受）、姓名、日期；不接受时必须写明替代处置（如缩小发布范围、另立课题）。本单随发布记录一并归档。

## GATE-1：目标分布式实例的 UPDATE/DELETE LIMIT 版本前提

| 项 | 内容 |
|---|---|
| 关联规则 | R058（UPDATE/DELETE 无 LIMIT 或 LIMIT 过大） |
| 本版变化 | LIMIT 行数上限由 1000 提升至 **2000**；判定由"全文关键字"改为**结构化读取** `parsed.dml_limit`（present / row_count / offset / parameterized / verifiable） |
| 设计依据 | §4.6、RISK-07（旧引擎版本不支持全局 DML LIMIT）、§11 发布顺序步骤 3、UAT-07 |
| 门禁内容 | R058 的结构化 LIMIT 判定以"目标 TDSQL 分布式实例引擎版本支持全局 DML LIMIT 语义"为前提。若目标实例版本不支持或行为与公开文档不一致，R058 的判定口径与上边界须重新评估 |
| 责任方 | DBA + 内网运维（对目标实例做只读语法验证）；必要时取原厂书面结论 |
| 验证方法 | 在**目标分布式实例**只读验证 `UPDATE/DELETE ... LIMIT row_count`、`LIMIT row_count OFFSET`（非法）、`LIMIT offset,row_count` 的实际支持与行为；记录实例版本号；以目标实例实测 + 原厂定版为准（设计 §14：不得用宽松全文正则绕过版本差异） |
| 未确认处置 | 不得发布 R058 相关行为到生产；开发与测试可继续 |

## GATE-2：DBA 接受 R030/R032 改域后集中式对象类型零覆盖

| 项 | 内容 |
|---|---|
| 关联规则 | R030（禁视图/存储过程/触发器/函数）、R032（临时表规范） |
| 本版变化 | 两条规则 `instance_scope` 由 **ALL 改为 DISTRIBUTED**（仅分布式适用） |
| 设计依据 | §4.3、§4.4、RISK-16、§10（零覆盖边界锁定）、§11 发布顺序步骤 4、§13 完成定义 |
| 门禁内容 | 改域后，**集中式实例**对以下对象类型变为**零规则覆盖**：视图 / 存储过程 / 触发器（原 R030 治理）、临时表（原 R032 治理）。**自定义函数仍有 R031 覆盖，不属于零覆盖**（R031 本版未改域，OUT-01 回归锁）。这是需求清单的明确结果，不得用 R031 对函数的残余覆盖掩盖其他对象缺口 |
| 责任方 | DBA（集中式实例对象类型治理需求方） |
| 验证方法 | DBA 审阅集中式实例是否仍需对视图/存储过程/触发器/临时表做规则治理；确认接受"集中式零覆盖"边界，或提出保留需求（触发另行评审，不得由实施方顺手改 R031） |
| 未确认处置 | 不得发布 R030/R032 改域到生产；开发与测试可继续（已用 test_instance_scope_rules.py、test_rules_v1632.py 锁定零覆盖边界） |
