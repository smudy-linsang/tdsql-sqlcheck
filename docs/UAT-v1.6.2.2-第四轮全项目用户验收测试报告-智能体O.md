## 五、缺陷明细与整改建议

### O-14（BLOCK）：解析错误的残缺 VIEW 在 CR 注释边界绿色通过

**复现输入：**

```sql
-- ordinary\rCREATE VIEW v AS SELECT 1 +
```

这里的 `\r` 是一个真实回车字符，不是两个可见字符。

**实测结果：**

- 解析器明确返回 `parse_error=Required keyword: 'expression' missing... Line 2`。
- 审核结果 `fired=[]`、`passed=true`。
- 第三轮同一输入会产生 `E999_SYNTAX_ERROR`，因此这是 Q 本次语句头改造引入的回归。
- 上传入口把该文件拆成 0 条语句，返回 `total_sql=0`，也没有把异常文件判失败。

**发生原因：**

`_lex_head_words()` 使用 sqlglot 词法器后，把 `\r` 识别成换行并得到 `CREATE VIEW` 语句头；`checker.py` 随后只凭语句头把全部解析错误归入 VIEW 豁免，跳过 E999。与此同时，解析结果的 `sql_type` 在这条边界上仍是 `UNKNOWN`，R030 也没有兜底，于是最终没有任何违规，形成绿色通过。

**处理机制建议：**

1. 在所有入口统一做通用换行规范化：先把 `\r\n`、单独 `\r` 统一为 `\n`，再交给拆句、解析和语句头判断；三个组件必须使用同一份规范化文本。
2. 增加硬性失败关闭不变量：非 KFN 的 `parse_error` 不能因为“像 VIEW/PROCEDURE/LOAD”就直接消失。至少保证 `parse_error` 存在时最终必有一个 ERROR 级阻断项。
3. 对确需兼容而解析器暂不支持的 TDSQL 语法，应进入显式 KFN/unsupported 合同并阻断或人工确认，不允许用宽泛语句头豁免变成 PASS。
4. 增加 LF、CRLF、单 CR、末尾无换行、前导空语句、字符串诱饵、反引号诱饵的即时/文件/上传三入口测试，并断言“解析错误绝不绿色”。

**验收标准：** 上述输入在三版本、三入口都不得 `passed=true`；文件入口不得以 0 条成功结束。

### O-15（BLOCK）：网关报告仍无法打开，并引入存储型脚本注入通道

**用户侧实测：**

管理员点击“深度诊断 → 网关日志分析 → 查看报告”后，抽屉中的 iframe 显示“127.0.0.1 拒绝了我们的连接请求”，报告正文和交互控件全部不可用。

**第一层原因——嵌入策略互相冲突：**

- 前端 iframe 使用 `sandbox="allow-scripts"`，没有 `allow-same-origin`，因此子文档被置为不透明源。
- 响应同时发送 `X-Frame-Options: SAMEORIGIN`。
- Chromium 在该组合下拒绝加载；源码注释所声称的“同源可嵌入”与实际浏览器行为不一致。

**第二层原因——不能直接放宽 sandbox：**

- 分析器把日志 SQL 原样装入 `flame_data`，再用普通 `json.dumps()` 写进 `<script>`。
- `json.dumps()` 不会把 `<` 转为 `\u003c`，日志 SQL 中的 `</script>` 能提前结束脚本元素。
- 本轮合成日志已在持久化 HTML 中形成完整的 `</script><script>...` 断点。
- 报告响应又放开 `script-src 'unsafe-inline'`。因此，若简单加入 `allow-same-origin` 或移除当前阻断而不先处理数据上下文，恶意日志内容可在查看报告时执行脚本。

**处理机制建议（顺序不可颠倒）：**

1. 先修数据到脚本上下文的编码。推荐把交互脚本移到固定外部 JS，把数据放入结构化 JSON 容器；序列化时至少把 `<`、`>`、`&`、U+2028、U+2029 转成 Unicode 转义。不能只做 HTML 实体编码，也不能只包在 `type=application/json` 的 script 中而不转义 `<`。
2. 去掉 `script-src 'unsafe-inline'`，使用固定外部脚本或响应级随机 nonce；所有脚本必须受同一 CSP 管理。
3. 在完成脚本上下文安全后，再统一 iframe 策略。建议保留不透明源 sandbox，删除与之冲突的 XFO，使用 `frame-ancestors 'self'` 控制嵌入；如果技术上必须 `allow-same-origin`，则应把报告部署到独立受限 origin，不能和主应用共享高权限同源环境。
4. 报告认证不要把长期令牌放进可见 URL；优先使用短时一次性报告票据或同源 HttpOnly 会话。
5. 加入真实 Chromium 测试：普通报告可见、折叠/时间范围/火焰图可操作、父页面不受影响；包含 `</script>`、`<img onerror>`、引号、反斜杠、U+2028/U+2029 的日志均不能执行合成标记脚本。

**验收标准：** iframe 正常显示且交互可用；CSP 不含 `unsafe-inline`；恶意合成标记在 DOM 中不执行；父页面 DOM 和认证信息不可达。

### O-16（MAJOR）：巡检全失败后仍展示上一组成功比对结果

**真实点击复现：**

1. 对 `2026-08-26/27` 生成成功比对，页面显示 13 条 `uat-node` 指标。
2. 日期切换为 `2026-08-28/29`，点击手动采集；两天均因 monitordb 不可用失败。
3. 页面顶部正确显示新日期失败消息，但下方仍保留旧日期的 13 条比对结果。

这会让用户把旧数据误认为本次失败日期的结果，是比“错误成功提示”更隐蔽的数据时效性问题。

**发生原因：** `runDailyInspect()` 在新任务开始、全部失败和异常分支都没有清空 `dailyCompareResult`、趋势数据和图表节点；`compareDailyInspect()` 的失败分支也只提示错误，不清理旧结果。

**处理机制建议：**

- 任务开始时先把旧结果移动到明确的“历史结果”区域或立即清空 `dailyCompareResult`、`dailyInspectChartData`、节点/IP 筛选和分页。
- 更稳妥的做法是给结果绑定 `{connection_id,date1,date2,generated_at,status}`，模板只有在结果范围和当前选择完全一致且状态成功时才显示。
- 全部失败、比较失败、切换实例、切换日期范围时统一执行 `resetDailyResult()`。
- 增加“先成功、后失败”的浏览器回归测试，不能只测一个全失败的空白初始页面。

### O-17（MAJOR）：混合网关日志静默丢行并按完整报告展示

**实测输入：** 3 行，其中 1 行有效、2 行无效。

**实测结果：** HTTP 200、`total_queries=1`，报告成功入库；响应和页面均不显示输入 3 行、跳过 2 行、跳过比例或原因。用户无法知道报告只覆盖了三分之一输入。

**发生原因：** 服务只累加成功解析的查询数；O-11 仅在 `total_queries==0` 时失败，没有记录 `nonempty_lines`、`parsed_lines`、`skipped_lines` 和原因。

**处理机制建议：**

- 解析器返回结构化质量统计：总行、空行、有效行、无效格式、无 timecost、数值错误、首个若干错误样例。
- 全无效继续 422；混合输入返回 `partial` 状态并在报告顶部显示醒目数据完整性告警。
- 对跳过比例设置可配置阈值；超过阈值时 422 或要求用户确认后才能生成报告。
- 健康结论必须携带覆盖率，不能在存在大量跳过时给出无条件“指标正常”。

### O-18（MAJOR）：索引 PDF 的重复索引对方名称仍为 `N/A`

**实测真数据：** `idx_code` 与 `idx_code_copy` 完全相同，生产明细为：

```text
索引 idx_code 与 idx_code_copy 列完全相同(code)
```

大屏已正确统计重复索引 1 组，得分 96；但 PDF 表格的“索引B（重复）”仍显示 `N/A`，包含列也为空。

**发生原因：** 消费端正则只识别“与 xxx 完全重复”，和生产端“索引 A 与 B 列完全相同(columns)”不匹配。第三轮报告已明确指出该契约问题，本次只修了 finding_type 映射，没有修结构化明细。

**处理机制建议：**

- 根治方案：在 finding 记录中增加 `related_index_name`、`index_columns` 等结构化字段；报告层不得解析面向人的 `detail` 文案。
- 兼容存量数据时，同时识别当前生产格式和旧格式，并依据 `index_name` 选择“另一方”。
- PDF 测试必须断言 `idx_code_copy` 和 `code` 出现在导出内容中，不能只断言计数。

### O-19（MAJOR）：保存但未连接的实例运行巡检返回裸 500

**实测结果：** 对 `uat_o_offline` 调用日常巡检，响应是 HTTP 500、`text/plain Internal Server Error`；前端只能显示 `HTTP 500`，无法给出 monitordb 或连接失败的明确原因。

**发生原因：** `registry.get()` 会尝试建立数据库连接，但 API 只捕获 `ConnectionNotFoundError`。真实的连接异常发生在后续通用 `try` 之外，直接穿透为 500。

**处理机制建议：**

- 将“获取连接池 + monitor_probe + run_daily”纳入完整异常边界。
- 在连接层定义稳定的领域异常（连接拒绝、认证失败、库不存在、monitordb 不可用），API 映射为 400/422 并返回可读信息。
- 不要捕获所有异常后都降成 400；未知程序错误仍应 500 并记录 request id，避免掩盖真正缺陷。

### O-20（MINOR）：跨库 EXPLAIN 的 SQL 预处理异常仍泄漏临时连接池

**独立故障注入：** 临时池创建和连接验证成功后，让第一步 SQL 预处理抛出合成异常。结果 `pool_count=1`、`close_all=0`。

**发生原因：** 临时池在第 304 行创建，SQL 预处理从第 326 行开始，而最终 `try/finally` 到执行 EXPLAIN 附近才开始；预处理阶段不在 finally 的承重范围内。

**处理机制建议：** 临时池一经创建，立即进入覆盖“验证、预处理、执行、分析、返回”的单一 `try/finally`，或用 `ExitStack` 注册清理；保留验证失败的友好错误映射。新增预处理每一步异常注入，全部断言 `close_all()==1`。

### O-21（MINOR）：正式 `run_all.py --mode implementation --matrix` 仍返回 FAIL

**实测结果：**

- 三版本清单通过。
- release 冻结 71 项通过。
- 全量 `1450` 项通过。
- manifest 文档章节、设计包哈希通过。
- 最后 `codestat generated section mismatch`，总结果 `RESULT FAIL count=1`。

**发生原因：** implementation 模式认可新的实现包哈希后，`_generator_checks()` 仍拿“当前实现生成的 codestat”去匹配旧设计文档中的生成章节。Q 只新增了实现哈希清单，没有同步解决生成章节的审计基线，因此门禁仍自相矛盾。

**处理机制建议：**

- 不要简单跳过 codestat。实现基线清单应包含经评审的 `codestat`/manifest 生成物哈希或独立实现审计章节；门禁重新生成并与该实现基线比较。
- 或者正式把 UAT 演进后的实现反写到设计文档并更新生成章节、设计包哈希，再回到设计一致模式。
- 最终验收必须以命令退出码 0 和 `RESULT PASS` 为准，不能只看到测试项通过就宣称门禁通过。

## 六、119 条核心规则与次生灾害结论

### 6.1 能确认未被整体破坏的部分

- 当前提交与第三轮签字基线相比，1000 条核心语料结果完全一致；R054、R077、UNIQUE 注释恢复和 KFN 语料未发生整体漂移。
- 324 条解析/恢复边界结果完全一致，`kfn_without_e999=[]`。

### 6.2 不能据此宣称“119 条全部无问题”的原因

- 合成元数据不等价于真实 TDSQL 在线元数据供给；涉及真实集群元数据的规则仍需在可控 TDSQL 验收环境中验证。
