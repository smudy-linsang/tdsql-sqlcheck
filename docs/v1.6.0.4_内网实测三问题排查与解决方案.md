## 1. 问题1：业务库枚举大面积失败

### 1.1 现象
富集扫描 208 实例，名称 100% 成功，但业务库仅 47/208（22.6%）成功；161 个 `enrich_status=dbs_failed:BUSINESS_PROXY_FAILED:OperationalError`。截图大量"枚举失败"。

### 1.2 根因（已核实代码）
`zk_scan_enrich_service.py::_list_business_databases`（L36-59）对 `proxy_list` 里**每一个**端点都 `pymysql.connect`，且 `connect` 在 `try` 之外（L38-41）。**任何一个**端点连接抛 `OperationalError`（不可达/鉴权失败/超时），异常直接抛出，整实例业务库枚举失败。

分布式 group 的 `proxy_list` 有 2 个 Proxy，只要其一不可达或 `checksql` 账号在其上无权限，就整实例失败。内网大量 group 的某个 Proxy 不可达，故 161 个失败。

### 1.3 解决方案
把"全部成功"改为"至少一个成功"：
1. 逐端点 `try` 连接+`SHOW DATABASES`，**捕获**异常并记录失败端点，不抛出；
2. 收集成功的 `catalogues`；若 0 个成功 → 返回 `NO_AVAILABLE_PROXY`；
3. 多个成功时做一致性校验：一致则用之；不一致 → 取**并集**并置 `databases_source=proxy_show_partial`（或记 warning），不整实例失败；
4. 在 `enrich_status`/`business_dbs` 之外，可选地把"失败端点数"带入供 UI 提示（如"2 个 Proxy 中 1 个不可达"）。

效果：只要有一个可达 Proxy 就能枚举业务库，161 个失败将大幅回落。

### 1.4 验收
- 原 161 个失败实例中，凡有 ≥1 可达 Proxy 的应转为有业务库；
- 全部 Proxy 不可达的仍标 `NO_AVAILABLE_PROXY`（不假数据）。

## 2. 问题2：导入预览频繁"会话已过期"

### 2.1 现象
填信息生成导入预览时报"发现会话已过期，请重新扫描"，频率高，"密码输入慢一点就过期"。

### 2.2 根因（已核实代码+部署）
- 发现会话 `_sessions`、预览 `_previews` 均为**进程内 dict**（`zk_discovery.py` L42-43），TTL 10 分钟（L39）。
- 部署 `deploy/tdsql-sqlcheck.service` L13 用 `uvicorn ... --workers 2`。**两个 worker 各自持有独立 `_sessions`**。
- 扫描 POST 落在 worker A（会话存 A）；导入预览 POST 被负载均衡，约 50% 落到 worker B（无该会话）→ `_load_session_items` 判过期/缺失 → 410"发现会话已过期"。
- 因此与"输入快慢"无因果，是**worker 路由随机丢失会话**，体感"很频繁"。

### 2.3 解决方案（推荐 A）
**方案 A（推荐）：会话/预览改存元数据库，worker 无关。**
1. 新建表 `zk_discovery_sessions`（discovery_id PK、owner、expires_at、items_json、created_at）与 `zk_discovery_previews`（preview_id PK、discovery_id、owner、expires_at、rows_json、business_enc、monitor_enc）；
2. `items_json`/`rows_json` 存脱敏结构；`business`/`monitor` 口令用现有 `encrypt_password` **加密**后入库（当前内存明文，入库必须加密）；
3. `_store_session/_load_session_items/_store_preview/_load_preview` 改为读写 DB，按 expires_at 判过期，定期清理过期行；
4. 移除对进程内 `_sessions/_previews` 的依赖。

**方案 B（临时）：** 把 `--workers 2` 改 `--workers 1`。立即消除跨 worker 丢会话，但牺牲并发，仅作应急。

### 2.4 验收
- `--workers 2` 下连续"扫描→慢慢填→预览"10 次不出现 410；
- 超过 TTL（10 分钟）才报过期（符合预期）。

## 3. 问题3：关闭导入弹窗后旧库仍在预览里

### 3.1 现象
选库 A 生成预览（未导入）→ 关闭弹窗 → 选库 B 生成预览 → 预览里同时有 A 和 B。

### 3.2 根因（已核实代码）
- 发现列表勾选经 `handleZkSelection` 做**跨页合并**（保留非当前页的旧勾选），设计目的是支持跨页多选批量导入。
- 关闭**导入**弹窗（取消/X）只置 `zkImportDialogVisible=false`，**不清** `zkSelected` 与列表勾选。
- 用户再勾选 B 时，A 仍处于勾选态 → `zkSelected=[A,B]` → 预览含两者。用户心智是"关了重来"，故视为 bug。

### 3.3 解决方案
关闭导入弹窗且**未提交**时，重置发现选择，使下次选择从零开始：
1. 给发现列表表格加 ref（如 `zkDiscoveryTableRef`）；
2. 新增 `closeZkImport()`：`zkImportDialogVisible=false; zkSelected=[]; zkImportRows=[]; zkImportPreviewId='';` 并 `zkDiscoveryTableRef.clearSelection()`；
3. 导入弹窗的"取消"与右上角 X 均绑定 `closeZkImport`；**提交成功**路径保持现有清理（`openZkDiscovery` 重置）。
4. 保留跨页合并能力（多选批量导入不受影响，因为合并在"打开导入弹窗前"完成，打开后一次性预览）。

### 3.4 验收
- 选 A 预览→关闭→选 B 预览 → 预览仅 B；
- 跨页勾选 A+B 后一次打开导入 → 预览含 A+B（批量能力保留）。
