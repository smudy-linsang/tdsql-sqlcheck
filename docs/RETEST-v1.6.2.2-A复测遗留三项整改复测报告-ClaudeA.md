## 3. ⚠️ OBS-1：换了一个更宽的洞（`DEF-A-6.2-c`）

### 3.1 目标已达成

三种 CTAS 形态现在都不再被剥离：`AS SELECT` / 无 `AS` 的 CTAS / `AS (SELECT …)`。✅

### 3.2 但门控放宽的代价没有被限定住

Q 把门控改成"语句体出现 `\bselect\b` 即视为 CTAS，不剥离"，并在注释里写明
"注释内含 select 的语句被误判为 CTAS 只是回到修复前形态（保守、安全）"。

**问题是这个"回到修复前"覆盖的面比换掉的那个洞大得多。** 实测 8 种形态：

| 形态 | 剥离是否发生 | A-6.2 |
|---|---|---|
| 基准：无 select | 是 | ✅ 生效 |
| 表注释含 `'select 结果缓存'` | 否 | **❌ 失效（E999 回归）** |
| 表注释含 `'cache for select'` | 否 | **❌ 失效** |
| 列注释含 `'select 用'` | 否 | **❌ 失效** |
| 反引号列名 `` `select` `` | 否 | **❌ 失效** |
| 行注释含 `-- select 说明` | 否 | **❌ 失效** |
| 表注释 `'用于select查询'`（中文夹注，无词边界） | 是 | ✅ 生效 |
| 列名 `t_select`（无词边界） | 是 | ✅ 生效 |

**8 例中 5 例失效。** 而"英文注释里出现 select"、"列名叫 `select`"在真实 DDL 中
远比"注释里有奇数个 `\'`"常见——**这一轮换掉的洞，比补上的那个更容易被踩到。**

### 3.3 这个取舍不必要——机器已经在手上

`_strip_index_order_modifiers()` 内部已经用 `_LITERAL_OR_COMMENT_RE` 把语句切成
"字面量/注释段"与"普通代码段"。**门控只要在普通代码段里找 `select` 就行**，
两个洞可以同时关掉，没有取舍：

```python
def _code_segments(sql):
    return _LITERAL_OR_COMMENT_RE.split(sql)[0::2]   # 偶数下标 = 字面量/注释之外

# 门控
if any(re.search(r"\bselect\b", seg, re.I) for seg in _code_segments(sql)):
    return sql
```

复测该修法 **8/8 全过**：

| 应剥离（A-6.2 必须生效） | 结果 |
|---|---|
| 无 select 基准 / 表注释含 select / 列注释含 select / 反引号列名 `` `select` `` / 行注释含 select | ✅ 5/5 |

| 应保留（CTAS 不得剥离） | 结果 |
|---|---|
| `AS SELECT` / 无 `AS` 的 CTAS / `AS (SELECT …)` | ✅ 3/3 |

### 3.4 当前暴露面

真实语料 2172 张表中，含独立词 `select` 的语句 **0 条**（两库均为 0），
故本轮线上样本不受影响。与上一轮的 `\'` 一样，属**潜在洞**而非**活动洞**。

**建议**：按 §3.3 收敛（约 4 行），补 2 条用例（注释含 select 的表必须仍被剥离）后关闭 OBS-1。

## 4. ⚠️ ENV-1：方向对，但只修了一层，且底下还有更深的问题

### 4.1 修好的那一层

`_normalize_default` 现在剥一层成对外层引号，MariaDB 的 `''` 与 MySQL 8 的空串归一。✅

### 4.2 紧接着暴露的下一层：整型显示宽度

```
迁移结构验收失败 [v4_040_instance_type_scope]:
列 audit_history.skipped_rules_count 类型不符: 期望 int 实际 int(11)
```

MariaDB 保留整型显示宽度（`int(11)` / `tinyint(4)`），MySQL 8.0.19+ 已移除。

我把验收改成**收集而非抛出**，一次性穷举了全部不符项：**共 5 条，全部是这一类**
（如 `audit_history.skipped_rules_count`、`tdsql_connections.instance_type_locked`）。
在比较前对整型剥离显示宽度后，**剩余不符项归零**（已实测验证）。

建议补法：

```python
_INT_WIDTH_RE = re.compile(r"^(tinyint|smallint|mediumint|int|integer|bigint)\(\d+\)", re.I)
actual_type = _INT_WIDTH_RE.sub(lambda m: m.group(1), actual_type)
```

### 4.3 但更根本的问题在下面：MariaDB 上元数据库**根本初始化不起来**

即使把上面两层都补上，在 MariaDB 上仍然：

```
建表警告: (1005, "Can't create table `…`.`instance_gate_rules`
                 (errno: 150 \"Foreign key constraint is incorrect\")")
```
→ 部分表建不出来 → **默认账号 `admin` 没有被创建** → 全量测试出现
**236 例 `assert 401 == 200`、20 例 `Login failed for admin`** 的级联失败。

这不是迁移层的问题，是 `_create_all_tables` 的外键定义在 MariaDB 上不被接受。

### 4.4 我的判断

**ENV-1 这条，要么做完，要么明确不做。**

现在的状态是最糟的第三种：修了最表层的一个症状，让人以为"MariaDB 兼容了"，
而实际上元数据库在 MariaDB 上连初始化都完不成。

* 若内网元数据库是 **MySQL/TXSQL** → ENV-1 本来就不必修，当前改动无害但也无用，
  建议在文档里明确写"元数据库仅支持 MySQL 8/TXSQL"，把这条从缺陷列表里划掉；
* 若内网元数据库确为 **MariaDB** → 当前修复远不足以让系统跑起来，需要按
  §4.2 补类型归一 + 单独排查 errno 150 的外键定义。

**这条请你先确认内网元数据库的品类，再决定处置方向。**
