## 3. ⚠️ OBS-1：换了一个更宽的洞（`DEF-A-6.2-c`）

### 3.1 目标已达成

三种 CTAS 形态现在都不再被剥离：`AS SELECT` / 无 `AS` 的 CTAS / `AS (SELECT …)`。✅

### 3.2 但门控放宽的代价没有被限定住

Q 把门控改成"语句体出现 `\bselect\b` 即视为 CTAS，不剥离"，并在注释里写明
"注释内含 select 的语句被误判为 CTAS 只是回到修复前形态（保守、安全）"。

**问题是这个"回到修复前"覆盖的面比换掉的那个洞大得多。** 实测 8 种形态：

| 形态 | 剥离是否发生 | A-6.2 |
|---|---|---|
| 基准：无 select | 是 | ✅ 生效 |
| 表注释含 `'select 结果缓存'` | 否 | **❌ 失效（E999 回归）** |
| 表注释含 `'cache for select'` | 否 | **❌ 失效** |
| 列注释含 `'select 用'` | 否 | **❌ 失效** |
| 反引号列名 `` `select` `` | 否 | **❌ 失效** |
| 行注释含 `-- select 说明` | 否 | **❌ 失效** |
| 表注释 `'用于select查询'`（中文夹注，无词边界） | 是 | ✅ 生效 |
| 列名 `t_select`（无词边界） | 是 | ✅ 生效 |

**8 例中 5 例失效。** 而"英文注释里出现 select"、"列名叫 `select`"在真实 DDL 中
远比"注释里有奇数个 `\'`"常见——**这一轮换掉的洞，比补上的那个更容易被踩到。**

### 3.3 这个取舍不必要——机器已经在手上

`_strip_index_order_modifiers()` 内部已经用 `_LITERAL_OR_COMMENT_RE` 把语句切成
"字面量/注释段"与"普通代码段"。**门控只要在普通代码段里找 `select` 就行**，
两个洞可以同时关掉，没有取舍：

```python
def _code_segments(sql):
    return _LITERAL_OR_COMMENT_RE.split(sql)[0::2]   # 偶数下标 = 字面量/注释之外

# 门控
if any(re.search(r"\bselect\b", seg, re.I) for seg in _code_segments(sql)):
    return sql
```

复测该修法 **8/8 全过**：

| 应剥离（A-6.2 必须生效） | 结果 |
|---|---|
| 无 select 基准 / 表注释含 select / 列注释含 select / 反引号列名 `` `select` `` / 行注释含 select | ✅ 5/5 |

| 应保留（CTAS 不得剥离） | 结果 |
|---|---|
| `AS SELECT` / 无 `AS` 的 CTAS / `AS (SELECT …)` | ✅ 3/3 |

### 3.4 当前暴露面

真实语料 2172 张表中，含独立词 `select` 的语句 **0 条**（两库均为 0），
故本轮线上样本不受影响。与上一轮的 `\'` 一样，属**潜在洞**而非**活动洞**。

**建议**：按 §3.3 收敛（约 4 行），补 2 条用例（注释含 select 的表必须仍被剥离）后关闭 OBS-1。

## 4. ✅ ENV-1：经确认不适用，已关闭

### 4.1 定性

使用方 2026-08-30 明确：**内网元数据库为 TDSQL/MySQL**。
本条原本就没有实际场景——上一轮报告把它列为"环境阻断"，是因为**我的沙箱用的是
MariaDB 10.11**，而 MariaDB 从来不是本项目的部署目标。**ENV-1 关闭，不再跟踪。**

### 4.2 Q 的改动无需回退——已实测确认在 MySQL 侧为空操作

Q 让 `_normalize_default` 剥一层成对外层引号。改动已合入，需确认它在 MySQL 上是否有害。

**关键事实**：`_expected_column_spec()`（`migrator.py:96`）**期望侧本来就剥引号**
（`dv.strip("'\"")`），两侧的比较基准是"已去引号"的值；而 MySQL 8 的
`COLUMN_DEFAULT` 本就不带引号，故实际侧再剥一层是**无操作**。

逐值实测（模拟 MySQL 8 的 `COLUMN_DEFAULT` 取值，旧实现 vs 现行实现）：

| I_S 取值 | 旧实现 | 现行实现 | |
|---|---|---|---|
| `''`（空串） | `''` | `''` | 一致 |
| `0` / `1` | `FALSE` / `TRUE` | 同 | 一致 |
| `abc` / `-1` / `0.00` | 原值 | 同 | 一致 |
| `CURRENT_TIMESTAMP` | `CURRENT_TIMESTAMP` | 同 | 一致 |
| `NULL` | `None` | 同 | 一致 |
| `'quoted'`（首尾同为引号） | `'quoted'` | `quoted` | **唯一分歧** |

唯一分歧形态需要 DDL 把默认值本身写成带引号的字符串（三重单引号写法）。
实测该 DDL 的**期望侧解析结果为空串**——期望侧正则 `'[^']*'` 本就无法处理这种写法，
**该形态在 Q 改动之前就已经是错的**，属既有限制，与本次改动无关。

**全量验证**：把 `_column_info` 的返回值改写成 MySQL 8 形态后跑完整迁移验收，
**现行实现与旧实现的结构不符项均为 0**。

**结论：无害，保留即可，不必回退。**

### 4.3 建议留一条文档

既然元数据库确定只支持 MySQL 8/TDSQL，建议在部署说明里写明这一条。
理由是本轮实测顺带证明了 MariaDB 上**根本跑不起来**（不只是迁移验收）：

```
建表警告: (1005, "Can't create table `…`.`instance_gate_rules`
                 (errno: 150 "Foreign key constraint is incorrect")")
```
→ 部分表建不出来 → 默认账号 `admin` 未创建 → 大面积 401。

写明支持范围，可以让下一个人不必再花一轮去查这件事。
