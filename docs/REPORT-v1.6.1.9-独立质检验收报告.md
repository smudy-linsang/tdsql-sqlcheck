## 2. 变更全景与核心机制掌握

### 2.1 缺陷背景与根因
在 TDSQL 生产环境中，内核 `SHOW CREATE TABLE` 输出的两种官方合规语法此前未被规则引擎支持：
- **HASH 分片表**：`... TDSQL_DISTRIBUTED BY HASH(col)` ➔ 旧版 R077 仅认 `shardkey=col`，误报为“未声明分片键的单表”。
- **广播表（全局表）**：`... shardkey=noshardkey_allset` ➔ 旧版将 `noshardkey_allset` 误当做真实字段名在主键中查找，导致 R077 与 R054 双双误报。

### 2.2 核心架构设计与防护机制
在 `backend/engine/rules/distributed.py` 中构建了一套高内聚、高鲁棒性的可信表选项提取体系：

```
                              ┌──────────────────────────────┐
                              │     原始建表 DDL (raw_sql)    │
                              └──────────────┬───────────────┘
                                             │
                                             ▼
                              ┌──────────────────────────────┐
                              │      _strip_sql_noise()      │
                              │  - 剥离行/块注释(--, /* */, #) │
                              │  - 严格 MySQL -- 空格词法     │
                              │  - 剥离单双引号字符串字面量   │
                              │  - 完整保留反引号标识符       │
                              └──────────────┬───────────────┘
                                             │
                                             ▼
                              ┌──────────────────────────────┐
                              │     _ddl_options_tail()      │
                              │  - 定位列定义闭括号后的尾部   │
                              │  - 杜绝列定义/COMMENT/伪造    │
                              └──────────────┬───────────────┘
                                             │
                                             ▼
                              ┌──────────────────────────────┐
                              │    _trusted_options_tail()   │
                              │    唯一可信表选项尾部文本     │
                              └──────┬────────────────┬──────┘
                                     │                │
             ┌───────────────────────┴──┐          ┌──┴────────────────────────┐
             ▼                          ▼          ▼                           ▼
  _extract_legacy_shard_key()   _extract_tdsql_hash_key()   _is_broadcast_sentinel()
   (识别 SHARDKEY= 列名)       (识别 TDSQL_DISTRIBUTED)    (严格等值匹配 noshardkey_allset)
```

1. **词法清洗 `_strip_sql_noise`**：
   - 严格按照 MySQL 5.7/8.0 规范，`--` 后必须紧跟空白符才视为注释，有效防止 `CHECK(a--b > 0)` 被错误截断。
   - 字符串字面量处理支持 `\'`, `\"`, `''`, `""` 等转义模式。
2. **尾部锚定 `_ddl_options_tail`**：
   - 仅在列定义清单右括号之后检索分片与广播语法，彻底杜绝在字段名、字段注释中伪造分片子句的攻击（如 `COMMENT='TDSQL_DISTRIBUTED BY HASH(id)'`）。
3. **广播表哨兵精确匹配 `_is_broadcast_sentinel`**：
   - 使用 `.casefold() == "noshardkey_allset"` 精确等值匹配，拒绝前缀模糊匹配，杜绝 `noshardkey_shadow` 等变体绕过。
4. **J-3 独立索引迭代 `_iter_unique_indexes`**：
   - 产出每个唯一索引的列集合，逐个检查是否包含分片键，避免展平并集导致的语义降级。
5. **空主键集合防御**：
   - 若建表语句未声明主键且分片键不在主键中，明确判定为 J-2 违规。

## 4. 上线交付与运维告知事项核查

核对 [`docs/DELIVERY-v1.6.1.9-上线交付说明.md`](file:///c:/TDSQL_SQLCHECK/TDSQL-SQLCheck/docs/DELIVERY-v1.6.1.9-%E4%B8%8A%E7%BA%BF%E4%BA%A4%E4%BB%98%E8%AF%B4%E6%98%8E.md)，以下 4 项业务告知事项明确且完整：

1. **`#3` 显示“零违规”不代表通过全量审核**：
   - `TDSQL_DISTRIBUTED BY HASH(...)` 会导致 `sqlglot` 降级为 `Command`，因此该表的结构类规则（如 R036 缺少时间戳、R037 缺少逻辑删除、R061 索引命名）目前处于漏审状态。本次修复仅消除了分布式语法的误报，结构规则的深度解析留待 Phase 2（ADJ-1）。
2. **两处规则净收紧说明**：
   - **FIX-3b**：R054 唯一索引判定支持反引号（如 `` UNIQUE KEY `uk_code` ``），若不含分片键将新增 R054 WARNING。
   - **FIX-5**：R054 对未声明主键的表判定 J-2 失败。
   - 实测现有语料影响为 0 条，且均为 WARNING 级别。
3. **HASH 语法在 R116/R117/R118 暂未覆盖**：
   - `oracle_compat.py` 中的分片键类型/长度/NOT NULL 检查目前仅识别 `shardkey=` 语法，未覆盖 HASH 语法（已登记为 ADJ-7，Phase 2 统一治理）。
4. **Phase 2 待办缺陷跟踪**：
   - 已清晰登记 ADJ-1、ADJ-2、ADJ-3（`tdsql_connector.py:1546` 变量名未定义静默缺陷，建议优先修复）、ADJ-7、ADJ-8。
