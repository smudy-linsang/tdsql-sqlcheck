## 1. 我第一轮判错的地方（撤回）

### 1.1 【撤回】M-01 §8.5 的可执行性判据是错的 —— O 的订正必须采纳

我在裁定里写的是：「只含真实标识符、无值占位符 → `executable=true, TEXT_ONLY_CHECKED`」。
**这条错了，而且错得不轻。**

O 指出的失效路径，我复核后确认成立：模型拿不到 DEFAULT 值、分区边界、WHERE 常量，
**产出"无占位符"文本最省事的办法就是把这些子句整个删掉**。
按我那条判据，一个被删掉 `DEFAULT`/`PARTITION`/`WHERE` 的候选，
因为"没有问号"就会被标成 `executable=true`——
这恰恰是本项目最不能出的那类错：**语法合法、语义失真、还带着"已复核"的标签**。

我把两件事混成了一件：**文本完整性**（无占位符）是必要条件，
**文本复核结论**（T09 的服务端判定）是另一回事。

Rev.C §5.4 的四态闭集
`INCOMPLETE_TEMPLATE / TEXT_ONLY_CHECKED / TEXT_ONLY_REJECTED / UNKNOWN`
＋"validation 由服务端生成、模型不能自填"＋"源必要子句丢失即不得标完整"，
比我那条严格且正确。**我撤回 §8.5 第一行，以 Rev.C §5.4 为准。**

Rev.C 另外补的两条我认为也对：`executable` 只作兼容字段、UI 一律显示"可送入审核编辑器"
而非"可直接执行"；新增名称必须标 `NEW_PROPOSAL` 并校验，不冒充已存在对象。

### 1.2 【撤回】N-04 我说"闭集短语零误判成本"是错的

O 举的两句是决定性的：

> 不能据此认定已通过审核。
> 历史记录 E1 显示当次审核已通过；本轮没有重新审核。

**这两句都合法，都会被我的闭集短语规则误杀。** 而"我已经把问题处理妥当"不在闭集里，
却正是要拦的那种假执行断言。**既误拒又漏检，我那句"本来就不该出现"是想当然。**

Rev.C §8.1.1 的做法更好：结构化 `outcome_claims`（claim_type 闭集 ＋ evidence_id ＋
fact_key ＋ observed_at，模型不得自填事实值）＋ 服务端按事实卡核对对象/时间/字段后
渲染状态句 ＋ "本助手已执行"恒拒绝；字符串规则降为**附加防线**且反例必须覆盖
否定/引用/假设/历史时点。**我撤回原提法，采纳 Rev.C。**

### 1.3 【撤回】"没有实质性能次生风险"

我第一轮的论据是"内网主机 61.59 GiB 内存余量充足"。O 指出这不能证明共享 MySQL
连接/锁、CPU、磁盘和并发审核时延没有问题。**他是对的，而且这是我第二次犯同一类错**——
v1.6.3.5 第一轮我就用内存 cgroup 高水位去推主机容量，被 O 纠正过一次。

具体我漏掉的是：Copilot runner 与审核引擎**共用同一个元数据库**。
大库审核时元数据库本来就是瓶颈（结果正文就落在那儿），再叠加 2 路 Copilot 并发查询
＋ 最多 2 GiB 正文写入，不是显然免费的。**我看的是主机内存，该看的是元数据库连接池与磁盘。**
撤回该结论，以 Rev.C 保留的 P95 劣化 ≤10% 门禁为准，由实测裁决。

### 1.4 【撤回】"7 项建议都不增加新的风险面"

这句和我自己报告 §8.4 自相矛盾——我在那里专门写了方案甲放开标识符后的注入加固要求。
**需要加固就说明增加了风险面。** O 指出双人授权增加流程与账号治理成本、
标识符投影增加注入面、反馈聚合增加读取与统计口径，都成立。撤回。

### 1.5 【部分撤回】CP-1A 独立上线

O 的三条反驳，我接受两条：

  keyring 加密存储、迁移、输出治理和资源限额；**少掉的只是出域这一面。**
- 第三条"改变了 Mr.Linsang 已定的交付范围"：这是程序问题，O 不能单方采纳我的建议，
  这点他说得对；但它本来就是提给 Mr.Linsang 的**建议**，不是提给 O 的要求。

修正后的表述：**这仍是一个可以问 Mr.Linsang 的问题，但我把它降为"可选"，不再作为评审意见推进。**

## 2. B-01：O 驳倒了我的方案，但他的结论也不成立

### 2.1 我接受 O 的反驳

我第一轮说"把十一张表移出失败关闭链路就只影响助手"。**这句不成立，O 说对了。**

`copilot_subjects` 不是 Copilot 内部表——它被 §9.1 接进了**现有账户生命周期**
（create_user / delete_user / bootstrap 同事务），§11.2 还要求账户变更前先取 `copilot_runtime` 锁。
于是：

- 表缺失而仍强制写 → **账户管理本身失败**（Copilot 故障变成了另一个核心功能故障）；
- 表缺失就跳过写 → **代际身份保证失效**，后面无法分辨哪些账号被删除重建过。

两条路都不是"只影响助手"。我当时没把这层耦合想透。

### 2.2 但"因此十一张表都留在统一链路"不成立

耦合发生在 **2 张表**上，不是 11 张。我按 Rev.C §10.2 逐表点了列声明：

| 归属 | 表 | 列声明数 |
|---|---|---|
| **确有耦合** | `copilot_subjects` | 7 |
| **确有耦合** | `copilot_runtime` | 8 |
| 无耦合 | providers / scene_routes / instance_grants / sessions / previews / turns / daily_budgets / provider_attempts / audit_events | 合计约 **115** |

§10.2 自己也写着「不增业务表列，不改 audit_history/scan_snapshots 原行；
**账户创建/删除的现有服务只增加本模块 subject 生命周期事务接点**」——
也就是设计自己确认了：除 subjects（及其锁序牵出的 runtime）外，其余 9 张表与既有路径无接点。

### 2.3 我的第三方案：按耦合关系拆分

- **`copilot_subjects` ＋ `copilot_runtime` 留在统一迁移链路**（失败关闭）。
  它们确实耦合账户生命周期，O 的理由成立；而且这 2 张表结构简单
  （共 15 个列声明，无大字段、无复杂类型），预演成本低。
- **其余 9 张表移到 Copilot 自有结构验收**：失败 → `COPILOT_SCHEMA_UNAVAILABLE`，
  **助手不可用，Web 正常启动**。

**效果**：全站启动失败面从约 130 个列声明降到 15 个，**降幅约 88%**，
同时完整保留 O 坚持的代际身份保证与锁序一致性。

补充一点：如果账户变更路径上的 `copilot_runtime` 锁只是为了统一锁序防死锁，
而非功能必需，那么 runtime 也可以移出，耦合只剩 `copilot_subjects` 一张表（7 个列声明）。
**这一点由 O 判断**，我不替他改锁序设计。

### 2.4 这仍是 Mr.Linsang 的选择题，我把两个选项的代价摆平

| 选项 | 全站启动风险面 | 代价 |
|---|---|---|
| **甲：统一迁移（O 建议）** | 约 130 个列声明 | 发布门禁最重（完全同发行版预演、维护窗口、实测回退）；**迁移失败仍可能全站起不来，关开关也绕不过** |
| **乙：按耦合拆分（我建议）** | 约 15 个列声明 | 需要设计 Copilot 自有结构验收与 `COPILOT_SCHEMA_UNAVAILABLE` 降级路径；两套验收并存，发布脚本要分别处理 |

我推荐**乙**，理由是：这个工具是内网生产的合规门禁，
**"新增一个助手功能可能让审核工具整体起不来"这个风险，和助手本身的价值不对称。**
但 O 说得对——乙不是零成本，它需要补一段独立验收与降级设计。
**两条路我都能签，请 Mr.Linsang 择一后 O 补齐对应设计。**

O 在 Rev.C §10.1/§16.3 把风险写明了（"预演和回退降低风险，不能保证零停服"），
INV-02 也改成了"运行隔离"而不是全面隔离。**这个改法是诚实的，我认可**——
他没有用改写不变量来宣布风险消失。

## 4. Rev.C 新引入的问题

### 4.1 【N-08｜MINOR】M-05 的"同库近期终态"查询没有可用索引，可能长期退化为不可用

Rev.C §5.3 写：「无合适索引/查询超时则给'近期证据不可用'，**不改业务表索引**或自动扩大扫描」。

我查了 `backend/schema/v15/150_metadata_audit_jobs.sql:39-43`，现有索引只有：

```
PRIMARY KEY (id)
UNIQUE uq_metadata_job_idem (created_by, idempotency_key)
UNIQUE uq_metadata_job_report (report_id)
KEY idx_metadata_job_creator (created_by, created_at, id)
KEY idx_metadata_job_state  (state, updated_at)
```

**没有 `(connection_id, db_name, finished_at)` 或等价索引。**
而 M-05 的查询恰恰是 `WHERE connection_id=? AND db_name=? AND state IN(...) ORDER BY finished_at DESC LIMIT 3`。

我不把这条抬高，因为 `metadata_audit_jobs` 是**单槽位**表、增长很慢，
实际行数很可能只有几百到几千，全扫也在毫秒级——**所以它多半能跑通**。
但现在的状态是：**既没确认它能跑通，也没确认它跑不通**，
而设计给的唯一兜底是"不可用"。于是有两种结局都可能发生：
兜底永不触发（那这句话是多余的），或者 M-05 这个增强在生产上长期是空的。

**建议**：SIT 时按内网真实行数实测执行计划与耗时；若确认退化，
**正确处理是在 Copilot 迁移里给 `metadata_audit_jobs` 加一个二级索引**——
加索引不改变业务语义、不改列、不影响既有查询，
和 Rev.C 想避免的"改业务表"不是一回事。为了守一条自定约束而让功能长期空转不划算。

### 4.2 【N-09｜MINOR】双人复核在单管理员部署下会把方案甲永久锁死

§9.1 规定「只有一个管理员时保持未授权，可用无实例本地帮助；不设置'应急自批'旁路」。
**这个取舍我支持**——不留旁路是对的。

但要让 Mr.Linsang 知情：**如果内网实际只有一个 admin 账号，
那么实例授权和标识符授权（方案甲）永远无法启用**，
CP-F04 就只能停在别名模板模式。这不是缺陷，是制度前提；
**需要在部署手册和 CP-GATE-DATA 材料里写成明确前置条件**：
启用助手业务资料能力前，须先具备至少两名具 `copilot-admin` 的独立管理员。

未明确写死的实现细节（文件命名、验收函数组织方式）仍属 O 的设计裁量。

### 7.2 分组（写死）

**A 组：留在统一迁移链路，沿用失败关闭** —— **2 张表**

| 表 | 留在 A 组的理由 |
|---|---|
| `copilot_subjects` | §9.1 接进 create_user / delete_user / bootstrap 同事务，是账户代际身份的锚点 |
| `copilot_runtime` | §11.2 要求账户变更事务先取 runtime 锁；留在 A 组才能保住统一锁序（见 §7.6） |

**B 组：Copilot 自有结构验收，失败只降级助手** —— **9 张表**

`copilot_providers`、`copilot_scene_routes`、`copilot_instance_grants`、
`copilot_sessions`、`copilot_previews`、`copilot_turns`、`copilot_daily_budgets`、
`copilot_provider_attempts`、`copilot_audit_events`。

分组依据是 Rev.C §10.2 自己的结论——除 subject 生命周期接点外，其余表与既有路径无接点。
**B 组不得再增加任何对既有服务/既有表的写接点；一旦某表需要这种接点，它必须移入 A 组并重新评审。**

### 7.3 O 缺口一：持久身份锚点 —— 由 A 组保证，无需新增机制

`copilot_subjects` 留在失败关闭链路，因此**代际身份锚点在任何情况下都存在**。
这正是 O 坚持的那条保证，方案乙完整保留，不做任何削弱。

### 7.4 O 缺口二：故障期撤权 —— 按 subject 失效，不依赖 B 组可读

这是 O 最实的一条质疑，答案是：**撤权的权威点在 A 组，不在 B 组。**

- §9.1 已规定所有 owner 比较、授权与额度**以 `subject_id` 为准**，`username` 只是展示快照；
  `copilot_instance_grants` 的主键是 `(subject_id, connection_id)`。
- 删除账号时在 A 组把 subject 置 `REVOKED`（该事务不依赖 B 组，永远可执行）。
- 被吊销 subject **无法通过 Copilot 鉴权**（§9.1 要求每次鉴权核对 ACTIVE subject），
  因此 B 组中一切以该 subject 为键的 grant / session / turn **自然失效**。

**结论：B 组不可读期间发生的账号删除，其撤权效力不受影响；
B 组残留行是不可达的死行，不是活授权。** 这一条必须写进设计并配反例测试（§7.8 T4）。

### 7.5 O 缺口三：重建恢复 —— 对账而非恢复语义

B 组恢复可读后执行一次**对账**（不是数据恢复，因为没有数据丢失）：

1. 把 `subject.state=REVOKED` 对应的 `copilot_instance_grants` 置 `enabled=0`，
   写 `GRANT_CHANGE` 审计（operator 记为系统事件）。**这是清理不是撤权**——
   撤权在 §7.4 已经生效，此步只为管理页不显示幽灵授权。
2. 处于 `ACCEPTED/RUNNING/CANCEL_REQUESTED` 的 turn 一律标 `INTERRUPTED`，
   沿用 Rev.C §11.4 既有规则：**不自动重调模型、保守计费、释放会话**。
3. 对账在 runner 取得命名锁后、开始受理前执行；对账失败保持 `COPILOT_SCHEMA_UNAVAILABLE`，
   不得"边对账边受理"。
4. 对账只读写 `copilot_*` 自身，**不触碰任何业务表**。

### 7.6 O 缺口四：启动与锁顺序 —— 因 runtime 在 A 组而原样保留

统一锁序 `runtime(id=1) → users/subject → session → 预算 → turn` **不变**。

- 账户生命周期事务只用到前两段（runtime、users/subject），**两者都在 A 组**，
  因此 B 组不可读时账户管理完全正常——这正是把 runtime 划进 A 组的原因。
- 启动顺序不变：统一迁移（含 A 组）→ 现存 subject 补齐 → bootstrap；
  **B 组验收排在这之后**，失败只置助手不可用标志。

如果 O 复核后认为账户变更路径上的 runtime 锁并非必需（仅为防死锁的统一约定），
可以把 runtime 也移入 B 组，A 组只剩 `copilot_subjects`（7 个列声明）。
**这一点由 O 判断并在设计中说明理由，两种都可接受，但不得在没有说明的情况下改动锁序。**

### 7.7 B 组的验收与降级合同（写死）

**建表方式不放松**：B 组仍用正式迁移文件、仍进 `schema_migrations` 校验和台账、
仍做列类型/可空/默认/索引的完整结构验收（Rev.C §10.1 原文保留）。
**唯一的区别是失败后的处置**：不向上抛断 `ensure_db()`，而是置
`COPILOT_SCHEMA_UNAVAILABLE` 并继续启动。

**禁止**：用 `CREATE TABLE IF NOT EXISTS` 加宽松 try/except 充当验收。
**"DDL 跑过了"不等于"结构正确"**——必须是显式结构验收产出 `READY` / `UNAVAILABLE` 二值，
**不存在部分可用状态**（任一 B 组表验收不过即整体 UNAVAILABLE）。

**降级行为闭集**：

| 面 | B 组不可用时的行为 |
|---|---|
| Web 启动、原审核/采集/页面/原报告导出 | **完全正常**（这是方案乙的全部目的） |
| `GET /copilot/capabilities` | 200，`mode=UNAVAILABLE`、`reason_code=COPILOT_SCHEMA_UNAVAILABLE`（必须可读，否则前端无法解释） |
| `GET /copilot/help` | **仍可用**（本地知识包，不依赖 B 组） |
| 其余 `/api/v1/copilot/*`、全部 `/api/v1/copilot-admin/*` | 503 `COPILOT_SCHEMA_UNAVAILABLE` |
| runner | `runtime.accepting=false`（runtime 在 A 组可写），不领新任务 |
| 健康页 | 明确区分"未启用（可接受）"与"schema 验收失败（需处理）" |

### 7.8 必须新增的测试（B-01 专项）

| 编号 | 场景 | 断言 |
|---|---|---|
| T1 | B 组任一表缺失 / 错列类型 / 缺索引 | Web 正常启动；原审核/导出可用；Copilot 业务端点 503；`capabilities` 与 `help` 仍可读 |
