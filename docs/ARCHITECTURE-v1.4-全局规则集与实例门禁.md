## 1. 需求背景

### 1.1 触发问题

现行设计中，「项目」绑定「规则集」与「质量门禁」，且扫描时可由使用者选择项目。这带来一个**尺度可被挑选**的问题：

> 某开发人员第一次用最严的项目扫描，未按规则整改；随后改选低尺度项目再扫一次，
> 声称「我的问题变少了」。

这个结论在逻辑上不成立。扫描采集的是**事实**（这张表没有主键、这条 SQL 使用了 `SELECT *`、这张表 800GB），规则集施加的是**判断**（这算不算问题、多严重、卡不卡上线）。换规则集时事实一个没变，变的只是判断，因此「问题变少」是伪命题。

### 1.2 现状核查：该风险已在系统中实际存在

对基线代码的核查表明，问题比表述的更严重：

| 核查项 | 现状 | 位置 |
|---|---|---|
| 规则集是否影响采集 | **否**。`get_enabled_rules()` 仅按 `{rule_id: {enabled, severity_override}}` 过滤参与执行的规则，全部规则跑在同一份解析结果上 | `backend/engine/checker.py:28-45` |
| 审核历史是否记录所用规则集 | **否**。`audit_history` 只落 `project_id`，不落 `rule_set_id`；而项目的规则集可随时修改，历史报告"当时用哪把尺"事后不可复现 | `backend/services/audit_service.py:58-62` |
| 扫描结果对比是否校验尺度一致 | **否**。`validate_pair` 校验了数量、自比、存在性、模块、实例、指纹算法版本，**唯独没有规则集** | `backend/services/scan_compare_service.py` |

第三条是本次最需要重视的既有缺陷：V1.3 的扫描结果对比功能，**当前就可以把两个不同尺度下产生的快照拿来对比，并算出一个看似权威的「整改率」**。相比使用者口头声称"问题变少了"，系统自动输出的数字更具误导性。

### 1.3 决策

团队负责人综合银行实际管理方式后决策采用**提案 B**：

1. 由管理员统一配置项目与规则集，并决定启用哪一个；
2. 管理员启用某规则集后，**系统全部功能全局指向该规则集**；
3. 必须始终有且仅有一个启用中的规则集；若管理员未启用任何自建规则集，则走系统内置默认规则集；
4. 质量门禁改为**与实例绑定**，按实例配置允许的 ERROR / WARNING 数量，**默认均为 0**；
5. 「项目」与「规则集」是否合并为一个概念，由设计方按改动成本与破坏度决策。

## 2. 决策一：项目与规则集是否合并

### 2.1 结论

**不做物理合并（不合表、不迁移历史数据），但完成概念合一：规则集成为唯一的"尺度"载体，项目降级为业务标签。**

### 2.2 论证

#### 2.2.1 影响面实测

对基线代码统计 `project_id` 的引用分布：

| 层 | 规模 |
|---|---|
| 后端 | 10 个文件、约 110 处引用（`audit_service` 19、`project_service` 16、`gate_service` 13、`database` 12、`api/project` 12、`api/gitlab_hook` 11、`ruleset_service` 6、`models` 6、`api/sql_audit` 6、`api/quality_gate` 6） |
| 前端 | `app.js` 16 处、`index.html` 16 处 |
| 数据表 | 7 张表携带 `project_id` 列 |

#### 2.2.2 决定性理由：`project_id` 大量存在于**历史留痕**中

7 张表中，以下三张的 `project_id` 是**已经发生的事实记录**，不是配置：

| 表 | 性质 | 合并的代价 |
|---|---|---|
| `audit_history` | 审核历史 | 改写历史审核记录 |
| `slow_queries` | 慢 SQL 记录 | 改写历史扫描数据 |
| `gate_audit_logs` | **门禁合规痕迹** | 改写审计证据 |

银行系统中，为了"概念整洁"去改写已落库的审计记录，是不可接受的风险与收益比。若改为保留兼容映射，则又没有真正简化，反而多一层映射逻辑。

#### 2.2.3 `projects` 本就不是纯粹的规则集包装

`projects` 表除 `rule_set_id` / `gate_rule_id` 外，还承载 `tdsql_connection_id`、`gitlab_project_id`、`gitlab_url`、`project_name`、`description`、`status`——这些是业务归属与 GitLab 集成的关注点，与"尺度"无关。把它整体并入 `rule_sets` 会把不相干的字段带进去。

#### 2.2.4 改为全局后，绑定关系自然失效，无需物理合并

这是最关键的一点：

- 采用提案 B 后，`projects.rule_set_id` **不再被读取**——全局启用的规则集胜出；
- 门禁改绑实例后，`projects.gate_rule_id` 同样**不再被读取**。

也就是说，**项目对规则集与门禁的绑定关系被移除后，"两个概念指向同一件事"的问题本身就消失了**，不需要通过合表来解决。剩下的 `projects` 是一个纯粹的业务标签 + GitLab 绑定，与规则集是两件不同的事，本来也不该合并。

### 2.3 落地方式

| 动作 | 处理 |
|---|---|
| `projects.rule_set_id` / `gate_rule_id` | **停用**：保留列、标注 `DEPRECATED`、代码不再读取。不删列，避免破坏既有查询与回滚路径 |
| 历史表的 `project_id` | **原值保留**，不迁移、不改写，作为历史留痕 |
| 菜单与导航 | 「规则集」提升为一级入口（尺度的唯一来源）；「项目管理」降级为可选功能（业务标签 / GitLab 绑定） |
| 各扫描入口的 `project_id` 入参 | 进入兼容期：接受但忽略，响应中提示已废弃（详见《API-v1.4》§5） |

## 3. 决策二：全局规则集的激活机制

### 3.1 权威来源：`system_config.active_rule_set_id`

在既有 `system_config` 表（`config_key` / `config_value`）中新增一个键：

```
config_key   = 'active_rule_set_id'
config_value = <rule_sets.id>
```

**为什么不在 `rule_sets` 上加 `is_active` 列**：MySQL 不支持部分唯一索引，无法在库层保证"有且仅有一个 active"，只能靠应用层事务维护；一旦出现双写不一致（例如并发切换、或有人直接改库），系统会出现两个"启用中"的规则集，而这恰恰是本次要消灭的歧义。用单一键作为唯一真相源，**唯一性由数据结构本身保证**，无需额外约束。

列表接口仍会返回 `is_active` 字段，但它是读取时与该键比对得出的**派生值**，不落库。

### 3.2 兜底链

按以下顺序解析当前生效规则集，任一环节不满足即向下回落：

```
system_config.active_rule_set_id
   ↓ 键不存在 / 值为空 / 指向的规则集已被删除
'default'（系统内置规则集，database.py:1331 已 INSERT IGNORE 保证存在）
   ↓ 内置规则集异常缺失（不应发生）
全部规则按引擎内置默认启停与级别执行（overrides = None）
```

这满足决策第 3 条"必须始终有一个启用中的规则集"：**从解析侧保证恒有结果**，而不是靠约束禁止用户取消启用。

### 3.3 不变式

| 编号 | 不变式 | 保障方式 |
|---|---|---|
| INV-1 | 任意时刻有且仅有一个生效规则集 | 单键结构 + §3.2 兜底链 |
| INV-2 | 不提供"停用"操作，只提供"切换到另一个" | 接口层不设 deactivate 端点 |
| INV-3 | 启用中的规则集不可删除 | 删除接口前置校验，返回 409 |
| INV-4 | 内置 `default` 规则集不可删除 | 既有 `is_builtin` 校验，保持不变 |

### 3.4 生效时延（多 worker）

生产以 `--workers 2` 运行（`deploy/tdsql-sqlcheck.service:13`）。规则集解析结果需缓存（否则每条 SQL 审核都要查库），而进程内缓存在多 worker 下不会互相失效。

**设计取舍**：采用 **30 秒 TTL 的进程内缓存**，明确对外承诺「切换规则集后最长 30 秒全量生效」，不追求即时。

理由：审核不是高频到无法承受一次主键查询的场景，但逐条审核都查库仍属浪费；而追求即时生效需要跨进程失效通知或放弃缓存，代价与收益不匹配。**该时延必须写入运维手册**，避免管理员切换后立即验证、发现未生效而误判为故障。

> 此处沿用 v1.3.3 会话吊销的同类教训：进程内缓存在多 worker 下的实际语义是「最长 TTL 内生效」，对外表述必须按此口径，不得写成"即时生效"。

## 4. 决策三：质量门禁改绑实例

### 4.1 目标模型

| 维度 | 现状 | V1.4 |
|---|---|---|
| 绑定对象 | 项目（`gate_rules.project_id` 主键） | **实例**（`instance_gate_rules.connection_id` 主键） |
| ERROR 上限 | 默认 0 | 默认 **0** |
| WARNING 上限 | 默认 **-1（不限）** | 默认 **0** |
| 未配置实例 | 回落 `default` 门禁规则 | 回落系统默认（0 / 0） |

### 4.2 ⚠ 重大行为变更提示：WARNING 默认值 -1 → 0

这是本次**唯一会立即改变放行结论**的变更，必须在上线前评估：

- 现状 `max_warning_count = -1` 表示 WARNING 不限量，只要没有 ERROR 就放行；
- 改为 0 后，**任何一个 WARNING 都会导致门禁不通过**。

以基线环境的规则分布估算，WARNING 级规则覆盖面广（命名、注释、索引建议等），一次典型的元数据审核产生数十个 WARNING 是常态。若直接切换，**几乎所有实例会立即变为"门禁不通过"**。

**建议的灰度方案**（详见《DETAIL-v1.4》§7）：

| 阶段 | 做法 |
|---|---|
| 阶段一（上线时） | 存量实例迁移时**保留现行等效值**（error=0 / warning=-1），新建实例才用 0/0 默认 |
| 阶段二（观察期） | 提供 `observe` 观察模式：按 0/0 判定并记录结果，但不真正拦截，供管理员评估影响面 |
| 阶段三（收紧） | 管理员按实例逐个调整为 0/0 正式生效 |

若团队决定不做灰度、直接全量 0/0，需在发布通知中明确告知业务方，并准备好回滚开关。**该取舍请团队负责人确认**。

### 4.3 与项目门禁的关系

`gate_rules`（按项目）表保留但停用，理由同 §2.3：`gate_audit_logs` 中存有历史门禁判定记录并以 `project_id` 关联，删表会破坏合规痕迹的可追溯性。

## 5. 总体架构

### 5.1 尺度解析链路（V1.4）

```
任意扫描/审核入口
        │  （不再接受 project_id 作为尺度依据）
        ▼
ruleset_service.get_active_overrides()
        │  30s 进程内缓存
        ▼
system_config.active_rule_set_id ──► rule_set_items ──► {rule_id: {enabled, severity}}
        │  兜底链见 §3.2
        ▼
checker.get_enabled_rules(overrides)   ← 决定哪些规则参与执行、以何级别
```

### 5.2 门禁判定链路（V1.4）

```
审核完成，得到 violations
        ▼
gate_service.evaluate(violations, connection_id)
        ▼
instance_gate_rules[connection_id]  ──未配置──►  系统默认 (0 / 0)
        ▼
passed / blocked  +  写 gate_audit_logs（补记 connection_id 与 rule_set_id）
```

### 5.3 受影响的功能模块

| 模块 | 改动性质 |
|---|---|
| 即时 SQL 审核 | 尺度来源改为全局；`project_id` 入参进入兼容期 |
| 文件审核 / 上传审核 | 同上 |
| 在线元数据审核（F1） | 同上；快照补记 `rule_set_id` |
| GitLab MR 审核 | 同上 |
| 慢 SQL 扫描 | 补记 `rule_set_id`（慢 SQL 本身不走规则集，但报告需标注尺度） |
| 大表治理 | 补记 `rule_set_id` |
| 扫描结果对比（V1.3） | **新增规则集一致性校验**，不一致拒绝对比（修复 §1.2 既有缺陷） |
| 质量门禁 | 绑定对象由项目改为实例 |
| 项目管理 | 降级为业务标签，移除尺度相关字段的读取 |

## 6. 可追溯性设计（解决 §1.2 的两个既有缺陷）

本次一并修复"历史不可复现"与"跨尺度对比"两个问题：

| 措施 | 说明 |
|---|---|
| 审核记录补记 `rule_set_id` | `audit_history` 增列，落库时写入**当时生效**的规则集 ID |
| 快照补记 `rule_set_id` | `scan_snapshots` 增列，供对比时校验 |
| 报告标注尺度 | 所有 HTML 报告页眉显示"评估尺度：{规则集名称}"，使报告自解释 |
| 对比强制同尺度 | `validate_pair` 新增校验：两快照 `rule_set_id` 不一致时返回 `E4007`，拒绝对比 |

> 说明：规则集内容本身可被修改（`rule_set_items` 可编辑），因此仅记录 ID 仍不足以完全复现。完整复现需要规则集版本化（改动即产生新版本、历史版本不可变）。**本期先落 ID，版本化列为后续项**，理由是版本化会显著扩大改动面，且当前首要目标是消除"可挑选尺度"这一治理问题。

## 7. 非目标（本期不做）

| 项 | 原因 |
|---|---|
| 规则集版本化 / 不可变快照 | 改动面大，本期先解决尺度全局唯一；见 §6 说明 |
| 物理合并 projects 与 rule_sets | 见 §2 论证 |
| 删除历史表的 `project_id` 列 | 破坏历史留痕，无收益 |
| 按实例配置不同规则集 | 与"全局统一尺度"的决策直接冲突 |
| 门禁的 `required_rules` / `blocked_rules` 迁移到实例维度 | 现状使用率为零，保持原样，仅迁移数量上限 |

## 8. 风险登记

| 编号 | 风险 | 等级 | 应对 |
|---|---|---|---|
| R-1 | WARNING 上限 0 导致全量实例门禁不通过 | **高** | §4.2 灰度方案；需团队负责人确认是否直接全量 |
| R-2 | 切换规则集后最长 30 秒才全量生效，管理员误判为故障 | 中 | 界面切换成功提示中明确写出；写入运维手册 |
| R-3 | 兼容期内调用方仍传 `project_id`，误以为仍然生效 | 中 | 响应体返回 `deprecated_params` 提示；日志告警 |
| R-4 | 存量 `gate_rules`（按项目）与新表并存造成理解混乱 | 低 | 旧表标注 DEPRECATED；UI 不再展示 |
| R-5 | 历史审核记录无 `rule_set_id`，对比时无法判定同尺度 | 中 | 空值视为"未知尺度"，与任何尺度对比均给出警告而非拒绝（避免存量数据完全不可用） |
