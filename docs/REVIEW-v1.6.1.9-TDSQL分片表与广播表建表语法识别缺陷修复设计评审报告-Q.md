### 2.3 附带发现

**R118 不受影响**：R118（分片键必须 NOT NULL）有独立的 `_RE_SHARDKEY_SINGLE` 提取逻辑。实测当 SQL 被 sqlglot 正确解析时，`noshardkey_allset` 因找不到对应列而不触发 R118。仅在 sqlglot 降级为 Command（`parsed.columns` 为空）时才可能误报——这属于设计文档已识别的 **ADJ-1**（Phase 2），不在本次修复范围内。

## 3. 设计质量评审

### 3.1 优点

| 维度 | 评价 |
|---|---|
| **根因分析** | 两个缺陷（A: HASH 语法不识别；B: 哨兵当列名）定位精准，附实测证据。共同根因（"按手写 SQL 形态设计，从未按内核真实输出验证"）洞察深刻。 |
| **修复方案** | 最小侵入（1 文件、2 类、净增 ~177 行），不碰解析器/元数据/其余 117 条规则。清洗→尾部锚定→精确哨兵的纵深防御设计合理。 |
| **安全性** | 防注入考虑充分：注释伪造（X1/X2/X2b/X14-X17）、字符串伪造（X3）、无据形态（X4）、畸形值（X25）均有反向鉴别用例。 |
| **测试设计** | 41 条验收用例覆盖 P（正向合规）、N（反向鉴别）、C（对照）、X（边界反例）四类。X13（承重性断言）防止未来依赖升级悄悄激活宽松分支。 |
| **已知缺陷管理** | ADJ-1~ADJ-6 六项邻接缺陷全部有明确处置决策（关闭/Phase 2/原子变更约束），不留模糊地带。 |
| **风险与回滚** | 单文件纯增量，`git revert` 即回滚。无 schema/接口/前端变更。 |
| **施工可执行性** | §5.10 提供三个关键方法的最终状态代码（整段比对而非拼接），§12 施工检查单逐项可验证。 |

### 3.3 未发现的问题

以下方面经审查**未发现缺陷**：

- 广播哨兵精确等值（非前缀匹配）——正确
- HASH 正则只接受 `HASH`、不接受 `KEY`——正确（R-11 合规）
- HASH 列名只接受裸标识符与反引号——正确
- `_ddl_options_tail()` 尾部锚定逻辑——正确（括号配对可靠）
- R077 与 R054 共享同一可信来源——消除了"各自猜一次"的不一致风险
- J-3 逐索引判定（不展平成列并集）——正确（NJ-3 合规）
- R077 的 `或` 判定保持不动（ADJ-4 已关闭）——正确
- `BROADCAST` 快速通道不动（ADJ-6 已关闭）——正确
