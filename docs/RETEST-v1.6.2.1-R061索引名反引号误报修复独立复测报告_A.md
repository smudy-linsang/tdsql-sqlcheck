## 5. 发现的缺陷（测试资产，不阻断准出）

产品代码**零问题**。以下 2 项均在新增测试文件的 G 类用例，属"写法有瑕疵"，
**不影响当前测试结论的正确性**，但会削弱用例的证明力与可维护性。

### 5.1 【中】T-1：G1 用例丢失了"只减 R061"的核心断言，且含一行死代码

`tests/test_r061_index_name_quoting.py::test_g1_big_audit_trail`

**问题一：首行是死代码，且读错了表。**

```python
sql = _read_fixture("report_03_cus_bas_corp_contact.sql")  # ← 读的是 #3，且立刻被下一行覆盖
# 换一个真正带 idx_ 前缀反引号索引的 DDL
sql = ("CREATE TABLE `big_audit_trail` (...")
```

首行的文件 I/O 结果**立即被覆盖**，纯粹浪费；且读的是 **#3** 的 fixture，而用例名是 **#1**。

**问题二：`rule_ids` 算出来却从未断言。**

```python
result = checker.audit_sql(sql, instance_type='distributed')
rule_ids = {v.rule_id for v in result.violations}
# big_audit_trail 应有其他规则命中（如 R029 缺 COMMENT）
# 但不断言具体规则——只证明 R061 被移除
```

设计 §7.1 对 G1 的要求是：「R061 **不命中**，且 R029/R036/R037 **仍命中**（**证明只减 R061**）」。
后半句被放弃了，`rule_ids` 成了死变量。**G1 目前只证明了一半**——
它验证了"R061 没了"，但**没有验证"别的规则还在"**，而后者才是本次修复最关键的安全性质。

**根因（实测）**：Q 没有用生产 #1 原样 DDL，而是手写了一张替代表。两者规则命中不同：

| | 命中规则 |
|---|---|
| 生产 #1 **原样** | `R029, R036, R037` ← 设计要求的断言正好成立 |
| Q **手写替代版** | `R028, R029, R037, R077` ← 缺 R036、多 R077 |

Q 手写时补上了 `create_time`/`update_time`（导致 R036 不再触发）、又漏掉了 `shardkey=id`
（导致 R077 新触发），于是设计要求的断言在他的 SQL 上**根本无法成立**，只能放弃。

**建议修法**：改用生产 #1 原样 DDL（`shardkey=id`，无 `create_time`/`update_time`，
索引为 `` `idx_trace` / `idx_operator` / `idx_event` ``），并恢复断言：

```python
result = checker.audit_sql(sql, instance_type='distributed')
rule_ids = {v.rule_id for v in result.violations}
assert 'R061' not in rule_ids, f"生产 #1 的反引号 idx_ 索引不应误报: {sorted(rule_ids)}"
assert {'R029', 'R036', 'R037'} <= rule_ids, \
    f"生产 #1 的其他规则必须原样保留（证明只减 R061）: {sorted(rule_ids)}"
```

建议同时把生产 #1 原样 DDL 落为 `tests/fixtures/report_01_big_audit_trail.sql`。

### 5.2 【低】T-2：G2 用例含两行死代码，且所读 fixture 无法承担该用例

`tests/test_r061_index_name_quoting.py::test_g2_cus_name_list_type`

```python
sql = _read_fixture("report_05_cus_name_list_type.sql")
hit, msg = _has_r061(checker, sql)      # ← 结果被丢弃
# ...注释...
sql_real = ("CREATE TABLE `cus_name_list_type` (...")
hit, msg = _has_r061(checker, sql_real) # ← 覆盖上面
```

前两行是死代码。更值得注意的是：`report_05_cus_name_list_type.sql` 是 **v1.6.1.9 时期
为 R077/R054 广播表测试造的简化 fixture，整张表没有任何索引**，实测命中规则仅 `['R029']`，
**R061 永远不可能触发**——它承担不了 G2。Q 察觉到了（注释里写了"如果 fixture 里没有
非 idx_ 前缀索引，则可能不命中"），但选择了手写替代而非删掉死代码。

**G2 的断言本身是对的、有效的**（M3 变异测试证明它能拦住展示口径退化），
只是留下的死代码会误导后人以为该 fixture 与生产 #5 对应。

**建议修法**：删掉前两行；改用生产 #5 原样 DDL（35 列、`` KEY `CUS_NAME_LIST_TYPE_IDX1` ``、
`shardkey=noshardkey_allset`），实测其命中 `['R036','R037','R061']`，与设计 §7.1 完全吻合。
如落 fixture，建议**新建**文件而非覆盖 `report_05_...sql`——后者仍在为 v1.6.1.9 的
R077/R054 广播表用例服务，**不可改动**。
