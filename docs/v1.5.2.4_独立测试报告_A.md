## 4. 缺陷详情与修复方法

### P0-01（阻断）服务端无法导入，进程起不来

**现象**：`uvicorn backend.main:app` 立即退出；所有 `import backend.main` 的测试在收集阶段崩溃（116 个）。

**根因**：`a1fdc53` 给 `ExplainBySqlRequest` 加 `db_name` 字段时，把**紧邻的 `StatusUpdateRequest` 类整个删掉了**，但 `backend/api/slow_query.py:214` 的使用点还在：

```diff
 class ExplainBySqlRequest(BaseModel):
     sql: str = Field(..., description="要分析的SQL语句")
     connection_id: str = Field(..., description="已保存的TDSQL连接ID")
-
-
-class StatusUpdateRequest(BaseModel):      ← 被误删
-    """状态更新请求"""
-    status: str = Field(..., description="新状态: pending/optimized/ignored")
-
+    db_name: Optional[str] = Field(None, description="选填的数据库名")
```

类型注解在 `def` 执行时求值，所以是**导入期**报错，不是调用期。

**影响**：v1.5.2.4 **完全不可用**。且 `PUT /api/v1/slow-queries/{id}/status`（慢SQL标记待处理/已优化/已忽略）本身也已失去请求模型。

**修复思路**：把误删的类补回原处。不要改使用点去迁就——`status` 字段需要 pydantic 校验，改成裸参数会绕过校验。

**具体方法**：`backend/api/slow_query.py`，在 `ExplainBySqlRequest` 之后插入：

```python
class StatusUpdateRequest(BaseModel):
    """状态更新请求"""
    status: str = Field(..., description="新状态: pending/optimized/ignored")
```

**验收**：`python -c "from backend.main import app"` 无报错；全量套件收集错误归零。

**流程侧建议**：把这一行加进 `deploy/preflight_check.sh` 与提交前自检，属一秒钟成本、能挡住整类事故：

```bash
python3 -c "import backend.main" || { echo "后端无法导入，禁止打包"; exit 1; }
```

### P1-02（严重）全新安装缺 5 个字段，管理员无法完成首次登录

**现象**：全新建库启动后，管理员首次登录返回 `must_change_password: true`，但调 `POST /api/v1/auth/change-password` 直接 **500**：

```
pymysql.err.OperationalError: (1054, "Unknown column 'token_version' in 'SET'")
```

首次登录**必须**改密，改密又必崩——**新装系统进不去**。

**根因**：`backend/services/database.py::init_db()` 的调用顺序是

```
372:  _migrate_old_tables(conn)     ← 先跑增量补列
375:  _create_all_tables(conn)      ← 后建表
```

而 `_migrate_old_tables` 在 459 行一次性快照 `table_names`，其后全部补列动作都被 `if "<表名>" in table_names:` 守卫（547 / 564 / 573 / 579 / 609 行）。

**全新安装时表还没建，快照为空 → 守卫全假 → 所有补列被静默跳过。** 建表 DDL 里没有这 5 列，于是它们就永远缺席。

实测缺失清单（全新库 vs 升级库）：

| 表 | 列 | 用途 |
|---|---|---|
| `users` | `token_version` | 会话吊销（改密/重置/登出递增，等保 2.0 三级 8.1.4.1） |
| `audit_history` | `db_name` | V1.3 审核落实例信息，扫描对比按实例筛选 |
| `audit_history` | `rule_set_id` | V1.4 可追溯性："这份报告用的哪把尺" |
| `gate_audit_logs` | `connection_id` | 门禁绑定实例的判定依据 |
| `gate_audit_logs` | `rule_set_id` | 同上 |

**关键特性：第二次启动会自愈。** 实测同一个新库连启三次：

| 启动次数 | 5 列到位数 |
|---|---|
| 第 1 次 | **0 / 5** |
| 第 2 次 | **5 / 5** |
| 第 3 次 | 5 / 5（稳定） |

因为第二次启动时表已存在，守卫转真、补列补上。这也解释了为什么这个缺陷一直没被发现——**开发/测试环境的库都不是第一次启动**。

**对本次升级的影响**：内网是 1.2.0.9 升级，表早就在，走的是"守卫为真"的路径，**不受影响**（已实测升级库 5 列齐全）。但只要 G 是**新建库部署**（新容器、蓝绿、灾备站点、或任何重建库的场景），必踩。

**修复思路**：`_add_column_if_not_exists` 自身已经查过列是否存在，是幂等的；那层 `table_names` 守卫只是省几次查询，却把正确性赌在了调用顺序上。让补列在建表**之后**跑即可。

**具体方法**（两条都做，与本项目既有的"双保险"惯例一致）：

1. `backend/services/database.py::init_db()`，把补列挪到建表之后：

```python
        # 创建所有表（IF NOT EXISTS确保幂等）
        _create_all_tables(conn)

        # 增量补列：必须在建表之后，否则全新安装时 table_names 为空、
        # 所有 if "<表>" in table_names 守卫为假，补列被整体跳过。
        _migrate_old_tables(conn)
```

2. 把这 5 列补进 `backend/schema/v0/001_init_tables.sql` 的建表 DDL，让全新安装**天生就对**，不依赖补列兜底。

> ⚠️ 改建表 DDL 会改变 `001_init_tables.sql` 的 SHA256。`migrator` 对已应用迁移只记 checksum 漂移告警、不重跑，所以**存量库不会因此被动**（存量库的这 5 列本来就已通过补列到位）。但请务必在改完后重跑一次本报告 R2 的"升级 vs 全新"比对确认。

**验收**：全新建库，**第一次启动**后即满足 5 列齐全，且 `change-password` 返回 200。

**给 G 的临时规避**（若来不及改码）：新建库部署时，**启动服务 → 停止 → 再启动**，第二次启动后再做首次登录。

### P2-03（中）R043 正则写错，逗号式多表 UPDATE 恒不告警

**现象**：`tests/test_sit_v1_rules.py::test_r043_multi_table_update` 失败。

```sql
UPDATE t_order o, t_user u SET o.status = 1 WHERE o.cust_id = u.id   -- R043 漏检
```

**根因**：`backend/engine/parser/parser_legacy.py:253`

```python
re.search(r"\bupdate\s+[^set]+,", clean_sql_no_comm, re.DOTALL)
```

`[^set]` 是**否定字符组**——匹配"不是字符 s、不是 e、不是 t"，**不是**作者以为的"不是单词 SET"。于是只要 `UPDATE` 与逗号之间出现过 s / e / t 中任意一个字母，就整体不匹配。

实测对照，一眼可见判据跑偏：

| SQL | 结果 |
|---|---|
| `UPDATE ab, cd SET x = 1` | ✅ 命中（"ab, " 里恰好没有 s/e/t） |
| `UPDATE t_order o, t_user u SET ...` | ❌ **漏检** |
| `UPDATE order1 o, user1 u SET ...` | ❌ 漏检（`order` 含 e） |
| `UPDATE t_order o JOIN t_user u ON ... SET ...` | ✅ 命中（走的是另一条 JOIN 正则） |

**影响**：本行的表命名规约是 `t_` 前缀，**必然含 t**——也就是说 R043 对逗号式联表 UPDATE **在生产里等于从不生效**。JOIN 写法仍能拦住，所以缺陷一直被掩盖。这是 ERROR 级规则的静默漏报，属"看不见的错"（违反规约 R-15）。

**修复思路**：改成"取 UPDATE 到 SET 之间的目标段，再判断该段里有没有逗号或 JOIN"，不要用字符组去模拟单词否定。

**具体方法**：

```python
# UPDATE 与 SET 之间的目标表段；[^set] 是否定【字符】组（排除 s/e/t），
# 不是排除单词 SET —— 旧写法对 t_/s_/e_ 开头的表名恒不匹配。
m = re.search(r"\bupdate\b(.*?)\bset\b", clean_sql_no_comm, re.DOTALL)
if m and ("," in m.group(1) or re.search(r"\bjoin\b", m.group(1))):
    parsed.is_multi_table_update = True
```

**必须补的反向用例**（规约 R-12）：`UPDATE t_user SET name = 'a,b' WHERE id = 1`——单表、但 SET 值里带逗号，不得误报。

### P2-04（中）文件审核遇截断语句会吞掉下一条语句

**现象**：`tests/test_v2_syntax_truncation.py::test_split_truncated_sql_file` 失败，3 条语句被切成 2 条。实测切分结果：

```
第1条: CREATE TABLE `t1` (...)              ← 正常
第2条: CREATE TABLE `t2` ( `id` int NOT NULL, `col2` varchar(20)
        ⏎ -- SQL Object: CREATE TABLE ⏎ -- Table: t3 ⏎
        CREATE TABLE `t3` (...)             ← t3 被 t2 吞掉了
```

**根因**：`backend/engine/checker.py::_split_sql_file`（318 行）**只认分隔符 `;`**。`t2` 因截断没有 `;`，于是它和其后的一切合成一个残块。

**影响**：`t3` 不再作为独立语句被审核，它的违规**要么漏报、要么记到 t2 名下**。而截断在本系统里是**常态**——仓库里专门有 `test_v2_syntax_truncation` 这套用例、有 `d0b8cef`「截断SELECT补全」这类提交，说明上游抽取本来就会产出截断 DDL。银行级审核工具静默跳过一张表的审核，性质等同漏审。

**修复思路**：本系统自己的抽取器（`backend/api/sql_audit.py:318 / 338 / 664`）在每条语句前会写 `-- SQL Object: xxx` 标记。**用这个标记做隐式语句边界**：遇到标记行时，若已积累了非注释内容，就先把当前块收尾。这样即使前一条缺 `;` 也能正确断开。

**具体方法**：在 `_split_sql_file` 的逐行循环开头、`current_stmt.append(l)` **之前**插入：

```python
            # 本系统抽取器会给每条语句加 `-- SQL Object:` 标记。
            # 若上一条因截断缺失分隔符，靠分隔符切不开，会把下一条整个吞掉，
            # 导致该语句被静默跳过审核 —— 故把标记行也当作隐式语句边界。
            if re.match(r'^--\s*SQL Object:', stripped_line, re.IGNORECASE):
                pending = "".join(current_stmt).strip()
                cleaned_pending = re.sub(r'--[^\n]*', '', pending)
                cleaned_pending = re.sub(r'/\*.*?\*/', '', cleaned_pending, flags=re.DOTALL).strip()
                if cleaned_pending:                    # 只在真有代码时断开，纯注释块不断
                    statements.append((pending, stmt_start_line))
                    current_stmt = []
                    stmt_start_line = line_no
```

**建议一并做**：截断语句被切出来后，应在审核结果里**标注"该语句疑似截断"**，而不是当作完整语句静默审核——否则使用者拿到的是一份"看起来完整"的结论。
