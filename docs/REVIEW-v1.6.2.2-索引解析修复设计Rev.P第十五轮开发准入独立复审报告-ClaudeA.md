## 5. BLOCK-15-01：`unique_constraints_complete` fail-open，造成 R054 静默漏审与净回归

### 5.1 机制

三处叠加，任何一处单独存在都不致命：

1. **`_preflight_known_fidelity_failures()` 失败即开放**：

   ```python
   defs, _primary, _auxiliary = _scan_definition_list(toks, open_idx, close_idx)
   if defs is None:
       return ()          # ← 扫不动 == 没有 KFN
   ```

   `_scan_definition_list()` 是严格白名单，遇到任何它不认识的定义项就整体返回 `None`。
   于是"**我看不懂这条语句**"被当成了"**这条语句没有保真问题**"。

2. **`_parse_create()` 的定义项循环没有 `exp.Constraint` 分支**：
   循环只处理 `ColumnDef` / `PrimaryKey` / `IndexColumnConstraint` / `UniqueColumnConstraint` /
   `CommentColumnConstraint`。`CONSTRAINT symbol UNIQUE (…)` 在候选 AST 里是 `exp.Constraint`，
   **静默落空**，`_unique_semantics_failed` 保持 `False`。

3. **完整性判据由两个默认宽松的标志相与**：

   ```python
   parsed.unique_constraints_complete = (
       not _unique_semantics_failed and not parsed.known_fidelity_failures)
   ```

   两个输入都默认"没问题"，于是得到**假的 `complete=True`**。

后果链：假 `complete=True` → `_iter_unique_indexes()` 走新通道并 `return` →
**raw 正则回退被关闭** → 新通道里没有那条 UNIQUE → **R054 不命中，且全程无 E999**。

> Rev.P 契约 #2 自述："只有成功遍历完整 `exp.Create` 定义列表、每个支持域 UNIQUE 均精确提取后，
> `unique_constraints_complete=True`。" **实现没有检查"成功遍历完整定义列表"这一条。**

### 5.2 净回归（相对当前生产版本 v1.6.2.1）

表：主键 `(id,sk)`、分片键 `sk`、唯一约束在 `c` 上 —— **R054 应命中**。

| # | 形态 | 基线 R054 | Rev.P R054 | Rev.P E999 | |
|---|---|---|---|---|---|
| A | `CONSTRAINT uq UNIQUE KEY uk (c)` | 命中 | 命中 | 有 | ✅ |
| **B** | **A + `FOREIGN KEY`** | **命中** | **不命中** | **无** | ❌ 净回归 |
| **C** | **A + `CHECK`** | **命中** | **不命中** | **无** | ❌ 净回归 |
| **D** | **`CONSTRAINT uq UNIQUE INDEX uk (c)` + `FOREIGN KEY`** | **命中** | **不命中** | **无** | ❌ 净回归 |

基线之所以命中，是因为 `parsed.indexes` 为空 → `seen=False` → raw 正则回退匹配到 `UNIQUE KEY uk (c)`。
Rev.P 把 `complete` 误判成 `True`，**主动关掉了这条救命回退**。
三版 sqlglot 结论一致（各 3/4 漏审）。

> ⚠️ **KFN-4 那两列的"全阻断"是偶然，不是机制。** `INT SIGNED` / `VARCHAR(n) BINARY`
> 之所以每格都阻断，是因为 **sqlglot 自身就 ParseError**，E999 来自解析器而不是 preflight。
> 一旦升级到能解析它们的 sqlglot 版本，这两列会立刻和 KFN-5/6 一样开始泄漏。
> **不能把它当成 preflight 有效的证据。**

### 5.4 为什么现有证据没抓到

Rev.P 新增的 R14-UQ / R14-KFN-CU / R14-KFN-SE / R14-KFN-DECOY 四组，
用例形态都是"**干净的**目标结构"。整个 manifest 里出现
`FOREIGN KEY` / `CHECK (` / `KEY_BLOCK_SIZE` 的地方一共只有 **2 处**。
**缺的是"伴随结构"这一整个维度**，不是缺某几条用例。

### 5.5 整改方向（两半分开，代价已实测）

关键在于把**两件被混在一起的事**拆开：

| 关注点 | 现状 | 应该是 |
|---|---|---|
| **通道可信度**（`complete`） | 由两个默认宽松标志相与 | 只要**定义列表没被完整理解**，就必须 `False`，交回 raw 回退 |
| **保真阻断**（KFN → E999） | 依赖 preflight 全量扫描成功 | 需要**逐项**扫描：能认出"第 k 项是 KFN-6"，同时容忍"第 j 项看不懂" |

我实测了两种原型：

| 原型 | 改动 | 33 例缺口 | 4 例净回归 | 全量测试 | 语料漂移 |
|---|---|---|---|---|---|
| **A** 扫不动即整句阻断 | preflight 返回 `("KFN-PREFLIGHT-UNSCANNABLE",)` + 补 `exp.Constraint` 分支 | **全部关闭** | 全部复原 | 1355 passed / 0 failed | **5 条 ❌** 凭空新增 E999 |
| **B** 只关闭通道、不造 E999 | 仅补 `exp.Constraint` 分支置 `_unique_semantics_failed=True`，且**不**写 `parse_error` | 仍 33 例 | **全部复原** | 1355 passed / 0 failed | **0 条 ✅** |

- **原型 B 是零代价的**，它单独就把 §5.2 的净回归全部消掉；**建议先落这一半**；
- 原型 A 证明"扫不动即阻断"能彻底关缺口，**但会误伤 5 条语料**（`030_global_ruleset_gate.sql`、
  `docker/mysql/init.sql`、`01_naming_ddl.sql` ×3 凭空多出 `E999_SYNTAX_ERROR`），
  所以**不能直接照抄**；正确做法是把 preflight 改成**逐定义项**扫描，
  只对"确实识别出 KFN 构造"的项阻断，对"看不懂但也没有 KFN 迹象"的项**只降 `complete`**。

## 6. MINOR-15-01：文档头的全量数字与 runner 自身输出不符

文档头证据行写：「发布版冻结专项 **71 passed**、全量 **1384 passed**」。
但同一份 runner 在 design 模式下的实际输出是：

```text
STEP frozen-71-release   rc=0 tail=... 71 passed
STEP full-tests-release  rc=0 tail=... 1355 passed, 29 skipped, 10 warnings
```

`1384 = 1355 + 29`，把 skipped 并进了 passed。
G-1 门槛的口径一直是"**只看 0 failed，不得硬编码单一环境分布**"，
这里既写错了数、又把它放进了文档头的结论位。

**整改**：改成 runner 原样输出的 `1355 passed / 29 skipped / 0 failed`，或直接只写 `0 failed`。

## 7. 观察项（不阻断准入，建议登记）

1. **preflight 的成本**：它对**每一条** `CREATE TABLE` 都做一次完整词法 + 定义列表扫描。
   实测占 `SQLParser.parse()` 总耗时 **18%~22%**（小表 0.17 ms、150 列 + 40 索引的大表 9.4 ms）。
   当前规模无问题，但如果将来做全库批量扫描，建议在 `parse()` 内**复用**已有的 token 流，
   避免同一条 SQL 被 tokenize 两次。
2. **KFN-4 的保护是偶然的**，见 §5.3 的警示框。
3. **`_scan_definition_list()` 的白名单缺口本身值得单独登记**：
   `FOREIGN KEY` / `CHECK` / `GENERATED` / `VISIBLE` / `KEY_BLOCK_SIZE` / 函数索引
   都是官方合法且常见的建表要素，目前一律使整条语句不可扫描。
   本轮不要求扩支持（会扩大爆炸半径），但建议登记为具名 ADJ，
   并在 §5.5 的"逐项扫描"改造中让它们成为"已知未支持项"而不是"扫描失败"。

## 10. 最终意见

Rev.P 是这一系列修订里**第一版可以谈"进开发"的方案**：隔离通道的方向正确且被冻结用例反向证明，
证据面从"写了规范"变成"真能跑"，双模式契约把"设计可施工"与"产品已施工"分得很清楚。

唯一阻断项是 §5 那一处 fail-open：**它把"我看不懂"当成了"没问题"**，
在最不该这样的位置上 —— 一条本来能救命的 raw 回退被主动关掉，
而受损的正是本次修复要保护的 R054。
