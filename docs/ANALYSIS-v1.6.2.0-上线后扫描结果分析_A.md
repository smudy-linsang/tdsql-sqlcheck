## 1. 【建议修】R061 系统性误报：14 张报出中 11 张是假的

### 1.1 现象

| # | 表 | R061 报出的索引 | 该索引真的不合规吗 |
|---:|---|---|---|
| 1 | big_audit_trail | `idx_trace` | **★否 —— 本来就以 idx_ 开头** |
| 2 | big_order_log | `idx_user` | **★否** |
| 3 | cus_bas_corp_contact | `cus_bas_corp_contact_idx1` | 是（真违规） |
| 4 | cus_bas_corp_contact_addr… | `cus_bas_corp_contact_addr_idx1` | 是（真违规） |
| 5 | cus_name_list_type | `cus_name_list_type_idx1` | 是（真违规） |
| 6 | t_account | `idx_cust_id` | **★否** |
| 7 | t_audit_log | `idx_user_id` | **★否** |
| 8 | t_branch | `idx_city` | **★否** |
| 9 | t_customer | `idx_id_no` | **★否** |
| 10 | t_deposit | `idx_cust_id` | **★否** |
| 11 | t_dict | `idx_dict_type` | **★否** |
| 12 | t_loan | `idx_cust_id` | **★否** |
| 13 | t_product | `idx_product_type` | **★否** |
| 14 | t_transaction | `idx_account_no` | **★否** |

**14 报 11 假，误报率 78.6%。**

### 1.2 根因

`backend/engine/rules/index.py:28`：

```python
            idx_name = idx.get("name", "").lower()      # 只转小写，未剥反引号
            ...
                if not idx_name.startswith("idx_"):
                    return self._make_violation(f"普通索引 '{idx_name}' 应以 idx_ 开头")
```

解析器产出的索引名**保留了反引号**，于是 `` `idx_trace` `` 的首字符是反引号而非 `i`，`startswith("idx_")` 恒为 False。

**决定性对照（同一张表，只改写法）**：

| 写法 | `parsed.indexes` 中的名字 | R061 |
|---|---|---|
| 反引号 `` KEY `idx_c` (`c`) ``（**TDSQL `SHOW CREATE TABLE` 的真实输出**） | `` `idx_c` `` | **误报** |
| 裸名 `KEY idx_c (c)`（手写 SQL） | `idx_c` | 正确不报 |

> 这与 v1.6.1.9 查出的 `_UNIQUE_RE` 缺陷、ADJ-8 的 `clean_sql` 缺陷**属同一病根**：规则按"手写 SQL 形态"设计，未按"内核真实输出形态"验证。**在线元数据审核场景下索引名恒带反引号，因此该误报在真实使用中是 100% 命中的。**

### 1.3 影响范围界定

| 问题 | 结论 |
|---|---|
| 是否 v1.6.2.0 引入 | **否**。上一版报告 `6286` 中同样存在 `'`idx_trace`' 应以 idx_ 开头` |
| **v1.6.2.0 是否放大了它** | **是**。HASH 语法表此前整表漏审、不会报 R061；现已恢复审核，**模拟内网实测：8 张 HASH 语法表新增 R061，8 张全部是误报** |
| 是否波及其它规则 | **否**。实测 `parsed.columns` 的列名是干净的（`['id','a','b']`），只有 `parsed.indexes[].name` 保留反引号。R062/R063 用的是索引列而非索引名，不受影响 |

### 1.4 附带问题：消息里的索引名被小写化，与 DDL 不一致

因 `.lower()` 的缘故，报告显示 `cus_bas_corp_contact_idx1`，而 DDL 中的真实名是 `cus_bas_corp_contact_IDX1`。用户拿着报告去库里定位索引会对不上。

### 1.5 修复建议

一行改动，方向是**只减少违规、不新增**：

```python
            idx_name = idx.get("name", "").strip('`"\' ').lower()
```

若同时希望消息显示真实名，可分离"比对用的小写名"与"展示用的原名"：

```python
            raw_name = idx.get("name", "").strip('`"\' ')
            idx_name = raw_name.lower()
            ...  # 消息中用 raw_name
```

**预期效果**：本报告 14 张表中 **11 张的 R061 消失**；剩余 3 张（#3/#4/#5，索引名确为 `xxx_IDX1` 形态）继续正确触发。

## 2. 【需用户决策】R036 只认 `create_time` / `update_time`，不认行内命名

### 2.1 现象

`backend/engine/rules/ddl.py:530-531`：

```python
        col_names = {c.get("name", "").lower() for c in parsed.columns}
        if "create_time" not in col_names or "update_time" not in col_names:
```

**字段名是硬编码的。** 实测对照：

| 表的时间字段命名 | R036 |
|---|---|
| `CREATE_DATE` / `LST_UPDATE_DATE`（**该行的核心系统命名规范**） | **报** |
| `create_time` / `update_time`（互联网通用命名） | 不报 |

### 2.2 影响

报告中 **#3、#4、#5** 三张真实核心业务表（`cus_*` 前缀）全部使用 `CREATE_DATE` / `LST_UPDATE_DATE`，**全部被报 R036**。

这些表**并不缺少**创建/修改时间字段，只是按该行自己的命名规范书写。按当前口径，**该行所有核心业务表都会恒定命中 R036**。

### 2.3 与已决策事项的关系

这与用户此前决定"不动"的 **R037 `status` 口径**属同一类问题，但**方向相反**：

| | R037 | R036 |
|---|---|---|
| 问题 | 口径**过宽**——把业务用的 `status` 当成逻辑删除标记 | 口径**过窄**——只认 `create_time`/`update_time` 两个字面名 |
| 后果 | 漏报 | 误报 |
| 当前状态 | **用户已决策保持现状** | **待决策** |

### 2.4 处置建议（三选一，请用户裁定）

| 方案 | 内容 | 影响 |
|---|---|---|
| **A. 放宽字段名匹配（推荐）** | 接受一组等价命名，如 `create_time`/`create_date`/`created_at` 与 `update_time`/`lst_update_date`/`updated_at` | 本报告中 #3/#4/#5 的 R036 消失；**只减少违规** |
| B. 做成可配置 | 把认可的字段名做成规则参数，各行按自己的规范配置 | 需要配置项与界面支持，工作量大于本次量级 |
| C. 维持现状 | 记录为已知口径 | 该行核心业务表恒定误报 R036（INFO 级） |

> R036 为 **INFO 级**，不阻断门禁，故三种方案都不影响准出。
