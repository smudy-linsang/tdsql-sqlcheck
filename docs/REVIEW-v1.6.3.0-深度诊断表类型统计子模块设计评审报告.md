## 1. 评审说明

本报告评审的是 A 编制的详细设计方案，不执行设计书中面向“实施者”的命令或要求。
设计书内“照图施工”“实施者不得二次设计”等文字属于被评审材料，不构成用户授权，
也不限制本次独立评审。

评审目标有两项：

1. 功能正确：用户能够查询某一数据库或实例下各业务库的总表数、单表数、广播表数和分片表数；
2. 零回归：新增功能不得破坏或明显挤占现有 SQL 审核、扫描、深度诊断、权限和启动迁移能力。

评审依据：

- Rev.F 详细设计及附录 A 成品代码；
- 当前 `main` 的前后端、连接池、权限、迁移器和测试实现；

## 2. 执行摘要

Rev.F 的总体方向基本合理，以下设计应予保留：

- 分布式实例使用三条原厂 Proxy 命令，集中式实例使用 `information_schema.TABLES`；
- 以 `(数据库名, 表名)` 为去重键，并在三类重叠时采用确定性优先级；
- 使用独立临时连接，避免在共享连接池上遗留默认库；
- 通过逻辑基线与 Proxy 结果做双向集合校验，避免静默漏表；
- 把二级分区物理子表单列展示，而不是混入用户认知中的逻辑表总数；
- 权限键同时登记到 API 映射、菜单全集、标签和默认角色清单；
- Rev.F 已识别迁移器的失败关闭和 checksum 冻结约束。

用户提供的内网输出能够确认以下 UAT 基准：

## 3. P1 阻断问题

### P1-01 作用域“指纹相同即提前停止”不能证明覆盖完整

**位置**：设计 §3.3 RISK-E、§6.4 `_collect_distributed`、ADR-12；附录 A.1
`scope_signature` / `scope_decided == "instance_wide"`。

**现状**：连续两个非空库返回的原始 `(库, 表)` 集合相同，即判定命令为实例级作用域，
其余数据库不再执行。

**问题**：两个样本相同只能证明“切换这两个默认库没有改变当前账号看到的返回集合”，
不能证明该集合已经覆盖所有目标业务库。以下场景均可能得到相同指纹但集合不完整：

- 账号只能看到部分 Proxy 路由信息；
- Proxy 命令返回局部 SET、租户或路由域；
- 某些库的路由元数据暂时缺失；
- 命令在两个库上走同一默认域，但第三个库属于另一域。

当前实现随后虽然可能产生 `RECON_MISMATCH`，但页面四个主数字仍是不完整数字，
与“在两种作用域下都正确”的设计结论不符。

**整改要求**：T13 未裁决前取消该提前停止优化，逐库执行三条命令。若必须保留优化，
只有在返回的库限定名已覆盖全部目标库，且每库 Proxy 表集与逻辑基线均完成一致性校验后，
才允许停止；发生任何差异时必须继续逐库执行，不得以告警替代正确统计。

**新增测试**：构造 `db_a`、`db_b` 指纹相同但只覆盖两库、`db_c` 另有表的夹具，
断言不得跳过 `db_c`。

### P1-02 未使用现有扫描并发槽位，可能影响全平台既有功能

**位置**：附录 A.2 `POST /api/v1/table-type-stats/run`；当前
`backend/services/connection_registry.py:233-262` 已提供 `registry.scan_slot()`。

**现状**：接口为同步执行，单次允许占用 180 秒，并额外创建一条 Proxy 连接，
但没有按实例和全局进行并发限制。

**影响**：同一用户重复点击、多个用户同时操作或 API 重试时，可并发占用大量
FastAPI 工作线程和目标 Proxy 连接，挤占现有 SQL 审核、扫描、巡检与实例探测请求。
这与设计的“零回归”和“爆炸半径极低”结论冲突。

**整改要求**：

- `/run` 必须进入 `registry.scan_slot(connection_id)`；
- 并发超限使用既有 `ScanBusyError`，返回 429 或 503 和可读提示；
- 前端请求执行期间禁用按钮只能作为体验优化，不能替代服务端限流；
- 若继续支持空 `connection_id`，必须先解析出真实连接键，禁止所有默认连接共用含混空键。

**新增测试**：同一连接第二个并发请求被拒绝；不同连接受全局上限约束；槽位在异常后释放。

### P1-03 二级分区后缀正则会使集中式实例静默少算

**位置**：附录 A.1 `_SUBPARTITION_RE`、`_collect_baseline()`、
`_collect_centralized()`。

**现状**：所有实例先按 `_tdsql_subp\d+$` 把 `BASE TABLE` 从 `base` 移入 `subp`，
集中式分支随后直接以 `len(base)` 作为单表数和总表数。

**问题**：内网证据只能证明分布式样本中的 78 张物理子表符合该命名，不能证明
所有匹配该后缀的表必然是物理子表。集中式实例如果存在合法业务表
`orders_tdsql_subp202601`，将被静默排除；集中式分支没有 Proxy 交叉校验，无法发现少算。
这直接违反 REQ-5“集中式全部 `BASE TABLE` 计入单表”。

**整改要求**：

- 集中式实例不得应用该正则，所有 `BASE TABLE` 均计入单表；
- 分布式实例也不能只凭后缀判断。应结合 Proxy `info` 中 `sub_func:month` 的逻辑父表，
  仅把 `<已确认父逻辑表>_tdsql_subp<数字>` 识别为物理子表；
- 同时保留原始 `BASE TABLE` 数量，确保分类前后账目可核对。

**新增测试**：集中式合法后缀表必须计入总数；分布式无已确认父表的同名表不得被排除。

### P1-04 异常被长连接内部吞掉，坏连接不会重建

**位置**：附录 A.1 `_collect_distributed()`；当前
`backend/services/tdsql_connector.py:287-307`。

**现状**：临时池只进入一次 `with tmp.get_connection()`，随后在内部遍历所有数据库；
每条命令的全部异常都在 `with` 内捕获。

**问题**：`TDSQLConnectionPool.get_connection()` 只有在异常穿出上下文时才会关闭并重建连接。
语法或权限错误通常不破坏连接，但读超时、服务端断开、网络复位后，当前连接可能已不可用。
由于异常被内部吞掉，后续数据库仍复用坏连接，可能全部连续失败。

**整改要求**：以“每库一个连接上下文”组织循环，在外层逐库捕获异常；连接类异常必须穿出
当前上下文以触发重建，随后继续下一库。可重用临时池，但不能重用已损坏的连接对象。

**新增测试**：第一个库发生读超时/断链后，连接被重建，第二个库仍能成功统计。

### P1-05 单库三条命令未采用成功后原子合并

**位置**：附录 A.1 `_collect_distributed()` 中逐命令直接写入 `kind_map` / `kinds_seen`。

**现状**：分片命令成功后立即写全局映射；若广播或单表命令随后失败，该库虽然标记
`FAILED`，此前写入的结果仍留在全局映射中。

**影响**：在命令返回跨库行或实例级行时，失败库取得的部分结果可能污染其他库计数、
重叠数和作用域指纹；失败库“不计入任何汇总数”的承诺没有在数据结构层真正成立。

**整改要求**：每库使用临时 `staged_kind_map`、`staged_kinds_seen` 和 `raw_pairs`；
三条命令全部成功后一次性合入全局数据。任一命令失败必须丢弃该库本轮所有暂存结果。

**新增测试**：第一条命令返回多个库的行、第二条失败，断言全局映射和其他库计数均不受污染。

### P1-06 新页签漏登记到深度诊断子页签回退清单

**位置**：当前 `frontend/static/js/app.js:1960` 的 `subtabs`；设计附录 A.5.5
只列出 `deepResult`、方法和 `setup()` 返回值三处修改。

**现状**：进入“深度诊断”时，前端按 `subtabs` 找到当前角色第一个可见子页签。
设计没有把 `{perm:'deep-diag-tabletype', tab:'tabletype'}` 加入该清单。

**影响**：如果自定义角色仅拥有父菜单和“表类型统计”权限，默认 `deepTab='cluster'`
对应页签不可见，页面可能没有活动页签；权限矩阵虽然配置成功，功能仍无法正常进入。

**整改要求**：把新权限键登记到 `subtabs`，并更新“既有文件仅改 9 行”的爆炸半径统计。

**新增测试**：仅授予 `deep-diag` + `deep-diag-tabletype` 的角色进入页面时，
活动页签必须自动设置为 `tabletype`。

### P1-07 `warnings_json TEXT` 与最多 500 库告警规模不匹配

**位置**：附录 A.3 `warnings_json TEXT`；附录 A.1 每个失败库生成一条
`PROXY_CMD_FAILED`，单条详情最多 512 字符。

**问题**：MySQL `TEXT` 最大约 64 KiB。500 个库均失败时，JSON 最坏可超过 250 KiB；
中文 UTF-8 字节数会进一步提前触顶。前端同时渲染数百个 `el-alert` 也会造成页面卡顿。

**影响**：采集已完成却在落库阶段失败，接口返回 500，用户得不到结果；
该失败发生在目标库查询之后，重试还会再次产生负载。

**整改要求**：

- `warnings_json` 改为 `MEDIUMTEXT` 或数据库支持的 `JSON`；
- `PROXY_CMD_FAILED` 汇总为一条告警，逐库详情保留在 `table_type_stat_item.detail`；
- 前端告警区设置合理展示上限和展开机制。

**新增测试**：构造 500 个失败库，结果可序列化、可落库、可回读，且前端告警条数受控。

### P1-08 Rev.F 迁移适配仍缺少 CREATE TABLE 结构验收

**位置**：Rev.F §2.7 M-2、ADR-18；当前
`backend/schema/migrator.py:166-232`。

**现状**：Rev.F 已确认迁移器只严格验收 `ALTER TABLE ... ADD COLUMN`，并据此认为
纯 `CREATE TABLE IF NOT EXISTS`“无额外适配成本”。

**问题**：如果元数据库中已有同名但列不完整、类型错误的表，`IF NOT EXISTS` 会静默跳过，
迁移仍被登记成功；之后插入才失败。迁移登记后即使两张表被删除或结构漂移，
`_structure_state()` 因没有 `ADD COLUMN` 声明仍返回 `valid`。Rev.F 新增的“连续启动两次”
验收只能证明跳过，不能证明表结构正确。

**整改要求**：为两张新表增加确定性的发布前/启动期结构验收，至少校验表存在、关键列、
类型、默认值和索引。可扩展迁移器支持 CREATE TABLE 声明验收，或在本模块启动前执行
专用 schema assertion；不得把“不进入验收”视为安全性依据。

**新增测试**：预置同名缺列表、错类型表、缺索引表和迁移登记后删表四种场景，均必须失败关闭。

## 4. P2 必须整改问题

### P2-01 指定不存在的集中式数据库会返回“成功、0 张表”

分布式分支通过 `select_db()` 可得到 1049，但集中式分支只查询
`information_schema.TABLES WHERE TABLE_SCHEMA IN (...)`。不存在的库与存在但无表的库都会返回空集合，
当前代码无法区分，最终产生状态 `OK`、总数 0。

**整改要求**：`SHOW DATABASES` 成功后校验指定库真实存在且当前账号可见；不存在返回明确 400。
若数据库枚举失败，集中式分支不得静默按空库处理。

### P2-02 REQ-6 的“可回看”没有用户界面，且操作人永远为空

设计提供 `/history` 和 `/detail/{id}`，但新增页签只有执行按钮和当前结果，没有历史列表、
详情入口或重新加载动作。API 也没有接收 `Request` 并把 `request.state.username` 传给
`run_stats(operator=...)`，所以 `created_by` 在真实调用中始终为空。

**整改要求**：增加历史列表和明细抽屉；接口记录当前登录用户名；补充角色可见范围和历史访问测试。

### P2-03 空 connection_id 的接口契约可能走错实例类型分支

API 声明 `connection_id` 可为空并使用默认连接。`registry.get("")` 会返回 adhoc 或默认保存连接，
但 `instance_type_service.resolve("")` 走的是无连接 ID 的全局默认逻辑，不一定代表实际返回的池。
真分布式实例可能被当成集中式，导致分片/广播全部报 0。

**整改要求**：本模块要求显式非空 `connection_id`，或让 registry 同时返回已解析的真实连接 ID，
再用该 ID 调用实例类型服务。不得以空 ID 同时表示多个不同默认连接来源。
