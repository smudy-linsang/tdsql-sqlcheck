## 2. 逐项复验

### 2.1 ① errno 分类：全 1045 → NO_BUSINESS_USER

用**真实连接**造三种 errno（不打桩）：容器里真建了 `checksql` 账号，正确口令 / 错误口令 / 死端口分别产生 errno `0 / 1045 / 2003`，先证明用例前提成立：

```
【0】前置：确认三种端点/凭据的真实 errno
  ✅ 正确口令可连 — errno=0
  ✅ 错误口令真返回 1045 — errno=1045
  ✅ 死端口真返回 2003 — errno=2003

【1】★全部 Proxy 鉴权失败（内网症状：未创建 checksql 用户）
  ✅ A(富集) 判为 NO_BUSINESS_USER
  ✅ B(导入预检) 判为 NO_BUSINESS_USER
  ✅ 两条路径口径一致
```

**三组反向鉴别**（这项改动最容易改坏的地方就是"把什么失败都说成没建用户"）：

```
【2】全部连接失败（Proxy 真不可达）
  ✅ A 仍为 NO_AVAILABLE_PROXY        ✅ B 仍为 NO_AVAILABLE_PROXY
【3】混合失败（一个 1045 + 一个 2003）
  ✅ A 判为 NO_AVAILABLE_PROXY（不误报）  ✅ B 判为 NO_AVAILABLE_PROXY（不误报）
【4】能连通时不得被误判为失败
  ✅ A 正常枚举 source=proxy_show 库数=18   ✅ B 正常枚举 source=proxy_show 库数=18
```

`_errno_of` 沿 `__cause__` 追一层原始异常的写法是必要的——导入侧 `_connect` 会把 pymysql 异常包成 `ZKImportPreparationError`（那是 v1.6.0.6 A-P2-02 的修复），errno 藏在 `__cause__` 里。我确认 `ZKImportPreparationError.args[0]` 是**字符串** detail，不会被 `isinstance(args[0], int)` 误当成 errno，一层追溯足够。

**状态串一路传到前端**：

```
【8】enrich_status 传递
    enrich_status='dbs_failed:NO_BUSINESS_USER'
  ✅ ★与前端精确匹配的那个串完全一致
  ✅ 反向鉴别：凭据正确时状态不是 dbs_failed（实为 'dbs_only'）
```

前端用的是 `row.enrich_status==='dbs_failed:NO_BUSINESS_USER'` **全等匹配**。我确认 `status_parts` 目前只可能有这一类元素，所以全等成立；但这是个脆弱耦合，将来若在 `enrich_status` 里再拼别的段（如名称解析失败），这个判断会静默失效。建议改成 `indexOf('NO_BUSINESS_USER')>=0`，一字之改，先记在这里。

## 4. A-P2-04（新，P2，不阻断）：有一个 Proxy 连不上，新诊断就失效

### 4.1 实测

**同一个错误的业务口令**，三个实例唯一的差别是有没有一个连不上的备 Proxy：

| 实例 | Proxy 构成 | 页面显示 | 颜色 |
|---|---|---|---|
| `set_uat_c2` | 1 个，全活（1045） | **未创建监控用户** ✅ | warning |
| `set_uat_c1` | 2 个，主活（1045）+ 备死（2003） | **Proxy 不可达** ❌ | danger |
| `group_uat_1` | 2 个，主活（1045）+ 备死（2003） | **Proxy 不可达** ❌ | danger |

发现列表侧同样：`set_uat_c2` 显示「未创建监控用户」，另两台显示「枚举失败」。

### 4.2 为什么值得管

判据是 `if failed and auth_failures == failed`——**要求所有失败都是 1045**。只要掺进一个连接类失败，就退回 `NO_AVAILABLE_PROXY`。

- 内网实例**普遍是双 Proxy**（你给的截图里每一行 `Proxy数` 都是 2）；
- "备 Proxy 不可达"正是 v1.6.0.5 放宽枚举的起因，说明这个形态在内网**确实存在**；
- 这两个条件叠加时，运维看到的是「Proxy 不可达」——**指向网络**，而真实原因是**账号没建**。主 Proxy 明明是通的，这个提示会把排查带偏。

从证据强度看，**任何一个 Proxy 回 1045，就已经是"这个账号在可达的 Proxy 上被拒"的确凿证据**，比"有 Proxy 连不上"更具体也更可操作。按 R-15，应该给更可见、更能动手的那条。

### 4.3 建议改法

```python
if not catalogues:
    if auth_failures:                      # 只要有 Proxy 明确回了 1045
        code = "NO_BUSINESS_USER"          # 就按"账号问题"报，附带说明另有 N 个 Proxy 不可达
    else:
        code = "NO_AVAILABLE_PROXY"
```

提示文案可写成：「业务账号在可达的 Proxy 上鉴权失败（另有 N 个 Proxy 未响应）：通常未创建监控用户…」——**两个事实都给到，不丢信息**。

**补用例（R-12）**：主活备死 + 错口令 → 断言归类为 `NO_BUSINESS_USER`；全部不可达（无 1045）→ 断言仍为 `NO_AVAILABLE_PROXY`。现有 6 条用例里**没有一条覆盖混合失败**，这也是它没被自测发现的原因。

### 4.4 内网自查方法（不依赖上面的修复）

在发现列表里，**枚举成功且带「部分 Proxy」标签**的实例，说明它的备 Proxy 是不可达的。对这类实例，若日后出现枚举失败，页面会显示「Proxy 不可达」而不是「未创建监控用户」——**此时应优先按"账号未建/口令不符"排查**，而不是先查网络。

## 5. 必须交代给内网的一条存量清理

**v1.6.1.0 的 sysdb 屏蔽只对"今后的枚举"生效，不会回收已经导入的连接。**

你给的 v1.6.0.7 预览截图里，`set_1779766229_1441` 的 7 条候选中就包含 `sysdb`，生成连接名为 `理财资管系统（理财组合分析绩效系统）-集中式-开发环境-15131-sysdb`。**如果那批已经提交入库，这些 sysdb 连接现在还在，并会继续参与慢 SQL 扫描与审核。**

升级后请在「实例管理」里按名称后缀 `-sysdb` 检索并**人工删除**（该库是 TDSQL 实例自带管理库，不属于业务审核范围）。重新扫描不会再产生它们。

## 6. 准出结论

**同意准出，可以打包发内网。**

三项改动均已验证到位，含 6 组反向鉴别；全量回归 0 失败；v1.6.0.5~0.6 的既有修复重跑无回归。

**下一版建议处理（都不阻断）**：

1. **A-P2-04**（§4.3）——有 1045 即报 `NO_BUSINESS_USER`，并补一条混合失败的反向鉴别用例；
2. 前端 `enrich_status==='dbs_failed:NO_BUSINESS_USER'` 的**全等匹配**改成包含匹配（§2.1 末），避免将来往该字段拼入其他段时静默失效；
3. **A-P2-03**（上一轮遗留，仍未处理）——MonitorDB 不可路由时逐实例重连，200 个实例外推约 620s，会被自带 nginx 的 `proxy_read_timeout 120s` 掐断。内网做大批量导入前，**MonitorDB 配置务必先用 ≤30 个实例试一次预览**。

### 给内网的三条动作

1. **清理存量 `-sysdb` 连接**（§5），这是本次升级唯一需要人工介入的事；
2. **升级后重新扫描一次**，此前显示「枚举失败」的实例会变成「未创建监控用户」，据此按实例补建 `checksql` 账号；
3. **MonitorDB 首次配置先小批量验通**（≤30 个实例）再全选，规避 A-P2-03。
