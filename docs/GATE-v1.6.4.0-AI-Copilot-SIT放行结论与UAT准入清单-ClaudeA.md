### 1.1 `backend/copilot_knowledge/builder.py` 第 141–143 行：注释指向了错的兜底

**现状**（这是第一版 `d3f07bd` 的论证，第四轮已被新锁取代）：

```python
    # N-04（SIT 第三轮）：newline="\n" 在 POSIX 上与默认行为等价，
    # 单独的 LF 断言在该平台是空锁；但 N-03 的重建比对锁会在 Windows 上
    # 删掉本参数后重建时检出 CRLF 产物与随包 LF 不匹配，构成有效兜底。
```

**改为**（指向真正起作用的那条锁）：

```python
    # N-04（SIT 第三/四轮）：newline="\n" 在 POSIX 上与默认行为等价，
    # 行为断言在该平台是空锁；真正的回退防护是
    # tests/copilot/test_knowledge_output.py::test_builder_has_no_translating_write，
    # 它对本文件做 AST 检查，撤掉本参数在任何平台都会报红（变异 X7 已验证）。
```

**为什么要改**：下一个人读到"兜底靠 N-03 的重建比对锁"，会以为 Linux 上有覆盖，
而实际上第四轮实测那条路径在 Linux 上抓不到（20 passed 存活）。注释把人指错方向，
比没有注释更糟。

## 5. UAT 必须覆盖的四类（四轮 SIT 一次都没真跑过）

四轮 SIT 全部停留在单元/集成层面。下面四类**一次都没有在真实环境跑过**，
是 UAT 存在的意义，不能用 SIT 结论替代：

1. **真实模型接入后，`projection_mode` 与实际出站载荷的一致性抽检**
   —— M-01 三道闸的价值全在这里兑现。SIT 只验了判定逻辑，没验真发出去的是什么。
   建议按"主备都允许 / 备用腿不允许 / 逐实例未授权"三种配置各抓一次实际出站报文。

2. **元数据库连接池与磁盘在 Copilot 并发下的占用**
   —— 这是 Copilot 与主产品**真正共享**的资源。我在设计评审阶段拿宿主机内存当依据
   搞错过一次、被 O 纠正，所以这条要实测，不要推理。重点看 Copilot 满并发时
   元数据审核任务会不会被挤到排队。

3. **知识包的实际检索质量**
   —— 四轮 SIT 只验证了产物完整性与"没漂移"，**完全没验证答得对不对**。
   建议备一个小黄金集（每个 authority 各若干题），至少留一个基线数，
   否则以后改知识包没有比较对象。

4. **`deploy/copilot_emergency_disable.sh` 实机演练**
   —— 出事时能不能一键摘掉 Copilot 而不影响审核主流程，必须真跑一次，
   不能只看 `bash -n` 通过。演练要覆盖：摘掉后主产品审核全流程可用、
   再恢复后 Copilot 能回到 READY。

### 5.1 另外两条 UAT 期间值得顺手验的（源自本版整改）

- **N-05 是加载期的闸，不是运行期看门狗**：`store.load()` 全仓唯一调用点在
  `copilot_bootstrap_check()` 里、挂 FastAPI lifespan，也就是进程启动时跑一次。
  现场换完知识包**必须重启**才会生效/才会拦。UAT 请按真实运维动作走一遍，
  确认手册写清楚了这一点。

- **B-01 的根因是跨平台换行**：如果 UAT 环境的知识包是在 Windows 上打包再传进内网的，
  请顺带核一次落地字节与 manifest 是否自洽（`test_shipped_bundle_ready` 跑一次即可）。
