## 1. 先说我被 Rev.D 纠正的三处

### 1.1 我第一轮的 P16 证据不能推广到 CREATE TABLE —— 这是我的推理错误

O 在答复 §3.1 说：现有 migrator 对 `ADD COLUMN` 逐列验证，
但 `CREATE TABLE` 路径**主要只核验表存在，不完整核验表内列与复合索引**。

我独立复核了 `backend/schema/migrator.py:228-255`，**完全属实**：

```python
ct = _CREATE_TABLE_RE.match(stmt)
if ct:
    if not self._table_exists(cursor, ct.group(1)):
        missing = True
    continue                      # ← 只验表存在就走
m = _ADD_COLUMN_RE.match(stmt)
...
self._verify_column(cursor, key, table, column, definition)   # ← 逐列严格验收
```

**这直接推翻了我第一轮 B-01 论证里的一个推广。** 我当时的实证是 v1.6.3.6 第三轮变异 P16
（一列 `INT` 改 `INT(11)` → migrator 结构验收失败 → app 起不来），
但我复核了那条证据的来源：`151_audit_history_completeness.sql` 是 **4 条 ALTER TABLE ADD COLUMN**，
正是会逐列验证的那条路径；而 `150_metadata_audit_jobs.sql` 是 **3 条 CREATE TABLE**，
走的是只验表存在的那条。**Copilot 的 11 张表全是 CREATE TABLE。**

也就是说：**按现有 migrator，Copilot 表里写错一个列类型根本不会让启动失败——它会被静默接受。**
我用 ADD COLUMN 的证据去推 CREATE TABLE 的结论，这一步不成立。

需要说清楚的是，**B-01 的结论没有因此失效，但理由变了**：
- 我原先强调的"类型写错 → 启动中止"这条机制，对 CREATE TABLE 表其实不成立；
- 但 CREATE TABLE 仍可能因**空间、权限、锁、字符集/排序规则、语法**等在执行期失败并向上抛断，
  方案乙对这些仍然有效；
- 而新暴露的问题**比我原来担心的更糟**：结构错误会被**静默接受**，然后在运行期以更难诊断的方式炸。

O 的处理是对的——新增 `backend/schema/contracts.py` 严格校验原语，A/B 两组共用，
并明确写着"当前 migrator 对 CREATE 只核表存在……**不能把已有能力写成足够**"。

### 1.2 我 §7.7 写的"沿用迁移器校验和＋完整结构验收"是个无法兑现的要求

我在方案乙合同里要求 B 组"仍做列类型/可空/默认/索引的完整结构验收"，
并写"沿用 Rev.C §10.1 原文"。但由 §1.1 可知，**现有 migrator 根本不提供这个能力**，
我那条要求当时无法兑现。O 补出了缺的那块（contracts.py ＋ 完整合同校验），
**这不是执行我的裁定，是补上了我裁定里缺的前提。**

### 1.3 "约 15 列 / 降 88%" 的说法，O 的订正成立

O 指出：A 组 runtime 因跨进程代次需要新增
`module_schema_state/revision/epoch/reconciled_epoch/checked_at`，
所以"约 15 列"不是 Rev.D 的精确 DDL 计数；**更重要的是，列数比不等于停服概率下降比。**

**这条订正对，而且是我反复犯的同一类错**（用一个可数的代理量去表述风险下降）。
准确的说法只能是：**A 组新增表数从 11 降到 2，落在失败关闭链路里的 DDL 面显著变小**；
至于停服概率降低多少，没有数据，不该给比例。我撤回"88%"这个数字。

## 2. 八个定点逐条复核

我按 O 给的定点清单逐条回 DETAIL 原文核对，不采信 §2 那张对照表。

### R3-01 分组及台账 —— ✅ 通过

§10.1 精确列明：A 组 `copilot_subjects` / `copilot_runtime` 在
`backend/schema/v16/160_copilot_identity_runtime.sql`（key `v16_160_copilot_identity_runtime`）；
B 组 9 表在 `backend/copilot_schema/v1/001_business.sql`（key `copilot_v1_001_business`）。

**B 组不被核心 loader 发现：我独立验证了。**
`backend/schema/loader.py:9` `SCHEMA_DIR = Path(__file__).parent` 即 `backend/schema/`，
`_VERSION_RE = ^v(\d+)$` 只匹配其直属子目录。`backend/copilot_schema/` 在扫描根之外，
**不会被自动发现**。§10.1 还写死"绝不把 B 文件放入 backend/schema/vN 再试图事后捕获它的错误"——
这条很关键，堵住了"放进去再 try/except"这种取巧写法。

N-08 若需索引，单列核心迁移 `161_metadata_job_copilot_lookup.sql`，不进 B 组 —— 符合我 §7.2
"B 组不得增加对既有表的写接点"。

### R3-02 完整结构验收与启动失败边界 —— ✅ 通过

§10.4 要求校验"表存在/引擎/排序规则、列全集/类型及长度精度/字符集/可空/默认、
主键/唯一性/索引名/列序/前缀长度"，并明确"不把 CREATE 内列、复合主键或索引当成只验表存在"。
DDL、合同与程序注册的 hash 一并进发布清单，新增解析须有正反例。

**O 另外堵了一个我没想到的坑**：§10.4 要求 A 组**不得沿用旧迁移的"表丢失自动重建"分支**。
我核了 `migrator.py:239-243`，该自愈分支（QC-DEFECT-07）确实存在且对所有 CREATE TABLE 生效。
若 `copilot_subjects` 被删后被静默重建成空表，**全部存量账号会被重新分配 subject，
旧 grant/session 全部成为孤儿**——虽然方向是安全的（不继承），但属于静默孤儿化，
运维不会察觉。O 要求这种情况失败关闭、强制人工介入，**判断正确**。

### R3-03 故障期身份与两条只读例外 —— ✅ 通过

§10.4 降级闭集与我 §7.7 逐项一致，且比我写的更全：
`capabilities` 200 带 `mode=UNAVAILABLE`/`reason_code`、`help` 200 本地帮助，
**其余 `/copilot/*`、全部 `/copilot-admin/*` 与 `/copilot-audit/*` 统一 503**
（我原来把 `copilot-audit` 归在"其余"里，Rev.D 单列更清楚），
且"schema 门禁先于任何 B 组对象/幂等查询"。

账户事务对 B 组 SQL 次数为 0；`help` 不读 B 组/模型配置/实例 grant；
故障期不写 B 组审计、只记无正文本地诊断，**且不得为"日志必须写成功"反向阻断账户管理**——
最后这句是我合同里漏掉的一个死锁风险，O 补上了。

### R3-04 恢复对账与跨进程代次 —— ✅ 通过

§11.6 五步对账与我 §7.5 一致，且补了三处我没写的：
- 按 `subject_id` 核对而非 username 重连，并明确"对账不是权限开始失效的时刻"
  （呼应我 §7.4 的结论，措辞更准）；
- 预算结算以"活动→终态同一 CAS 事务"为一次性标记，重复恢复不二次收费；
- 每批 ≤100 行、单事务 ≤1 秒、**批间释放 runtime 行锁**，不阻塞账户管理直到对账结束。

跨进程代次（`module_schema_epoch` / `reconciled_epoch`）是 Rev.D 新增的，
我第二轮没考虑到 **uvicorn `--workers 2` 下两个 Web 进程各自就绪状态不一致**的问题。
§10.4 要求"每个 Web 进程默认本地未就绪，先完成自身验收，不能照抄另一进程的 READY"，
出站/发布冻结 epoch、旧代次 attempt 拒绝发布。**这是对的，补得好。**

§3.4 与 §11.6 末段把"纯结构故障的对账"和"数据缺失的恢复"分开：
表被删/回滚旧备份/预算审计有缺口时保持 UNAVAILABLE，
**不建空表、不补零、不伪造历史通过对账**。符合本项目一贯的失败关闭取向。

### R3-05 五条发布链路与回退 —— ✅ 通过

§16.3 按两组重写，其中三处我认为写得好：

1. **明确区分"核心安装可用"与"完整 v1.6.4.0 发布通过"**——B 组失败不阻止原工具，
   但也不许伪报整包成功。
2. **给脚本写死可区分的退出码**：`0=READY / 20=核心可用但 B 组失败 / 1=核心或未知错误`，

   这两句是实打实的施工级约束。
3. 补丁链路写明"差分必须含 A/B 两个目录……**不能只匹配 schema/vN**"。

**我本来担心 B 组放在新目录会被打包漏掉，核完发现不成立**：
`make_release.sh:56` 是 `cp -a "${ROOT}/backend"` 整目录复制；
`make_patch.py:82` 走 `copy_tree_filtered(ROOT_DIR/"backend", ...)`，
其 ignore 清单只排除 `__pycache__/*.pyc/.pytest_cache/node_modules` 等，
**`backend/copilot_schema/` 两条链路都会被收进去**。记为阴性结论，免得后面重复查。

回退侧保留 A2/B9 表、两组台账行与 keyring、不 DROP，并要求"旧目录不得残留新 A/B 文件供旧 loader 误扫"。

**O 在 §3.4 另提了一条我和他都没在前两轮想到的**：回退到不维护 subject 的旧版期间，
账号增删不会维护 subject，再升级时身份连续性有缺口。他的处置是保守的——
默认吊销旧代际、重新分配授权、旧正文不按同名承继，并要求写进手册。
**方向对（宁可失去历史，不可错误继承）**，代价是用户会丢失回退窗口前的 Copilot 会话，
这一点手册必须写明。我在此确认该边界可接受。

## 3. Rev.D 新引入的问题

### 3.1 【N-10｜MINOR】关闭 A 组的"表丢失自愈"要改共享 migrator，缺一条回归锁

§10.4 要求 A 组"不沿用旧迁移'表丢失自动重建'分支"。但该分支在
`migrator.py:239-243` 的 `_structure_state` 里，**是所有 CREATE TABLE 迁移共用的路径**
（QC-DEFECT-07 引入，本身是为了解决"整表丢失导致后续 ALTER 撞 1146 不可自愈"的真实缺陷）。

要对 A 组关掉它，就得在共享函数里按文件/键区分行为——**这动的是每条既有迁移都会走的代码。**
Rev.D §10.4 写了"既有迁移校验和与失败关闭回归保持"，但没有点名这条自愈分支的回归。

**建议**（改动很小，只是把要求写明确）：在 §15 增加一条锁——
**既有 CREATE TABLE 迁移的自愈行为必须保持有效，同时对 A 组必须失效**，
两个方向都要有正反例；与 N-01 的既有权限回归一并做受控前后对比。

严重度我按 MINOR：走偏的后果是静默孤儿化（存量账号被重分配 subject、旧会话变孤儿），
方向仍是安全的"不继承"，不构成越权或数据泄漏，但运维不可见。
