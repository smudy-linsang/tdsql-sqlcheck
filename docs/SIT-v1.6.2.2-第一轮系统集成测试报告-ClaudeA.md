   前者是本次修复的目标域，**后者才是次生灾害嫌疑**，逐条核验。

### 5.2 生成式扫描（2304 次审核）——本轮最强的护栏

1152 条 DDL 覆盖：6 种附加列（含 `TEXT`、列级 `UNIQUE`）× 4 种主键形态（含 `PRIMARY KEY … COMMENT`）
× 8 种索引形态（含普通/唯一/带注释/`USING BTREE`/`FULLTEXT`）× 6 种表尾（含 `shardkey`、广播哨兵、
`BROADCAST`、`TDSQL_DISTRIBUTED BY HASH`、二级分区）。

| 分类 | 次数 | 判定 |
|---|---:|---|
| 基线**本来就 E999**（本次修复目标域） | 1008 | 预期内 |
| 基线**可正常解析却发生变化**（次生灾害嫌疑） | **15** | **逐条核验，全部为真阳性** |
| 无变化 | 1281 | —— |
| Q 侧抛异常 | **0** | ✅ |

**15 次嫌疑逐条核验结论**：全部是同一形态 ——
`` `u` VARCHAR(32) UNIQUE `` 列级唯一索引建在**非分片键列**上，
表尾为 `shardkey=sk` / `HASH(sk)`。按 TDSQL 规范"唯一索引必须包含分片键"，
**R054 本就应该命中**；基线因 ADJ-5（`parsed.indexes` 不产出 UNIQUE）漏报，施工后补上。
**15/15 均为真阳性，无一例误报。**

## 6. SIT-02（观察）：宽表解析的性能代价

同机、同数据、20~200 次取平均：

| 列数 | 语句形态 | 基线 parse | 施工后 parse | 倍数 |
|---:|---|---:|---:|---|
| 10 | 无 UK 注释（原本就能解析） | 3.14 ms | 3.97 ms | 1.26× |
| 120 | 无 UK 注释 | 32.93 ms | 40.04 ms | **1.22×** |
| 400 | 无 UK 注释 | 106.08 ms | 129.44 ms | **1.22×** |
| 120 | 含 UK 注释（原本 E999） | 12.02 ms | 77.90 ms | 6.5×（见下） |
| 400 | 含 UK 注释（原本 E999） | 48.41 ms | 255.32 ms | 5.3×（见下） |

两点必须说清楚，否则容易误读：

1. **原本就能解析的语句：稳定 +22%~26%**，来自新增的 source preflight。
   这是全局固定成本，随列数线性增长，**属可接受范围**；
2. **"含 UK 注释"那两行的 6.5× 不是退化。** 基线在这些语句上是**直接 E999 失败**的
   （所以它"快"），根本没做审核；施工后是**真的把表解析出来并完整审核**。
   同版本内的公平对比是"恢复路径 vs 原生路径" = **约 2×**，这是恢复链的代价，
   换来的是从"错误结论"变成"正确结论"。

**建议**：当前单表规模（生产 14 表最宽约 40 列）无影响。
若后续要做**全库批量扫描**，建议先用真实库的 P99 建表语句长度压一遍；
设计文档 §6 观察项 1 已登记"复用 token 流"的优化方向，可作为后续性能专项。

## 7. 需用户知悉的行为变更（设计如此，非缺陷）

`CONSTRAINT … UNIQUE`、`SERIAL`、`SERIAL DEFAULT VALUE` 这三类形态，
按设计（KFN-5 / KFN-6）现在会**报 E999 并整句失败关闭**，而基线是**静默通过**的。

这是**刻意的安全取舍**：这些形态的唯一语义无法完整供给 R054，
与其静默漏审，不如显式报错。但它是**用户可见的变化**，运维需要知道。

**现网暴露面实测**（211 条真实语料 + 生产 14 表）：

| 形态 | 出现次数 |
|---|---:|
| `CONSTRAINT … UNIQUE` | **0** |
| `SERIAL` | **0** |
| 列级 `UNIQUE` | **0** |
| `UNIQUE … COMMENT` | 1（fixture） |
| `PRIMARY KEY … COMMENT` | 0（但用户已确认**内网实际存在**，故立项 DEF-3） |

即在可见样本中暴露面为 0；内网真实分布超出本次样本范围，建议上线后观察首周 E999 构成。

## 8. SIT-01（MAJOR）：版本号未更新

```text
VERSION                       → 1.6.2.1   （应为 1.6.2.2）
backend/config.py APP_VERSION → "1.6.2.1" （应为 "1.6.2.2"）
backend/config.py APP_DESCRIPTION → 仍是 V1.6.2.1 的描述文案
```

设计说明书施工检查单 **C-16** 明确要求：
「版本号更新：`VERSION` 与 `backend/config.py` 的 `APP_VERSION`、`APP_DESCRIPTION` → `1.6.2.2`」。

这不影响审核正确性，但会让**部署后的系统自报版本号是错的** ——
对银行级工具，运维靠这个确认现网跑的是哪一版，必须修。

**整改**：三处一并更新，`APP_DESCRIPTION` 补上本次修复内容；改完重跑
`--mode implementation`（这两个文件不在 bundle 内，不影响哈希）。
