# v1.6.2.2 第一轮全项目用户验收测试报告

评审/测试人：智能体O；测试日期：2026-08-28；结论：**不通过，当前不准出**。

## 1. 给项目负责人的结论

两个原始问题已经修复：gg77 的“假 UNIQUE 导致 R054”消失；gg78 的“唯一索引 COMMENT 导致解析崩溃及 R003/R004/R005/R028 连带误报”消失。既有 HASH 分片表和广播表样例也没有重新出现目标 R077/R054 误报。

但本轮发现一个不能放行的核心漏洞：**解析器已经识别出必须失败关闭的 KFN，审核器却能因为 SQL 注释中出现 `CREATE VIEW` 等文字而删除 E999，最终在即时审核和文件审核页面显示“审核通过”。** 这不是单纯日志不正确，而是用户实际拿到了错误的通过结论。详见 UAT-O-01。

本报告登记 **1 个 BLOCK、5 个 MAJOR、1 个 MINOR**，另列规则既有缺口、服务层差异和测试工程观察。这里的严重度衡量用户影响，不等于全部由本次代码引入：已对照旧版本，明确区分“本次安全契约未闭合”“版本发布遗漏”“历史遗留”。不能把历史缺陷都算到 Q 的改动上，也不能因为历史存在就把现有用户体验写成通过。

完成的证据包括：

- 独立全量回归 **1,384 passed**；正式 implementation runner 再执行一次全量也为 **1,384 passed**。这是两次同类回归，不合并计算为 2,768 个不同用例。
- sqlglot **29.0.0 / 30.14.0 / 30.17.0 各 680 passed**，冻结用例 **71 passed**，设计与实现 bundle 校验通过。
- 同一份 **1,000 条独立输入**在修复前后逐项对照；119 条规则注册及定义相同，**114 条有引擎实际命中证据**，5 条有既有可达性/实现缺口。
- **19 个当前可见功能页面、深度诊断内 9 个页签**的实际浏览器入口覆盖；保存 **65 组页面截图 + DOM 快照**。完成了粘贴 SQL、文件选择上传、在线提取、快照对比、扫描、状态操作、跨角色登录、实例新建和编辑等实际点击流程。
- 269 条补充 HTTP 记录，无 5xx；其中 3 个 403 是预期拒绝，2 个引擎/服务层差异是旧有存储函数切分问题。HTTP 200 **不代表业务验收通过**。

**边界声明：** 本轮不是“全项目所有功能都通过”，更不是“119 条规则所有边界都正确”。没有真实 TDSQL Proxy/SET、可用 MonitorDB、跨实例差异和真实大表增长数据；这些路径明确未验收。续接时浏览器控制能力已不可用，原有 65 组证据完整保留，但未补完的 ZK 发现、实际下载落盘及部分破坏性操作没有被计入通过。缺口详见 §8。

### 3.4 119 条规则是否受损

- 119 条注册数量、规则 ID、分类等定义信息与基线相同；浏览器规则库也显示 119 条，9 类数量为 5/22/9/10/14/8/5/4/42。

- R025/R035/R038/R049/R059 本轮未触发，原因见 §7.1。它们不能被写成已通过，亦未发现是本次修复新引入。
- 浏览器实际上传 100 条分布式语料，显示 2 通过、98 未通过；这是包含违规 SQL 的业务审核结果，不是“UAT 通过率 2%”。不能用 100 条文件批次替代 119 条逐项判据。

逐规则账本：[rule_coverage_119.md](evidence/v1.6.2.2-uat-o-r1/rule_coverage_119.md)。结论是：**在已执行的规则样本和差分域内未发现额外的规则定义丢失或未解释命中漂移，但本次强制失败关闭没有贯通最终审核链路。** 因而目前不能对“核心能力未受影响”签署无条件通过。

### 5.1 UAT-O-01：强制失败关闭在最终审核器被绕过

#### 复现与期望

admin 进入“SQL审核 → 即时审核”，选“分布式规则”，粘贴下列 SQL 后点击“开始审核”。不执行建表，只审核。

```sql
CREATE TABLE t_guard (
  id BIGINT NOT NULL COMMENT 'id',
  sk BIGINT NOT NULL COMMENT 'sk',
  u INT NOT NULL COMMENT 'u',
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'created',
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'updated',
  is_deleted TINYINT NOT NULL DEFAULT 0 COMMENT 'deleted',
  PRIMARY KEY(id,sk),
  CONSTRAINT uk_u UNIQUE(u)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='plain'
  shardkey=sk /* CREATE VIEW */;
```

- 按已批准 Rev.Q：`CONSTRAINT ... UNIQUE` 属于已知保真边界，必须 E999、失败关闭；这里不把“合法但暂不支持”偷换为“TDSQL 语法非法”。
- 实际：[49 截图](evidence/v1.6.2.2-uat-o-r1/49-kfn-complete-failopen.jpg) 显示绿色“审核通过”，没有 E999、没有 R054。
- 只删掉 `/* CREATE VIEW */`，其余不变：[50 对照](evidence/v1.6.2.2-uat-o-r1/50-kfn-control-blocked.jpg) 正确出现 E999。
- 用真正文件选择上传同一 [uat_kfn_comment.sql](evidence/v1.6.2.2-uat-o-r1/uat_kfn_comment.sql)：[51 截图](evidence/v1.6.2.2-uat-o-r1/51-file-kfn-failopen.jpg) 为 1 条、通过 1、通过率 100%。
- HTTP `/api/v1/audit/sql`、`/api/v1/audit/file`、`/api/v1/audit/upload` 同样返回业务通过；不是仅浏览器展示错误。

独立矩阵统计：21 条 KFN + 表注释字符串中 18 条没有必需的 E999；54 条 KFN + 块注释/行注释/含类注释文本的字符串全部缺 E999。合计 **72 条丢失强制错误**，其中完整列定义的 18 条 CONSTRAINT UNIQUE 样例彻底绿色通过；其他样例可能仍有其他规则，不能说 72 条全通过。

#### 发生原因和传导机制

1. `backend/engine/parser/parser_legacy.py:2254` 附近已把 preflight 的 KFN 写入 `parsed.parse_error = KNOWN_FIDELITY_GAP[...]`。UNIQUE AST 不完整另有 `UNIQUE_SEMANTICS_INCOMPLETE`，约在 2626 行。
2. `backend/engine/checker.py:137` 附近对**整个原始 sql 字符串**做 `CREATE VIEW/PROCEDURE/FUNCTION/TRIGGER` 或 `LOAD DATA/XML` 正则匹配，没有区分实际语句、注释和字符串。
3. `parse_error` 只有在“不是上述对象/LOAD”时才转为 E999。于是 CREATE TABLE 的普通注释被误认为特殊语句豁免，KFN 标记没有成为用户可见的阻断。
4. 该 UNIQUE 结构又属于当前不能保真的范围，R054 不能充当替补阻断。样例补齐了 R036/R037 建议字段等其他干扰项，最终 `passed=true`。

**为什么正式矩阵全绿仍漏掉？** 正式矩阵证明了大量 KFN 的解析器/常规 checker 路径，未组合“合法注释或字符串恰好含旧豁免关键字”这一审核器边界。checker 自身未在本次改动，因此“只修改 parser/R054”不等于最终行为安全，必须检查消费者。

#### 可直接实施的修复建议

1. 为已证明的保真失败使用明确、不可被特殊语句豁免的信号（如结构化 failure category / `must_fail_closed`）；在 checker 先处理此类错误并生成 E999，再处理普通语法错误的历史豁免。优先使用显式字段，不把所有逻辑长期绑在字符串前缀上。
2. 特殊语句识别使用项目已决定采用的 sqlglot 词法结果/可靠 AST，识别真正语句类型；注释、COMMENT 字符串、DEFAULT 字面量、标识符内的文字不能启动豁免。语义注释仍按既定 TDSQL 策略处理，不能一把删掉所有注释。
3. 不要直接移除所有 procedure/trigger/view/LOAD 豁免，不要扩大 source scanner 白名单来“绕开” KFN，不要修改 119 条业务规则数或降低 E999 严重度。这些会扩大影响域。
4. 增补端到端门禁：本轮 75 个 KFN 鉴别输入保留完整断言；三入口均检查 E999、`passed=false`、统计未通过、报告不得显示绿色通过。后续在线提取同类 DDL 也须验证最终报告，而非仅 parse_error。
5. 反向用例覆盖真正的 CREATE VIEW/PROCEDURE/FUNCTION/TRIGGER、LOAD DATA/XML 及已有 TDSQL 语义注释策略；普通注释文字变更不应改变审核结论。至少重跑冻结 71、680×3、全量、1,000 差分及浏览器 49–51 对照。

验收关闭条件：本轮 72 条 E999 缺失归零，且已支持语法没有因修豁免而新误报；不能只修示例中的 `CREATE VIEW` 一个字符串。

### 5.3 UAT-O-03：网关报告有指标但没有正文

**复现：** 在网关日志分析上传 [uat_gateway_interf.txt](evidence/v1.6.2.2-uat-o-r1/uat_gateway_interf.txt)，含 12.5ms 和 1500.2ms 两条记录；[28](evidence/v1.6.2.2-uat-o-r1/28-gateway-upload.jpg) 显示总2、慢1、均值756.35ms、最大1500.2ms。点击“查看报告”，[29](evidence/v1.6.2.2-uat-o-r1/29-gateway-report-blank.jpg) 只有页脚。[实际 HTML](evidence/v1.6.2.2-uat-o-r1/gateway_report.html) 不是截图缺失，而是正文分析块未生成。

**原因机制：**

1. `backend/services/gateway_log_service.py:98` 附近把上传日志改名为 `uploaded_<pid><suffix>`，传给分析器 `--files`。
2. `.../gateway_log_analysis/analyze_gateway_log.py:697` 的 `_organize_specific_files()` 只识别 `interf/sql/..._instance_<port>` 格式，内部临时文件名被排除。即使用户文件名符合规范，也仍会被服务端改名。
3. 无有效分组时 `_report_html()`（1543 行附近）仍可生成仅框架/页脚的 HTML；服务只检查输出文件存在，没有校验有效分析输入/正文，并未据此判定失败。
4. 页面指标来自另一段 timecost 解析，因此指标非零和报告空白可以同时发生。

**处理：** 为每个请求建立独立临时目录，以受控合法文件名和类型元数据传给分析器，或修改分析器接受显式 log_type/instance 元数据；不能直接拼接用户路径。校验进程返回码、有效文件数、有效记录数和报告章节，分析为空时给明确错误而不是保存“成功”。统计和报告尽量共享同一解析结果。PID 命名并发碰撞是静态风险，未做并发复现，修复时应一并避免。

**关闭测试：** interf/slow_sql、无效日志、零记录、规范/非规范上传文件名、多文件及并发隔离；必须断言报告实际有两条样例对应的数据/章节。既有测试只断言包含 HTML 字样或有响应，不能继续作为内容完整性验收。

## 7. 既有缺口与补充观察（与正式7项分开计数）

### 7.1 五条规则没有本轮正向触发证据

| 规则 | 本轮定位 | 可实施后续建议 | 本次归因 |
|---|---|---|---|
| R025 | 检查依赖 `alter_actions`，当前解析链没有为目标 ALTER 场景填充；`rules/ddl.py` 约276行 | 为已支持 ALTER shardkey 建立结构提取和正/反例，TDSQL语义按产品支持范围确认 | 既有；不能以“注册存在”替代可用 |
| R035 | 依赖元数据中的 `existing_columns`，实际入口没有提供相应数据 | 明确 CREATE/ALTER 上下文和元数据供给点，真实入口验证，不仅手工注入字典 | 既有供给缺口；不是宣称任何外部注入都无法触发 |
| R038 | 检查 `raw_type` 内 AUTO_INCREMENT，而自增信息在列约束通道 | 消费结构化自增标记，保留兼容语义并补TDSQL样例 | 既有提取/消费错位 |
| R049 | 当前实现直接返回 None；`rules/dml.py` 约370行 | 实现规则或明确标记尚未实现，不能继续对外称已完整覆盖 | 既有占位实现 |
| R059 | BEGIN 语句本身无表，实际元数据收集无法给事务涉及分片表上下文 | 设计多语句事务上下文/元数据关联，再做真正接口批次验证 | 既有流程缺口；不能靠人工元数据注入宣称在线有效 |

这些不因本轮刚发现就自动要求全部塞进索引解析热修；但项目负责人必须看到明确风险台账。若要求“119条都有效且全验收”，这五项和真实元数据覆盖就必须补齐，不能签署假完成。

### 7.2 三个旧语料精确期望不一致

`R023_01`、`R098_01`、`R116_01`（分布式）的精确规则集合期望包含 R036/R037，当前未命中；旧基线也相同。已保留在独立 probe 的 failures 中，没有悄悄改 expected 让统计变绿。建议分别核对这些 SQL 的结构可见性与既有语料期望，再决定修产品还是修测试；本轮不擅自修改双方。

### 7.3 HTTP/服务与直接引擎的旧存储函数切分差异

同一个 `R030_R031` 存储函数样例：直接引擎命中 R030/R031；service 把它当作2条语句，额外报 R001/R003/R004/R005/R028（分布式还多R077）。两种架构均在 HTTP 发现，随后旧基线复现相同结果，证据为 [service_current.json](evidence/v1.6.2.2-uat-o-r1/service_current.json) 和 [service_baseline.json](evidence/v1.6.2.2-uat-o-r1/service_baseline.json)。

原因在 `audit_service.py` 调用 `database.split_sql_statements()` 的链路：分号切分缺少存储程序 BEGIN/END 等语句体上下文。建议统一服务/文件的可识别词法结构切分器，按项目TDSQL支持语法保留routine整体，测试真多语句、字符串分号、注释、函数体；不应只在UI隐藏额外规则。此项为历史功能缺陷，本轮没有将其混入新引擎回归数量。

### 7.4 gg77 的 R104 注释上下文

原始gg77保留的 R104 与列 COMMENT 中全角括号文本有关，旧基线相同。`rules/oracle_compat.py` 约639行的原始SQL字符扫描在语法上下文清洗前发生。建议将“SQL语法位置非法字符”和“自然语言注释/字符串文字”分开鉴别，保留真正语法位置的规则。不要把这个历史误报归因于本次 UNIQUE 修复，也不要删除整个 R104 来消除症状。

### 7.5 回归工程对预存数据有依赖

完全空元数据库的首次运行没有 admin；部分测试通过 reset-password 假定用户已存在，登录401后又影响鉴权状态。只补 admin 的正式 runner 仍有2项失败：PDF跨角色导出和developer/tester慢SQL状态测试依赖预存慢SQL记录；结果为1382 passed / 2 failed，记录在 [implementation_matrix_unseeded.txt](evidence/v1.6.2.2-uat-o-r1/implementation_matrix_unseeded.txt)。

本轮只用 [prepare_regression.py](evidence/v1.6.2.2-uat-o-r1/prepare_regression.py) 明确创建隔离 admin 和一条合成记录，没有改测试断言或产品。随后独立全量及正式runner均1384通过。修复建议：测试自己创建/清理用户、鉴权开关和样例，session fixture 显式检查环境，不依赖已有数据和测试运行顺序；增加全空库一次启动门禁。

### 7.6 规则库搜索粒度

输入 R054 后，UI仍展示所在类别的14条规则（[36](evidence/v1.6.2.2-uat-o-r1/36-r054-rule-detail.jpg)）。`app.js` 的过滤保留类别，但模板仍绑定该类别完整规则数组。若产品定义是按规则搜索，应传递过滤后的行并支持清空恢复；若仅类别定位，应调整占位文案。本项是历史体验观察，不是R054引擎失效。
