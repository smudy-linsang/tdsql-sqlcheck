## 3. 发现的缺陷

### P3-01：报告口径横幅的冲突文案与实际判定策略不符（**已修复**）

**位置**：`frontend/index.html:329`

**原文**：

> 探测与声明不一致，**审核按探测结果执行**，请核实实例配置。

**问题**：这是 **v1.5 的"探测一律优先"语义**。v1.5.1 已改为**保守合并（取更保守者）**——当探测判集中式、声明判分布式时，系统实际采用的是**声明值（分布式）**，而非探测结果。此时该文案会告诉使用者"按探测结果执行"，与事实相反。

**影响**：不影响判定正确性，但**误导使用者对判定依据的理解**——而"让报告自证口径"正是 v1.5 的目标 G4。同一信息在实例列表页（`index.html:936`）的 tooltip 中措辞是**正确**的（"已按保守原则取…"），属两处不一致。

**修复**：改为

> 各判定源结论不一致，已按保守原则取「X」，请点「探测类型」查看多源明细并核实实例配置。

**连带修复**：3 处代码注释仍写"探测优先"（`audit_service.py:183`、`tdsql_manage.py:529`、`sql_audit.py:109`），已同步更正为"多源分级 + 保守合并"。

> `tdsql_connector.py:536` 的"探测优先于声明"**保留不动**——它位于事故记录 docstring 中，描述的是 v1.5 的历史行为，表述正确。

**回归**：修复后 63 项测试全部通过，3 个改动文件编译通过。

## 4. 必须记录：Q 补上了本人设计的一处遗漏

**这是本次交付中最有价值的一项，且不在我的设计文档里。**

### 缺口

我的设计 §5.4 写明"存量数据不回填"，但**只针对新增的 ZK 列**。我**没有处理 v1.5 那个恒真探测已经写进 `detected_instance_type` 的脏数据**。

### 若不处理的后果

v1.5.1 的解析器逻辑是：

```python
raw = saved.get("detected_instance_type")
if raw in (DISTRIBUTED.value, CENTRALIZED.value):
    detected = InstanceType(raw)          # ← 直接采用，不会重新探测
else:
    detected, _ = self._probe_and_persist(connection_id)
```

v1.5 的恒真探测已给**每一台可连实例**写入 `detected_instance_type='distributed'`。升级后该值命中 `if` 分支，**永不触发重新探测** → `SIT-集中式实例A` 仍被判分布式 → 保守合并取分布式 → 跑满 119 条 → **R077 依旧误报**。

> **净效果：全新接入的实例正常，而所有存量实例——包括用户最初报告缺陷的那一台——G1 仍不达成。** 这是一个只在升级路径上暴露、在全新环境测试中完全看不到的缺陷。

### Q 的处理

迁移脚本 E-3 段一次性作废该批数据：

```sql
UPDATE tdsql_connections
   SET detected_instance_type = NULL,
       instance_type_detected_at = NULL,
       instance_type_probe_error = 'v1.5 探测判据经实测证伪，结果已作废（v1.5.1 迁移）'
 WHERE detected_instance_type IS NOT NULL;
```

**并且 Q 在注释里主动回应了我"禁止回填"的约束，说明为何这不违反它**：

> 这不是"凭猜测回填"（明令禁止的是往权威字段写猜测值）——这是清除已被实测证伪的数据，将判定如实下沉至声明值。

**这个区分是正确的。** 禁止回填的本意是"不要凭猜测写入权威字段"；而清除一批**已被实测证伪**的数据，方向恰好相反——它把系统从"持有错误的确定性"退回到"如实的未知"。

**本人已独立推演验证该项的必要性**（见 §2 推演），确认其为升级路径的**必要条件**，非锦上添花。
