## 一、验收结论

Q 对第四轮 8 项问题的整改大部分有效：CR 换行残缺语句已恢复失败关闭；网关报告可嵌入、脚本上下文和部分解析告警均正常；日常巡检旧结果会清理；重复索引名称和列已结构化展示；跨库 EXPLAIN 临时池能释放；正式门禁通过。全量自动化 `1506 passed`，三套 sqlglot 版本未发现核心语料整体漂移。

但本轮发现 **1 个 BLOCK、2 个 MAJOR**：

1. 生产部署明确使用两个 Uvicorn worker，而一次性报告票据保存在进程内字典。30 次双 worker、新 TCP 连接实测中 12 次返回 401，用户点击“查看报告”会随机失败。
2. 索引结构化字段迁移会吞掉任意 ALTER 失败，随后仍把迁移写入 `schema_migrations`。生产升级一旦遇到锁超时、权限、空间等异常，会永久记录“已应用”但实际缺列。
3. 日常巡检把未知程序异常也转换为 422“实例连接失败”，会掩盖真实代码缺陷，破坏 500 告警和故障定位。

因此当前提交不能放行。三项均须修复后再做第六轮 UAT。

## 五、缺陷明细与可实施整改

### O-22（BLOCK）：报告一次性票据使用进程内字典，双 worker 下随机 401

**复现结果：** 在 `AUTH_ENABLED=true`、`uvicorn --workers 2` 下，先由认证连接申请票据，再用新 TCP 连接打开报告。30 次消费中 18 次 HTTP 200、12 次 HTTP 401。浏览器连续 8 次直接点击均成功，是因为同一浏览器复用了上游连接，不能代表生产 Nginx 请求会落在同一 worker。

**发生原因：**

- `deploy/tdsql-sqlcheck.service` 明确以 `--workers 2` 启动。
- `backend/services/gateway_log_service.py` 用模块级 `_REPORT_TICKETS` 字典保存票据。
- 票据签发和报告消费是两个独立 HTTP 请求；两个进程不共享字典。消费请求落到另一个 worker 时必然找不到票据并返回 401。
- Q 的浏览器验证使用连接复用；若用 `AUTH_ENABLED=false`，认证中间件还会完全跳过票据消费，均不能证明生产链路。

**整改机制：**

1. 票据必须进入所有 worker 共享的存储。优先使用现有元数据库：只保存票据哈希、`report_id`、`username`、`expires_at`、`consumed_at`，不得明文持久化。
2. 消费必须是数据库原子操作，例如以“未消费且未过期且报告匹配”为条件执行单条 UPDATE，并以受影响行数等于 1 作为成功判据；先查再改无法保证一次性。
3. 票据签发是产生状态的操作，应由 GET 调整为 POST；前端同步修改并继续禁止把长期 access token 放入 iframe URL。
4. 定时或按批次清理过期票据；错误报告、过期、重放、跨用户均返回统一 401，不泄露票据存在性。
5. 新增真实 `AUTH_ENABLED=true + --workers 2 + 新 TCP 连接` 自动化；至少连续 100 次签发/消费全部 200，100 次重放全部 401。若生产前置 Nginx，还需通过同一 Nginx 入口验收。

**验收标准：** 100 次跨连接首次消费成功率 100%，重放成功率 0%；普通浏览器报告及现有 CSP、sandbox、XSS 用例继续通过。

### O-23（MAJOR）：索引字段 ALTER 失败后迁移仍被记录为已应用

**独立故障注入：** 让 `related_index_name` 的 ALTER 抛出 `synthetic ALTER failure`。实测迁移器继续执行第二条 ALTER，随后仍插入：

```text
v11_110_index_finding_structured
```

证据结果为 `migration_record_inserted_after_failure=true`、`commits=2`。下一次启动会因版本键已存在而直接跳过该文件，缺失字段不会自愈。

**发生原因：** `backend/schema/migrator.py` 对每条迁移语句使用宽泛 `except Exception`，只记录 warning、不回滚、不区分“字段已存在”和真实失败，循环结束后无条件写入 `schema_migrations`。本次 `110_index_finding_structured.sql` 有两条 ALTER，运行时又已经依赖两个新字段，故该缺陷直接承重 O-18 修复。

**整改机制：**

1. 迁移默认 fail-closed：任一未知 DDL 异常立即中止，绝不能写版本键；记录结构化错误和 request/startup context，并使启动健康检查失败。
2. 不要靠吞 `Duplicate column` 实现幂等。迁移前读取 `information_schema.columns`，分别确认两个字段；不存在才 ALTER，存在则严格校验类型、长度、默认值是否符合设计。
3. 两列全部验收通过后才插入 `schema_migrations`。MySQL/TDSQL DDL 可能隐式提交，不能把数据库事务当成完整回滚保证，必须采用“逐项可恢复 + 最终结构验收”。
4. 增加四类测试：全新库、两个字段均无、仅一个字段存在、首/次 ALTER 注入锁超时或权限异常；最后一类必须无版本记录且下次可重试成功。
5. 双 worker 并发启动必须覆盖；版本键竞争可接受幂等冲突，但最终表结构和版本记录必须一致且只有一条。

**验收标准：** 任一真实 ALTER 失败时迁移状态不得为 applied；缺列时应用不得宣称就绪；恢复条件后重启可自动补齐并完成索引体检。

### O-24（MAJOR）：未知程序异常被包装成 422 连接失败，掩盖真实缺陷

**独立故障注入：** 将 `registry.get()` 替换为 `RuntimeError("synthetic programming defect")`，日常巡检返回 HTTP 422，详情为“实例连接失败：synthetic programming defect”。直接调用转换器也得到 `InstanceConnectionError`。

**发生原因：** `daily_inspect.py` 捕获 `registry.get()` 的全部异常并调用 `translate_db_error()`；后者对不认识的异常仍无条件返回 `InstanceConnectionError`。这与代码注释及整改目标“未知程序错误保持 500”相反，会让监控把代码缺陷当成用户连接问题。

**整改机制：**

1. `translate_db_error()` 改为严格白名单映射：只识别连接拒绝/超时、认证失败、库不存在、monitordb 不可用等明确类型或稳定错误码；未知异常返回 `None` 或原样抛出。
2. 调用端只在映射成功时抛领域异常；映射失败必须 `raise` 原异常，由统一 500 处理器记录完整堆栈并返回 `X-Request-ID`。
3. 不以错误消息模糊包含关系识别程序异常；优先使用异常类型、MySQL/TDSQL errno 和异常链。
4. 增加表驱动测试：2003/1045/1049 等已知连接错误为 422；`RuntimeError`、`AttributeError`、`TypeError` 为 500 且有请求 ID；日志保留原始堆栈。

**验收标准：** 已知连接异常保持当前友好提示；未知异常不再伪装成 422，监控和日志可准确识别服务端缺陷。

- 注册规则仍为 119 条；1000 条主语料结果与第四轮签字基线逐项完全相同，未发现大范围规则漂移。
- 主语料观察到 114 条规则；补充上下文命中 R035、R059，共证明 116 条有可观测命中。R025、R038、R049 的现有合成样例未命中目标规则，不能把“注册存在”写成“规则有效性已证明”。
- 1000 条语料仍有 3 个已知精确期望差异，均是 R036/R037 缺失，和第四轮完全一致，不是 Q 本轮新增回归。

- TDSQL HASH 分片表未触发 R077，广播表未触发 R054/R077；UNIQUE 注释、KFN 和 R042 浏览器真实点击均通过。
- 以上能证明核心审核能力未整体破坏，但不能替代真实 TDSQL 环境中对元数据相关规则及 R025/R038/R049 的专项验收。
