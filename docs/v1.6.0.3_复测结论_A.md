## 2. P1-01：v9 迁移把"重名"当成"重复"，静默删除真实实例

### 2.1 问题出在去重判据

`backend/schema/v9/090_connection_unique.sql` 第 1 步：

```sql
-- ── 1. 存量重复清理：同名连接（保留最早一条）──
DELETE c1 FROM tdsql_connections c1
JOIN tdsql_connections c2
  ON c1.name = c2.name
 AND (c1.created_at > c2.created_at OR (...));
```

**只按 `name` 匹配就删。** 但**重名 ≠ 重复实例**：

| 情形 | 是不是重复 | 现在的处理 |
|---|---|---|
| 同名 **且** 同 host:port:database | ✅ 真重复 | 删（正确，这是第 2 步在做的事） |
| 同名，**但端点/库不同** | ❌ **两个不同实例，只是命名冲突** | 🔴 **也删**（错误） |

第 2 步（按 `host+port+database` 去重）才是真正的重复清理，那一步是对的。**问题全在第 1 步。**

### 2.2 连带损失比"删一条连接"大

| 损失项 | 实测结果 |
|---|---|
| 连接登记 | 直接删除 |
| **质量门禁配置** | `instance_gate_rules` 外键是 **`ON DELETE CASCADE`** → **一并静默删除**（这是配置，不是历史） |
| 历史数据 | **25 张表**逻辑引用 `connection_id`（`scan_tasks`/`slow_queries`/`audit_history`/`scan_snapshots`/`inspection_tasks`/`scan_schedules`…），全部变成指向不存在连接的孤儿 |
| 可见性 | 迁移日志**不记录删了什么**，运维事后无从追溯 |

### 2.3 责任我也有一份

我在上一轮报告的 SQL 建议里写的是"先清理存量重复（保留最早一条）"，**没有把"重复"的定义写死**。Q 按字面实现成了"同名即重复"。这个歧义是我留下的，我在这里说明。

### 2.4 修复方案（推荐第 1 条）

**方案 A（推荐）：放弃 `uq_conn_name`，只保留 `uq_conn_endpoint`，迁移不删任何数据**

```sql
-- v9 迁移改为：
-- 1) 删掉"按 name 去重"那一整段（重名是命名冲突，不是数据重复，不该用删数据解决）
-- 2) 只保留"按 host+port+database 去重"——那才是真重复
-- 3) 只建 uq_conn_endpoint (host, port, `database`)
ALTER TABLE tdsql_connections ADD UNIQUE KEY uq_conn_endpoint (host, port, `database`);
```

理由：

- **端点唯一才是防重复导入的实质约束**——同一个 host:port/库被登记两次才是真问题；
- **名字重复不影响正确性**，而且用户可能是有意的（同一业务系统在不同环境同名）；
- 这样迁移**完全不需要删任何数据**，本条风险直接归零；
- 仍想防重名的话，应该在**应用层建连接时提示"该名称已存在，是否继续"**，而不是在数据库层强行删。

**方案 B（若坚持要 `uq_conn_name`）：迁移遇到重名必须中止并报错，绝不自行删除**

```sql
-- 先探测冲突，有冲突就让迁移失败，把清单交给管理员人工改名后再升
SELECT name, COUNT(*) c, GROUP_CONCAT(CONCAT(host,':',port,'/',`database`)) endpoints
FROM tdsql_connections GROUP BY name HAVING c > 1;
```

**无论选哪条，还必须补三件事**：

1. 删除任何连接前，先处理 `instance_gate_rules` 的 CASCADE 与 25 张表的逻辑引用（要么迁移到保留的那条连接上，要么明确记录为孤儿）；
2. 迁移日志**逐条记录删了什么**（连接 ID / 名称 / 端点 / 关联记录数），不能只打一句"应用迁移"；
3. **升级手册措辞必须改**。现在写的是：

   > "升级后实例列表可能出现此前的重复连接被合并为一条，**属预期行为**"

   这句话有两处不实：**不是"合并"（是删除，数据没有被并过去）**，被删的**也不一定是"重复"**。运维照这句话会直接接受一次真实的数据丢失。

### 2.5 为什么 Q 的自测没发现

Q 的用例覆盖了 `IMPORT_CONFLICT` 链路（ZI-10）和手工建连路径的唯一约束兜底，**但没有一条覆盖迁移本身的去重行为**，更没有"同名不同端点"这一情形。

**必须补的用例**（R-12 反向鉴别）：

- 老库存在同名不同端点的两条连接 → 升级后**两条都必须还在**；
- 老库存在同名同端点同库的两条连接 → 升级后合并为一条，且**关联数据不成孤儿**；
- 被删连接若有 `instance_gate_rules` → 必须有明确处置，不得静默 CASCADE。
