## 5. 逐行代码审查要点

### 5.1 写得好的地方

| 位置 | 评价 |
|---|---|
| `zk_connection_import_service.commit()` | 单事务、全有或全无、批次+明细双表审计、失败批次独立短事务留痕、提交后 `instance_type_service.invalidate()`。异常分类处理（`ZKImportCommitError` 直接抛、其他包装成 `IMPORT_TRANSACTION_FAILED`），且**不回显原始异常内容** |
| `_list_business_databases()` | 任一 Proxy 枚举失败即整实例预检失败（`BUSINESS_PROXY_INCOMPLETE`），并在注释里正确援引 R-15；跨 Proxy 目录一致性校验；`SHOW DATABASES` 无标识符拼接，无 R-10 风险 |
| `_discover_with_kazoo()` | `kazoo` **惰性导入**，缺失时转 `ZKDiscoveryUnavailableError("Python ZooKeeper 客户端不可用")`；带 `stage` 变量做失败阶段定位，日志不带凭据 |
| ZK 配置服务 | 口令加密存储、不回显浏览器（UI 上写明"口令不会返回浏览器；仅加密保存"） |

### 5.2 🟠 P2-01：唯一约束缺失，事务内"复查"挡不住并发

**代码现状**（`zk_connection_import_service.py::commit`）：

```python
# 事务内再检查，阻止两位操作者的预览并发覆盖同一连接。
by_endpoint = conn.execute("SELECT id FROM tdsql_connections WHERE host=? AND port=? AND `database`=? LIMIT 1", ...)
by_name     = conn.execute("SELECT id FROM tdsql_connections WHERE name=? LIMIT 1", ...)
if by_endpoint or by_name:
    raise ZKImportCommitError("IMPORT_CONFLICT", ...)
```

**注释声称能"阻止两位操作者的预览并发覆盖同一连接"，但实际挡不住。** 实测 `tdsql_connections` 上的索引只有：

```
PRIMARY (id)              UNIQUE
idx_conn_default (is_default)  NON-UNIQUE
```

**`name` 和 `(host, port, database)` 都没有唯一约束。** 我直接插了两条同名连接：

```
同名连接插入 2 次 → 库中实际 2 条 → 无唯一约束
```

在 MySQL 默认 REPEATABLE READ 下，那两条 `SELECT` 是非锁定一致性读，**不产生间隙锁**，两个并发事务会双双通过检查再双双插入：

```
T1: SELECT → 无冲突          T2: SELECT → 无冲突
T1: INSERT ✓                 T2: INSERT ✓     ← 重复连接产生
```

**触发场景**：两位管理员同时导入有交集的选择；或一位管理员双击/超时重试。

**影响**：实例列表出现同名同端点的重复连接，后续扫描、门禁、实例类型判定都会按两个独立实例各跑一遍。

**修复方案**（推荐第 1 条，一次解决且同时保护手工建连接路径）：

```sql
-- 迁移 backend/schema/v9/090_connection_unique.sql
-- 先清理存量重复（保留最早一条），再建唯一约束
ALTER TABLE tdsql_connections ADD UNIQUE KEY uq_conn_name (name);
ALTER TABLE tdsql_connections ADD UNIQUE KEY uq_conn_endpoint (host, port, `database`);
```

并在 `commit()` 里捕获重复键错误，转成既有的 `IMPORT_CONFLICT`，保持"零连接写入"的语义不变：

```python
except pymysql.err.IntegrityError as exc:
    conn.rollback()
    raise ZKImportCommitError("IMPORT_CONFLICT", "提交期间发现既有连接，未创建任何连接") from exc
```

> 备选方案是把两条 `SELECT` 改成 `... FOR UPDATE`，但它只保护导入这一条路径，手工新建连接仍可绕过。**唯一约束是根治。**

**必须补的回归用例**（R-12）：两个并发 `commit` 提交同一候选 → 恰好一个成功、另一个收到 `IMPORT_CONFLICT`，且库中只有一条。

### 5.3 🔵 P3-01：升级手册未提示新增依赖 `kazoo`

v1.6.0.1 在 `requirements.txt` 新增 `kazoo>=2.10,<3`（ZK 客户端），但 `v1.6.0.1_upgrade_manual.md` 与 `V1.6.0.1全量更新部署说明.md` **均未提及**。

**我踩到了**：容器里依赖是上一版装的，跑全量套件时 `test_zk_discovery.py` 两条 kazoo 用例直接 `ModuleNotFoundError` 失败。装上后 1165 全过。

**影响面已核实，属可控**：

- `kazoo` 是 `kazoo-2.11.0-py2.py3-none-any.whl`，**纯 Python、无 ABI/架构风险**，离线打包安全（这一点比我在 v1.5.3 评审里担心的 paramiko 好得多）；
- 导入是**惰性**的，缺失时**应用照常启动**，只有 ZK 发现返回 503 且错误信息清晰（"Python ZooKeeper 客户端不可用"）。

所以不阻断，但离线升级时若运维只替换代码目录而没重跑 wheels 安装，会出现"其他功能都正常、唯独 ZK 发现报 503"的困惑现象。

**修复方案**：升级手册补一节：

```markdown
## 依赖变更（v1.6.0.0 → v1.6.0.1）
本版新增 Python 依赖 kazoo>=2.10,<3（ZooKeeper 客户端，纯 Python 包）。
离线升级必须重新执行依赖安装，否则 ZK 自动发现将返回 503：
    <venv>/bin/pip install --no-index --find-links ./wheels -r requirements.txt
验证：<venv>/bin/python -c "import kazoo; print(kazoo.__version__)"
```
