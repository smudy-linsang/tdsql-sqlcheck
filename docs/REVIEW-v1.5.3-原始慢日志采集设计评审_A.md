## 1. 总评

这是一份**能照图施工的设计**，不是方案陈述。几处判断我认为是对的，而且是这个项目吃过亏才换来的：

- **时间口径分三层写死**（`event_time` / `collected_at` / SQL 执行时间三者严格区分，页面必须常驻标注）——这正是 v1.5.2.3 monitordb 时间窗那次的教训，这次在设计阶段就堵住了。
- **D5「尾块不完整绝不推进游标」**、**§14 失效方向表**——严格遵循 R-15，宁可延迟一轮也不把半条 SQL 当完整事件，宁可标红"覆盖不完整"也不给"零慢SQL"的假结论。
- **D8 + §16.2 实测门禁**——"文件名叫 `interf` 不等于它是 MySQL 风格慢日志"，未实测的格式不得进生产解析器。这是 R-11 的正确用法。
- **拒绝逆向赤兔页面内部 HTTP 接口**、**拒绝 root 免密降级**（§17 末尾"应暂停而不是降级实现"）——两个都是对的，值得肯定。
- **D2 双层路径白名单**——客户端只传 `remote_source_key`，路径由目标机导出器白名单决定。这条边界防住了"有 CheckSQL 配置权限的人借采集账户读目标机任意文件"，比旧的 `gateway_collect.sh` 强一个数量级。

## 2. 必须先补，否则会卡住施工（3 项）

### B1 🔴 SSH 库依赖与离线打包链路冲突 —— 最可能让施工中途卡死的一项

**问题**：设计通篇只说"Python SSH 客户端"（§8.1），**没有指定库**。而 `requirements.txt` 里**没有任何 SSH 库**：

```
requirements.txt: cryptography>=41.0.0   ← 只有这个
                  无 paramiko / asyncssh / fabric
```

这在本项目是**硬约束问题**，不是选型偏好：

1. 内网是**离线部署**，依赖靠 `make_release.sh` 预下载 wheels；
2. 该脚本用 `pip download --only-binary=:all:` 且指定 `--platform manylinux2014_${ARCH} --abi cp${PYTAG}`；
3. **明确支持 aarch64**（鲲鹏/飞腾）；
4. paramiko 会带进 `bcrypt` + `pynacl`，两者都是**含原生扩展**的包。

**风险**：只要 `bcrypt` / `pynacl` 在目标 `(ABI, arch)` 组合上缺 manylinux wheel，`--only-binary=:all:` 会在**打包阶段**直接失败；若被 `|| true` 吞掉则产出缺依赖的包，到目标机才暴露。aarch64 + 较旧 cp 标签这个组合历史上正是 wheel 覆盖的薄弱区。

**需要补充**：

1. 在文档里**明确指定 SSH 库及版本下限**；
2. 增加一节"依赖与离线打包影响"，列出新增依赖的**传递闭包**；
3. 把下面这条**写成施工前置门禁**（阶段 A 第 0 步），在写任何代码前跑通：

```bash
# 对每个实际交付的 (arch, pytag) 组合各跑一次，任何一个失败即需换库
python3 -m pip download <ssh-lib> \
  --platform manylinux2014_aarch64 --platform manylinux_2_17_aarch64 --platform any \
  --python-version 311 --implementation cp --abi cp311 --abi none --abi abi3 \
  --only-binary=:all: -d /tmp/wheelcheck
```

4. **备选方案预案**：若原生依赖过不去，评估改用 `ssh` 二进制 + `subprocess`（目标机通常自带 OpenSSH 客户端，零新增 Python 依赖）。此路仍可满足 D3 的全部安全约束（`-o StrictHostKeyChecking=yes -o UserKnownHostsFile=... -o BatchMode=yes`，不拼接任何用户输入）。**这条建议我认为值得认真评估，不只是兜底**——它同时消掉了 B1 的全部风险。

### B2 🔴 远端导出器是"设计了协议、但没有交付物"

§8 把导出器的协议帧定义得很细（probe / pull / manifest / chunk / eof、SHA-256 校验、偏移连续性），但**从头到尾没说这个导出器本身是什么**：

| 缺失项 | 后果 |
|---|---|
| 用什么语言实现 | 无法排期、无法评审 |
| 如何构建、如何版本化 | 目标机上装的是哪一版？协议 `version:1` 由谁保证？ |
| 如何交付 | `make_release.sh` 的复制清单里**没有它**——发布包里根本不含导出器 |
| 目标机的运行时前提 | 若用 Python，Proxy 机上有没有？哪个版本？（银行生产机未必有 3.9+） |
| 如何升级 N 台 Proxy | 协议演进时的灰度与兼容策略 |

**这不是小事**：在银行生产 Proxy 主机上安装一个新的常驻/被调用程序，是要走变更评审的。设计必须给出交付物形态，否则实施阶段一定卡在"这东西谁写、装什么、怎么装"。

**需要补充**：新增一节「远端导出器交付」，至少包含实现语言与运行时前提、构建产物形态（建议**单文件、无第三方依赖**，最大化目标机兼容性）、随发布包分发（同步改 `make_release.sh` 复制清单）、版本协商（客户端校验导出器版本，不兼容即失败而非降级）、安装/升级/回滚步骤。

### B3 🔴 容量与保留策略在规模上不成立

§13 标题是"容量、保留与可观测性"，但**通篇没有一个容量数字**。按设计给的默认值推算：

```
max_events_per_run = 2000，poll_interval = 60s
→ 单源上限 2000 事件/分 = 2.88M 事件/天
→ 保留 180 天 → 单源上限 5.18 亿行
```

即使按实际的 1% 折算，单源也有 500 万行；而内网是"数百实例"规模，多源叠加后 `slow_log_events` 轻易到亿级。**该表还带 4 个二级索引和一个 TEXT 列。**

更要命的是**现有清理机制扛不住**。`retention_service.py:97`：

```python
cursor = conn.execute(
    f"DELETE FROM {table} WHERE {time_col} < DATE_SUB(NOW(), INTERVAL ? DAY)", (int(days),))
```

**单条不分批 DELETE，且所有表在同一个连接、同一个事务里删完才 `conn.commit()`。** 在亿级表上这会产生超长事务、巨大 undo、锁压力，**并且会把同一轮里其他表的清理一起拖住**。

**需要补充**：

1. **容量估算**：按"每实例每天 N 条慢日志"给出三档（保守/典型/峰值）的行数与磁盘估算；
2. **`slow_log_events` 按 `event_time` 做 RANGE 分区**，保留清理改为 `DROP PARTITION`——O(1) 且不产生大事务。这是这类事件表的标准解法；
3. 若不分区，则**必须**改造 `retention_service` 支持**分批删除**（`DELETE ... LIMIT N` 循环 + 每批 commit），并把大表清理与其他表的清理**解耦到独立事务**；
4. **事件表默认保留期建议下调到 30~60 天**，180 天留给聚合/汇总。设计里"与既有慢 SQL 运行数据基线一致"这个理由不成立——既有 `slow_queries` 是**聚合指纹**，本表是**逐条执行事件**，量级差好几个数量级，不能沿用同一保留期。

## 3. 建议在开工前写进文档的正确性缺口（4 项）

### C1 🟠 copytruncate 后"快速重新长回"会漏判，导致偏移错位

§8.3 规则 3 判截断的依据是 `size < cursor_offset`。但 copytruncate 之后文件 **inode 不变**，若在**一个轮询周期内**被重新写到超过旧 `cursor_offset`，则：

```
轮询 T0: cursor_offset = 10 MB
        ↓ (copytruncate，随后 60 秒内又写了 12 MB)
轮询 T1: size = 12 MB ≥ 10 MB → 判为"正常增长"
        → 从 10 MB 处继续读 → 读到的是【新文件的中段】
        → 偏移全部错位，且唯一键用的正是偏移
```

60 秒轮询 + 繁忙 Proxy，这个窗口是现实存在的。**后果属于"静默读错数据"，正是本项目最忌讳的失效方向。**

**建议**：游标额外保存一个**锚点哈希**（如 `cursor_offset` 前 64 字节的 SHA-256，或文件首块哈希）。续读前先让导出器回传该锚点校验；不匹配即判定为新代际、`generation + 1`、从 0 重读。协议侧只需在 pull 请求里加一个 `anchor_sha256` 字段。

### C2 🟠 「复用既有脱敏」指向不明，而现有实现有三份且互相不一致

D6 要求"复用/扩展既有 SQL 脱敏规则"，但仓库里**已经有三份不同的实现**：

| 实现 | 位置 | 差异 |
|---|---|---|
| `normalize_sql` | `gateway_log_analysis/analyze_gateway_log.py:656` | **截断到 200 字符** |
| `normalize_sql` | `gateway_log_analysis/interf_deep_analysis.py:273` | **截断到 800 字符**，字面量规则也不同（实测两处 diff 不一致） |
| 平台入库脱敏 | `slow_query_service.py:39-52`（`DATA_MASKING_ENABLED`） | 字面量→`?` |

不指定就会产生**第四份**。

**更严重的是截断**：前两份都会截断 SQL。**若 `sql_fingerprint` 在截断后的模板上计算，则前 200/800 字符相同的不同 SQL 会碰撞成同一指纹**——对一个以"逐次执行保真"为立身之本的模块，这是致命的。

**建议**：

1. 文档里**点名**规范实现（建议以平台 `DATA_MASKING_ENABLED` 那条为准并抽成公共函数），顺手把三份收敛为一份；
2. 明确规定：**指纹必须在完整脱敏文本上计算，不得先截断后哈希**；
3. 明确 `sql_template` 的长度策略（`TEXT` 上限 64 KB），超长时截断并置 `truncated` 标记位，**且该标记必须在页面与导出中可见**——不能让使用者以为看到的是完整 SQL。

### C3 🟠 跨节点的逻辑重复没有机械防护

唯一键是 `(source_node_id, file_identity, generation, origin_offset_start)`，**含 `source_node_id`**。若两个节点配置指向同一份底层文件（共享存储/NFS 挂载，或同一台主机被登记成两个 `node_key`），同一条事件会**入库两次且不被发现**。

§16.2 门禁第 6 条要求人工确认"从哪个节点采集、是否会重复"，但这是**人工核对，没有机械防护**。

**建议**：probe 时记录 `(ssh_host_key_fingerprint, file_identity)`；启用节点时校验，若已有另一启用节点声明了相同组合，直接拒绝启用并给出冲突节点。这条成本很低，能把一类静默重复挡在配置阶段。

### C4 🟠 采集吞吐有硬上限，但没有追赶策略

`max_events_per_run=2000` / `poll_interval=60s` ⇒ **单源上限约 33 事件/秒**。一旦 Proxy 慢日志产生速率超过它，采集将**永久落后且滞后无界增长**。

设计有 `raw_slowlog_source_lag_seconds` 指标（很好），但**没有对应的策略**。

**建议**：

1. 文档里把这个上限**显式写出来**，让实施方按实例实际慢日志速率配参数；
2. 定义**追赶行为**：单次运行内允许连续拉取多批直到耗尽时间预算（如 30 秒）或追平，而不是死守 2000 条；
3. 滞后超阈值（如 > 10 × poll_interval）要触发**告警**并在页面标红，而不只是记个指标——否则又变成"看不见的落后"。

## 4. 小问题（4 项）

### 4.1 `TEXT NOT NULL` 无默认值

`sql_template` / `extra_json` / `error_detail` 均为 `TEXT NOT NULL`。MySQL 的 TEXT **不能有 DEFAULT**，而本系统跑在 `STRICT_TRANS_TABLES` 下，任何省略这些列的 INSERT 都会直接报错。代码始终显式赋值即可，但建议在文档里写明，避免施工时踩。

### 4.2 基线提交号

文档表头写 `main @ 1d1d282`，但文档自身提交是 `33947f9`，中间还有若干提交。建议按 O 自己给我提过的那条意见（版本可追溯性）同步修正。

### 4.3 v7/070 的 `INSERT retention_policies` 依赖调用顺序，建议写明

我核实了当前 `init_db()` 顺序是：

```
_create_all_tables  →  run_migrations  →  _migrate_old_tables  →  _init_default_data
```

`retention_policies` 由 `_create_all_tables` 建（`database.py:1186`），在 `run_migrations` 之前，所以 v7/070 的 INSERT **当前能成功**。但这个顺序是 v1.5.2.4 P1-02 修复时才调成这样的，**属于隐式依赖**。建议在 §6.3 加一句注明该前提，并在 U16 里加一条断言，防止将来有人再调顺序时无声打破。

### 4.4 §16.1 建议增补三条用例

| 编号 | 用例 | 对应 |
|---|---|---|
| U17 | copytruncate 后立即写超过旧游标 → 锚点校验触发新代际 | C1 |
| U18 | 两个启用节点声明同一 `(host, file_identity)` → 启用被拒 | C3 |
| U19 | 超长 SQL（> 64 KB）→ 截断标记可见，且指纹在完整文本上计算 | C2 |

## 5. 施工前置建议

按依赖关系，开工前应先做完这三件，顺序不可颠倒：

1. **B1 依赖门禁**：对每个实际交付的 `(arch, pytag)` 组合跑通 SSH 库的 wheel 下载。**不通就换方案（含 `ssh` 二进制路线），不要先写代码。**
2. **B2 导出器形态定稿**：语言、构建产物、随包分发方式、目标机运行时前提。这决定了阶段 A 能不能写 fake exporter 测试。
3. **B3 容量方案定稿**：分区还是分批删、事件表默认保留期定多少。这决定了 v7/070 的建表 DDL——**建表语句一旦落地再改分区，代价远大于现在定**。

C1~C4 建议在阶段 A 开始前补进文档，它们都会影响表结构或协议帧字段（锚点哈希要加进 pull 请求、`truncated` 标记要加进事件表），**同样是越早定越省事**。

## 6. 一句话结论

**设计方向、安全模型和失效方向都是对的，可以作为施工基线；但"用什么 SSH 库、导出器是什么东西、亿级事件表怎么存怎么删"这三件事没定，现在开工必然中途返工。** 建议 O 补完 B1~B3、把 C1~C4 写进文档后再进入阶段 A。
