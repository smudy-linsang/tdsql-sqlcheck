## 0. 一句话结论

**报告测的是 `deploy/tdsql_inventory.sh` 这个独立 shell 脚本，产品自己的发现代码路径（`ZKDiscoveryService` + `/api/v1/tdsql/discover`）全程跑在 Mock 上，一次真实执行都没有。**

报告最终判"通过"，但把它当成"实例管理的 ZK 自动发现功能正确"的依据，是不成立的。

## 1. 最严重：ZK 不可达时，发现接口**编造数据并返回 200**

### 1.1 报告自己实证了这一点

报告 ZK-06 明确记录：

```
ZKDiscoveryService.is_zk_port_open('127.0.0.1:2118') => False
（ZK 在 10.243.21.11，10.243.16.238 无法直接访问 2118 端口）

POST /api/v1/tdsql/discover
Request:  {"zk_server":"127.0.0.1:2118", ..., "force_mock": false}
Response: 200 OK, 3条Mock实例记录
```

**注意 `force_mock: false`——调用方明确要求真实发现，系统却返回了编造数据，且是 200 成功。**

### 1.2 代码证据

`backend/services/zk_discovery_service.py`：

```python
if not use_mock:
    if not self.is_zk_port_open(zk_server):
        logger.warning(f"ZooKeeper {zk_server} 端口不可达，使用 Mock 列表")
        use_mock = True        # ← 静默降级

if use_mock:
    return [ {"service_name": "TDSQL-Set-1(合约库)", "host": "127.0.0.1", "port": 15005,
              "instance_kind": "groupshard", "instance_type": "distributed", ...},
             {... "TDSQL-Set-2(交易库)" ...},
             {... "TDSQL-Set-3(已隔离)" ...} ]
```

这三条不是空列表、不是错误对象，而是**带着业务化名字（"合约库""交易库"）、端口、账号、形态的完整实例记录**。使用者从界面上完全看不出这是假的：

- 响应体里**没有任何 `is_mock` / `data_source` 标识**（已全仓库检索确认）；
- HTTP 状态是 **200**；
- 前端拿到就直接渲染成可注册的实例列表。

### 1.3 更麻烦的：Mock 结果会写进权威源

`backend/api/zk_discovery.py::discover_instances` 拿到结果后立刻：

```python
synced = zk_discovery_service.sync_instance_kinds(results)   # ← results 可能是 Mock
```

而 `sync_instance_kinds` 的匹配规则是「已注册实例的 `host:port` ∈ 该 ZK 实例的 proxy_list」。Mock 的三个端点是 `127.0.0.1:15005/15006/15007`。

**一旦某个已注册实例落在这三个端点上，一次 Mock 发现就会把编造的 `instance_kind` 写进它的 `zk_instance_kind`**——那是 v1.5.1 多源判定链里的 **S2 权威源**，直接决定 27 条 DISTRIBUTED 规则跑不跑。

> 内网实例实际在 15001/15008/15070 等端口，与 Mock 端点不撞，**当前不会触发**。但这条通路本身没有任何闸门：编造的数据可以无阻碍地流进权威源写入路径。

### 1.4 为什么这是设计缺陷而不是小瑕疵

按团队规约 **R-15（失效方向不对称时一律偏向"可见的错"）**：

| 方向 | 后果 | 可见性 |
|---|---|---|
| ZK 不可达 → **显式报错** | 使用者知道发现失败，去查网络 | 一眼看见，可纠正 |
| ZK 不可达 → **返回编造实例** | 使用者以为这就是集群现状 | **完全不可见，且主动误导** |

现在的实现选了后者。**Mock 的正当用途是本地开发联调（`force_mock=true` 显式请求），而不是生产环境的静默兜底。**

### 1.5 修复建议

1. **删除"端口不可达自动降级"这条路径**。`force_mock` 为假时 ZK 不可达 → 返回 **503 + 明确原因**（端口不通 / 认证失败 / zkCli 不存在），绝不返回实例列表。
2. Mock 只在 `force_mock=true` 时生效，且**响应体必须带 `"is_mock": true`**，前端显著标注"演示数据，不可注册"。
3. `sync_instance_kinds` **加闸**：Mock 结果一律不得进入权威源写入路径。
4. Mock 端点从 `127.0.0.1:1500x` 换成明显不可能撞车的保留值（如 `mock.invalid:0`），避免误匹配已注册实例。

## 2. 报告数字自相矛盾，而这正指向最该查的地方

### 2.1 矛盾在哪

报告自己的两处记录对不上：

| 出处 | 记录 |
|---|---|
| **ZK-02** | `ls /tdsqlzk/sets` → **127 个** set 节点 |
| **ZK-02** | `ls /tdsqlzk` → 返回 `agent, groups, sets, group_*...`，**根下存在 `group_` 前缀节点** |
| **ZK-04** | 清单共 **209 条**，`instance_kind` **全部为 noshard**，groupshard **0 条** |

### 2.2 为什么这不可能同时成立

查 `deploy/tdsql_inventory.sh`，`noshard` 行**只有一个来源**：

```bash
# line 382：只列 /tdsqlzk/sets
_noshard_list_raw=$(zk_exec "ls ${ZK_ROOT}/sets")
# line 444：每个 set 出一行 noshard
echo "noshard|${sid}|${ZK_ROOT}/sets/set@${sid}|${sid}" >> "${_inventory_records}"
```

`groupshard` 行来自另一处（`/tdsqlzk/${gid}/sets`，每个 group 出一行代表）。

**既然 `/tdsqlzk/sets` 只有 127 个 set，noshard 最多 127 行。报告却说 209 行全是 noshard——多出的 82 行不可能是 noshard。**

### 2.3 两种可能，都必须查清

| 可能 | 后果 |
|---|---|
| **A. 那 82 条其实来自 `group_*`，但形态被标成了 noshard** | **82 个分布式实例会被当成集中式注册**，27 条 DISTRIBUTED 规则在它们上面**静默不生效**——正是引出整个 v1.5 的那类缺陷，且方向是漏报 |
| **B. "127" 或 "209" 其中一个数字记录有误** | 报告数据不可信，需重测 |

**无论哪种，"全部 noshard 所以通过"这个判断都不能接受。** 而且报告 ZK-02 自己写了根下有 `group_*` 节点，与"零 groupshard"直接冲突，报告全程没有注意到。

### 2.4 一条命令就能定案（下次必做）

脚本**本身就会打印形态分布**：

```bash
# deploy/tdsql_inventory.sh line 466
log "共发现 ${_total_inst} 个实例 (noshard ${_ns_cnt:-0} + groupshard ${_gs_cnt:-0})"
```

**但测试加了 `-q`（quiet），恰好把这行压掉了。** 下次去掉 `-q`，这一行直接给出答案。

补充要跑的两条：

```bash
# 1) 根下到底有多少 group_ 节点
ls /tdsqlzk | tr ',' '\n' | grep -cE '^\s*group_'

# 2) 清单里的形态分布（不依赖脚本日志）
awk -F, '{print $9}' inventory.csv | sort | uniq -c
```

## 3. 断言写法无法失败（违反 R-12）

报告 ZK-04 用的判据是：

> 形态为 noshard 或 groupshard => 全部 noshard **通过**

**这条判据在"全 noshard"时恒为真，永远不可能失败**——它无法区分"确实全是集中式"和"分布式全被误判成集中式"。这正是规约 R-12 要求反向鉴别用例的原因。

**建议改成能失败的判据**：

```
若 ZK 根下存在 group_* 节点，则清单中 groupshard 计数必须 > 0；
否则判定为形态识别失败（而非通过）。
```

同理，`总记录数 == noshard 计数 + groupshard 计数` 也应作为断言，本次的 127/209 矛盾会当场暴露。

## 8. 回答项目负责人的三个问题

**Q1：当前实例管理从 ZK 自动发现的功能是否正确？**

**不能判定为正确。** 报告测的是独立 shell 脚本；产品的发现代码路径全程跑在 Mock 上，真实链路一次没验证过。脚本层的形态区分逻辑和形态映射函数经我核对是对的，但**端到端功能未被验证**。

**Q2：有没有核心问题？**

**有两个：**

1. **ZK 不可达时编造数据并返回 200**（§1）——设计级缺陷，违反 R-15，且编造数据能流进权威源写入路径。这是必须修的。
2. **报告数字自相矛盾（127 sets vs 209 全 noshard）**（§2）——若是形态误判，则 82 个分布式实例会被当集中式，27 条规则静默失效。**必须先查清再谈通过。**

**Q3：有没有需要修复的地方？**

**代码侧必修**：§1.5 的四条（去掉静默降级、Mock 显式标识、权威源加闸、Mock 端点换保留值）。

**测试侧必改**：§3 的断言写法（现在的判据永远不会失败）+ §6 的六条复测清单。

**流程侧**：报告脱敏（§5）。
