## 1. 我对这件事本身的意见

### 1.1 方向我赞成，理由是我自己四轮 SIT 趟出来的

这个工具现在的产出是"R011 违规，第 42 行"。**真正贵的从来不是发现问题，是解释问题。**
我在 v1.6.3.5/3.6 四轮 SIT 里花时间最多的几件事——6000 表库审核到一半失败到底是什么原因、
ECIF 库 0 秒崩溃是新错还是旧条件被改成致命、R043 那个 CREATE 误报算不算误报——
没有一件是"查规则编号"能解决的。一个懂本工具、能把证据摆在一起讲清楚的助手，
确实能省下大量人力。方向没问题。

### 1.2 O 的安全边界定得对，这一点我明确支持

`INV-01 模型不是裁决者`、`ADR-02 不开放模型自主工具循环`、`CP-1 不执行任何目标库操作`、
`默认关闭 / 不自动公网回退` —— 这几条是这份设计里最值钱的部分。
**对一个承担合规门禁职责的审核工具，AI 只能出现在"解释"位置，不能出现在"裁决"位置**，
O 把这条守住了，而且守得很干净（§8.3 动作卡闭集里没有 RUN_SQL/APPLY_PATCH，
§5.2 明确 `CP-1 provider请求中不发送tools/functions`）。这比市面上多数"AI 运维助手"清醒。

### 1.3 但 CP-1 的投入产出比是歪的，这是我最想提的一点

安全机器造得很重：11 张表、独立 runner、四层鉴权、独立 keyring、出站 CIDR 绑定、
幂等/租约/fencing、60 条测试用例、100 题黄金集。**这些我一条都不建议砍**——
在银行环境里它们是必需品。

问题在另一头：**能力太薄**。CP-1 能干的事基本是"解释"和"给不可执行的模板"。
27—40 人日换这个，不划算。而且这不是"再加点功能"能解决的，是两处具体设计导致的：

- **M-01**：脱敏契约把表名/列名全别名化了，导致 P0 的"候选 SQL 修改"永远只能产出
  `executable=false` 的模板（详见 §5.1）；
- **M-05**：`JOB_TROUBLESHOOT` 的取证面只有一条任务记录 + 帮助文本，
  恰好错过本项目最贵的那类问题（详见 §5.5）。

**这两处都是有界的、确定性的改动，不碰 ADR-02，不放开模型自主性。** 修掉它们，
这套安全机器才对得起它的造价。

### 1.4 我的实施建议：先交本地档，用真实使用率决定要不要接模型

设计里 CP-1A 已经是"无模型也能跑通的完整纵向链路"。我建议**把 CP-1A 当作一次独立的
可交付物先上**：规则解释（RULE_RUNTIME 是活的，不靠知识包）＋ 使用指南 ＋ 证据摘要，
**零出域、零模型成本、零供应商依赖**，安全面只剩本地权限一条。

跑一到两个版本，看真实使用率和反馈。如果本地助手都没人用，接上模型也救不回来；
如果用得起来，再做数据出域审批和模型接入，那时的投入是有依据的。
这比一次性压上 27—40 人日再验证要稳得多，也给 CP-GATE-DATA 的审批留出了时间。

## 3. 【B-01｜BLOCK】11 张 Copilot 表进统一迁移链路，与 INV-02 直接冲突

### 3.1 矛盾

- `INV-02`：**Copilot 开关关闭、模型宕机/额度不足不阻断原审核、采集、页面和原报告导出**。
- §16.3：**十一表由统一迁移链路建立**；HLD §7 也写"新增 Schema 迁移失败仍遵循现有数据库迁移失败关闭原则"。

这两条不能同时成立。**统一迁移链路 = Copilot 的表定义出错会让整个 SQL 审核工具起不来。**

### 3.2 这不是理论推演，我有直接实证

`backend/services/database.py:408-411` 明确写着"迁移失败必须失败关闭——绝不降级为告警后继续启动"，
`migrator.run_migrations()` 异常直接 `raise`。而 `ensure_db()` 在 `backend/api/admin.py`、
`bigtable.py`、`dashboard.py`、`slow_query_service.py` 等多处是**导入期**调用的。

我在 v1.6.3.6 第三轮 SIT 做变异测试时实测过这条链路：变异体 P16 把**一个新增迁移文件里
一列**的 `INT` 改成 `INT(11)`，migrator 的结构验收当场失败；同一轮的冒烟里
`from backend.main import app` 直接抛 `MigrationError` 起不来。

现在要一次加 **11 张表、约 200+ 个列声明**，跨 MySQL 8 / 生产实际小版本。
**一个列类型写法不对，整个审核工具停服。** 这个风险面是新的，而且和 Copilot 本身
是否启用无关——`COPILOT_ENABLED=false` 也救不了，因为迁移在开关之前跑。

### 3.3 我的处理建议

**不要削弱现有业务表的失败关闭原则**——那条原则是 v1.6.2.2 UAT-O-23 用事故换来的，
必须保留。正确的做法是把 Copilot 的表**移出**这条链路：

1. Copilot 的 11 张表放在**独立的建表/验收路径**（不进 `migrator.run_migrations()` 的
   失败关闭范围），由 Copilot 自己的启动结构验收负责；
2. 该验收失败 → `COPILOT_CRYPTO_UNAVAILABLE` 同级的 `COPILOT_SCHEMA_UNAVAILABLE`，
   **只让助手不可用，不影响 Web 启动**；这才真正满足 INV-02；
3. 若一定要走统一迁移链路（例如为了复用校验和机制），则必须在 §16.3 增加一条硬门禁：
   **迁移必须在与生产完全同版本的 MySQL 上做过预演**，且回退脚本经实测——
   并且要在设计里明确写出"Copilot 表故障会导致全站不可用"，让 Mr.Linsang 知情后决定。

设计里必须二选一并写明，不能两条都写着。

## 4. 次生灾害评估

### 4.1 【M-02】Copilot 的 GET 端点在现有 RBAC 下是 fail-open 的，而现有回归锁看不见

我把 `check_permission` 完整读了一遍（`auth_service.py:406-484`，fail-open 在第 482 行），实际行为是：

```
第一级：role == "dba"      → allowed = True          （任意路径，含写）
       role == "auditor"  → allowed = method in READ （任意 GET）
       role == "developer"→ 任意 GET  → allowed=True
第二级：按 _PATH_TO_MENU 前缀匹配菜单可见性
       ...都不匹配 → return True  # 无映射的路径默认放行   ← 显式 fail-open
```

也就是说：**只要 `/api/v1/copilot/...` 没登记进 `_PATH_TO_MENU`，
auditor 和 developer 就能 GET 到所有 Copilot 接口**——包括
`GET /turns/{id}/result`（回答正文）、`GET /sessions/{id}/turns`（整轮对话）。
这与 §9.1「auditor 默认关闭 copilot」直接冲突。

O 已经预警了这一点（"未映射端点存在兜底逻辑；新路径必须显式登记并做接口内复核"），
CP-TST-32 也写了"未映射路径覆盖测试通过"。**但这里有个具体的坑 O 没看到**：

现有回归锁 `tests/test_rbac_path_coverage.py` 的文档字符串写得很清楚——
它**只扫描写端点**（POST/PUT/DELETE/PATCH），GET 的 fail-open 是当年被明确接受的
（因为多数 GET 返回的业务数据这些角色本来就能看）。

**而 Copilot 的 GET 返回的是对话正文，不是业务数据，这个前提不成立了。**
照现状实现，CP-TST-32 会"通过"，但 Copilot 的 GET 一条也没被覆盖。

**建议**：新增 Copilot 专属路径覆盖锁，扫描 `/api/v1/copilot*` 的**全部方法**（含 GET），
未登记即失败；并且 Copilot 路由采用 deny-by-default 的独立断言，**不依赖全局中间件**
（全局中间件在结构上就是 fail-open 的，不该把新的正文型接口托付给它）。

### 4.2 【N-01】改 `check_permission` 的风险面

设计说"最小修改 auth_service.py"。现有权限锁共 23 条用例
（`test_rbac_path_coverage` 4 + `test_v2_rbac_matrix` 5 + `test_v3_rbac_instances` 14）。
改动前后必须做受控前后对比（失败集合逐条一致），这在本项目已是成熟做法，写进 §15 即可。

### 4.3 【N-02】升级后存量 JWT 在 Copilot 侧全部 401

§9.1 要求"现有 JWT 的 iat 严格晚于 subject.created_at，否则 401 提示重新登录"。
首次迁移给存量账号分配 subject 时 `created_at = 迁移时刻`，
**因此升级后所有在用 token 的 iat 都早于它 → 每个用户首次用 Copilot 都会被要求重新登录。**

这是设计的正确意图（防止同名重建账号继承旧会话），不是缺陷；
但必须写进部署手册作为**预期行为**，否则上线当天会被当成故障报上来。

### 4.4 性能与资源：我认为没有实质次生风险

- 独立 runner、独立锁、不复用 `metadata_audit_slot`（§7 明确），这一点是对的；
  我在 v1.6.3.5 查过单槽位争用的坑，O 避开了。
- `MemoryMax=1G` + 并发 2，对照内网主机 61.59 GiB 物理内存（`wde.txt:110` MemTotal=64578408 kB），
  余量充足。
- §15.3 的"开/关 Copilot 对照，原接口 P95 劣化 ≤10%"是可执行的量化门禁，口径也写清了
  （固定硬件/并发/样本、3 轮取分布、不只报均值）。**这条门禁我认可，到 SIT 我会照此复测。**

## 5. 安全性与实用性的独立评估

### 5.1 【M-01】P0 的"候选 SQL 修改"在现有脱敏契约下基本交付不出价值

这是我认为最需要 Mr.Linsang 拍板的一条。

**事实链**：
- §4.1：「模型只收到 `E1`、别名 `INSTANCE_1/TABLE_1/COLUMN_1` 及获准结构字段」
- §4.3-2：源字段白名单投影，「ID 变服务端别名」
- §4.3-3：SQL 只出「语句类型、列类型/长度、索引组成、关联关系、命中规则」，
  「字面量值、默认值、分区边界和注释不出站」
- §4.3-5：「输出候选中含别名/值占位符，则 `executable=false, validation=INCOMPLETE_TEMPLATE`」

**推论**：模型从头到尾不知道这张表叫 `cus_bas_merge_log`、这列叫 `cus_no`。
它能产出的最好结果是 `ALTER TABLE TABLE_1 MODIFY COLUMN COLUMN_3 bigint ...`，
按 §4.3-5 必然被判 `executable=false`。

**CP-F04 是 P0**，但用户拿到的永远是要自己把 `COLUMN_3` 映射回真实列名的模板。
对一张 100 列的宽表（内网实测存在 84—114 列的表），这个映射本身就是活儿。
**这不是"功能有点弱"，是 P0 功能与用户预期之间有系统性落差。**

**根子在于数据分级只有三档，缺了最关键的一档**：
表名/列名/索引名属于**结构标识符**，它既不是业务行数据，也不是凭据，
其敏感度与「已经存在于元数据库里的 DDL」是同一量级——而 §4.3 把它和客户数据同等对待了。

**我的建议（需要 Mr.Linsang 定）**，二选一：

- **方案甲（我推荐）**：新增一档可独立审批的投影级别 `SCHEMA_IDENTIFIERS`
  ——只放行表名/列名/索引名，**不放行字面量、默认值、分区边界、注释**，
  默认 **OFF**，仅允许配到已批准的 INTERNAL 网关，且需要与实例授权同级的书面批准记录。
  开启后 CP-F04 才能产出可执行候选；不开启时行为与现设计完全一致。
  这样既保住了严格默认，又让 P0 功能在获批环境里真正可用。
- **方案乙**：维持现状，但**把 CP-F04 从 P0 降级**，并在需求、UI 文案、验收判据里
  统一改口径为"结构级修改建议（模板，需人工补全标识符）"，不让用户产生错误预期。

不能既写 P0 又交付不出可执行建议，那会在 UAT 变成争议。

### 5.2 【M-03】知识包会在两个版本内过时，且过时是静默的

本项目的规则是**活的**：R035 长度已不参与比较、R043 事实链重构、R058 阈值动态、R121 新增，
都发生在最近几个版本。

- §6.1-2 规则取 `RULE_RUNTIME`（动态）——这部分没问题，设计对了；
- §6.1-1（USER_GUIDE 操作说明）和 §6.1-4（TDSQL 厂商语法摘要）是**冻结在知识包里**的，
  带 `app_min/app_max` 和 `expires_at`。

问题有两个：
1. **没有定义知识包随版本重建的强制流程**。§16.3 五条发布链路里只写了"知识包及 hash"
   随包交付，没有写"规则/菜单变更时必须重建知识包并做差异复核"。
2. **版本不匹配是静默降级**：§6.2 检索时"先按产品族、app_version、内核范围、ACTIVE 过滤"，
   超出范围的段被过滤掉 → 表现为"查不到"，而不是"知识包已过期，请更新"。

**建议**：(a) 把"知识包重建 + 差异复核"写进 §16.3 的发布必检项；
(b) 启动时若 `app_version` 落在 `app_min/app_max` 之外，`/capabilities` 与管理健康页
明确报 `KNOWLEDGE_BUNDLE_STALE`，而不是让用户以为助手"不知道"。

### 5.3 【M-04】内容保留 30 天 vs 审计保留 180 天 —— 中间 150 天无法回答"当时发了什么"

- `COPILOT_SESSION_RETENTION_DAYS=30`：正文（含 `model_projection_envelope`，
  也就是**实际发给模型的那份投影**）30 天后清理。
- `COPILOT_AUDIT_RETENTION_DAYS=180`：审计元数据保留 180 天，但 §10.2 明确
  `copilot_audit_events.detail_json` 只放白名单元数据，`copilot_provider_attempts`
  只存 `response_digest`，**不保存请求内容**。

**后果**：第 31—180 天之间如果发生数据外泄核查（银行场景下这是常规动作），
「2026-10-01 我们到底把哪些字段发给了模型」**答不出来**。
`EGRESS_START/EGRESS_END` 事件只证明发生过出域，不能重建出域内容。

**建议**：在 `EGRESS_START` 审计事件里落 `projection_hash` ＋ **投影清单**
（源 kind/ID/字段名列表，不含值），随审计保留期一起留 180 天。
这样既不延长正文保留（不违反最小化），又能在取证时证明"发出去的是哪些字段、不含哪些"。

### 5.4 【N-03】实例授权是单人可自授

`copilot_instance_grants` 要求 `approved_by` 和 `approval_ref`，但这两个字段由操作的
管理员自己填。**一个 admin 可以给自己授权把某实例资料交给模型**——这是内部数据出域的
实际闸门，在银行环境里应当是双人复核。

**建议**：实例授权走两人确认（申请 + 复核分离），或至少在 `copilot_audit_events` 里
把 `GRANT_CHANGE` 标为需要事后强制复核的事件类型，纳入月度审计抽查。

### 5.5 【M-05】`JOB_TROUBLESHOOT` 的取证面太窄，恰好错过本项目最贵的问题

§5.3 固定编排里：`JOB_TROUBLESHOOT: T04 + T01` ——
**一条任务状态记录 + 帮助文本检索**，没别的。

拿我自己四轮 SIT 的真实问题对照：
- 「ECIF 库 0 秒失败」：靠的是比对 v1.6.3.4 的产物（219 对象、`_tdsql_sub` 出现 0 次）
  才认定"这是旧条件被改成致命"，单看一条任务记录得不出结论。
- 「6097 表库审核到一半失败」：靠的是从报错数字 88381164 反推真实体量 42.1 MiB，
  再结合提取统计，才定位到 `*2` 假预检。

**T04 给不出这些。** 而好消息是：**v1.6.3.6 刚刚把需要的证据补齐了**——
`audit_history` 现在有 `skipped_objects / skipped_benign / skipped_abnormal / omitted_results`
（`sql_audit.py:314` 已在列表 API 返回），`metadata_audit_jobs.progress_json` 里有
`enumerated/selected/extracted/skipped_benign/skipped_abnormal`。
**这些恰恰就是回答"这次审核完不完整、为什么失败"所需要的全部事实，而 §4.2 的
metadata_job 适配器字段清单里一个都没有。**

**建议（不碰 ADR-02，全部是服务端固定编排）**：
1. `metadata_job` 适配器的字段白名单显式纳入上述完整性字段；
2. `JOB_TROUBLESHOOT` 的固定编排扩为 `T04 + T03(同库最近 N 条终态，N≤5) + T01`——
   同一 connection+db 的近期任务终态是有界的、确定性的、权限同源的，
   但足以支撑"这是偶发还是必现""上次成功是什么时候"这类判断；
3. 对应地在 §15.4 黄金集里补"报告完整性判读"题（`skipped_abnormal>0` 时
   必须指出本次审核不完整，不得说"审核通过"）。

这三条加起来工作量很小，但会把 F05 从"复述错误码"变成"真能帮上忙"。

### 5.6 【N-04】生产侧缺少对"禁止断言"的确定性输出过滤

§15.4 把「伪造已审核通过 / 伪造实机结果 / 自动执行」列为 **0 容忍**，做法是发布前
跑 100 题黄金集。**但上线之后没有任何持续机制**——`feedback` 只有 ±1 和四个 code。

对 0 容忍项，只靠发布前抽样是不够的：换模型、换知识包、供应商静默升级都会漂移。

**建议**：在 §8 输出校验里加一道**确定性后置过滤**，对闭集短语直接判 `OUTPUT_SENSITIVE`/
`OUTPUT_INVALID` 并降级——例如「已通过审核」「已执行」「已修复」「已扫描」
「性能提升 N%」「已验收」。这是纯字符串规则，无误判成本（这些话本来就不该出现），
而且它挡的正是 0 容忍那一类。

### 5.7 【N-05】缺停用演练与事故处置流程

`COPILOT_ENABLED` 是硬闸，`/copilot-admin/settings` 可进一步关闭，设计都有。
但**没有写"发现疑似数据外泄后，谁、用什么命令、在多长时间内切断"**。
§16.4 只有健康告警。

**建议**：§16 增一节"停用与事故处置"：一条命令级的紧急停用路径（含 runner）、
目标时限、执行人、以及停用后如何保全审计线索。发布前做一次演练并留证。

### 5.8 【N-06】内网模型网关自身的日志策略需要 G 书面确认

§17.2 已经正确区分了 `store=false` ≠ 供应商零留存。但**批准的内网网关是另一个主体**——
它自己会不会把 prompt 落盘、保留多久、谁能查，不在本工具控制范围内。

**建议**：CP-GATE-DATA 的材料清单里明确加一项——**网关侧的日志/留存策略书面说明**，
与供应商留存条件并列。否则本工具这边脱敏做到极致，出了门被网关全量落盘。

### 5.9 【N-07】反馈数据白白浪费了"误报发现"这个最大副产品

`feedback_code` 有 `INCORRECT`，§6.3 明确"用户纠正仅记为该轮反馈，不自动改规则"——
**这个保守是对的**。但设计里没有任何**人看得到**这些反馈的聚合视图。

一个审核工具最值钱的运营数据就是"哪条规则被用户反复质疑"。
R043 那个 CREATE 误报，如果当时有 Copilot 并且有人反馈，会比走缺陷流程早暴露很久。

**建议**：`/copilot-admin/health` 或审计侧加一个只读聚合——按 `scene + rule_id` 统计
`INCORRECT` 反馈数，作为规则维护的输入。不自动改任何东西，纯看板，零新增风险。

### 5.10 UX 风险提示（不计为问题）

90 秒预算 + 2 秒轮询 + 首期不做流式（ADR-03）。我认同"可靠恢复比打字动画重要"这个取舍，
在合规工具里是对的。但要提醒：**用户对聊天框的耐心通常在 10 秒量级**。
§3.2 已经要求展示"后台处理阶段与耗时"，这是正确的缓解；
建议 UAT 时**量一下用户在结果返回前的放弃率**，作为后续是否投入流式的依据，而不是拍脑袋。

## 7. 评审意见

**不予直接开工，但也不需要推倒重来——B-01 一条解决完即可进入施工。**

- **B-01 必须在开工前给出选择并写进设计**，因为它决定表怎么建、发布链路怎么走，
  是结构性的，不能留到编码阶段发现。
- **M-01 需要 Mr.Linsang 拍板**（新增投影级别 / 还是降级 F04 口径），
  因为它涉及数据出域范围，不是我或 O 能单方决定的。我的推荐是方案甲。
- M-02 ~ M-05 由 O 在设计里补齐即可，不需要新一轮大改。
- N-01 ~ N-07 是加强项，建议一并纳入，都不增加新的风险面。

另外重申 §1.4 的实施建议：**先把 CP-1A（无模型本地档）作为独立可交付物上线**，
用真实使用率决定是否投入模型接入。这既降低 27—40 人日的一次性风险，
也给 CP-GATE-DATA 的数据出域审批留出时间。

最后说一句：O 这份设计在"AI 只能解释、不能裁决"这条线上守得很干净，
对本项目现有代码的核对也是我见过最实的一次。我的意见集中在
**"安全机器造得对，但能力要配得上这个造价"**，而不是在质疑它的安全取向。
