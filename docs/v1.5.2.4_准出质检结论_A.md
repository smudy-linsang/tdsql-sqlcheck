## 3. 本轮新发现

### 3.1 🔴 必改：`make_release.sh` 版本号硬编码 1.4.0.1，会让部署验证确定性失败

**证据链**：

```
deploy/make_release.sh:12   VERSION="1.4.0.1"        ← 硬编码，且参数解析里没有 --version
      ↓ 产出 tdsql-sqlcheck-v1.4.0.1-linux-x86_64.tar.gz，包内 VERSION 文件写 1.4.0.1
deploy/verify_deploy.sh:13  EXPECTED_VER=$(cat ../VERSION)        → 1.4.0.1
deploy/verify_deploy.sh:20  VER=$(curl /health | ...)             → 1.5.2.4
deploy/verify_deploy.sh:21  [[ "$VER" == "$EXPECTED_VER" ]]       → 假
                            bad "版本号异常: 1.5.2.4(期望 1.4.0.1)"
deploy/verify_deploy.sh:68  FAILC>0 → exit 1                      ← 部署验证整体失败
```

仓库根 `VERSION` 文件是对的（`1.5.2.4`），`backend/config.py:25` 也是 `1.5.2.4`——**只有打包脚本没跟上**，而且它会用自己的硬编码值**覆盖**包内的 VERSION 文件。

**修复方法**（二选一，推荐后者）：

```bash
# 简单：改这一行
VERSION="1.5.2.4"

# 更好：从仓库 VERSION 文件读，永不再漂移
VERSION="$(cat "$(dirname "${BASH_SOURCE[0]}")/../VERSION" | tr -d '\r\n')"
```

**验收**：打出的包名含 `v1.5.2.4`，包内 `VERSION` 为 `1.5.2.4`，目标机 `verify_deploy.sh` 版本号一项 PASS。

### 3.2 🟠 附带：`--py` 参数文档里有、实现里没有

`make_release.sh` 的用法注释写着 `--arch aarch64 --py 39`，但参数解析只有 `--arch` / `--with-python`，其余走 `*) shift`。实测 `--arch aarch64 --py 39` 得到的是 `PYTAG=311`。

**后果**：目标机若是 python3.9（`preflight_check.sh` 明确支持 3.9），按文档加 `--py 39` 打包，实际下载的仍是 **cp311 wheels**，装到目标机上会失败，而打包时无任何提示。

**修复方法**：给解析器补一条 `--py) PYTAG="$2"; shift 2;;`；或删掉用法注释里的 `--py`，二者必居其一，不要让文档和实现对不上。

### 3.3 🟠 R043 的 DELETE 分支仍有误报，且相对内网现版本是**新增**的

Q 把 UPDATE 分支限定到了 `UPDATE..SET` 目标段，修得对；但 **DELETE 分支原样未动**：

```python
backend/engine/parser/parser_legacy.py:261
re.search(r"\bdelete\s+.*?\bjoin\b", clean_sql_no_comm, re.DOTALL)
```

`.*?\bjoin\b` 不限范围，**WHERE 子查询里的 JOIN 也会被算成联表 DELETE**：

| SQL | 判定 |
|---|---|
| `DELETE FROM t_a WHERE id IN (SELECT id FROM t_b JOIN t_c ON t_b.k=t_c.k)` | ❌ **误报 R043** |
| `DELETE FROM t_a WHERE id IN (SELECT id FROM t_b, t_c WHERE t_b.k=t_c.k)` | ✅ 不报（逗号式反而没事） |
| `DELETE a FROM t_order a JOIN t_user b ON a.cid=b.id` | ✅ 正确命中 |

**关键点：内网现行 1.2.0.9 对这条 SQL 不报警**（JOIN 检测是 `7c90fa5` 之后才加的）。也就是说**升级会引入一个原来没有的误报**。

**影响**：R043 是 ERROR 级，而 v1.4 质量门禁的 ERROR 阈值默认为 0——一条合法的 `DELETE ... WHERE id IN (SELECT ... JOIN ...)` 会被**挡在门禁外**，属于上线即可能被投诉的类型。

**修复方法**（与 UPDATE 分支同构，取 DELETE 与 FROM/WHERE 之间的目标段）：

```python
# DELETE：只看 FROM 之前的目标段与 FROM 后的直接表引用，
# 不能用 `.*?\bjoin\b` 满句扫 —— WHERE 子查询里的 JOIN 会被误算成联表 DELETE。
m_del = re.search(r"\bdelete\b(.*?)\bwhere\b|\bdelete\b(.*)$",
                  clean_sql_no_comm, re.DOTALL)
del_seg = (m_del.group(1) or m_del.group(2) or "") if m_del else ""
del_multi = bool(re.search(r"\bjoin\b", del_seg)
                 or re.search(r"\bdelete\s+[a-zA-Z0-9_`\s,]+from\b", clean_sql_no_comm))
```

**必须补的反向用例**（R-12）：`DELETE FROM t_a WHERE id IN (SELECT id FROM t_b JOIN t_c ON t_b.k=t_c.k)` 不得命中。

> 严重度说明：这是**误报**方向，按 R-15 属"看得见的错"，比修好的那个静默漏报轻一个量级，也可以靠规则集临时关掉 R043 兜底。所以我不把它列为准出阻断，但**强烈建议同批修**——一行的事，且它会在上线第一天就打扰使用者。
