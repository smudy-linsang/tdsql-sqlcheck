## 3. 逐项复测明细

### 3.1 F1 — 时区锁假绿（已闭合）

第一轮的判定是：G 的锁只覆盖"文件名时间戳"，锁不住"落库时间"这条真实路径，因此把落库时间退回 UTC 的变异 **MC** 可以整体逃逸。

本轮 `tests/test_v1637_filename_rule.py` 新增 **L5 `test_l5_publish_created_at_is_local_time`**（monkeypatch repo/registry/pipeline，捕获 `audit_columns_values`，断言 `cols[1]` 文件名时间戳与 `cols[13]` 落库 `created_at` 处于同一时基、容差 ≤2 秒且不是 UTC）。独立变异结果：

| 变异 | 目标 | 结果 |
| --- | --- | --- |
| MA | 命名还原本体（改回 `job_id[:8]` UUID 形态） | ✅ caught（真实断言失败） |
| MB | 时间戳取 UTC | ✅ caught |
| MC | 落库 `created_at` 退回 UTC（**合法值**，不依赖已删除的 `_utcnow`，模拟真实缺陷态） | ✅ **caught**（第一轮逃逸点已封堵） |
| MD | 审核流 `file_path` 与落库 `source` 解耦（契约漂移） | ✅ caught |

还原产品文件后：`6 passed`（`docs/evidence/v1.6.3.7-sit-d/sit-mutation.json`）。
**注**：本轮 MC 的构造刻意避开"引用已删除符号导致 `NameError`"，第一轮曾出现此类**假阳性捕获**，本轮已纠正为语义等价变异。

### 3.3 F3 — 订正脚本（**未闭合，BLOCK**）

脚本已按第一轮意见从"硬编码 #1377"升级为"自动备份 + 通用正则 + 动态时区偏移 + 幂等可回滚"，并补齐了 `deploy/rollback_v1637_source.sql`。**形式全部达标，但实跑暴露两处硬缺陷。**

测试方式：在 `uat_d_1636_meta` 中构造 3 条 UUID 形态记录（#1377 复刻生产形态 `extracted_lzbj_ecif_a27123e1.sql`、#1378 `..._deadbeef.sql`、#1379 `..._cafebabe.sql`，`created_at` 均为 UTC 时基 `2026-09-12 08:07:52`），再**逐条执行脚本中的真实语句**，执行两遍。

**缺陷 ①（BLOCK）：MySQL `DATE_FORMAT` 占位符用错 —— `%M` 是"月份英文名"，分钟是 `%i`。**

```sql
-- 现状（错误）
SET source = CONCAT('extracted_', db_name, '_', DATE_FORMAT(created_at, '%Y%m%d_%H%M%S'), '.sql')
```

第一遍执行后实际产出：

```
extracted_lzbj_ecif_20260912_16September52.sql
extracted_uat_d_1636_dist_20260912_16September52.sql   ← #1378/#1379
```

`%Y%m%d` = 20260912，`%H` = 16，`%M` = **September**，`%S` = 52。**这是 Python `strftime`（`%M`=分钟）与 MySQL `DATE_FORMAT`（`%i`=分钟）的语义陷阱**：脚本第 5 步照抄了产品代码里的 Python 格式串。

后果：订正后的历史记录会被写入 `..._16September52.sql` 这类**畸形文件名**，`scan_snapshots.scan_label` 同步被污染（步骤 6 已实测同步），且**下一步核验（步骤 7）与第一轮产品代码的命名契约校验都会失败**——等于在生产元数据库里制造一批新的不合规数据。

**缺陷 ②（BLOCK）：`OR id = 1377` 分支不幂等，重复执行继续漂移。**

脚本注释与设计 §4 均声称"**幂等可重复执行**"。实测：第二遍执行后

| 记录 | 第一遍后 | 第二遍后 | 说明 |
| --- | --- | --- | --- |
| #1378 / #1379（正则命中） | `2026-09-12 16:07:52` | `2026-09-12 16:07:52` | ✅ 真幂等（已改名，正则不再命中） |
| **#1377（`OR id = 1377` 命中）** | `2026-09-12 16:07:52` | **`2026-09-13 00:07:52`** | ❌ **又 +8 小时** |

机理：`id = 1377` 是无条件兜底条件，**不随改名而失效**；而步骤 4/5 又恰好用"是否命中同一条件"来判断"是否需要再订正"，于是每次执行都再叠加一次时区偏移。脚本头"幂等"的自述与实测不符（`idempotent: false`）。

**照图施工级修正（二选一，推荐 A）：**

```sql
-- 【修正 A（推荐）】统一条件：把 OR id = 1377 纳入"备份表 + 形态判定"，天然幂等
-- 步骤 1/2/4/5 的条件统一改为：
WHERE audit_type = 'extracted_schema'
  AND id IN (SELECT id FROM _bak_v1637_audit_history)   -- 以备份表锁定一次性目标集
  AND source REGEXP '^extracted_.+_[0-9a-f]{8}\\.sql$';  -- 形态判定兜住"已订正"记录

-- 【修正 B（最小改动）】保留原条件形状，给 1377 分支补形态判定
WHERE audit_type = 'extracted_schema'
  AND (source REGEXP '^extracted_.+_[0-9a-f]{8}\\.sql$'
       OR (id = 1377 AND source REGEXP '^extracted_.+_[0-9a-f]{8}\\.sql$'));
-- 等价于只保留正则分支；若确需保留 1377 兜底，须加"仅执行一次"断言：
--   SELECT COUNT(*) FROM _bak_v1637_audit_history WHERE source NOT REGEXP '^extracted_.+_[0-9a-f]{8}\\.sql$'
--   非 0 时人工介入，而不是再次 UPDATE。
```

```sql
-- 【必须同步修正】步骤 5 的日期格式串：MySQL 分钟是 %i，不是 %M
SET source = CONCAT('extracted_', db_name, '_',
                    DATE_FORMAT(created_at, '%Y%m%d_%H%i%s'), '.sql')
```

**执行前必须补齐的工序（第一轮已提，本轮再次强调）**：`dry-run（步骤 2 的 SELECT 人工核对）→ 备份（步骤 1 已含）→ 执行 → 步骤 7 核验`，且核验项应显式包含"改名结果匹配 `^extracted_.+_\d{8}_\d{6}\.sql$`"这一断言，而不是只把备份表里的行打印出来。

**已闭合的部分（上一轮 F3-2）**：`deploy/rollback_v1637_source.sql` 已交付，本轮实跑 **PASS**——`audit_history.source/created_at` 与 `scan_snapshots.scan_label` 均被完整还原为测试前状态（`UPDATE` 行数 6 / 4，无残留）。
