## 3. P1-01：参数采纳，但必须纠正的事实

### 3.1 历史高水位不等于物理内存

本轮重新读取 Mr.Linsang 提供的 `C:/Users/linsa/OneDrive/Desktop/wde.txt`：

| 原始位置 | 值 | 正确含义 |
|---|---|---|
| 第107行 free -m | total=63064 MiB，available=58592 MiB | 当时主机总内存约61.59 GiB、可用约57.22 GiB |
| 第110行 /proc/meminfo | MemTotal=64578408 kB | 物理可用总量口径，按1024字节单位换算，不是10.68 GiB |
| 第112行 | MemAvailable=59998844 kB | 检查时估计可用量；不是故障瞬时读数 |
| 前轮wd2e的memory根组 | max_usage_in_bytes=11465011200 | 约10.68 GiB历史使用高水位，不代表主机只装了10.68 GiB |

原件 SHA-256：`6B52E1A7BD46D45661777855FAA03848DA6F74DDD63144E9B00207FA97A4C31D`。仓库内已归档的 [O 排查报告](DIAG-6000表元数据审核失败-O独立排查与证据边界报告.md) §13—14 也明确区分这几个量。Linux 官方分别定义 MemTotal 与 cgroup历史使用峰值，不能互相替换。[Linux /proc](https://docs.kernel.org/filesystems/proc.html)、[cgroup v1 memory](https://docs.kernel.org/admin-guide/cgroup-v1/memory.html)

因此 8 GiB 约为已记录物理内存的 **13.0%**，不是75%；4 GiB约6.5%，也不是40%。不能基于峰值计算“超过40%必先swap”或断言该主机没有8GiB可供分配。反过来，检查时内存充足也不能保证以后没有内存压力。

### 3.2 为什么仍然采纳 1024 MiB

原8192默认预算在尚无修复后完整子进程RSS容量数据时偏宽，允许回归消耗更多资源才止损。默认收紧、限制配置范围、加实际容量比例预检，是合理的防御性选择，不需要先证明“主机只有10.7GiB”才能成立。

A 上轮 [独立量化报告](DIAG-6000表元数据审核失败-A独立排查结论与量化验证-ClaudeA.md) §3 写明测量工具为 **tracemalloc**；1600表18.9MB属于该合成审核阶段测量，6000表63MB是外推。它们不等于完整子进程RSS，未覆盖提取全文、解析碎片、序列化/SQL转义、HTML制备和数据库发送。不能据此认定1GiB有已证实的15倍余量。

Rev.B明确：1GiB是初始保护预算；超限明确RESOURCE_LIMIT失败，不截表、不关规则、不静默升限。容量验收按完整生命周期回填后再校准；默认保护线下真实6000+表三次全部完成，才叫默认配置容量通过。

### 3.3 25%预检的准确实现

采纳 A 的 MemTotal×25%硬性拒绝，并补充实际runner cgroup/祖先有限限制：有效容量=min(物理MemTotal,适用有限limit)。原始current/peak不参与容量公式，v1无限制哨兵/v2 max不当有限容量。

比较整数bytes：`rss_limit_bytes*4 > effective_capacity` 才拒绝，等于允许；范围仍必须512—4096。读取失败不猜主机大小，安装/升级及每次runner启动均失败关闭。它只是静态预算，不是当前MemAvailable保留机制；1Hz采样依旧存在超调窗口，不能宣传绝对防OOM。

Rev.A JOB-09其实已覆盖“内存越界”一般场景，因此不认可“原清单完全没有该项”的字面说法；但 A 要求补充**实际触碰RSS、TERM/KILL两分支、两个Web不受影响**是有价值的具体化，已新增JOB-17，而不是只改表中的数字。

## 6. P3-01：采纳真实可观测性，不制造无效配置/伪证据

1. **固定5秒认可**：在实际Web unit的ExecStart加 `--timeout-worker-healthcheck 5`；新安装/升级/补丁/CORE_SAFE共享此模板。CLI优先于env，避免仅写环境变量仍被其他配置覆盖。独立metadata-runner不运行Uvicorn，不给它写无效的UVICORN参数。[Uvicorn官方配置](https://uvicorn.dev/settings/)
2. **诊断扩充认可**：列Web argv、白名单env、有效值/来源、版本/hash和PID；禁止全量导出environ泄漏口令。
3. **延迟需区分**：事件循环lag、普通线程tick lag、HTTP响应时间均不是supervisor实际ping应答。Rev.B把这些命名分开；正常发行版不增发第二路ping、不修改site-packages或Uvicorn的强杀决定。
4. **实际ping仅测试取证**：版本/hash匹配的测试harness记录原有调用的elapsed/result和原监督决策，不改变调用数量/返回值/阈值；附无插桩对照及影响声明。未采到时写UNKNOWN，不以线程打点替代。

因此不照写“两个unit都配Uvicorn变量”或“有一个最大延迟值就能直接确定强杀原因”。Rev.A已要求阶段/PID/退出日志，但欠缺窗口固定及清晰观测分类，本次已补齐；A的担忧采纳，过度确定性不采纳。
