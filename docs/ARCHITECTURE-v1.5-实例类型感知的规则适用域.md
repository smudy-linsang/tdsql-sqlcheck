## 1. 问题陈述

### 1.1 现象

在「SQL审核 > 在线元数据审核」中对一个**集中式实例**执行扫描，报告中出现了 **R077**：

> R077：TDSQL分布式实例建表必须声明分片键(SHARDKEY)或广播表标记(BROADCAST)，不允许创建单表

集中式实例不存在分片概念，该实例上的每一张表本来就是单表，**这条告警在集中式实例上100%是误报**。

### 1.2 这不是一条规则的 bug

R077 只是**第一个被看见的症状**。经过对全部 119 条规则与全部扫描通道的完整勘察，确认这是一个**贯穿"规则模型 — 引擎 — 扫描通道 — 报告 — 门禁"五层的结构性设计缺陷**：

> **系统从来没有"这台实例是什么类型"这个概念参与审核判定。**

具体到代码事实：

| 层 | 事实 | 证据 |
|---|---|---|
| 规则模型 | `BaseRule` 只有 `rule_id / category / severity / description / enabled / spec_source / fix_suggestion` 七个属性，**没有任何表达"我适用于哪种实例"的字段** | `backend/engine/rules/base.py:16-22` |
| 引擎 | `RuleChecker.audit_sql()` 对每条 SQL **无条件遍历全部启用规则**，唯一的过滤是"DDL 规则只在 CREATE/ALTER/DROP 时跑" | `backend/engine/checker.py:121-124` |
| 引擎接口 | `audit_sql()` / `audit_file()` 的入参里**根本没有实例类型这个形参** | `backend/engine/checker.py:91-93, 158-159` |
| 扫描通道 | 在线元数据审核**明明手上有 `connection_id` 和 `conn_info`**（里面就有 `is_distributed`），却只把 `content` 和 `file_path` 传给引擎 | `backend/api/sql_audit.py:220-223, 305-310` |
| 数据 | `tdsql_connections.is_distributed` 字段**存在、被前端表单写入、在列表页显示**，但**全库检索确认：除了展示和慢SQL数据源选择，从未被任何审核逻辑读取过** | `is_distributed` 全量引用见 §2.2 |
| 报告 | `audit_history` 无任何字段记录"本次是按什么口径评估的" | `backend/services/audit_service.py:59-64` |

`is_distributed` 这个字段的存在，加上前端那句提示语——

> "分布式与集中式实例的审核规则不同，请根据实际情况选择"（`frontend/index.html:972`）

——说明**这个能力在需求上一直是被承诺的，只是从未被实现**。用户按提示如实勾选了"集中式"，系统却完全无视这个输入。这是承诺与实现之间的空洞，属于最严重的一类缺陷。

### 1.3 影响面：不止 R077，也不止规则引擎

#### （1）规则引擎：25 条仅分布式适用的规则会在集中式实例上误报

完整测绘见 `DETAIL-v1.5` §3 的 119 行判定表。此处只给最关键的结论：

**若按 `category == "distributed"` 过滤（最直觉的做法），会漏掉 11 条规则。**

| 漏网规则 | 现 category | 为什么它其实是分布式专属 |
|---|---|---|
| R023 | `ddl` | 描述原文："TDSQL**分布式**不支持" CREATE TABLE…SELECT |
| R024 | `ddl` | 描述原文："**分布式实例**不支持" CREATE TEMPORARY TABLE |
| R043 | `dml` | `spec_source` 原文："DML规范**【分布式】**"，告警文案："分布式环境下可能导致**跨SET**操作" |
| R092 | `oracle_compat` | 描述原文："**分布式实例**不支持WITH AS(CTE)；**集中式8.0**递归场景可评估 WITH RECURSIVE" |
| R100 | `oracle_compat` | 描述原文："**分布式实例**DELETE语句不支持对被删表设置别名" |
| R111 | `oracle_compat` | 描述原文："**分布式实例**不支持窗口函数" ← **集中式 MySQL 8.0 完全支持窗口函数** |
| R112 | `oracle_compat` | 描述原文："TDSQL**分布式**不支持游标" |
| R115 | `oracle_compat` | 描述原文："**分布式实例** update/delete…limit 依赖 **proxy** 内嵌 myisam 临时表" |
| R116 | `oracle_compat` | "**分片键**只支持一个字段" |
| R117 | `oracle_compat` | "**shardkey** 字段类型必须是…" |
| R118 | `oracle_compat` | "**shardkey** 字段的值不能为 NULL" |

这 11 条里，**R111 是最能说明问题的**：它会在一台集中式 MySQL 8.0 实例上，把完全合法、性能良好的 `ROW_NUMBER() OVER(...)` 判成 **ERROR**。开发按它去改，只会把好代码改坏。

> **架构结论 1：`category` 是"规范章节归类"，不是"适用性"，二者是正交维度，绝不能复用。必须新增独立的一等属性。**

#### （2）规则引擎之外，还有 3 处独立的缺陷位点

这是本次勘察最重要的发现——**只修规则引擎，问题解决不掉**：

| 位点 | 代码 | 问题 |
|---|---|---|
| **即时审核的"深度分布式检查"** | `backend/services/audit_service.py:132-149` | 每次「即时SQL审核」都无条件调用 `check_shard_key_presence(expr, ["order_id", "user_id"])`，产出 `DIST_001`/`DIST_002`。**两个致命问题**：① 完全不看实例类型，集中式必误报；② 分片键是**硬编码的 `order_id`/`user_id`** ——这两个字段名与任何真实实例都无关，等于在拿虚构的分片键去审核真实 SQL。`DIST_001` 更是只要 DML 没有 WHERE 就报 ERROR，与实例毫无关系。 |
| **元数据巡检 C07** | `backend/engine/schema_inspector.py:127-144` | 检查项"无主键的表"，其 `suggestion` 文案写死为"**TDSQL分布式架构**要求所有表必须有主键"。集中式实例上这条检查**结论本身是对的**（无主键表在任何库上都该治理），但**理由是错的**，会误导使用者。属于文案与适用性都要处理的位点。 |
| **分布式 EXPLAIN 分析** | `backend/engine/distributed_explain.py` | 整个模块的语义（命中单SET/跨SET广播/分片表无WHERE）在集中式实例上无意义。目前无实例类型闸门。 |

#### （3）质量门禁被连带污染

门禁按 ERROR/WARNING 计数判定（`gate_service.evaluate_for_instance`，默认 `max_error=0`）。集中式实例上凭空多出的 R077/R111 等 ERROR，会**直接把本该放行的变更卡住**。v1.4 刚建立的实例级门禁，其判定基础是错的。

#### （4）扫描对比（基线快照）会显示虚假的"整改成果"

v1.3 的 `scan_compare_reports` 拿两次快照做差。修复上线后，同一台集中式实例的问题数会从"含误报"掉到"不含误报"，对比报告会呈现一次**根本没发生过的大幅整改**。这与 v1.4 我们花大力气消灭的"换项目刷低问题数"是同一类伪命题，必须在设计上一并堵住。

### 1.4 用户提出的问题："规范里有没有专门针对集中式实例的规则？"

**答案：没有，一条都没有。**

对 119 条规则的 `__doc__` / `description` / `spec_source` / `fix_suggestion` 四个文本字段做全量关键词扫描（`集中式`/`单机实例`/`noshard 实例`/`非分布式`），命中"仅集中式适用"的规则数为 **0**。

出现"集中式"字样的 4 条（R091/R092/R106/R114）全部是**在讲分布式与集中式的差异**，用于给出不同的改写建议，而不是"这条规则只在集中式生效"。

这个结论对设计很重要：

> **架构结论 2：适用域是一个"全集 + 分布式子集"的结构，不是三分天下。因此本次改造对集中式实例只做减法（跳过不适用的规则），对分布式实例行为 100% 不变——这把回归风险压到了最低。**

不过设计上仍然保留 `centralized` 这个取值。原因：TDSQL 规范会演进（例如未来可能出现"集中式实例应配置半同步复制"这类规则），模型必须能表达，否则下一次又要动引擎。**留取值不留特例代码**，成本为零。

## 2. 现状分析

### 2.1 全部扫描/检查通道盘点

这是"整个系统各个扫描功能"的完整清单，以及各自能否拿到实例类型：

| # | 通道 | 入口 | 有 `connection_id`？ | 现状 |
|---|---|---|---|---|
| 1 | **在线元数据审核** | `POST /api/v1/audit/extract-and-audit` | ✅ **有**（且必填） | **有数据却不用** —— 缺陷现场 |
| 2 | 元数据审核 + 门禁 | 同上 → `_evaluate_gate` | ✅ 有 | 门禁计数被误报污染 |
| 3 | 即时 SQL 审核 | `POST /api/v1/audit/sql` | ⚠️ 选填 | 未用；且额外叠加硬编码分片键检查 |
| 4 | 文件审核 | `POST /api/v1/audit/file` | ⚠️ 选填 | 未用 |
| 5 | 文件上传审核 | `POST /api/v1/audit/upload` | ❌ 无 | 无从判断 |
| 6 | 批量流式审核 | `POST /api/v1/audit/batch-stream` | ❌ 无 | 无从判断 |
| 7 | 带元数据审核 | `POST /api/v1/tdsql/audit/with-metadata` | ✅ 有 | 未用 |
| 8 | GitLab MR 审核 | `POST /api/v1/gitlab/audit-diff` | ❌ 无 | 模块级单例 `checker`，无实例概念 |
| 9 | GitLab 仓库审核 | `POST /api/v1/gitlab/audit-repository` | ❌ 无 | 同上 |
| 10 | 元数据巡检 | `backend/api/inspection.py` → `SchemaInspector` | ✅ 有 | C07 文案写死分布式 |
| 11 | 大表治理 | `bigtable_engine` | ✅ 有 | 建议文案含分片假设，需复核 |
| 12 | 慢SQL 分析 | `slow_analyzer` | ✅ 有 | `set_id` 已按实例类型区分，无缺陷 |
| 13 | CLI | `backend/cli.py` | ❌ 无 | 离线场景 |

**分成两类，这是整个设计的分水岭：**

- **A 类（1/2/3/4/7/10/11/12）——实例已知**：系统手上有 `connection_id`，实例类型是**客观事实**，必须自动解析、不容用户干预。这类通道占了误报的绝大部分，**包括用户报告的现场**。
- **B 类（5/6/8/9/13）——无实例上下文**：审核的是一段文本/一个仓库，物理上不存在"目标实例"。这类通道的实例类型**只能由使用者声明**，系统不能凭空猜。

### 2.2 `is_distributed` 的可靠性问题

现状：这是一个**用户在建连表单上用单选框勾的、默认为"分布式"的自填字段**。

```
backend/api/tdsql_manage.py:36   is_distributed: bool = Field(True, description="是否分布式实例")
frontend/index.html:972          <el-radio :value="true">分布式实例</el-radio> …
```

把审核结论的正确性完全押在一个可能被勾错的复选框上，是不可接受的。两个方向的错勾后果**严重不对称**：

| 错勾方向 | 后果 | 可见性 | 危害 |
|---|---|---|---|
| 分布式实例被标成"集中式" | 25 条分布式规则被跳过 | **完全不可见**（报告里少的东西没人会发现） | **致命：静默漏报** |
| 集中式实例被标成"分布式" | 多出误报 | 一眼看见 | 可忍：等同今天的行为 |

> **架构结论 3：必须引入自动探测；且当探测与人工声明冲突时，以探测为准。人工声明只在探测无结论时兜底。**
> **兜底方向必须偏向"分布式"——宁可多报不可漏报。**

**探测手段是现成的**，代码里已有：

```
backend/services/tdsql_connector.py:475   rows = self._execute("/*proxy*/show status")     # 仅 Proxy 可执行
backend/services/tdsql_connector.py:506   SELECT … FROM information_schema.TDSQL_SHARDING_RULES  # 仅分布式存在
```

两个探针在集中式实例上都会失败/返回空，在分布式实例上有一个成功即可判定。

## 3. 设计目标

### 3.1 功能目标

| 编号 | 目标 |
|---|---|
| G1 | 集中式实例的任何扫描，**不得**出现仅分布式适用的规则告警（含 R077） |
| G2 | 分布式实例的扫描结果与 v1.4.0.1 **逐条完全一致**（零回归） |
| G3 | 实例类型由系统**自动探测**得出，人工声明仅作兜底，冲突时探测优先 |
| G4 | 报告必须**自证口径**：清楚写明"本次按哪种实例类型评估、跳过了哪些规则" |
| G5 | 无实例上下文的通道（文件/上传/GitLab/CLI）能**显式声明**实例类型，并有确定的默认值 |
| G6 | 规则引擎之外的 3 个位点（硬编码分片键检查、巡检C07、分布式EXPLAIN）同步治理 |
| G7 | 门禁计数基于**过滤后**的违规集 |
| G8 | 扫描对比**拒绝跨口径比较**，杜绝虚假整改率 |

### 3.2 非功能目标

| 编号 | 目标 |
|---|---|
| N1 | 单次扫描新增探测开销 ≤ 1 次轻量查询，且**结果缓存**，不得拖慢批量审核 |
| N2 | 探测失败**绝不阻断审核主流程**（沿用 v1.4 `_resolve_scale` 的失败回落约定） |
| N3 | 数据库变更为**纯增量**（只加列/加表/加配置项），可平滑回滚 |
| N4 | 存量 `audit_history` 记录的 `instance_type` 为 `NULL`，语义="v1.5 前记录，口径未知"（复用 v1.4 `rule_set_id` 的 NULL 约定） |

### 3.3 明确的非目标

- ❌ 不重新审定 119 条规则的技术正确性——只判定"适用于哪种实例"
- ❌ 不改变规则集（RuleSet）的语义与交互
- ❌ 不为集中式实例新增任何规则（现规范中没有）
- ❌ 不做"按库/按表"的细粒度适用域——粒度就是实例

## 4. 方案选型

### 方案对比

| 方案 | 做法 | 判定 |
|---|---|---|
| **A. 按 `category` 过滤** | 集中式实例跳过 `category == distributed` 的规则 | ❌ **否决**。§1.3 已证明会漏掉 11 条，其中 R111 会把集中式的合法窗口函数判 ERROR。改完等于"看起来修了，其实没修"，比不修更危险 |
| **B. 规则集里手工关掉** | 建一个"集中式规则集"，管理员逐条禁用 | ❌ **否决**。① 把**客观事实**（这条规则在集中式上物理不适用）降级成**主观配置**（管理员觉得不用查），语义错位；② 一台实例只能对应一个全局规则集（v1.4 决议），无法同时服务两种实例；③ 新增规则时要人肉维护，必然遗漏 |
| **C. 每条规则内部自行判断** | 在 `check()` 里读 `table_metadata` 猜是不是分布式 | ❌ **否决**。119 处重复逻辑、无法统一测试、无法向报告解释"跳过了什么"，且元数据未必可得 |
| **D. 规则声明适用域 + 引擎统一过滤** ★ | `BaseRule` 新增 `instance_scope` 一等属性；扫描侧解析实例类型；引擎在唯一收口点过滤 | ✅ **采纳** |

### 为什么是 D

1. **知识放在唯一正确的位置**：一条规则适不适用于集中式，是**规则自身的固有属性**，就该写在规则类上，和 `severity` 平级。新增规则时，作者在同一个类里就必须回答这个问题，漏填有默认值兜底（`ALL`，偏保守）。
2. **过滤只有一个收口点**：`RuleChecker.get_enabled_rules()`。所有扫描通道最终都汇聚到这里，一处正确处处正确，且**可被单元测试穷举验证**。
3. **可解释**：过滤发生在引擎内，能精确产出"跳过了哪 25 条"，直接喂给报告，满足 G4。
4. **与规则集正交**：适用域（客观）和规则集（主观）是两个维度，串联即可，互不侵蚀。

## 5. 总体设计

### 5.1 分层模型

```
┌──────────────────────────────────────────────────────────────────┐
│ ① 声明层：规则自述适用域                                          │
│    BaseRule.instance_scope ∈ {ALL, DISTRIBUTED, CENTRALIZED}     │
│    默认 ALL（保守）· 119 条已完成判定 · 25 条 DISTRIBUTED         │
└────────────────────────────┬─────────────────────────────────────┘
                             │
┌────────────────────────────┴─────────────────────────────────────┐
│ ② 事实层：实例类型解析器 InstanceTypeResolver                     │
│                                                                  │
│    优先级：探测(probed) > 声明(declared) > 全局默认(default)      │
│                                                                  │
│    探测：/*proxy*/show status  或                                 │
│          information_schema.TDSQL_SHARDING_RULES                 │
│    缓存：进程内 TTL 300s（多worker语义 = 最长 5 分钟生效）        │
│    冲突：探测≠声明 → 以探测为准 + 落 WARNING 日志 + 前端标记      │
└────────────────────────────┬─────────────────────────────────────┘
                             │  InstanceContext(type, source, conflict)
┌────────────────────────────┴─────────────────────────────────────┐
│ ③ 贯通层：13 条扫描通道全部携带 InstanceContext                    │
│    A类(有connection_id)：自动解析，不接受调用方覆盖                │
│    B类(无实例)：调用方显式声明，缺省取 system_config 全局默认      │
└────────────────────────────┬─────────────────────────────────────┘
                             │
┌────────────────────────────┴─────────────────────────────────────┐
│ ④ 执行层：RuleChecker 统一过滤（唯一收口点）                      │
│    生效规则 = 全部规则                                            │
│               ∩ 适用域匹配(instance_scope)     ← 客观，只做减法    │
│               ∩ 规则集启用(rule_overrides)     ← 主观             │
│    同时闸控：DIST_001/002 硬编码分片键检查、distributed_explain    │
└────────────────────────────┬─────────────────────────────────────┘
                             │
┌────────────────────────────┴─────────────────────────────────────┐
│ ⑤ 留痕层：口径写入报告与历史                                      │
│    audit_history: instance_type / instance_type_source /          │
│                   skipped_rules_count                             │
│    报告页横幅："本次按【集中式】口径评估，已跳过 25 条仅分布式规则" │
│    扫描对比：口径不同 → 拒绝比较并提示                            │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 核心数据结构

```python
class InstanceType(str, Enum):
    DISTRIBUTED = "distributed"   # 分布式实例
    CENTRALIZED = "centralized"   # 集中式实例

class InstanceScope(str, Enum):
    ALL         = "all"           # 通用（默认）
    DISTRIBUTED = "distributed"   # 仅分布式适用
    CENTRALIZED = "centralized"   # 仅集中式适用（当前 0 条，为演进预留）

class TypeSource(str, Enum):
    PROBED   = "probed"    # 连库探测得出（最高可信）
    DECLARED = "declared"  # 读 tdsql_connections.is_distributed
    REQUEST  = "request"   # 调用方在请求里显式声明（B类通道）
    DEFAULT  = "default"   # 落到 system_config.default_instance_type
```

### 5.3 匹配规则（唯一判定式）

```
规则 r 在实例类型 t 上生效  ⟺  r.instance_scope == ALL  or  r.instance_scope == t
```

**没有"未知"这个第三态。** 这是一个刻意的设计决定：

如果允许 `instance_type = unknown`，就必须回答"未知时跑哪些规则"，而任何答案都是错的——跑全部＝今天的误报，只跑通用＝静默漏报。因此**解析器保证永远返回一个确定的类型**，把不确定性收敛在"是怎么得到的"（`TypeSource`）而不是"是什么"上。使用者通过 `source` 判断这个结论有多可信，而引擎永远拿到确定输入。

### 5.4 兜底方向：默认 `distributed`

`system_config.default_instance_type` 出厂值 = `distributed`。理由：

1. **安全方向正确**：兜底走分布式＝跑全部规则＝宁可多报不可漏报（§2.2 的不对称性）。
2. **零行为变更**：无实例上下文的通道（文件/上传/GitLab/CLI）行为与 v1.4.0.1 **完全一致**，这些通道本来就不该被本次改造波及。
3. **符合现场**：TDSQL 场景以分布式实例为主，前端 `is_distributed` 默认值也是 `true`。

管理员可在「系统配置」改为 `centralized`（例如某些行只用集中式实例的环境）。

### 5.5 与 v1.4 规则集的关系

**串联，且方向是不对称的：**

```
最终生效 = 适用域过滤(客观) ∩ 规则集过滤(主观)
```

- 规则集**可以**关掉一条适用的规则（管理员认为尺度太严）——允许。
- 规则集**不能**打开一条不适用的规则（在集中式实例上强开 R077）——**禁止，且不提供任何开关**。

因为后者不是"尺度松紧"问题，而是"这个检查在物理上没有意义"。留一个后门就等于把 §3.1 的 G1 变成"可配置的"，可靠性保证随即失效。

**副作用（必须知晓）**：规则集页面显示的"启用 N 条"是全局口径，而集中式实例实跑数会更少。因此 API 与前端都要暴露 `effective_rules_count`（按实例类型算出的实跑条数），避免使用者困惑。

### 5.6 引擎之外 3 个位点的处理

| 位点 | 处理 |
|---|---|
| `audit_service` 硬编码分片键检查 | **① 加实例类型闸门**：仅 `distributed` 执行；**② 去掉硬编码**：分片键改为从 `table_metadata` 真实读取，取不到就整段跳过，不再拿 `order_id`/`user_id` 硬编。这两条一起做——只加闸门的话，分布式实例上的假分片键误报依然存在 |
| `schema_inspector` C07 | **不跳过**（无主键表在任何实例上都该治理），但**按实例类型换文案**：分布式→"TDSQL分布式架构要求所有表必须有主键"；集中式→"无主键表无法保证行唯一定位，且影响主从复制与在线DDL，建议补充主键"。为此给巡检检查项引入与规则相同的 `instance_scope` 字段 |
| `distributed_explain` | 调用侧加闸门：仅 `distributed` 调用 |

### 5.7 扫描对比的口径隔离

`scan_snapshots` 增加 `instance_type` 列。对比时：

- 两侧口径相同 → 正常对比
- 两侧口径不同 → **拒绝生成对比报告**，返回明确原因
- 任一侧为 `NULL`（v1.5 前的存量快照）→ 允许对比，但报告顶部打**醒目警示**："基线快照采集于 v1.5 之前，评估口径未知，问题数变化可能包含口径调整因素，不代表真实整改"

与 v1.4 处理 `rule_set_id` NULL 的方式保持一致：**不删存量、不假装可比、把不确定性显式告知使用者**。

## 7. 风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| R1 | **误把通用规则判成"仅分布式"→ 集中式实例静默漏报** | **高** | ① 判定原则从严：**只有规则文本明确限定分布式才归 DISTRIBUTED，边界一律归 ALL**；② 25 条判定表逐条附证据原文，供 DBA 复核；③ 单列 4 条「待复核」清单（R038/R097/R113/R114），当前保守归 ALL；④ 单元测试锁定 25 条清单，改动即失败 |
| R2 | 探测误判（网络抖动/权限不足） | 中 | 探测失败不算结论，退回声明值；探测结果缓存 300s；不因探测异常阻断审核（N2） |
| R3 | 用户把分布式实例声明成集中式，且探测也失败 | 中 | 兜底方向偏分布式；探测与声明冲突时前端红色标记；实例列表页显示类型来源徽标 |
| R4 | 集中式实例问题数骤降被误读为"整改成效" | 中 | §5.7 口径隔离 + 报告横幅明示跳过条数；发布说明中单独提示 |
| R5 | 探测查询拖慢批量审核 | 低 | 单次扫描只解析一次，结果随 `InstanceContext` 传递；进程内缓存 |
| R6 | 多 worker（`--workers 2`）下缓存不一致 | 低 | 沿用既有约定：文档与提示语一律写"**最长 5 分钟生效**"，绝不写"即时生效" |
| R7 | 新增规则忘填 `instance_scope` | 低 | 默认 `ALL`（保守，等同今天）；CI 增加清单一致性测试 |

## 8. 验收标准

| # | 验收项 | 判定方法 |
|---|---|---|
| A1 | 集中式实例在线元数据审核**不再出现 R077** | 真实集中式实例扫描，报告内检索 R077 = 0 条 |
| A2 | 集中式实例不出现全部 25 条分布式规则 | 同上，逐条检索 = 0 |
| A3 | **分布式实例结果零回归** | 同一实例、同一库，v1.4.0.1 与 v1.5 各扫一次，违规条目**逐条 diff 完全一致** |
| A4 | 集中式实例的合法窗口函数不再被 R111 判 ERROR | 构造 `SELECT ROW_NUMBER() OVER(...)`，集中式口径下无 R111 |
| A5 | 探测优先于声明 | 把分布式实例故意声明为"集中式"，扫描仍按分布式执行，且前端显示冲突标记 |
| A6 | 探测失败回落声明 | 断开探测能力，验证仍取 `is_distributed` |
| A7 | 报告自证口径 | 报告页可见"按【X】口径评估，跳过 N 条" |
| A8 | 门禁基于过滤后计数 | 集中式实例上原被 R077 卡住的变更现应放行 |
| A9 | 跨口径对比被拒绝 | 集中式 vs 分布式快照对比 → 明确报错 |
| A10 | 硬编码分片键检查失效 | 集中式即时审核无 DIST_001/DIST_002；分布式下分片键取自真实元数据 |
| A11 | 巡检 C07 文案分型 | 集中式实例巡检 C07 不含"分布式"字样 |
| A12 | 全量回归通过 | `pytest` 全绿，新增用例见 `DETAIL-v1.5` §7 |
