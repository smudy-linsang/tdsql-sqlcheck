## 2. 逐项复验

### 2.1 A-P2-02　MonitorDB 填错不再掀翻整批

**服务层三种输入对比（真实连接，不打桩）**：

```
① 主机留空: 逐行返回 1 行 code={'MONITOR_CONNECT_FAILED'}
   ✅ 逐实例报错、不整批崩
   ✅ 失败详情可读且不含口令 — "未提供 MonitorDB 配置，无法解析实例名称"
② 端口不通: 逐行返回 1 行 code={'MONITOR_CONNECT_FAILED'}
   ✅ 逐实例报错、不整批崩
   ✅ 失败详情可读且不含口令 — "无法连接 MonitorDB 127.0.0.1:19999，请核对主机、端口、账号、口令与网络"
③ 口令错误: 逐行返回 1 行 code={'MONITOR_CONNECT_FAILED'}
   ✅ 逐实例报错、不整批崩
   ✅ 失败详情可读且不含口令 — "无法连接 MonitorDB 127.0.0.1:13306，请核对主机、端口、账号、口令与网络"
```

上一轮 ②③ 是「整体抛出 OperationalError」→ 接口兜底 HTTP 500「生成 ZK 导入预览失败」。现在三种都收敛到同一个可读的 `MONITOR_CONNECT_FAILED`，**且提示里有端点、没有口令**（我专门断言了 `wrong_pw` 不出现在 `failure_detail` 里）。

**接口层的直接对照**——跨 worker 那组用例里有一步是"进程外注入会话 + 不可达的 MonitorDB"，上一轮和这一轮的同一条断言：

```
上一轮: ✅ ... — HTTP 500 body={"detail":"生成 ZK 导入预览失败"}
本  轮: ✅ ... — HTTP 200 body={"preview_id":"639c2ab3...","summary":{"selected_instances":1,...
```

**同一个请求，从"无指向的 500"变成了"200 + 逐行可读失败"。** 这是这项修复最直观的证据。

**两条反向鉴别**（防止"把所有失败都归到 MonitorDB 头上"）：

```
【2】业务 Proxy 全不可达 → 1 行 code={'NO_AVAILABLE_PROXY'}
  ✅ 未与 MonitorDB 混淆
【3】MonitorDB 可连时 → code={'INSTANCE_NAME_UNRESOLVED'}
  ✅ 不再误报 MONITOR_CONNECT_FAILED
```

`_connect` 现在统一抛 `DB_CONNECT_FAILED`，名称解析分支再归一成 `MONITOR_CONNECT_FAILED`——业务 Proxy 那条路径由 `_list_business_databases` 的 `except Exception: continue` 接住，**两条路径的语义没有串味**，实测确认。

### 2.2 A-P3-02　已存凭据可以清除了，且既有便利没被改坏

```
【1】先存上两组凭据
  ✅ 两组凭据均已入库          ✅ 口令密文入库、非明文

【2】★清除业务凭据：清空用户名保存
  ✅ ★清空业务用户名可以保存（不再 400 死路） — HTTP 200
  ✅ ★业务口令密文已真正清除 — 残留=''
  ✅ MonitorDB 那组未被误伤 — monitor_user='mon_user' 密文在=True

【3】★清除 MonitorDB 凭据：整段置空保存
  ✅ ★MonitorDB 整段置空可以保存 — HTTP 200
  ✅ ★MonitorDB 口令密文已真正清除 — 残留=''

【4】反向鉴别：只改其他项、不重填口令时，既有密文必须【保留】
  ✅ 改监控默认库不重填口令 → 两组密文都还在 — monitor_db='uat166_changed'

【5】反向鉴别：成对校验没被删掉
  ✅ 只填业务用户名、无口令 → 仍 400
  ✅ MonitorDB 填了主机端口但用户名/口令/库不全 → 仍 400
```

**第 4、5 组是这项修复的关键风险点**，必须验：

- **第 4 组**：口令为空时继承旧密文，本来是"改其他项不用重打口令"的合理便利。加"清除"语义时最容易把这个便利一起干掉——实测**没有**，改 `monitor_db` 时两组密文都还在。
- **第 5 组**：清除语义也可能被实现成"干脆不校验了"。实测成对校验**原样还在**，只填用户名不填口令仍被拒。

**两组凭据互不干扰**也验了（清业务时监控那组纹丝不动）。

Q 补的两条用例我看了，`test_ap202_...` 断言了 `"10.9.9.9:15999" in failure_detail`（要有端点指向）且 `"wrong" not in failure_detail`（不得回显口令），**打在点上**。

## 3. A-P2-03（新，由本次修复引入）：MonitorDB 不可路由时预检耗时线性放大

### 3.1 现象与量测

修法把"首次连不上即整批中止"换成了"逐实例各报一次错"，但 `monitor_conn` 失败后仍为 `None`，**下一个实例会重新尝试连接**。用 RFC5737 文档地址 `192.0.2.10`（不回包，形态等同内网填错 IP 或被防火墙丢包；本机 `19999` 是内核直接 RST，量不出真实代价）实测：

```
前置：192.0.2.10:15001 OSError 耗时 3.1s（确为超时，非瞬时拒绝）
N=1   耗时    3.3s  单实例约 3.3s  返回 1 行 code={'MONITOR_CONNECT_FAILED'}
N=3   耗时    9.3s  单实例约 3.1s  返回 3 行 code={'MONITOR_CONNECT_FAILED'}
→ 按接口上限 _MAX_PREVIEW_INSTANCES=200 外推：约 620s（10.3 分钟）
→ 修复前的行为：首个实例失败即整批中止，约 3s 后返回 HTTP 500
```

### 3.2 为什么值得管

`deploy/nginx-sqlcheck.conf` 第 26 行 `proxy_read_timeout 120s`。按实测 3.1s/实例，**选到约 39 个实例就会撞上网关超时**：

| 选中实例数 | 结果 |
|---|---|
| ≤ 约 39 | ✅ 正常拿到逐行 `MONITOR_CONNECT_FAILED`，修复生效 |
| > 约 39 | ❌ **nginx 504**，运维**既拿不到逐行诊断、也没有原来那个 3 秒的快速失败** |

**内网有 209 个实例，"全选后生成预览"正是他们的标准动作。** 也就是说：MonitorDB 一旦配错，这项修复在最需要它的批量场景里反而拿不到收益。

严格说这不是新增的**故障类别**（配错本来就失败），只是失败变慢、且诊断信息在批量时拿不到。所以我按 **P2** 记，**不阻断打包**。

### 3.3 修法（很小）

MonitorDB 是**整批共用的一条连接**，失败一次就够了，没必要每个实例重试：

```python
monitor_conn = None
monitor_failure = None          # ← 新增：记住这批已经确认连不上
...
    if monitor_conn is None and monitor_failure is not None:
        raise monitor_failure    # 直接复用首次的失败，不再重连
    if monitor_conn is None:
        try:
            monitor_conn = self._connect(...)
        except ZKImportPreparationError as exc:
            monitor_failure = ZKImportPreparationError(
                "MONITOR_CONNECT_FAILED", f"无法连接 MonitorDB {monitor.host}:{monitor.port}，...")
            raise monitor_failure from exc
```

效果：200 个实例仍然**每行都有可读失败**，但总耗时回到约 3 秒。

**补用例（R-12）**：MonitorDB 不可达 + 选 N 个实例 → 断言**行数 == N 且每行都是 `MONITOR_CONNECT_FAILED`**（保住诊断），**同时断言 `_connect` 只被调用 1 次**（保住耗时）。只断言"有 N 行错误"抓不到这个问题。

## 4. 打包前必做：把版号推到 1.6.0.7

**`8a8da77` 改了两个后端服务文件，但 `VERSION` 和 `APP_VERSION` 仍是 `1.6.0.6`**（提交信息里写的"不改版号"）：

```

 backend/services/zk_discovery_config_service.py  |  9 ++++
```

也就是说，**会存在两个内容不同、版号都叫 1.6.0.6 的构建**：一个是我 8 月 5 日上午签署准出的，一个是 G 即将打包送内网的。

这在银行内网是实打实的追溯问题：

- 内网智能体报"我装的是 1.6.0.6"时，**无法判定含不含这两项修复**；
- 出问题要回滚时，**没有办法指定回到哪一个 1.6.0.6**；
- 页面标题、`/api` 的 `APP_VERSION`、发布包名三处都会给出同一个版号，**没有任何一处能区分**。

而且团队**刚刚**才花了一次提交去收拾上一回的版号混乱（`1.6.0.51` 笔误，`07cd4bf`）。同一个坑不值得再踩一次。

**建议**：`VERSION` 与 `backend/config.py::APP_VERSION` 一并改为 `1.6.0.7`，前端标题/登录页版号同步，再让 G 打包。改动极小，但把"装的到底是哪一版"这件事锁死。

> 如果出于流程原因确实要保持 1.6.0.6，那么**发布包名与内网部署记录里必须带上 commit 短号**（如 `v1.6.0.6-8a8da77`），并在升级手册里写明与前一个 1.6.0.6 的差异。二者取其一，不能都不做。

## 6. 准出结论

**代码同意准出。打包前请先把版号推到 1.6.0.7（§4）。**

- 我提的两项历史遗留已修好，两项都配了反向鉴别，**没有出现"修一个坏一个"**；
- 全量回归 0 失败，四组既有能力重跑无回归；
- **A-P2-03**（§3）建议同批修——5 行以内，且内网"全选 209 个实例生成预览"正是它会发作的场景。若本批不修，请在升级手册里写明：**MonitorDB 配置务必先用少量实例（≤30 个）试一次预览，确认能连通后再全选**。

### 给内网的三条动作

1. **先小批量验通 MonitorDB**：首次配置后先选 5~10 个实例生成预览，确认没有 `MONITOR_CONNECT_FAILED` 再全选。这条在 A-P2-03 修掉之前尤其重要。
2. **升级后重新扫一次 ZK**：若此前用的是 `driver=shell`，A-P1-03 意味着分布式实例一直没被发现过，需要重扫后补登记。
3. **看到「部分 Proxy」标签不要忽略**：该实例有 Proxy 未响应，业务库列表可能不全，人工确认后再导入。
