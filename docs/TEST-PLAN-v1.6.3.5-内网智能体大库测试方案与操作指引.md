### 测试用例 1：部署就绪与双服务探针验证（前置用例）

#### 1.1 操作步骤
通过 SSH 登录测试服务器，执行以下两行检查命令：
```bash
# 1. 检查双服务运行状态
systemctl status tdsql-metadata-runner.service tdsql-sqlcheck.service --no-pager

# 2. 检查应用健康端点
curl -s http://127.0.0.1:8000/health | python3 -m json.tool
```

#### 1.2 预期结果
1. `tdsql-metadata-runner.service` 状态为 **`active (running)`**；
2. `tdsql-sqlcheck.service` 状态为 **`active (running)`**；
3. `curl /health` 返回 JSON 且包含 `"status": "ok"` 或 `"healthy": true`。

### 测试用例 2【核心门禁】：6000+ 表真实大库全流程连续 3 次实跑

> [!IMPORTANT]
> 这是本次质检最核心的验收门禁！需要验证大库在真实内网数据库下的网络拉取、流式审核、内存峰值与结果展示。

#### 2.1 测试前准备：打开后台物理监控
在终端打开一个单独窗口，执行以下命令，实时观察 runner 执行器的内存与日志：
```bash
# 实时跟踪 runner 日志
journalctl -u tdsql-metadata-runner -f
```

#### 2.2 界面实操步骤
1. 打开 Chrome/Edge 浏览器，访问：`http://10.243.16.252:8000` 并登录系统；
2. 导航至左侧菜单：**「SQL审核」 $\to$ 「在线元数据审核」**；
3. 在页面上方配置项：
   - **目标实例**：选择 `10.243.20.13:15063`（若未激活先在「实例管理」激活）；
   - **目标数据库**：输入或选择 `sungl_am`（6000+ 表大库）；
   - **审核范围**：保持默认全选（TABLE, INDEX, VIEW, SHARDKEY）；
4. 点击蓝色按钮：**「拉取元数据并执行文件审核」**；
5. **观察执行过程（约 3~4 分钟）**：
   - 界面弹出消息提示：“元数据审核任务已受理，正在后台执行…”；
   - 任务卡片呈现：展示任务 ID、状态显示为 **「运行中」**，进度条实时更新（例如显示当前正在提取的表计数与阶段）；
   - **重点观察**：**绝不再弹出红色的 `提取失败: Failed to fetch`**！
6. **观察完成状态**：
   - 约 3~4 分钟后，任务卡状态转为 **`SUCCEEDED`（已完成）**，弹出成功提示；
   - 界面下方渲染出规则违规汇总与分页结果列表（第 1 页展示前 50 条，支持翻页到第 2、3 页）；
   - 点击页面上的 **「下载完整提取SQL」** 按钮，确认浏览器能够成功下载一个数十兆的 `.sql` 文件，用文本编辑器打开头部包含 `sungl_am` 元数据说明。

#### 2.3 物理资源采样命令（任务运行到一半时在终端执行）
```bash
# 查看 runner 进程与 worker 子进程的物理 RSS 内存 (单位 KB)
ps -eo pid,ppid,cmd,rss,%mem,%cpu | grep -E "metadata_runner|metadata_audit_worker" | grep -v grep
```

#### 2.4 三连跑要求
请将上述 2.2 的操作**连续重复执行 3 次**（第 1 次跑完后，点击「重新扫描」跑第 2 次，再跑第 3 次）。

#### 2.5 预期结果与合格标准
- 连续 3 次任务全部以 **`SUCCEEDED`** 成功结束，**0 次失败、0 次断连**；
- 界面绝对不出现 `Failed to fetch` 或 `ERR_EMPTY_RESPONSE`；
- runner 与 worker 的物理内存 **RSS 始终低于 1024 MiB（实测预期在 100MB~300MB）**；
- 检查 `journalctl -u tdsql-sqlcheck`，Uvicorn Web 服务进程 **0 次重启、0 次 worker died**。

### 测试用例 3：页面刷新与断线自愈恢复验证

#### 3.1 操作步骤
1. 在「在线元数据审核」页面点击「拉取元数据并执行文件审核」；
2. 当看到进度条开始滚动、任务处于「运行中」时（例如提取到第 1500 张表左右）：
   - **直接按键盘 `F5` 刷新整个浏览器页面**，模拟用户意外刷新或网络闪断；
3. 页面重新加载完成后，重新点击进入「在线元数据审核」页面；
4. 点击「重新扫描」按钮旁边的 **「恢复查看上次任务」** 按钮。

#### 3.2 预期结果
1. 点击「恢复查看上次任务」后，页面**立即无缝恢复**刚才正在运行的大库任务卡片；
2. 进度条继续正常向前滚动，轮询无缝接续；
3. **未重复创建新任务**（数据库中只有刚才那 1 个任务在跑）。

---

### 测试用例 4：任务运行中友好取消与独占槽释放验证

#### 4.1 操作步骤
1. 再次发起一次大库审核任务；
2. 在任务处于「运行中」状态时，点击任务卡上的红色 **「取消任务」** 按钮；
3. 在弹出的二次确认对话框中点击 **「确认取消」**；
4. 观察界面状态变化；
5. 任务显示取消后，**立刻再次点击「拉取元数据并执行文件审核」发起新任务**。

#### 4.2 预期结果
1. 点击确认后，任务卡片状态平稳转为 **`CANCELLED`（已取消）**，耗时数字停止走动并锁定；
2. runner 立即释放受理槽；
3. 紧接着再次点击发起新任务时，新任务**能够立即被正常受理并开始执行**，证明独占槽位已完全释放，无死锁残留。

### 测试用例 5：单机独占并发互斥排队保护验证

#### 5.1 操作步骤
1. 打开浏览器标签页 A，发起大库审核任务（进入运行态）；
2. 立即打开另一个浏览器标签页 B，进入「在线元数据审核」页面，点击「拉取元数据并执行文件审核」。

#### 5.2 预期结果
1. 标签页 B 不会强行抢占或打垮服务器，而是收到友好的黄色告警提示：  
   **`当前已有元数据审核任务，请稍后重试`**（后端返回 HTTP 409 METADATA_BUSY）；
2. 标签页 A 中的大库任务继续稳定运行，不受任何干扰。

### 测试用例 6：旧同步接口 410 Gone 退役校验

#### 6.1 操作步骤
在测试服务器终端执行 curl，模拟调用旧版的同步阻塞接口：
```bash
curl -i -X POST http://127.0.0.1:8000/api/v1/audit/extract-and-audit \

  -d '{"connection_id":"dummy"}'

{"detail":"旧提取审核路径已退役（已升级为任务执行器）。请使用 POST /api/v1/audit/metadata-jobs"}
```

## 三、 异常诊断与运维只读自检 SQL 指南

如果内网智能体在测试中遇到任何疑问，可随时通过以下只读 SQL 查询系统底表状态（纯只读，不修改任何数据）：

```bash
ssh root@10.243.16.252 "mysql -h127.0.0.1 -P3306 -uroot -ptdsql_test_2024 tdsql_sqlcheck" << 'EOF'
-- 1. 查看最近的元数据审核任务记录（查看状态、耗时、已处理表数）
SELECT job_id, state, phase, progress_json, error_json, created_at, finished_at 
FROM metadata_audit_jobs 
ORDER BY id DESC LIMIT 5;

-- 2. 查看当前独占槽状态
SELECT * FROM metadata_audit_slot WHERE id = 1;
EOF
```

**判读规则**：
- 任务执行中：`metadata_audit_slot` 的 `active_job_id` 填有当前正在跑的任务 ID；
- 任务结束后（无论成功、失败或取消）：`active_job_id` 自动清空为 `NULL`，表示槽位已空闲就绪。
